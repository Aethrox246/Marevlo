01 · The Three Categories of LLM Systems

Engines, Chatbots, Agents:
A Taxonomy That Actually Matters

Every LLM application you will ever build belongs to one of three categories. The distinctions are not aesthetic — they drive entirely different architectural decisions, latency profiles, error modes, and deployment strategies. Misclassifying your use case leads to over-engineering simple tasks and under-engineering complex ones.

● Engine — bounded, stateless, invoked

An engine delivers a specific, well-defined capability: summarization, classification, translation, content generation. It receives input, produces output, and stops. It does not decide what to do next, carry state forward, or initiate follow-up actions. Engines are typically deployed as shared REST API services invoked by other systems.

Summarization engine flow

POST /summarize {text: "...long article..."}
→ LLM processes: generate 3-sentence summary
← Return {summary: "...", tokens_used: 342}
→ Caller stores result or displays to user
→ Engine has no memory of this call

Q&A engine (RAG) flow

POST /ask {question: "Who founded Marevlo?"}
→ Embed question → search vector store
→ Retrieve top-3 relevant chunks
→ LLM: answer using chunks + question
← Return {answer: "...", sources: [...]}

● Chatbot — conversational, stateful, interactive

A chatbot maintains context across multiple exchanges in a conversation. Unlike an engine, it tracks message history: what the user said, what the bot replied, and how the conversation evolved. This continuity allows follow-up questions ("What about the pricing?"), reference resolution ("How much does it cost?"), and contextual refinement across turns.

User: Summarize this article about climate change.
Bot: The article argues that methane emissions are rising faster than CO2...
User: What does it say about solutions? ← references previous context
Bot: The article proposes three solutions: carbon capture, renewable energy...
User: Can you make that last point shorter? ← "that last point" requires history
Bot: The article recommends methane regulations as the fastest-acting lever.

● AI Agent — autonomous, tool-using, goal-directed

An AI agent uses an LLM to choose actions, plan, and execute multi-step work to reach a goal. Unlike engines (single output) and chatbots (conversational), agents loop: they observe results, decide what to do next, call tools or APIs, and adapt based on intermediate outcomes. The LLM acts as the reasoning engine; tools and APIs are its hands.

Goal: "Book a holiday package: flights + hotel + activities in Tokyo for 7 days"
Step 1: LLM decides to call flight_search("Tokyo", "2024-12-01", "2024-12-08")
Step 2: Gets results. LLM decides to call hotel_search("Tokyo", "budget: $200/night")
Step 3: Gets results. LLM calls activity_search("Tokyo", "cultural experiences")
Step 4: LLM synthesizes all results, generates a complete travel plan
Output: Structured itinerary with booked flights, hotel, 5 activities
💡

Why the classification matters for engineering

Engines are stateless — deploy them as standard REST microservices, scale horizontally, cache aggressively. Chatbots need session state management (Redis, database) and conversation history trimming to avoid context window overflow. Agents need tool registries, loop guards, observability traces, and max_iterations limits. Building a chatbot with agent complexity or an engine with chatbot state tracking wastes engineering effort and introduces bugs.

02 · Introducing LangChain

Modular Building Blocks:
The LangChain Architecture Explained

LangChain is a framework for building LLM applications. It eliminates the boilerplate of wiring together document loaders, text splitters, embedding models, vector stores, LLM calls, and output parsers — letting you focus on application logic. It provides a consistent interface regardless of which LLM provider, vector database, or tool you choose.

LangChain architecture: the seven-layer stack

Document LoadersIngest content from any source: PDF, URL, S3, databases, APIs, GitHub. Output: standardized Document objects with page_content and metadata.
Text SplittersBreak large documents into chunks that fit in the LLM context window. Strategies: recursive character, HTML header, semantic, token-based.
Embedding ModelsConvert text to vector representations. Pluggable: OpenAI, HuggingFace, Cohere, local models. Output: float vectors for similarity search.
Vector StoresStore and retrieve embeddings by similarity. Options: Chroma (local), Qdrant, Pinecone, Weaviate, FAISS. One-line swap between providers.
LLMs & Chat ModelsStandardized interface to GPT-4, Claude, Gemini, Llama, Mistral. Same .invoke() call works for all. Handles token counting, retries, streaming.
Chains (LCEL)Compose components with the | operator: prompt | llm | parser. LangChain Expression Language enables async, streaming, batching, tracing automatically.
Agents & ToolsEnable LLMs to call functions, APIs, search engines, databases. Tools are Python functions with descriptions; agents decide when to call them.
✓

The LCEL pipe operator: composing without boilerplate

LangChain Expression Language (LCEL) lets you compose pipeline steps using Python's | operator. Each component exposes the same Runnable interface: .invoke(), .stream(), .batch(), .ainvoke(). This means you can swap any component (change embedding model, switch LLM provider, add a caching layer) without rewriting the chain definition. The pipe operator chains are also automatically compatible with LangSmith tracing.

The core object model: Document and LLM hierarchies

Document object model

class Document:
  page_content: str # the text
  metadata: dict # source, page, date...

# Created by any DocumentLoader:
loader = PyPDFLoader("policy.pdf")
docs = loader.load() # List[Document]

# Split into chunks:
splitter = RecursiveCharacterTextSplitter(
  chunk_size=500, chunk_overlap=50)

LLM / ChatModel object model

# All models share the same interface:
from langchain_anthropic import ChatAnthropic
from langchain_openai import ChatOpenAI

llm = ChatAnthropic(model="claude-sonnet-4-20250514")
# Swap to GPT-4 with one line change:
llm = ChatOpenAI(model="gpt-4o")

# Same .invoke() call either way:
response = llm.invoke("Explain embeddings")
print(response.content) # AIMessage
03 · LCEL: Your First LangChain Chain

The Pipe Operator in Action:
Prompt | LLM | Parser

LCEL (LangChain Expression Language) is the core composition pattern in modern LangChain. Every component implements the Runnable interface, and the | operator chains them together. This gives you streaming, async, batching, and LangSmith tracing with zero additional code.

Anatomy of an LCEL chain

1. Prompt TemplateDefines the structure of the prompt with placeholder variables. ChatPromptTemplate.from_messages([]) builds a list of (role, content) tuples. Variables in {curly_braces} are filled at invoke time.
2. LLM (or ChatModel)The LLM receives the formatted prompt and returns an AIMessage. Temperature=0 for deterministic outputs (classification, extraction). Higher for creative tasks.
3. Output ParserParses the AIMessage into the format your application needs. StrOutputParser extracts .content as a string. JsonOutputParser parses JSON. PydanticOutputParser validates against a schema.

first_chain.py

from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# ── Step 1: Define the prompt template ───────────────────────
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant that explains technical concepts clearly."),
    ("human", "Explain {concept} in 2-3 sentences for a {level} audience.")
])

# ── Step 2: Choose the LLM ───────────────────────────────────
llm = ChatAnthropic(
    model="claude-sonnet-4-20250514",
    temperature=0  # deterministic output
)

# ── Step 3: Compose with the | operator ──────────────────────
chain = prompt | llm | StrOutputParser()

# ── Invoke with variables ────────────────────────────────────
response = chain.invoke({
    "concept": "embeddings",
    "level": "beginner"
})
print(response)
# "Embeddings are numerical representations of text..."

# ── Streaming (first token in ~400ms instead of waiting) ──────
for chunk in chain.stream({
    "concept": "transformers", "level": "intermediate"
}):
    print(chunk, end="", flush=True)  # tokens arrive one by one

# ── Async (non-blocking for FastAPI/web servers) ──────────────
import asyncio
async def explain(concept: str) -> str:
    return await chain.ainvoke({"concept": concept, "level": "expert"})

# ── Batch (multiple inputs in parallel) ──────────────────────
responses = chain.batch([
    {"concept": "RAG", "level": "beginner"},
    {"concept": "fine-tuning", "level": "intermediate"},
    {"concept": "agents", "level": "expert"},
])

The most common architecture mistake

Building an agent for a task that should be an engine. Agents add loop risk, unpredictability, and 5-10x the latency of a single LLM call. If your task has a fixed input-output structure (document in, summary out), always use an engine. Only reach for agents when the task genuinely requires multi-step decision-making, tool selection, or adaptive planning based on intermediate results.

05 · How to Adapt an LLM to Your Needs

Prompt Engineering, RAG,
and Fine-Tuning: When to Use Each

LLMs are general-purpose and know nothing about your specific domain by default. You have three tools to specialize them. Each operates at a different layer: prompt engineering changes what you ask, RAG changes what context the LLM sees, and fine-tuning changes the model weights themselves. They are complementary, not mutually exclusive.

Prompt Engineering

Craft the input to guide model behavior without modifying the model. Role instructions, examples, reasoning chains, output format specs.

Pros

✓ Zero-cost: no training or indexing
✓ Instant: change prompt and test
✓ Flexible: any task with clear instructions

Cons

✗ Cannot add new factual knowledge
✗ Fails on private/proprietary data
✗ Inconsistent on highly specific formats
When: Start here always. If prompt engineering alone achieves 90%+ quality, stop.
Customer support: "You are a Marevlo support agent. Answer only from the provided context. If unsure, say I don't know."

RAG (Retrieval-Augmented Generation)

Retrieve relevant documents at query time and inject them into the context window. The model sees current, specific information without being retrained.

Pros

✓ No model training required
✓ Knowledge stays current (just re-index)
✓ Traceable: can cite source documents

Cons

✗ Adds retrieval latency (20-200ms)
✗ Requires indexing infrastructure
✗ Quality depends on retrieval precision
When: Use when your application requires knowledge not in training data, or needs to cite specific sources.
Policy Q&A: embed your policy documents → retrieve relevant sections → LLM answers with citations.

Fine-Tuning

Train the model on your domain data to update its weights. The model internalizes your style, format, and domain knowledge permanently.

Pros

✓ Fastest inference (no retrieval step)
✓ Learns style/format consistently
✓ No context window needed for learned facts

Cons

✗ Expensive: 100s-1000s of dollars
✗ Requires labeled training data
✗ Knowledge freezes at training time
When: Use only when: (1) prompt engineering + RAG cannot hit quality target, (2) you need consistent format/style the model doesn't have, (3) you have 500+ high-quality labeled examples.
Medical coding: fine-tune on 10,000 clinical note → ICD-10 code examples to learn domain-specific extraction patterns.

Decision flowchart: which strategy to use

Does prompt engineering alone achieve target quality?YES → use prompt engineering only
Does the task require proprietary or current knowledge?YES → add RAG
Does RAG + prompt engineering still miss quality target?YES → consider fine-tuning
Do you have 500+ high-quality labeled training examples?NO → collect data before fine-tuning
Is the knowledge static (will not change frequently)?NO → use RAG instead (fine-tuning freezes knowledge)
After all checks: go ahead with fine-tuning + RAG
06 · Which LLMs to Choose

GPT, Claude, Gemini, and Open Models:
A Practical Selection Guide

Model choice affects latency, cost, quality, privacy, and deployment complexity. There is no single best model — the right choice depends on your task type, context length requirements, privacy constraints, and cost budget. This guide covers the decision dimensions that matter in production.

OpenAI GPT-4o / GPT-4.1 — most widely used, strong general capability

Strong baseline for most tasks. GPT-4o adds native vision and audio capabilities. GPT-4.1 extends context to 1M tokens with strong long-context performance. Best ecosystem: most LangChain plugins, most community examples, most third-party tool integrations. Function/tool calling is mature and reliable. Use when: you want maximum community support and ecosystem coverage.

Anthropic Claude Sonnet 4 / Claude Opus 4 — strongest on long-context and instruction following

Consistent citation and grounding behavior makes Claude well-suited for RAG applications where faithfulness matters. Sonnet 4 offers strong quality at moderate cost. Opus 4 is the highest-capability model for complex reasoning. Claude excels at following nuanced system prompt instructions and producing structured output. Use when: you need strong grounding, citation accuracy, or complex multi-step instructions.

Google Gemini 2.5 Pro / Flash — best native multimodal, largest context

Gemini 2.5 Pro handles 2M token contexts natively — useful for very long document analysis without chunking. Flash is fast and cheap for high-throughput use cases. Native multimodal from the ground up: processes images, audio, and video without external adapters. Use when: you need very long context windows, multimodal inputs, or tight Google Cloud integration.

Open Models Llama 4, Mistral, Qwen — self-hosted, full data privacy

Deploy on your own infrastructure (Ollama locally, vLLM on GPU servers). Zero data leaves your environment — critical for healthcare, legal, and financial data. Llama 4 Scout / Maverick reach competitive quality with proprietary models. Smaller models (7B-14B params) run on a single GPU at 50-100 tokens/second. Use when: data privacy is non-negotiable, you need offline deployment, or cost at high volume makes API pricing prohibitive.

09 · Assessment

Module 0 Quiz

1. You are building a system that generates weekly performance reports from employee data files. The system runs automatically, produces a PDF, and stops. No user interaction occurs. Which architecture category does this belong to, and why?

Correct. An engine is stateless: input goes in, output comes out, no memory persists. The system you described has a fixed input-output structure (employee data → PDF report) and no multi-step decision-making. If employees later need to ask follow-up questions about their reports, THAT component would be a chatbot. The report generator itself remains an engine.

2. In LangChain's LCEL, what does the | operator do, and what interface must every component implement to be usable in a chain?

Correct. LCEL's | operator creates a RunnableSequence. When you write prompt | llm | parser, LangChain creates a chain where prompt.invoke() feeds into llm.invoke() feeds into parser.invoke(). Because every component is a Runnable, you get streaming, async, batching, and LangSmith tracing for free on the entire chain without extra code.

3. Your team has built a customer support chatbot using prompt engineering. It sometimes gives incorrect answers about your new pricing plans (introduced last month) that were not in the LLM's training data. What is the correct fix?

Correct. This is the canonical RAG use case: the LLM has correct general capability (customer support) but lacks specific, current knowledge (last month's pricing). RAG injects that knowledge at query time from your indexed documents. Adding it to the system prompt works for very small amounts of data but doesn't scale to a full pricing catalog and requires manual prompt updates on every change.

4. A startup wants to use an LLM to process patient medical notes and extract structured data (diagnoses, medications, dosages). Their compliance team says no patient data can leave their infrastructure. What model choice is appropriate?

Correct. When data cannot leave your infrastructure, open-weights self-hosted models are the only option. A BAA with Anthropic or OpenAI may satisfy some compliance frameworks, but some organizations require full on-premise deployment. Ollama (local laptop/server) or vLLM (GPU cluster) are the standard deployment tools for open models in LangChain workflows. langchain-community includes Ollama integration.

5. When should you NOT reach for fine-tuning, even if your prompt-engineered + RAG system is not hitting quality targets?

Correct. Both conditions together are the strongest signal to avoid fine-tuning: (1) insufficient labeled data — you need hundreds of high-quality (input, output) pairs that cover edge cases; (2) dynamic knowledge — fine-tuning bakes facts into weights, so anything that changes (prices, policies, people) must trigger a new fine-tuning run. In these situations, invest in better RAG retrieval (hybrid search, reranking) before considering fine-tuning.
