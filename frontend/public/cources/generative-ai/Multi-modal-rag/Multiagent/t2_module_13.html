01 · Deployment Options

From Localhost to Production:
LangServe, FastAPI, and LangGraph Platform

A LangChain chain or LangGraph agent running locally is not a product. Production deployment requires a reliable HTTP interface, auto-scaling, health checks, monitoring integration, and authentication. Three deployment paths are available: LangServe (simplest, built on FastAPI), raw FastAPI (most control), and LangGraph Platform (managed, with built-in checkpointing and tracing).

LangServe

Wraps any Runnable (chain or compiled graph) as a REST API with a single add_routes() call. Automatically creates /invoke, /stream, /batch, and /playground endpoints.

pip install langserve from langserve import add_routes add_routes(app, my_chain, path="/agent")

Best for: Simple deployment, prototypes, internal tools

FastAPI (custom)

Full control over endpoints, authentication, request/response schemas, middleware, rate limiting. More boilerplate but no framework constraints.

@app.post("/chat") async def chat(req: Request): result = await agent.ainvoke(req.body) return result

Best for: Production APIs requiring custom auth, complex schemas, WebSocket streaming

LangGraph Platform

Fully managed deployment from Anthropic/LangChain. Built-in checkpointing, horizontal scaling, LangSmith integration, and agent lifecycle management. Push a graph definition, get a production URL.

langgraph deploy # Deploys to managed infrastructure # Auto-scales, checkpointer included # LangSmith traces automatically

Best for: Teams needing zero-ops deployment with full observability

LangServe: the fastest path to a production API

deploy_langserve.py

from fastapi import FastAPI
from langserve import add_routes
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

app = FastAPI(title="Marevlo Travel Agent API")

# ── Simple chain deployment ───────────────────────────────────
chain = (
    ChatPromptTemplate.from_messages([("human", "{input}")])
    | ChatAnthropic(model="claude-sonnet-4-20250514")
    | StrOutputParser()
)

add_routes(app, chain, path="/travel")
# Creates endpoints automatically:
# POST /travel/invoke  → {"input": "...", "output": "..."}
# POST /travel/stream  → SSE token stream
# POST /travel/batch   → multiple inputs in parallel
# GET  /travel/playground → browser UI for testing

# ── LangGraph agent deployment ────────────────────────────────
add_routes(app, compiled_agent.with_types(
    input_type=dict, output_type=dict
), path="/agent")

# ── Run the server ────────────────────────────────────────────
# uvicorn deploy_langserve:app --host 0.0.0.0 --port 8000 --workers 4

# ── Docker deployment ────────────────────────────────────────

02 · Agent Evaluation

Measuring Quality for Systems
That Are Non-Deterministic by Design

Evaluating an agent is harder than evaluating a chain. Chains have deterministic outputs — the same input always produces the same output. Agents explore different paths on every run. You cannot check for exact output match. Instead, you evaluate: (1) was the task completed correctly? (2) did the agent use the right tools? (3) was the answer grounded and accurate? (4) was it efficient?

Evaluation dimensionWhat to measureHow to measureTarget
Task completionDid the agent fully satisfy the user request?LLM judge: "Given the request and the agent's response, was the task completed? Yes/No + reason">90% completion rate
Tool selection accuracyDid the agent call the right tools in the right order?Compare tool_calls in state against an expected tool sequence from a golden test set>85% correct sequence
Factual accuracyWere facts in the response correct and grounded in tool results?LLM judge: "Are the facts in this response supported by these tool results? Rate 1-5">4.0 average
EfficiencyDid the agent use the minimum number of tool calls?Count tool calls per successful task. Compare to baseline minimum required calls.<2x baseline calls
Guardrail effectivenessAre harmful/off-topic queries correctly rejected?Adversarial test set: 50 blocked queries. Check BLOCK rate. Also 50 legitimate queries → check PASS rate.>98% BLOCK, >99% PASS
LatencyDoes the agent respond within the SLA?p50, p95, p99 response times via LangSmith metrics. Alert on p99 > 15s.p50 < 5s, p99 < 15s
💡

LLM-as-judge: the practical evaluation approach for agents

Traditional evaluation metrics (exact match, BLEU, ROUGE) cannot evaluate open-ended agent responses. The standard production approach is LLM-as-judge: use a separate LLM (often Claude Opus or GPT-4 for high accuracy) to score agent responses against criteria. Example: "Given this travel request and this agent response, rate the response on: (1) Completeness 1-5, (2) Factual accuracy 1-5, (3) Helpfulness 1-5. Provide scores and brief justification." This is automated but semantically rich evaluation.

03 · Testing Non-Deterministic Agents

How to Write Tests
When Output Varies Every Run

Unit tests for deterministic functions check exact outputs: assert function(input) == expected_output. You cannot do this for agents. Agents may produce different but equally valid responses on different runs. Testing strategy must shift from exact-match to property-based and behavioral assertions: "the response must mention a hotel", "the agent must call hotel_search", "the response must not contain competitor names".

What to test and how

Tool sequence tests

Assert that specific tools were called in the right order for specific query types

For "find hotel in Tokyo": assert "hotel_search" in tool_calls. For "plan trip": assert tool_calls.index("hotel_search") < tool_calls.index("book_accommodation").

Content property tests

Assert output CONTAINS key elements without checking exact wording

assert "hotel" in response.lower() or "accommodation" in response.lower()

Content exclusion tests

Assert output does NOT contain prohibited content

assert "booking.com" not in response.lower() and "expedia" not in response.lower()

Guardrail tests

Assert blocked queries are blocked and legitimate queries pass

for blocked_query in BLOCKED_TEST_SET: assert agent_response == REJECTION_MESSAGE

State transition tests

Assert the graph follows expected node sequences

Use get_state_history to verify node execution order matches expected path

Idempotency tests

Assert running the same query 3 times produces equivalent (not identical) answers

Run 3 times, LLM judge all 3, assert all score >= 4/5 on accuracy

Agent test suite example

import pytest from langchain_core.messages import HumanMessage @pytest.fixture def agent(): # Use MemorySaver for test isolation return graph.compile(checkpointer=MemorySaver()) def test_hotel_search_called_for_accommodation_query(agent): result = agent.invoke({ "messages": [HumanMessage("Find a hotel in Tokyo")], "iteration": 0 }, config={"configurable": {"thread_id": "test_1"}}) # Get all tool calls from state tool_calls = [ tc["name"] for msg in result["messages"] if hasattr(msg, "tool_calls") for tc in msg.tool_calls ] assert "hotel_search" in tool_calls, f"Expected hotel_search, got: {tool_calls}" def test_guardrail_blocks_off_topic(agent): result = agent.invoke({ "messages": [HumanMessage("What is 2+2?")], "iteration": 0 }, config={"configurable": {"thread_id": "test_2"}}) final_message = result["messages"][-1].content # Should be a polite rejection, not an answer to the math question assert "travel" in final_message.lower() or "only" in final_message.lower() assert "4" not in final_message # did not answer the math def test_no_competitor_names_in_output(agent): result = agent.invoke({ "messages": [HumanMessage("Find me a hotel in Paris")], "iteration": 0 }, config={"configurable": {"thread_id": "test_3"}}) final = result["messages"][-1].content.lower() for competitor in ["booking.com", "expedia", "airbnb"]: assert competitor not in final, f"Competitor mention found: {competitor}"
04 · Cost Management at Scale

Keeping LLM Costs Predictable
as Query Volume Grows

A single agent conversation costs $0.01-$0.10 in LLM API calls. At 10,000 conversations per day, that is $100-$1,000 per day. Cost optimization is not premature optimization — it is survival planning. The four levers are: model tiering, caching, token optimization, and cost monitoring with alerts.

Cost leverHowExpected savingQuality impact
Model tieringUse fast cheap models (Haiku, GPT-4o-mini) for guardrails and classification. Reserve Sonnet/GPT-4o for main agent reasoning.50-80% reduction in guardrail costsNone — classification tasks do not need full-size models
Semantic cachingCache agent responses by embedding the query. Cosine similarity >0.95 → serve cached response without running the agent.20-40% of queries served from cacheNone — cached answers are from real agent runs
Token optimizationTrim message history to last N turns. Summarize long tool results before adding to context. Remove verbose boilerplate from system prompts.15-30% reduction in per-query tokensMinimal — history trimming can lose context on very long conversations
Streaming (cost-neutral)Does not reduce cost but improves perceived latency, reducing user abandonment and retries.Reduces retry rate by ~15%Positive — users get faster responses
Budget alertsSet daily/hourly spend alerts in LangSmith or your cloud provider. Alert at 80% of daily budget, hard stop at 100%.Prevents runaway cost incidentsNone — alerts and stops are operational, not quality-affecting

Semantic cache for agents

Skipping agent.") return cached # Cache miss: run agent result = await app.ainvoke( {"messages": [HumanMessage(content=question)], "iteration": 0}, config=config ) # Store in cache (with 1-hour TTL via metadata) cache_store.add_texts( [question], metadatas=[{"response": json.dumps(result)}] ) return result

05 · Production Readiness Checklist

Before You Deploy:
The Complete Production Checklist

Every item below has caused a production incident for someone. Work through this checklist before deploying any agent that will handle real user requests. Items marked CRITICAL have caused complete system failures or data breaches when skipped.

The production readiness checklist

CRITICALIteration guard in all graphs

All LangGraph applications with conditional loops have a max_iterations counter and a forced exit path in should_continue. Tested: does it terminate within N steps even when all tools return empty results?

CRITICALSQL injection prevention

If using NL→SQL: all generated SQL validated as SELECT-only before execution. Tested: does "DROP TABLE users;" generated by the LLM get rejected?

CRITICALAPI key rotation and secrets management

No API keys in code or environment files committed to git. Using secrets manager (AWS Secrets Manager, GCP Secret Manager). Keys rotate on a schedule.

CRITICALInput guardrails tested with adversarial inputs

Tested with 50+ adversarial queries: prompt injection attempts, off-topic questions, harmful requests. BLOCK rate > 98% on adversarial set.

HIGHCheckpointer configured for production

MemorySaver replaced with PostgresSaver or Redis-backed checkpointer. State persists across process restarts and scales horizontally.

HIGHLangSmith tracing enabled

LANGCHAIN_TRACING_V2=true in production. Project name set. Sampling configured (100% in staging, 10-20% in production for cost).

HIGHRate limiting implemented

Per-user rate limits on the API (e.g., 100 requests/hour). Per-tool rate limits in agent state (e.g., max 5 hotel_search calls/conversation).

HIGHCost alerts configured

Daily spend alerts at 80% and 100% of budget. Hourly alerts for anomalies (>3x normal spend in an hour).

MEDIUMOutput validator in place

Post-generation validation checking for competitor names, PII, out-of-range prices, and system prompt leakage.

MEDIUMGraceful degradation

If LLM API is unavailable or rate-limited, the system returns a user-friendly error rather than a 500. Retry with exponential backoff.

MEDIUMHuman-in-the-loop for irreversible actions

Any action that cannot be undone (booking, payment, external communication) requires explicit human confirmation before execution.

MEDIUMTest suite with CI integration

Property-based agent tests run on every PR. Guardrail effectiveness tests, tool sequence tests, content exclusion tests all passing.

LOWSemantic cache deployed

Cache hit rate monitored. TTL configured per content type. Invalidation on knowledge base updates.

LOWModel tiering implemented

Fast cheap model for guardrails and classification. Full model only for main reasoning.

LOWDocumentation for operators

Runbook: how to restart the agent, how to clear stuck state, how to roll back to previous version, how to disable specific tools.

07 · LangGraph Platform & Open Agent

Managed Deployment:
Zero-Ops Agent Infrastructure

The LangGraph Platform is a managed deployment environment for LangGraph applications. You push a graph definition and configuration; the platform handles horizontal scaling, state persistence, checkpoint management, and LangSmith integration. The Open Agent Protocol allows agents deployed on the platform to interoperate with other agent frameworks and tools.

LangGraph Platform: what it provides

Deployment

Push graph definition → get a production HTTPS endpoint. No server management required.

Scaling

Automatic horizontal scaling based on request volume. Handles burst traffic without configuration.

State persistence

Built-in PostgreSQL-backed checkpointer. No MemorySaver workarounds needed.

Thread management

Thread creation, listing, and deletion via API. Built-in per-user thread isolation.

LangSmith integration

All traces automatically sent to LangSmith. No env var configuration required.

SDK

Python and JavaScript SDKs for invoking deployed agents. Streaming and async support built-in.

09 · Final Assessment

Module 13 Final Quiz

1. You deploy a LangGraph agent using LangServe on a single FastAPI server. It handles 100 requests/day fine but crashes under 1,000 requests/day load. What are the two most impactful changes?

Correct. LangServe runs on FastAPI and Uvicorn, which support multiple workers and async request handling. A single worker handles only one synchronous request at a time, causing queuing under load. Multiple workers + async LLM calls allow concurrent request processing. The combination of horizontal scaling (more workers/replicas) and async I/O (eliminate blocking calls) is the standard pattern for production LangServe deployment.

2. You want to evaluate whether your travel agent correctly handles hotel booking requests. The agent response varies on each run. What evaluation approach works?

Correct. Non-deterministic evaluation requires property-based and behavioral assertions. Exact match and BLEU/ROUGE are inappropriate for free-form agent responses — the agent may correctly book a hotel using completely different wording each time. Property tests verify structural invariants (must call hotel_search, must contain a hotel name). LLM-as-judge evaluates semantic quality. Running both across a test set of 20+ queries and aggregating gives statistically meaningful quality scores that can be tracked over time.

3. Your production agent's daily cost doubled overnight without any change in user volume. LangSmith shows average conversation length increased from 4 LLM calls to 8 LLM calls per session. What likely happened and what do you investigate first?

Correct. A sudden doubling of calls per conversation with stable query volume is a code regression, not a traffic problem. The systematic debugging approach: (1) git blame for recent changes touching routing logic or system prompts — even minor wording changes can cause the agent to loop more; (2) sample specific traces with 8 calls and read the Thought steps — is the agent re-calling the same tool? Is it not recognizing when it has enough information? (3) A/B compare against a known-good previous version via LangSmith project comparison.

4. A user reports your travel agent told them "Booking.com has the best rates for this hotel." This is both a competitor mention AND a factual claim you cannot verify. Which layer of your safety stack failed and what is the fix?

Correct. The input guardrail (option A) cannot block this because the user's request ("find me a hotel") was legitimate. The system prompt (option C) is a soft constraint that the LLM can violate. The tool restriction (option D) controls what tools the agent calls, not what it says. The output validator is the layer specifically designed to catch this: it scans the generated response before it reaches the user. A two-layer approach — LLM validator (catches semantic violations) + regex filter (catches exact-match patterns) — provides defense in depth.

5. You are designing the test suite for a new multi-agent travel system with 3 specialist agents and a supervisor. What is the correct testing order and why does order matter?

Correct. The bottom-up testing order mirrors the dependency structure: the supervisor depends on specialists working correctly. If you discover a bug in an integration test, you cannot tell whether it is in the supervisor routing, the specialist tool selection, or a specialist's output format without having validated each layer separately. Testing specialists in isolation first establishes a baseline: you know accom_agent correctly calls hotel_search for accommodation queries and rejects transport queries. This baseline makes integration test failures unambiguous — if they happen, the bug must be in the coordination layer.
