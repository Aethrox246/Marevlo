01 · The ReAct Pattern

Reason, Act, Observe, Repeat:
How Agents Make Decisions

ReAct (Reason + Act) is the foundational pattern for AI agents that use tools. Instead of producing a direct answer, the LLM generates a Thought (reasoning about what to do), then an Action (tool call), observes the result, and reasons again — repeating until it has enough information to produce a Final Answer. This loop is what makes agents adaptive rather than predetermined.

ReAct execution trace: building a travel plan

User: "Plan a 3-day trip to Tokyo for next week."

Thought: I need to find activities in Tokyo, check the weather, and find hotels.
Action: search_travel_info("Tokyo 3-day trip attractions")
Observation: "Tokyo has Senso-ji Temple, Shibuya, Akihabara, Mt. Fuji day trips..."

Thought: I have activities. Now I need to check weather for next week.
Action: get_weather("Tokyo", "2024-12-09", "2024-12-12")
Observation: "Tokyo next week: 8-14°C, partly cloudy, light rain Wednesday."

Thought: Activities and weather ready. Now I need hotels.
Action: search_hotels("Tokyo", "2024-12-09", "2024-12-12", budget=150)
Observation: "Shinjuku Garden Hotel: ¥14,200/night. Akihabara Stay: ¥11,800/night."

Thought: I have all the information I need to create a complete travel plan.
Final Answer: "Here's your Tokyo itinerary: Day 1 — Senso-ji and Akihabara..."

Thought

The LLM's internal reasoning step: "What do I know? What do I still need? Which tool should I call?" Not sent to the user — only the Final Answer is.

Action

A structured tool call: tool name + arguments. The LLM selects which tool to call based on tool descriptions in the system prompt.

Observation

The tool's return value, fed back into the context as input for the next Thought step. The cycle continues until Final Answer.

💡

ReAct vs direct generation: why the loop matters

Without the ReAct loop, an LLM answering "Plan a Tokyo trip" guesses at activities, invents hotels, and makes up weather — all from training data. With ReAct, every fact comes from a real tool call: actual hotel prices, real weather forecasts, current attraction information. The grounding makes the answer accurate and trustworthy. The loop also enables adaptive behavior: if the hotel search returns no budget options, the agent can call it again with different parameters.

02 · Tool Calling Mechanics

From Function to Tool:
Schema, Registration, and Execution

A tool is a Python function with a description that the LLM can read. The LLM selects tools based on their names and descriptions — tool quality is entirely determined by how well you describe what the tool does, what it expects, and when to use it. The @tool decorator or StructuredTool.from_function() handles the schema extraction automatically.

Defining tools: three approaches

from langchain_core.tools import tool from langchain.tools import StructuredTool from pydantic import BaseModel, Field # Approach 1: @tool decorator (simplest) @tool def get_weather(city: str, date: str) -> str: """Get weather forecast for a city on a specific date. Use for: planning activities that depend on weather conditions. city: city name (e.g., 'Tokyo', 'Paris') date: ISO date string (e.g., '2024-12-09') Returns: temperature range, conditions, precipitation chance.""" return weather_api(city, date) # real API call # Approach 2: StructuredTool with Pydantic schema class HotelSearchInput(BaseModel): city: str = Field(description="Destination city") check_in: str = Field(description="ISO date: YYYY-MM-DD") check_out: str = Field(description="ISO date: YYYY-MM-DD") max_price_usd: float = Field(description="Max price per night in USD") hotel_tool = StructuredTool.from_function( func=search_hotels, name="search_hotels", description="Search for hotels. NOT for flight or activity searches.", args_schema=HotelSearchInput )

How tool calling works inside the LLM node

1LLM receives: system prompt + tool schemas (name, description, args) + conversation history
2LLM produces: either text response OR tool_calls list in the AIMessage
3Agent detects tool_calls in AIMessage → dispatches to ToolNode
4ToolNode executes the function, wraps result in ToolMessage
5ToolMessage appended to conversation → LLM sees result → next Thought
⚠️

Tool description IS the routing logic

The LLM selects tools by matching the current context to tool descriptions. "Get weather" is a bad description. "Get weather forecast for a city on a specific date. Use for: planning activities that depend on weather conditions. NOT for hotel or flight availability." is a good description. The NOT FOR clause prevents the LLM from using the weather tool for hotel availability queries — a common mistake without explicit negative guidance.

03 · LangGraph Agent Graph

The Standard Agent Architecture:
LLM Node + Tool Node + Conditional Edge

The canonical LangGraph agent consists of three elements: an LLM node that reasons and decides which tool to call, a ToolNode that executes tool calls, and a conditional edge that routes back to the LLM after each tool call or terminates when the LLM produces a final answer. This simple graph implements the full ReAct loop.

The minimal ReAct agent: three components

agent node

Runs the LLM with current state (messages). If LLM produces tool_calls, returns them. If LLM produces final text response, that terminates the loop.

tools node

Receives tool_calls from agent state. Executes each tool function. Appends ToolMessage(s) with results. Always routes back to agent.

should_continue (conditional edge)

Checks last message: has tool_calls? → go to "tools". No tool_calls? → go to END. Also checks iteration counter as safety guard.

Graph flow diagram

START → agent → should_continue?
                            ↙              ↘
              tools               END
                ↓
         (back to agent)

tool_calls present → tools → agent → loop
no tool_calls → END (final answer returned)

travel_agent.py — basic ReAct agent

import operator
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from langchain_anthropic import ChatAnthropic
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage

# ── Tool definitions ─────────────────────────────────────────
@tool
def search_travel_info(query: str) -> str:
    """Search for travel information about destinations, attractions, and activities.
    Use for: tourist spots, cultural experiences, local tips.
    NOT for: hotel bookings, weather, flight prices."""
    return rag_chain.invoke(query)  # queries travel knowledge base

@tool
def get_weather(city: str, date: str) -> str:
    """Get weather forecast. city: city name. date: YYYY-MM-DD."""
    return weather_service.forecast(city, date)

@tool
def search_hotels(city: str, check_in: str, check_out: str, max_price_usd: float) -> str:
    """Search hotels. Returns name, price, rating, location. NOT for activities."""
    return hotel_api.search(city, check_in, check_out, max_price_usd)

tools = [search_travel_info, get_weather, search_hotels]

# ── State ────────────────────────────────────────────────────
class AgentState(TypedDict):
    messages: Annotated[list, operator.add]  # append-only conversation
    iteration: int

# ── LLM bound to tools ───────────────────────────────────────
llm = ChatAnthropic(model="claude-sonnet-4-20250514").bind_tools(tools)

# ── Agent node ───────────────────────────────────────────────
def agent_node(state: AgentState) -> dict:
    return {
        "messages": [llm.invoke(state["messages"])],
        "iteration": state["iteration"] + 1
    }

# ── Conditional edge ─────────────────────────────────────────
def should_continue(state: AgentState):
    if state["iteration"] >= 10: return "end"  # hard stop
    last = state["messages"][-1]
    if hasattr(last, "tool_calls") and last.tool_calls: return "tools"
    return "end"

# ── Graph assembly ───────────────────────────────────────────
g = StateGraph(AgentState)
g.add_node("agent", agent_node)
g.add_node("tools", ToolNode(tools))
g.set_entry_point("agent")
g.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})
g.add_edge("tools", "agent")
app = g.compile()

# ── Run ──────────────────────────────────────────────────────
result = app.invoke({
    "messages": [HumanMessage(content="Plan a 3-day trip to Tokyo next week.")],
    "iteration": 0
})
print(result["messages"][-1].content)
04 · Multi-Tool Agents and System Guidance

Five Tools, One Agent:
System Prompt as the Routing Logic

A single-tool agent is predictable. A five-tool agent introduces tool selection errors: the LLM calls the weather tool for hotel availability, or calls search_travel_info when it should book with search_hotels. System prompt guidance — explicit instructions about when to use each tool and in what order — is the primary mechanism for controlling multi-tool agent behavior.

System prompt as agent control layer

SYSTEM_PROMPT = """You are a travel planning assistant. You have access to these tools: 1. search_travel_info: Use FIRST to find attractions and activities. Do NOT use for hotels, weather, or flights. 2. get_weather: Use AFTER finding activities to check weather. Always check weather before recommending outdoor activities. 3. search_hotels: Use AFTER checking weather. Never call before activities and weather are confirmed. 4. book_hotel: Use ONLY when user explicitly says 'book' or 'reserve'. Always confirm hotel choice with user before booking. 5. search_flights: Use when user mentions travel dates AND origin city. For trip planning, ALWAYS follow this order: activities → weather → hotels → (flights if needed) If a tool returns no results, retry with different search terms."""

Common multi-tool failure patterns and fixes

Failure patternRoot causeFix
Agent calls hotel search before checking activitiesNo ordering constraint in system prompt"ALWAYS follow this order: activities → weather → hotels"
Agent calls book_hotel without user confirmationNo confirmation gate in prompt"Use book_hotel ONLY when user explicitly says 'book'"
Agent loops calling same tool 5 timesTool returns ambiguous results; no retry strategy"If results are unsatisfactory, retry with different terms. Max 2 retries per tool."
Agent ignores a tool when it should use itTool description too similar to another tool"Use [tool X] specifically for Y. NOT [tool Z]." — explicit exclusion helps.
Agent tries to call non-existent toolLLM hallucinates a tool name not in the registryBind exactly the tools the agent should use: llm.bind_tools([t1,t2,t3])
💡

Using the prebuilt LangGraph ReAct agent

LangGraph provides a prebuilt create_react_agent() function that implements the standard agent graph (agent node + ToolNode + conditional edge) with a single line of code. Use it for simple single-agent tasks: agent = create_react_agent(llm, tools, messages_modifier=system_prompt). Build the graph manually (as in Section 3) when you need: human-in-the-loop checkpoints, custom state fields beyond messages, multiple specialized nodes, or non-standard routing logic.

05 · Step-by-Step Agent Expansion

From Single Tool to Multi-Tool:
An Incremental Development Strategy

Do not build a 10-tool agent from scratch. Start with one tool, verify it works correctly, add a second tool and verify the agent selects between them correctly, then add a third. Each tool addition multiplies the selection complexity. Incremental validation catches tool confusion early — much easier to debug 2 tools than 8.

Incremental development: four phases

1

Phase 1: single tool: [search_travel_info]

Test: Ask only destination questions

Check: Does it call the tool? Does it use tool output in the answer?

↓ verify works correctly before adding next tool
2

Phase 2: add weather tool: [search_travel_info, get_weather]

Test: Ask "activities + weather" questions

Check: Does it call both tools in the right order? Does it call weather for non-weather queries?

↓ verify works correctly before adding next tool
3

Phase 3: add hotel tool: [search_travel_info, get_weather, search_hotels]

Test: Full trip planning questions

Check: Does it follow activities → weather → hotels order? Does it avoid premature hotel search?

↓ verify works correctly before adding next tool
4

Phase 4: add booking tool: [+ book_hotel]

Test: Explicit booking requests

Check: Does it wait for user confirmation? Does it avoid auto-booking on search queries?

06 · LangSmith Observability for Agents

Debugging Non-Deterministic Agents:
Traces, Tool Calls, and Run Comparison

Chains follow a fixed path — debugging means inspecting one predictable trace. Agents follow different paths on every run. Without observability, debugging a wrong agent answer means reading thousands of tokens of log output. LangSmith traces every node, tool call, and LLM response as a structured span tree — making agent debugging as straightforward as clicking through a hierarchy.

What an agent trace looks like in LangSmith

▶ TravelAgent [12.4s | 3 loops | $0.031]
  ▶ Loop 1: agent node [1.8s | 1,234 tokens]
    → tool_call: search_travel_info("Tokyo attractions")
  ▶ Loop 1: tools node [342ms]
    search_travel_info result: "Senso-ji, Shibuya, Akihabara..."
  ▶ Loop 2: agent node [2.1s | 1,456 tokens]
    → tool_call: get_weather("Tokyo", "2024-12-09")
  ▶ Loop 2: tools node [187ms]
    get_weather result: "8-14°C, partly cloudy, light rain Wed"
  ▶ Loop 3: agent node [3.2s | 2,341 tokens]
    → Final Answer (no tool calls) — generating itinerary
  Final: "Here's your 3-day Tokyo plan..."

Agent-specific debugging scenarios

Agent called wrong tool

Open the Loop N agent node span → see which tool was selected → check the tool call args → compare to tool description

Agent looped N times unnecessarily

Check each tool node span → see what result was returned → identify why the LLM decided to loop again instead of answering

Agent produced wrong final answer

Open the last agent node span → inspect the full messages history → verify all tool results were correct → check if LLM ignored a relevant result

Compare two runs with different system prompts

Use LangSmith's side-by-side comparison view → run A vs run B → identify which nodes differ and how tool selection changed

full_travel_agent.py — production grade

import os, operator
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from langchain_anthropic import ChatAnthropic
from langchain_core.tools import tool
from langchain_core.messages import SystemMessage, HumanMessage

# ── LangSmith ─────────────────────────────────────────────────
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_PROJECT"] = "travel-agent-prod"

# ── Tools ────────────────────────────────────────────────────
@tool
def search_travel_info(query: str) -> str:
    """Search travel knowledge base for destinations and activities."""
    return travel_rag_chain.invoke(query)

@tool
def get_weather(city: str, date: str) -> str:
    """Forecast for city on date (YYYY-MM-DD). Check before outdoor plans."""
    return weather_api(city, date)

@tool
def search_hotels(city: str, check_in: str, check_out: str, max_usd: float) -> str:
    """Search hotels. call AFTER activities+weather confirmed. NOT for bookings."""
    return hotel_api(city, check_in, check_out, max_usd)

tools = [search_travel_info, get_weather, search_hotels]

# ── State ────────────────────────────────────────────────────
class TravelState(TypedDict):
    messages: Annotated[list, operator.add]
    iteration: int

# ── LLM + System prompt ──────────────────────────────────────
SYSTEM = SystemMessage(content="""You are a travel planning assistant.
Tool order: search_travel_info → get_weather → search_hotels
Never skip steps. Never book without explicit user request.""")

llm = ChatAnthropic(model="claude-sonnet-4-20250514").bind_tools(tools)

# ── Nodes ────────────────────────────────────────────────────
def agent_node(state: TravelState) -> dict:
    msgs = [SYSTEM] + state["messages"]
    return {"messages": [llm.invoke(msgs)], "iteration": state["iteration"]+1}

def should_continue(state: TravelState):
    if state["iteration"] >= 10: return "end"  # safety stop
    last = state["messages"][-1]
    return "tools" if hasattr(last, "tool_calls") and last.tool_calls else "end"

# ── Graph ────────────────────────────────────────────────────
g = StateGraph(TravelState)
g.add_node("agent", agent_node)
g.add_node("tools", ToolNode(tools))
g.set_entry_point("agent")
g.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})
g.add_edge("tools", "agent")
app = g.compile()

# ── Run ──────────────────────────────────────────────────────
result = app.invoke({
    "messages": [HumanMessage(content="Plan a 3-day Tokyo trip for Dec 9-12.")],
    "iteration": 0
})
print(result["messages"][-1].content)

09 · Final Assessment

Module 10 Quiz

1. Your travel agent calls search_hotels before calling search_travel_info or get_weather, producing plans with hotels listed before any activities are confirmed. What is the most effective single fix?

Correct. System prompt is the primary control layer for multi-tool behavior. Explicit ordering instructions ("ALWAYS follow this sequence") directly shape the LLM's Thought step reasoning, which determines which tool it calls next. This is more maintainable than state-based guards (option D) because it works at the LLM reasoning level rather than requiring complex state tracking. State guards (LangGraph conditional edges) are the secondary line of defense when prompt-based control is insufficient.

2. Your agent with 5 tools (search, weather, hotels, flights, restaurants) is selecting the wrong tool 30% of the time. What are the two most impactful improvements?

Correct. Tool selection accuracy degrades with tool count and similarity between tool descriptions. The two highest-impact fixes are: (1) NOT FOR clauses that create explicit boundaries between similar tools — "search_hotels: lodging only. NOT for flights" eliminates the confusion between accommodation and flight search; (2) few-shot examples that demonstrate correct selection for the exact query types that cause confusion. LLMs are excellent pattern matchers — showing them the correct tool for common ambiguous queries dramatically improves selection accuracy.

3. You have a ReAct agent that loops 8 times on a simple "find me a hotel in Tokyo" query. LangSmith shows it is repeatedly calling search_travel_info even after getting good results. What is causing this and how do you fix it?

Correct. This is the "unnecessary loop" failure mode: the agent collects results but keeps searching instead of synthesizing. The primary fix is prompt-based: explicit guidance telling the agent to check if it can answer after each tool call. The secondary fix is increasing the iteration guard to a lower value (e.g., 5 instead of 10) to force faster termination. Blocking re-calls (option D) is too aggressive — sometimes the same tool should be called twice with different parameters (e.g., search_hotels once for Tokyo center, once for Tokyo suburbs).

4. When should you use create_react_agent (prebuilt) vs building the LangGraph graph manually?

Correct. create_react_agent is production-grade for standard use cases and should be the default starting point. Build manually when you hit its limitations: (1) custom state beyond messages — prebuilt only tracks messages; (2) human-in-the-loop — requires compile(checkpointer=..., interrupt_before=[...]) which prebuilt supports but may be harder to configure; (3) specialist sub-agents — requires custom multi-graph coordination; (4) non-standard routing — conditional edges beyond "tools or end". If you find yourself patching prebuilt behavior, switch to manual.

5. A user reports your travel agent occasionally invents hotel names that don't exist. LangSmith traces show the agent sometimes generates the Final Answer without calling search_hotels. Why does this happen and what are the two fixes?

Correct. This is the core hallucination risk in agents: when the agent skips a tool call and generates from training data instead. Two defenses work in combination: (1) Prompt-level constraint: "NEVER mention specific hotel names without first calling search_hotels." This guides the Thought step. (2) Graph-level enforcement: a custom should_continue that inspects whether tool_messages for search_hotels exist in state before allowing Final Answer — if hotels are mentioned in the final response but no hotel search was performed, route back to the tools node. Defense-in-depth is essential for production agents.
