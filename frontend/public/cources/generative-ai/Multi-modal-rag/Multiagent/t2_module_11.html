Multi-Agent
Systems

One agent with ten tools becomes unreliable — the LLM struggles to select among too many options. Multi-agent systems solve this by dividing responsibilities: specialist agents each handle a narrow domain with 2-3 tools, and a coordinator dispatches requests to the right specialist. This module covers the router pattern, the supervisor pattern, and how to wire sub-graphs together in LangGraph.

01 · Why Multi-Agent Systems

The Problem With One Agent
and Too Many Tools

Research shows LLM tool selection accuracy degrades sharply beyond 6-8 tools. An agent handling hotel search, flight booking, weather, activities, restaurants, currency conversion, visa requirements, local transport, and event tickets will routinely select the wrong tool for ambiguous queries. Multi-agent architecture solves this by partitioning tools: each specialist agent sees only 2-3 tools relevant to its domain.

Single agent vs multi-agent: the selection accuracy problem

02 · Designing Specialist Agents

Each Specialist Owns a Domain:
Tools, System Prompt, and Boundaries

A specialist agent is a complete ReAct agent scoped to a specific domain. It has its own set of tools (2-4 maximum), its own system prompt explaining its role and what it should and should not handle, and its own LangGraph sub-graph. The coordinator never needs to know how the specialist works internally — it just dispatches requests and receives results.

Accommodation Specialist Agent

@tool def hotel_search(city: str, check_in: str, check_out: str, budget_usd: float) -> str: """Search hotels. Use for full-service hotels only. NOT for B&Bs.""" return hotel_api(city, check_in, check_out, budget_usd) @tool def bb_search(city: str, check_in: str, check_out: str) -> str: """Search bed & breakfasts and guesthouses. Smaller, personal stays.""" return bb_api(city, check_in, check_out) @tool def book_accommodation(property_id: str, guest_name: str) -> str: """Book a property. ONLY call after user explicitly confirms booking.""" return booking_api(property_id, guest_name) ACCOM_SYSTEM = """You are an accommodation specialist. You handle: hotels, B&Bs, guesthouses, and accommodation bookings. You do NOT handle: flights, transport, activities, or restaurants. Always search before booking. Confirm with user before calling book_accommodation.""" accom_agent = create_react_agent( model=llm, tools=[hotel_search, bb_search, book_accommodation], messages_modifier=ACCOM_SYSTEM )

Transport Specialist Agent

@tool def flight_search(origin: str, destination: str, date: str) -> str: """Search flights. Requires origin city and destination.""" return flight_api(origin, destination, date) @tool def local_transport(city: str, from_loc: str, to_loc: str) -> str: """Local transport options: taxi, metro, bus between locations within a city.""" return transport_api(city, from_loc, to_loc) @tool def car_rental(city: str, pickup_date: str, return_date: str) -> str: """Car rental options. NOT for taxis or public transit.""" return rental_api(city, pickup_date, return_date) TRANSPORT_SYSTEM = """You are a transport specialist. You handle: flights, local transport, car rentals. You do NOT handle: accommodation, activities, or food.""" transport_agent = create_react_agent( model=llm, tools=[flight_search, local_transport, car_rental], messages_modifier=TRANSPORT_SYSTEM )
💡

Each specialist is independently testable

Test each specialist in isolation before wiring them into the coordinator. Call accom_agent.invoke with accommodation-only requests and verify it: (1) never calls non-accommodation tools, (2) handles hotel vs B&B differentiation correctly, (3) refuses to book without explicit user confirmation. Only after each specialist passes isolated tests should you assemble the multi-agent graph. Isolated testing is dramatically simpler than debugging the full multi-agent system.

03 · The Router Pattern

One Router, Multiple Specialists:
Dispatch and Return

The router pattern uses a coordinator agent that classifies incoming queries and dispatches them to the appropriate specialist sub-graph. The coordinator does not handle the task itself — it only decides which specialist should handle it. Each specialist processes the request and returns its result to the coordinator, which assembles the final response if multiple specialists were involved.

Router architecture: classify → dispatch → collect

User: "Find me a hotel in Tokyo for Dec 9-12 and book a flight from London."
Router: Classifies → ["accommodation", "transport"] (two specialists needed)
→ AccomAgent: hotel_search("Tokyo", "Dec 9", "Dec 12") → "Shinjuku Hotel: ¥14,200/night"
→ TransportAgent: flight_search("London", "Tokyo", "Dec 9") → "BA Flight: £480 return"
Router synthesizes: "I found a hotel at ¥14,200/night and a flight for £480 return. Shall I book both?"

Router implementation in LangGraph

from typing import Literal # Router classifies into specialist names ROUTER_PROMPT = ChatPromptTemplate.from_messages([ ("system", "Route to specialists. Output JSON array of needed specialists:\n" "['accommodation', 'transport', 'experience']\n" "Output ONLY a JSON array."), ("human", "{query}") ]) def router_node(state): routes = (ROUTER_PROMPT | llm | JsonOutputParser()).invoke( {"query": state["messages"][-1].content} ) return {"routes": routes, "results": {}} def should_dispatch(state) -> list[str]: """Return list of specialist names to run.""" return state.get("routes", ["accommodation"])

State for the multi-agent graph

04 · The Supervisor Pattern

Agent of Agents:
Dynamic Dispatch With Feedback Loops

The router dispatches once and collects results. The supervisor pattern goes further: the supervisor LLM can read each specialist's result, decide whether it is satisfactory, dispatch to another specialist for follow-up, combine outputs, and only terminate when it judges the full task complete. This bidirectional coordination enables complex multi-step workflows across specialist boundaries.

One-way (router) vs return-ticket (supervisor)

Router: one-way interaction

Router → AccomAgent: "Find hotel in Tokyo"
AccomAgent → Router: "Found Shinjuku Hotel ¥14,200"
Router: done. Returns result to user.
Problem: if hotel is fully booked, Router cannot re-dispatch.

Supervisor: return-ticket interaction

Supervisor → AccomAgent: "Find hotel in Tokyo Dec 9-12"
AccomAgent → Supervisor: "Shinjuku Hotel ¥14,200 (only 2 rooms left)"
Supervisor: reads result, decides → TransportAgent: "Book flight now before hotel sells out"
TransportAgent → Supervisor: "BA Flight £480 booked for Dec 9"
Supervisor: both tasks done → synthesize final answer
Benefit: Supervisor adapts based on specialist results.

Supervisor node: reads results, decides next action

from typing import Literal SUPERVISOR_PROMPT = """You are a travel coordinator supervising specialist agents. Available specialists: accommodation, transport, experience After each specialist result, decide: - Which specialist to call next (if more info needed) - "FINISH" if you have enough to answer the user Output JSON: {"next": "accommodation"|"transport"|"experience"|"FINISH", "instruction": "what to ask the specialist"}""" def supervisor_node(state: MultiAgentState): # Build context from all specialist results so far context = "\n".join( f"{k} result: {v}" for k, v in state.get("results", {}).items() ) or "No results yet." decision = (SUPERVISOR_PROMPT_TPL | llm | JsonOutputParser()).invoke({ "query": state["messages"][-1].content, "context": context }) return {"next_agent": decision["next"], "instruction": decision["instruction"]} def route_supervisor(state) -> Literal["accommodation","transport","experience","synthesize"]: nxt = state.get("next_agent", "FINISH") if state.get("iteration", 0) >= 8: return "synthesize" # guard return "synthesize" if nxt == "FINISH" else nxt
05 · Assembling the Multi-Agent Graph

Wiring Specialists Into
a LangGraph Supervisor Graph

Each specialist is an independent sub-graph (or create_react_agent). The supervisor is a node in the outer graph. Conditional edges route from the supervisor to each specialist and back, enabling the supervisor to call specialists in any order, multiple times, based on accumulated results.

multi_agent_graph.py

import operator
from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import create_react_agent
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser, StrOutputParser
from langchain_core.messages import HumanMessage

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

# ── Specialist agents (defined in Section 2) ─────────────────
accom_agent = create_react_agent(llm, [hotel_search, bb_search, book_accommodation],
                                 messages_modifier=ACCOM_SYSTEM)
transport_agent = create_react_agent(llm, [flight_search, local_transport, car_rental],
                                     messages_modifier=TRANSPORT_SYSTEM)
experience_agent = create_react_agent(llm, [activity_search, restaurant_search, events_search],
                                      messages_modifier=EXPERIENCE_SYSTEM)

# ── State ─────────────────────────────────────────────────────
class SupervisorState(TypedDict):
    messages: Annotated[list, operator.add]
    results: dict        # specialist_name → result text
    next_agent: str      # "accommodation"|"transport"|"experience"|"FINISH"
    instruction: str     # what to ask the next specialist
    iteration: int

# ── Supervisor node ───────────────────────────────────────────
SUPERVISOR_TPL = ChatPromptTemplate.from_messages([
    ("system", """Travel coordinator. Specialists: accommodation, transport, experience.
Results so far: {context}

Output JSON: {{"next": "accommodation"|"transport"|"experience"|"FINISH",
             "instruction": "specific task for the specialist"}}"""),
    ("human", "User request: {query}")
])

def supervisor_node(state: SupervisorState) -> dict:
    context = "\n".join(f"{k}: {v}" for k, v in state.get("results", {}).items())
    decision = (SUPERVISOR_TPL | llm | JsonOutputParser()).invoke({
        "query": state["messages"][-1].content,
        "context": context or "None yet"
    })
    return {"next_agent": decision["next"], "instruction": decision["instruction"],
            "iteration": state.get("iteration", 0) + 1}

# ── Specialist wrapper nodes ──────────────────────────────────
def _run_specialist(agent, name: str, state: SupervisorState) -> dict:
    query = state.get("instruction") or state["messages"][-1].content
    result = agent.invoke({"messages": [HumanMessage(content=query)]})
    answer = result["messages"][-1].content
    return {"results": {**state.get("results", {}), name: answer}}

accom_node     = lambda s: _run_specialist(accom_agent, "accommodation", s)
transport_node = lambda s: _run_specialist(transport_agent, "transport", s)
experience_node= lambda s: _run_specialist(experience_agent, "experience", s)

# ── Synthesis node ────────────────────────────────────────────
SYNTH_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "Combine specialist results into one clear travel plan for the user."),
    ("human", "Query: {query}\nResults:\n{results}")
])

def synthesize_node(state: SupervisorState) -> dict:
    combined = "\n".join(f"{k}:\n{v}" for k, v in state.get("results", {}).items())
    final = (SYNTH_PROMPT | llm | StrOutputParser()).invoke({
        "query": state["messages"][-1].content, "results": combined
    })
    return {"messages": [AIMessage(content=final)]}

# ── Routing function ─────────────────────────────────────────
def route_after_supervisor(state) -> str:
    if state.get("iteration", 0) >= 8: return "synthesize"  # safety
    nxt = state.get("next_agent", "FINISH")
    mapping = {"accommodation":"accom", "transport":"transport",
               "experience":"experience", "FINISH":"synthesize"}
    return mapping.get(nxt, "synthesize")

# ── Graph assembly ────────────────────────────────────────────
g = StateGraph(SupervisorState)
g.add_node("supervisor", supervisor_node)
g.add_node("accom",      accom_node)
g.add_node("transport",  transport_node)
g.add_node("experience", experience_node)
g.add_node("synthesize", synthesize_node)
g.set_entry_point("supervisor")
g.add_conditional_edges("supervisor", route_after_supervisor,
    {"accom":"accom", "transport":"transport", "experience":"experience", "synthesize":"synthesize"})
for node in ["accom", "transport", "experience"]:
    g.add_edge(node, "supervisor")  # return to supervisor after each specialist
g.add_edge("synthesize", END)
app = g.compile()

# ── Run ──────────────────────────────────────────────────────
result = app.invoke({
    "messages": [HumanMessage(content="Plan a Tokyo trip Dec 9-12 with hotel and flights.")],
    "results": {}, "next_agent": "", "instruction": "", "iteration": 0
})
print(result["messages"][-1].content)
06 · Choosing the Right Pattern

Router vs Supervisor vs Single Agent:
The Decision Framework

ScenarioBest patternWhy
Single domain task (booking only)Single specialist agentOne domain, 2-3 tools, no coordination needed
Classifiable requests, each handled independentlyRouter patternTasks are independent; router dispatches once; no cross-specialist feedback needed
Complex multi-step tasks where specialist results affect what to ask nextSupervisor patternSupervisor reads results, adapts follow-up questions, handles conditional flows
10+ tools in one agent with tool confusionMulti-agent (any)Partition tools into specialists; selection error drops dramatically
All specialists always needed for every queryParallel fan-outSkip router/supervisor; run all specialists in parallel and synthesize
Agent must adapt based on partial results (e.g., hotel sold out → different date)SupervisorOnly supervisor can read result and re-dispatch with modified parameters
⚠️

Multi-agent adds coordination overhead — use only when needed

Every multi-agent interaction adds latency: the supervisor LLM call (classify + dispatch) costs 1-2 seconds per cycle. A 3-specialist supervisor that dispatches to all three adds 3-6 seconds of coordination overhead plus each specialist's own execution time. Start with a single agent. Move to multi-agent only when tool count causes selection errors or when you need domain-specific system prompts that contradict each other in a single agent.

07 · Observing Multi-Agent Systems

Nested Traces and
Cross-Agent Debugging in LangSmith

Multi-agent systems produce nested traces: the outer supervisor run contains spans for each specialist invocation, and each specialist span contains its own tool call spans. LangSmith renders these as a tree, making it possible to see the complete coordination flow — which specialist was called, in what order, with what result, and how much each step cost.

08 · Production Patterns

Three Multi-Agent Patterns
and Their Production Tradeoffs

Router

Coordinator classifies query → dispatches to one or more specialists → collects all results → synthesizes.

Pros

✓ Simple coordination logic
✓ Specialists run independently
✓ Easy to add new specialists

Cons

✗ No adaptive re-dispatch
✗ All specialists run once only
✗ Cannot handle "hotel full → try different dates"
Best for: Independent parallel tasks

Supervisor

Supervisor LLM orchestrates: reads each specialist result, decides next action, can call same specialist twice with different params.

Pros

✓ Adaptive coordination
✓ Handles conditional flows
✓ Reads partial results before deciding

Cons

✗ More LLM calls (supervisor + each specialist)
✗ Harder to debug (dynamic paths)
✗ Supervisor can get confused on long chains
Best for: Complex multi-step tasks with dependencies

Parallel fan-out

All specialists run simultaneously, results merged by synthesizer. No coordinator makes routing decisions — all specialists always run.

Pros

✓ Fastest: all specialists in parallel
✓ No routing errors
✓ Predictable execution path

Cons

✗ Wastes calls if only 1-2 specialists needed
✗ No adaptive behavior
✗ Higher cost per query
Best for: Always need all specialists for every query
09 · Assessment

Module 11 Quiz

1. Your single travel agent has 9 tools and makes wrong tool selections 35% of the time. You split it into 3 specialists with 3 tools each. What specific mechanism causes the selection accuracy to improve?

Correct. Tool selection accuracy degrades with the number of tools because the LLM must evaluate more descriptions and disambiguate more potential matches. With 9 tools, tools like "hotel_search" and "local_transport" might both seem relevant for "find somewhere nearby" queries. With 3 tools per specialist, every choice is within a single domain — the accommodation specialist cannot confuse hotel search with flight search because flight_search is not in its tool list.

2. What is the key difference between the router pattern and the supervisor pattern?

Correct. The architectural distinction is feedback: does the coordinator see specialist results before dispatching to the next specialist? Router: no — it classifies the query and dispatches immediately. Supervisor: yes — it reads each result in a cycle (supervisor → specialist → supervisor → next specialist → ...). This feedback loop is what makes the supervisor pattern capable of adaptive behavior: adjusting follow-up queries based on partial results, handling errors, and changing direction based on intermediate findings.

3. You build a multi-agent travel system where the accommodation, transport, and experience specialists always run for every query (parallel fan-out). A user asks "What's the weather tomorrow?" — all three specialists run and return irrelevant accommodation/transport/experience results. What is the design flaw?

Correct. Parallel fan-out wastes resources (LLM calls, money, latency) when most specialists do not apply to the current query. The pattern is only efficient when the query domain is always the same (e.g., every user request ALWAYS needs accommodation + transport + experience). For diverse query types, a router or supervisor must first determine which specialists are relevant. A weather query calling three travel specialists produces irrelevant results and triple the cost of a single correct specialist call.

4. In the supervisor pattern, you add an edge from each specialist node back to the supervisor node. What would happen if you accidentally added an edge directly from a specialist to END instead?

Correct. The "return ticket" is implemented by the edge "specialist → supervisor." Without it, once a specialist completes, control passes to END and the graph terminates. The supervisor never gets to read the result or decide what to do next. Every specialist in a supervisor pattern must return control to the supervisor (add_edge(specialist_name, "supervisor")), and only the synthesize node connects to END. This is why explicitly testing each edge in the graph is essential before deploying multi-agent systems.

5. Your supervisor makes 12 LLM calls for a simple one-specialist query ("just search for hotels in Tokyo"). Why is this happening and how do you fix it?

Correct. Unnecessary supervisor loops are the most common multi-agent performance problem. The supervisor LLM generates its next-action decision, and if the FINISH condition is not clearly specified or the output parsing is unreliable, it keeps dispatching to specialists. The three fixes work at different layers: prompt guidance shapes the LLM's generation, the iteration guard is the hard safety net, and parsing verification ensures the decision is correctly interpreted. For simple queries, the supervisor should detect sufficiency after 1-2 specialist calls.
