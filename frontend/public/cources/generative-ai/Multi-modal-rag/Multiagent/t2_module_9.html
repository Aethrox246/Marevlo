This module covers self-querying retrieval (metadata filters from natural language), natural language to SQL, semantic SQL search, graph database queries, intelligent chain routing, and Reciprocal Rank Fusion for postprocessing.

01 · Beyond Vector Search

When Semantic Similarity Is Not Enough:
Structured Data Sources

Vector search retrieves semantically similar text chunks. It works perfectly for natural language questions against document corpora. It fails for questions that require filtering by structured attributes ("Products released after 2023 under $50"), aggregate calculations ("How many users enrolled in Q3?"), or relationship traversal ("Show me all prerequisites of this course"). These need structured retrieval.

Query typeExampleRight retrieval methodWhy vector search fails
Natural languageWhat is the refund policy for annual plans?Vector search (semantic)Works perfectly — meaning-based match
Metadata filterShow me documents about pricing from 2024Self-querying retrieverVector search ignores date/category metadata
AggregateHow many users enrolled in January?SQL generationVector search cannot count or aggregate
Exact lookupWhat is the price of SKU-4892?SQL + semantic SQLExact IDs need exact match, not similarity
Relationship graphWhich courses are prerequisites of Module 7?Graph query (Cypher)Graph traversal requires graph DB, not vector
Mixed questionFind documentation about pricing AND check the user count for that planChain routing + multiple retrieversNeeds multiple retrieval strategies in sequence
💡

The production pattern: route first, retrieve second

Production knowledge systems combine multiple retrieval strategies. An LLM router classifies the query type (semantic, SQL, graph, metadata filter) and dispatches to the appropriate retriever. Chain routing (Section 6 of this module) implements this as an LCEL chain with a classification step before retrieval. The final answer synthesizes results from whichever retriever(s) handled the query.

02 · Self-Querying Retriever

Natural Language to Metadata Filters:
Automatically Narrowing the Search Space

Self-querying retrieval lets users filter vector store results using natural language without knowing anything about metadata structure. The user asks "Find documents about refunds from 2024" — the self-querying retriever extracts the structured filter (date >= 2024, topic = "refunds") and applies it before vector similarity search. Result: precise, filtered results from a subset of the corpus.

How self-querying works: two-step process

1

LLM parses the query

Extracts structured filter conditions from the natural language query and reformulates the semantic search part.

2

Execute filtered vector search

Applies the parsed metadata filter before ANN search. Only matching documents are candidates for similarity ranking.

User query: "Find documents about refund policies updated in 2024"
LLM extracts:
  filter: {year: 2024, topic: "refunds"}
  query: "refund policies" (semantic part)
Qdrant executes: ANN search on "refund policies"
               WHERE metadata.year == 2024 AND metadata.topic == "refunds"
Returns: only 2024 refund documents, ranked by similarity

Setting up the self-querying retriever

from langchain.retrievers.self_query.base import SelfQueryRetriever from langchain.chains.query_constructor.base import AttributeInfo # Describe your metadata fields to the LLM metadata_field_info = [ AttributeInfo(name="year", description="Year the document was published", type="integer"), AttributeInfo(name="topic", description="Main topic: refunds, pricing, features, legal", type="string"), AttributeInfo(name="plan_tier", description="Plan tier: basic, pro, enterprise", type="string"), ] retriever = SelfQueryRetriever.from_llm( llm=llm, vectorstore=vector_store, document_contents="Marevlo help documentation", metadata_field_info=metadata_field_info, verbose=True # show extracted filter in logs ) # Natural language automatically becomes a structured filter docs = retriever.invoke("Find 2024 documents about enterprise refunds") # Internally applies: filter={year:2024, topic:"refunds", plan_tier:"enterprise"}
⚠️

Metadata must be set at ingestion time — not retrieval time

Self-querying only works if your documents have rich metadata stored in the vector database. At ingestion time: enrich each Document's metadata dict before calling add_documents(). Extract metadata using an LLM ("What year was this document published? What topic does it cover?") or from structured sources (filename patterns, frontmatter, database joins). A corpus with empty metadata cannot benefit from self-querying retrieval.

03 · Natural Language to SQL

Querying Databases With
Plain English Questions

Many organizations keep their most important data in relational databases — user counts, revenue, enrollment statistics, product inventory. Natural language to SQL lets users ask "How many enterprise users enrolled in January 2024?" and get an answer without writing SQL. The LLM generates a valid SQL query from the question, which is then executed against the real database.

Three-step NL to SQL pipeline

1

1. Describe the database schema

Provide the LLM with table names, column names, data types, and example values. The more context, the more accurate the generated SQL. LangChain's SQLDatabase.get_table_info() extracts this automatically.

↓
2

2. LLM generates SQL from NL question

The LLM receives the schema description + user question and outputs a syntactically valid SQL SELECT statement. Temperature=0 for maximum consistency. Use Claude or GPT-4 for complex multi-table queries.

↓
3

3. Execute SQL and format response

Execute the generated SQL against the real database. Pass the query results + original question to the LLM for a natural language response. Always validate: ensure the generated SQL is a SELECT (read-only) before executing.

nl_to_sql.py

from langchain_community.utilities import SQLDatabase
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

# ── Connect to database ───────────────────────────────────────
db = SQLDatabase.from_uri("sqlite:///marevlo.db")
print(db.get_table_info())  # shows schema to verify

# ── Step 1: Generate SQL ──────────────────────────────────────
SQL_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "You are a SQLite expert. Given a question and database schema,\n"
     "generate a syntactically correct SQLite SELECT query.\n"
     "Output ONLY the SQL query, no explanation.\n"
     "Never generate INSERT, UPDATE, DELETE, or DROP statements.\n"
     "Schema:\n{schema}"),
    ("human", "Question: {question}")
])

sql_chain = SQL_PROMPT | llm | StrOutputParser()

# ── Step 2: Validate and execute ─────────────────────────────
def safe_execute(sql: str) -> str:
    sql = sql.strip().rstrip(";")
    if not sql.upper().startswith("SELECT"):
        raise ValueError(f"Non-SELECT SQL rejected: {sql[:50]}")
    return db.run(sql)

# ── Step 3: Natural language answer ──────────────────────────
ANSWER_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "Answer the question based on the SQL query results. Be concise."),
    ("human", "Question: {question}\nSQL: {sql}\nResults: {results}")
])
answer_chain = ANSWER_PROMPT | llm | StrOutputParser()

# ── Full pipeline ────────────────────────────────────────────
def ask_database(question: str) -> str:
    schema = db.get_table_info()
    sql = sql_chain.invoke({"schema": schema, "question": question})
    results = safe_execute(sql)
    return answer_chain.invoke({"question": question, "sql": sql, "results": results})

print(ask_database("How many enterprise users enrolled in January 2024?"))
# Generated SQL: SELECT COUNT(*) FROM enrollments
#   WHERE plan_tier='enterprise' AND strftime('%Y-%m', enrolled_at)='2024-01'
# Answer: "247 enterprise users enrolled in January 2024."
04 · Semantic SQL Search

Combining SQL Filters With
Vector Similarity in One Query

Standard SQL retrieves exact matches: SELECT * WHERE category = "refund". Semantic SQL combines SQL filtering with vector similarity search within the database. "Find courses similar to machine learning that cost under $100" requires both semantic similarity (similar to machine learning) and a structured filter (cost < 100). Some databases (pgvector, Qdrant hybrid) support this natively.

Standard SQL vs Semantic SQL

Standard SQL — exact match only

# Finds courses WHERE category = 'ml' — exact string match # Misses: "machine learning", "deep learning", "neural networks" SELECT * FROM courses WHERE category = 'ml' AND price < 100

Semantic SQL — meaning + structured filter

# Step 1: embed the semantic query query_vec = embedder.embed_query("machine learning techniques") # Step 2: pgvector: semantic filter inside SQL # SELECT *, embedding <=> query_vec AS distance # FROM courses WHERE price < 100 # ORDER BY distance LIMIT 5 # Step 3: returns courses semantically similar to # "machine learning" AND under $100 # Finds: "Neural Networks Fundamentals $89", # "Deep Learning Bootcamp $79", etc.

Python implementation with pre-filtered vector search

import sqlite3, numpy as np from langchain_openai import OpenAIEmbeddings embedder = OpenAIEmbeddings(model="text-embedding-3-small") conn = sqlite3.connect("courses.db") def semantic_sql_search(semantic_query: str, max_price: float, k: int = 5): # Step 1: embed the semantic query q_vec = np.array(embedder.embed_query(semantic_query)) # Step 2: SQL pre-filter (structured constraint) rows = conn.execute( "SELECT id, title, description, embedding FROM courses WHERE price < ?", (max_price,) ).fetchall() # Step 3: compute cosine similarity on filtered rows scored = [] for row_id, title, desc, emb_blob in rows: emb = np.frombuffer(emb_blob, dtype=np.float32) sim = float(np.dot(q_vec, emb) / (np.linalg.norm(q_vec) * np.linalg.norm(emb))) scored.append((sim, title, desc)) # Step 4: return top-k by similarity scored.sort(reverse=True) return [(title, desc, sim) for sim, title, desc in scored[:k]] results = semantic_sql_search("machine learning techniques", max_price=100)
05 · Graph Database Queries

Traversing Relationships With
Natural Language to Cypher

Knowledge graphs store entities and their relationships: "Course A requires Course B", "User X completed Module Y", "Company Z is a subsidiary of Company W". Vector search cannot traverse these relationships — it finds similar text, not connected entities. Graph databases (Neo4j) with Cypher queries answer relationship questions that are impossible for vector or SQL retrieval.

What graph databases enable

"Which courses are prerequisites for the RAG Masterclass?"

Relationship traversal: PREREQUISITE_OF edges

"Who completed Module 5 AND Module 6?"

Multi-hop: User → COMPLETED → Module nodes

"What is the shortest learning path from Python basics to LLM agents?"

Path finding: Dijkstra on prerequisite graph

"Which users are 3 connections away from this enterprise customer?"

Social graph: BFS traversal

Natural language to Cypher with LangChain

from langchain_community.graphs import Neo4jGraph from langchain.chains import GraphCypherQAChain # Connect to Neo4j graph database graph = Neo4jGraph( url="bolt://localhost:7687", username="neo4j", password="password" ) print(graph.schema) # shows node/relationship types # Chain: NL → Cypher query → execute → NL answer chain = GraphCypherQAChain.from_llm( llm=llm, graph=graph, verbose=True # shows generated Cypher ) result = chain.invoke( "What courses are prerequisites for the RAG Masterclass?" ) # Generated Cypher: # MATCH (c:Course)-[:PREREQUISITE_OF]->(rag:Course) # WHERE rag.name = "RAG Masterclass" # RETURN c.name, c.description # Answer: "Python Fundamentals and LangChain Basics # are prerequisites for the RAG Masterclass."
06 · Chain Routing

One Query, Multiple Retrievers:
Routing to the Right Data Source

A knowledge system with documents, a SQL database, and a graph database needs to send each query to the right retriever. Chain routing uses an LLM to classify the query type and dispatch to the appropriate chain. The router is the intelligence layer that makes a multi-source system behave as a unified interface.

Router architecture: classify then dispatch

User query → Router LLM (classify query type)
                ↓
"semantic" → Vector RAG chain → document answer
"sql"     → SQL chain → database answer
"graph"   → Graph chain → relationship answer
"hybrid"  → Multiple chains → synthesized answer

Router prompt and classification chain

ROUTER_PROMPT = ChatPromptTemplate.from_messages([ ("system", "Classify this query into ONE of: semantic, sql, graph, hybrid.\n" "semantic: questions about documents or policies\n" "sql: questions requiring counts, aggregates, or exact lookups\n" "graph: questions about relationships or paths\n" "hybrid: questions requiring both documents and data\n" "Output ONLY the category name."), ("human", "{query}") ]) router_chain = ROUTER_PROMPT | llm | StrOutputParser() # Examples: # "What is the refund policy?" → "semantic" # "How many users enrolled in Q1?" → "sql" # "What are the prerequisites?" → "graph" # "Explain the policy AND show usage stats" → "hybrid"

Dispatch function — route to the right chain

def route_query(query: str) -> str: route = router_chain.invoke({"query": query}).strip().lower() if route == "semantic": return rag_chain.invoke({"input": query, "chat_history": []}) elif route == "sql": return ask_database(query) elif route == "graph": return graph_chain.invoke(query) elif route == "hybrid": doc_answer = rag_chain.invoke({"input": query, "chat_history": []}) sql_answer = ask_database(query) return synthesize(query, doc_answer, sql_answer) else: return rag_chain.invoke({"input": query, "chat_history": []}) # fallback
07 · Retrieval Postprocessing & RRF

After Retrieval: Reranking,
Filtering, and Reciprocal Rank Fusion

Postprocessing transforms the raw list of retrieved documents into an optimal set for the LLM. Four postprocessors are commonly used: similarity score filtering (remove low-confidence chunks), keyword filtering (require specific terms), time weighting (prefer recent documents), and Reciprocal Rank Fusion (merge ranked lists from multiple retrievers).

PostprocessorWhat it doesWhen to useLangChain class
Similarity filterRemoves documents below a cosine similarity threshold before passing to LLMWhen you need to refuse out-of-scope queries and prevent hallucination on low-confidence retrievalsSimilarityPostprocessor(similarity_cutoff=0.75)
Keyword filterKeeps only documents containing specific required keywordsDomain-restricted systems where certain terms must appear (e.g., "HIPAA" for medical queries)KeywordPostprocessor(required_keywords=["HIPAA"])
Time weightingScores documents using both similarity and recency — recent docs ranked higherNews, changelog, or policy systems where freshness mattersTimeWeightedVectorStoreRetriever(decay_rate=0.01)
RRF (Reciprocal Rank Fusion)Merges ranked lists from multiple retrievers (e.g., BM25 + dense) using rank position mathHybrid search: combine keyword retrieval and semantic retrieval into one ranked listCustom: EnsembleRetriever or manual RRF formula

RRF: Reciprocal Rank Fusion explained

RRF merges two or more ranked lists by computing a score for each document based on its rank in each list. A document ranked #1 in BM25 and #3 in dense retrieval gets a higher combined score than one ranked #10 in both. The formula: RRF_score = Σ 1/(k + rank_i) where k=60 is a constant preventing rank-1 from dominating.

Input: two ranked lists

# BM25 results (keyword search): # 1. "Annual plans non-refundable after 30 days" # 2. "Refund request process: email billing team" # 3. "Enterprise refund exceptions" # Dense results (semantic search): # 1. "Enterprise refund exceptions" ← ranked 3 in BM25 # 2. "Annual plans non-refundable..." ← ranked 1 in BM25 # 3. "30-day cancellation policy" ← not in BM25

RRF scores (k=60)

# Doc: "Enterprise refund exceptions" # BM25 rank 3: 1/(60+3) = 0.01587 # Dense rank 1: 1/(60+1) = 0.01639 # RRF score: 0.01587 + 0.01639 = 0.03226 # Doc: "Annual plans non-refundable..." # BM25 rank 1: 1/(60+1) = 0.01639 # Dense rank 2: 1/(60+2) = 0.01613 # RRF score: 0.01639 + 0.01613 = 0.03252 ← wins!
# LangChain EnsembleRetriever implements RRF automatically from langchain.retrievers import EnsembleRetriever from langchain_community.retrievers import BM25Retriever bm25_retriever = BM25Retriever.from_documents(docs, k=5) dense_retriever = vectorstore.as_retriever(search_kwargs={"k": 5}) ensemble = EnsembleRetriever( retrievers=[bm25_retriever, dense_retriever], weights=[0.5, 0.5] # equal weight to both retrievers ) # Returns RRF-merged results from both retrievers docs = ensemble.invoke("annual plan refund policy")
08 · Production Code

Complete Multi-Source Retrieval System
With Router + RRF + SQL + Vector

hybrid_retrieval_system.py

from langchain_anthropic import ChatAnthropic
from langchain_community.utilities import SQLDatabase
from langchain_community.vectorstores import Qdrant
from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

# ── Retriever 1: Hybrid vector+BM25 with RRF ─────────────────
bm25 = BM25Retriever.from_documents(all_docs, k=5)
dense = vectorstore.as_retriever(search_kwargs={"k": 5})
hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25, dense], weights=[0.4, 0.6]
)

# ── Retriever 2: SQL database ─────────────────────────────────
db = SQLDatabase.from_uri("sqlite:///marevlo.db")
SQL_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "Generate SQLite SELECT only. Schema:\n{schema}"),
    ("human", "{question}")
])
sql_chain = SQL_PROMPT | llm | StrOutputParser()

# ── Router ────────────────────────────────────────────────────
ROUTER_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "Classify query: semantic (documents) or sql (database). One word."),
    ("human", "{query}")
])
router = ROUTER_PROMPT | llm | StrOutputParser()

# ── RAG prompt ────────────────────────────────────────────────
RAG_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "Answer from context only. Cite sources."),
    ("human", "Context:\n{context}\n\nQuestion: {question}")
])

# ── Unified query function ────────────────────────────────────
def query(question: str) -> str:
    route = router.invoke({"query": question}).strip().lower()

    if "sql" in route:
        sql = sql_chain.invoke({"schema": db.get_table_info(), "question": question})
        if not sql.strip().upper().startswith("SELECT"): sql = "SELECT 1"  # safety
        results = db.run(sql)
        return (RAG_PROMPT | llm | StrOutputParser()).invoke(
            {"context": f"SQL: {sql}\nResults: {results}", "question": question})

    else:  # semantic (default)
        docs = hybrid_retriever.invoke(question)
        context = "\n\n".join(d.page_content for d in docs)
        return (RAG_PROMPT | llm | StrOutputParser()).invoke(
            {"context": context, "question": question})

# Semantic query → hybrid retriever → RAG chain
print(query("What is the refund policy for annual plans?"))
# SQL query → SQL chain → database
print(query("How many enterprise users enrolled last month?"))
09 · Assessment

Module 9 Quiz

1. A user asks: "How many Pro plan users signed up in Q1 2024?" Your system routes this to the vector RAG chain, which returns irrelevant documentation chunks. What went wrong and what is the fix?

Correct. The router is the most impactful component in a multi-source system — a misclassification sends the query to completely the wrong retrieval mechanism. Counting (How many) and time-filtering (Q1 2024) are unmistakable SQL signals. The router prompt must include clear examples of each category and explicitly state what types of questions belong to each. Few-shot examples in the router system prompt dramatically improve classification accuracy.

2. Explain what RRF (Reciprocal Rank Fusion) achieves that neither BM25 alone nor dense retrieval alone can achieve.

Correct. BM25 and dense retrieval have complementary failure modes: BM25 fails on synonym/paraphrase queries, dense retrieval can miss exact technical terms and IDs. RRF exploits this complementarity: for any query, at least one of the two retrievers will rank the relevant document highly. A document ranked #1 in BM25 gets a strong RRF score even if it ranks #8 in dense retrieval. EnsembleRetriever in LangChain implements this with configurable weights.

3. You want users to ask "Find ML courses under $100 available in English" and get results that satisfy BOTH the semantic requirement (similar to ML) AND the structured constraints (price < 100, language = English). Standard vector search returns courses over $100. What approach works?

Correct. Self-querying retriever (option C) would also work but requires Qdrant/Chroma native filter support and the LLM to correctly parse the price constraint as a numeric comparison. Semantic SQL is the more direct approach for database-stored structured data: SQL pre-filtering efficiently reduces the candidate pool to items satisfying hard constraints, and similarity search then ranks the filtered candidates by semantic relevance. No hard-constraint item (price > $100) ever enters the ranking.

4. Your self-querying retriever returns 0 results for "Find documentation about refunds from 2024" even though 2024 refund documents exist in the vector store. What are the two most likely causes?

Correct. Self-querying has two critical dependencies: (1) metadata must be stored at ingestion time — if documents don't have a "year" field in their metadata dict, no filter can match it; (2) the AttributeInfo must correctly describe the field type (integer vs string) and possible values. Use retriever = SelfQueryRetriever(..., verbose=True) to see the exact filter the LLM generates. If the filter looks wrong, improve the AttributeInfo description or add few-shot examples to the query constructor prompt.

5. You have BM25 and dense retrieval with EnsembleRetriever(weights=[0.5, 0.5]). Your corpus has many exact product code queries (SKU-4892, order-7731). Users report that exact code queries return wrong products. How would you adjust the weights and why?

Correct. EnsembleRetriever weights should reflect the query distribution and the relative strength of each retriever for your specific corpus. For corpora with many exact identifiers (SKUs, order IDs, model numbers), BM25 is the more reliable retriever because these identifiers are exact tokens, not semantic concepts. Dense retrieval excels at meaning-based queries where phrasing varies. An even better solution is query-type-aware weighting: if the router detects an exact-code query, dispatch to BM25 only; if it detects a semantic query, use dense or ensemble.
