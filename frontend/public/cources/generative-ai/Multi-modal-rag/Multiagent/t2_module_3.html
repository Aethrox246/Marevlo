Research Summarization
Engine: Full Project Build

This module builds a complete, production-ready research summarization engine from scratch. Given a user question, the engine generates targeted web searches, scrapes and summarizes the results, and synthesizes everything into a structured research report — all orchestrated through LangChain LCEL chains.

01 · System Architecture Overview

What We Are Building:
Four Stages, One LCEL Chain

The research summarization engine answers questions that require current web information — the kind of question an analyst would research by hand. Given a question like "What are the latest trends in multi-modal AI models?", it automatically generates search queries, fetches and cleans web content, summarizes each source, and synthesizes a structured report with citations.

System architecture: four stages in sequence

1. Query Decomposition 1 LLM call — generates JSON array of search queries

LLM breaks the user question into 3-5 targeted search queries. "What are the latest trends in multimodal AI?" becomes: "multimodal AI models 2024 trends", "vision language models progress 2024", "GPT-4V Gemini multimodal capabilities comparison", etc.

↓
2. Web Search 1 search API call per query — returns URLs + snippets

Each search query is sent to a search API (DuckDuckGo, Serper, Tavily). Returns URLs and snippets for the top results. Multiple queries run in parallel to minimize latency.

↓
3. Scrape and Summarize N parallel LLM calls — one summary per source URL

Each URL is fetched (with BeautifulSoup cleaning) and its content is summarized individually using the summarization prompt. 5-10 LLM calls running in parallel via abatch().

↓
4. Report Synthesis 1 LLM call — structured markdown report with citations

All source summaries are combined with the original question into one final LLM call that generates a structured research report with section headings, key findings, and citations.

💡

Why decompose the query into multiple searches?

A single search query returns results biased toward one framing of the topic. "Multimodal AI 2024" returns vendor marketing. "Vision language model limitations" returns academic criticism. "Gemini vs GPT-4V benchmarks" returns comparison sites. Query decomposition ensures the engine gathers a diverse, multi-perspective set of sources, making the final report more balanced and comprehensive than any single search could produce.

02 · Core Components

Web Search, Scraping, and
JSON Object Conversion

Each stage of the pipeline is implemented as a standalone Python function. This modularity makes each component independently testable and replaceable — swap the search API without changing the scraping logic, change the summarizer without touching the search implementation.

Web search: DuckDuckGo (free) and Serper/Tavily (paid)

The search function wraps an API call and returns a list of (url, snippet) tuples. DuckDuckGo requires no API key but has rate limits. Serper.dev and Tavily provide more reliable results with higher rate limits at low cost ($0.001-$0.01 per search).

from langchain_community.tools import DuckDuckGoSearchResults from langchain_community.utilities import SerpAPIWrapper # Option 1: DuckDuckGo (free, no API key) search = DuckDuckGoSearchResults(num_results=5) results = search.run("multimodal AI trends 2024") # Option 2: Tavily (paid, better results) from langchain_community.tools.tavily_search import TavilySearchResults search = TavilySearchResults(max_results=5) # Returns: [{"url": "...", "content": "..."}]

Web scraping: BeautifulSoup content extraction

Raw HTML contains navigation, ads, footers and boilerplate that confuse the summarizer. The scraper fetches a URL, removes all non-content elements, and returns clean article text. Error handling is critical — many URLs return 403, paywalls, or redirects.

import requests from bs4 import BeautifulSoup def scrape_url(url: str) -> str: try: r = requests.get(url, timeout=8, headers={"User-Agent": "Mozilla/5.0"}) soup = BeautifulSoup(r.text, "html.parser") # Remove nav, ads, scripts for tag in soup(["script","style","nav","footer","aside"]): tag.decompose() return soup.get_text(separator=" ", strip=True)[:6000] except: return "" # fail silently, skip this URL

JSON to Python object converter: the critical parsing step

LLMs return text. When you ask for JSON, you get a JSON string embedded in the response. A robust parser must: strip markdown code fences, handle extra text before/after the JSON, and fall back gracefully on malformed output. Never use a bare json.loads() without sanitization.

Fragile (breaks in production)

# LLM returns: "```json\n[\"query1\", ...]\n```" result = json.loads(llm_output) # JSONDecodeError!

Robust (handles real LLM output)

import json, re def safe_json(text: str): # strip code fences text = re.sub(r"```(?:json)?\n?","",text).strip() # find first [ or { m = re.search(r"[[{]", text) if m: text = text[m.start():] return json.loads(text)
03 · Query Decomposition

Breaking One Question Into
Many Targeted Search Queries

Query decomposition is the intelligence layer that makes the engine produce comprehensive research rather than narrow search results. Instead of searching for exactly what the user asked, the engine generates 3-5 diverse search queries that approach the topic from different angles, ensuring broad source coverage.

How query decomposition transforms a single question

User question

"What are the main challenges and recent breakthroughs in training large language models?"

Generated search queries

Overview angle"LLM training challenges computational cost 2024"
Technical angle"gradient instability training large transformers solutions"
Data angle"training data quality curation LLM recent research"
Efficiency angle"parameter efficient training PEFT LoRA QLoRA advances"
Recent work"GPT-4 Claude Llama training methodology breakthroughs 2024"

Query decomposition prompt

System: You are a research query generator. Given a question, produce 4-5 targeted web search queries that together will gather comprehensive information to answer the question. Each query should approach the topic from a different angle: overview, technical depth, recent developments, expert opinions. Output ONLY a JSON array of strings. No explanation. Human: Generate search queries for: {question} Output: ["query1", "query2", "query3", "query4", "query5"]
💡

Output format discipline: always ask for JSON arrays

When asking an LLM to generate a list of items (queries, summaries, key points), always specify JSON array output and parse with your safe_json() function. Never ask for "a numbered list" — numbered lists require regex parsing that breaks on formatting variations. JSON is machine-readable, consistent, and trivially parsed. Include "Output ONLY a JSON array. No explanation." in every extraction prompt.

04 · Three Specialized Prompts

Query Generation, Source Summarization,
and Report Synthesis

Each stage of the research engine uses a different prompt optimized for its task. The query generation prompt focuses on diversity and coverage. The source summarization prompt focuses on extraction and faithfulness. The report synthesis prompt focuses on structure and insight generation. Using the same generic prompt for all three stages degrades quality significantly.

PromptSystem RoleKey ConstraintsOutput Format
Query GenerationResearch query generator with expertise in finding authoritative sourcesProduce 4-5 diverse queries from different angles (overview, technical, recent, expert opinion)JSON array of strings only
Source SummarizationPrecise fact extractor who reports only what is in the source textNever add information not in the source. Include specific claims, numbers, and dates. Note source URL.3-5 bullet points with cited URL
Report SynthesisSenior research analyst synthesizing findings into structured reportsOrganize by theme, not by source. Identify agreements and contradictions. Note confidence level on key claims.Markdown with headers, findings, and citation footnotes

Search Prompt

System: Generate 4-5 diverse web search queries... Human: Generate searches for: {question} Output ONLY JSON array: ["query1", "query2", ...]

JSON ensures machine-parseable output for the search loop

Source Summarizer

System: You extract facts from web sources. Report ONLY what the source says. Human: Source URL: {url} Content: {content} Extract 3-5 key facts as bullets.

Faithfulness constraint prevents hallucination into the summary

Report Synthesizer

System: You are a research analyst. Synthesize source summaries into a structured report. Human: Question: {question} Sources: {summaries} Write a structured report.

Synthesis prompt generates insight not present in any single source

05 · LCEL Chain Assembly

Wiring the Components
With LangChain Expression Language

Each component (query generator, scraper, source summarizer, report synthesizer) is a Python function or LCEL chain. The research engine orchestrates them using Python async/await for parallelism and LCEL for the LLM-calling steps. The result is a clean, testable pipeline where each step is independently observable.

💡

Why keep each step as a typed Python function

Each stage transforms a well-defined input type to a well-defined output type. This discipline makes the pipeline easy to debug: if the report is wrong, check the source summaries. If a source summary is wrong, check the scraped content. If scraping is wrong, check the URL list. Typed stage outputs also make unit testing straightforward — you can test each function in isolation with fixed inputs without running the full pipeline.

06 · Architecture Enhancement: Query Decomposition

Before vs After Adding
Intelligent Query Expansion

The simplest version of the research engine uses the user's question directly as the search query. This works but returns narrow results biased toward exact phrasing. Adding query decomposition makes the engine generate multiple diverse queries, dramatically improving source coverage and report completeness.

v1: Direct search (simple but narrow)

User question → search API → 5 URLs
→ scrape 5 pages → 5 summaries
→ synthesize report from 5 sources
Result: narrow, may miss key perspectives

Problem: "multimodal AI trends" returns only 5 pages all framing the question the same way. Missing: technical limitations, comparison studies, academic papers.

v2: Query decomposition (comprehensive)

User question → LLM → 5 diverse queries
→ 5 parallel searches → 25 URLs
→ scrape 25 pages → 25 summaries (async)
→ synthesize from 25 sources → rich report
Result: 5x more sources, balanced perspectives

Benefit: Technical papers, vendor docs, comparison studies, academic criticism, and practical guides all represented in the final report.

⚠️

Query decomposition adds one LLM call and latency

Adding query decomposition costs one extra LLM call (~$0.003) and ~1.5s of latency. This is almost always worth it for the quality improvement. To mitigate latency, run the query decomposition call in parallel with any initialization work (database connections, credential loading). The first real search cannot start until queries are ready, but setup work can happen concurrently.

07 · Reimplementing as LCEL Chains

Converting Functions to
Composable LCEL Chains

The initial implementation uses plain Python functions called sequentially. Reimplementing as LCEL chains gains automatic LangSmith tracing (every step is a named span), streaming support (report tokens stream to the client as they are generated), and standardized error handling via LCEL's retry and fallback mechanisms.

ComponentImperative (functions)LCEL (chains)LCEL benefit
Query generationllm.invoke(query_prompt.format(...))query_chain = query_prompt | llm | JsonOutputParser()Auto-traced, retryable, streaming-compatible
Source summarizationfor url in urls: summarize(url)source_chain.abatch(inputs, config={"max_concurrency": 5})Parallel, rate-limited, each call traced
Report synthesisllm.invoke(report_prompt.format(...))report_chain = report_prompt | llm | StrOutputParser()Streamable: tokens arrive as generated
Error handlingtry/except per functionchain.with_retry(stop_after_attempt=3)Automatic retry with exponential backoff
Observabilityprint() statements@traceable decorator or LangSmith auto-traceFull trace tree in LangSmith UI
💡

When to keep functions vs convert to LCEL

LCEL is ideal for LLM-calling steps (query generation, summarization, report synthesis). Keep plain Python functions for non-LLM steps like scraping and search API calls — these are standard I/O operations with their own error handling patterns. The research engine hybrid approach (LCEL for LLM steps, asyncio for I/O steps) is the production standard in LangChain applications.

08 · Complete Production Code

The Full Research Engine
in One File

research_engine.py

import asyncio, requests, json, re
from bs4 import BeautifulSoup
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser, JsonOutputParser
from langchain_community.tools.tavily_search import TavilySearchResults

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)
search_tool = TavilySearchResults(max_results=5)

# ── Prompt 1: Query decomposition ────────────────────────────
QUERY_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "Generate 4-5 diverse web search queries for comprehensive research coverage.\n"
     "Each query should approach the topic from a different angle.\n"
     "Output ONLY a JSON array of strings. No explanation."),
    ("human", "Generate search queries for: {question}")
])

# ── Prompt 2: Source summarization ───────────────────────────
SUMMARIZE_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "You extract facts from web sources. Report ONLY what the source states.\n"
     "Never add information not in the source text.\n"
     "Include specific claims, statistics, and dates."),
    ("human",
     "Source: {url}\n\nContent:\n{content}\n\nExtract 3-5 key findings as bullet points.")
])

# ── Prompt 3: Report synthesis ────────────────────────────────
REPORT_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "You are a senior research analyst. Synthesize source summaries into a\n"
     "structured research report. Organize by theme, not by source.\n"
     "Identify where sources agree and disagree. Note confidence level."),
    ("human",
     "Research question: {question}\n\nSource summaries:\n{summaries}\n\nWrite a structured research report with: Overview, Key Findings (by theme), Notable Debates, and Conclusion.")
])

# ── Chains ────────────────────────────────────────────────────
query_chain = QUERY_PROMPT | llm | JsonOutputParser()
summarize_chain = SUMMARIZE_PROMPT | llm | StrOutputParser()
report_chain = REPORT_PROMPT | llm | StrOutputParser()

# ── Helper: safe JSON parse ───────────────────────────────────
def safe_json(text: str) -> list:
    text = re.sub(r"```(?:json)?\n?", "", text).strip()
    m = re.search(r"[\[{]", text)
    return json.loads(text[m.start():]) if m else []

# ── Helper: scrape one URL ────────────────────────────────────
def scrape(url: str, max_chars: int = 5000) -> str:
    try:
        r = requests.get(url, timeout=8, headers={"User-Agent": "Mozilla/5.0"})
        soup = BeautifulSoup(r.text, "html.parser")
        for tag in soup(["script", "style", "nav", "footer"]): tag.decompose()
        return soup.get_text(" ", strip=True)[:max_chars]
    except: return ""

# ── Main research function ────────────────────────────────────
async def research(question: str) -> str:
    # Stage 1: query decomposition
    queries: list[str] = await query_chain.ainvoke({"question": question})
    print(f"Generated {len(queries)} search queries")

    # Stage 2: web search (parallel)
    search_tasks = [asyncio.to_thread(search_tool.invoke, q) for q in queries]
    all_results = await asyncio.gather(*search_tasks)
    urls = list({r["url"] for results in all_results for r in results})
    print(f"Collected {len(urls)} unique URLs")

    # Stage 3: scrape + summarize (parallel)
    scrape_tasks = [asyncio.to_thread(scrape, url) for url in urls]
    contents = await asyncio.gather(*scrape_tasks)
    valid = [(url, c) for url, c in zip(urls, contents) if len(c) > 200]

    summaries = await summarize_chain.abatch(
        [{"url": u, "content": c} for u, c in valid],
        config={"max_concurrency": 5}
    )
    print(f"Summarized {len(summaries)} sources")

    # Stage 4: synthesis
    combined = "\n\n".join(f"[Source {i+1}: {u}]\n{s}"
                           for i, ((u,_),s) in enumerate(zip(valid, summaries)))
    report = await report_chain.ainvoke({"question": question, "summaries": combined})
    return report

# Run: asyncio.run(research("Latest breakthroughs in multimodal AI models?"))
09 · Assessment

Module 3 Quiz

1. Your research engine returns an error: json.JSONDecodeError on the output of the query decomposition chain. The LLM responded with: "Here are your search queries:\n```json\n[\"query1\", \"query2\"]\n```". What is the fix?

Correct. This is the most common JSON parsing failure in production LLM pipelines. LLMs frequently add markdown code fences and explanatory preambles even when told not to. safe_json() handles all variants: bare JSON, JSON in ```json blocks, JSON with preceding text, JSON with trailing text. It uses a regex to find the first structural character ([ or {) and parses from there.

2. The scraping stage of your research engine returns empty strings for 60% of URLs. What are the two most likely causes and their fixes?

Correct. Empty scraping results have two primary causes in production: timeouts (paywalled pages, slow servers, redirect loops) and bot detection (403 responses, CAPTCHA redirects). Both manifest as empty strings from your scrape() function's except clause. The fix: log the response status code and content length before returning "" so you can distinguish the causes. Add retry logic with delay for 429 responses and skip results with status 403.

3. You want to add streaming to the research engine so the report text appears token-by-token in the user's browser. Which stage should stream and how do you implement it?

Correct. Streaming is meaningful only for the generation step because it is what produces visible text output. Streaming query generation (a few dozen tokens) is imperceptible to users. Streaming source summaries produces 5-10 small outputs rather than one coherent report. The report synthesis is the one step where streaming dramatically improves perceived responsiveness: the user starts reading a 500-token report within ~400ms instead of waiting 5+ seconds for the full response.

4. Your research report on "AI in healthcare 2024" cites 20 sources but all 5 search queries returned results about the same 3 vendor product pages. What is the underlying problem and how do you fix the query decomposition prompt?

Correct. Source diversity is the main quality lever in the research engine, and it is controlled entirely by query diversity. If queries are semantically similar, search engines return semantically similar results. The fix is to prescribe specific coverage angles in the query decomposition prompt, forcing the LLM to generate queries that will hit different parts of the web: academic databases (include "research paper" or "study"), news sites, government/regulatory sites, technical blogs, and critical/skeptical perspectives.

5. You are comparing two architectures: (A) one research engine call that generates 5 queries and scrapes 25 pages, versus (B) five separate research engine calls each with 1 query scraping 5 pages, results combined by a final LLM call. What are the tradeoffs?

Correct. Context sharing is the key advantage of Architecture A. When all 5 queries are generated together, the LLM knows not to generate overlapping queries ("multimodal AI 2024" and "recent multimodal models" cover the same ground). The single synthesis step at the end sees all 25 source summaries and can identify themes across all sources simultaneously. Architecture B's final synthesis call sees 5 sub-reports rather than 25 raw summaries, losing the granularity needed for accurate thematic synthesis.
