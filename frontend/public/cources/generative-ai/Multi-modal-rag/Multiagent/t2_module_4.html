LangGraph for
Agentic Workflows

LangChain chains execute a fixed sequence of steps. LangGraph executes a dynamic graph: nodes make decisions, conditional edges route based on state, and loops enable self-correction. This module covers workflows vs agents, LangGraph's core component model, and the step-by-step conversion of the research engine from a linear chain to a controllable state machine.

01 · Workflows vs Agents

Two Execution Models:
Fixed Sequence vs Adaptive Loop

A workflow executes a predefined sequence of steps in a fixed order. An agent decides what to do next based on what it has seen so far — it can loop, branch, call different tools, and self-correct. Understanding this distinction is the foundation of LangGraph: it supports both models in a single unified framework, giving you the control of a workflow with the adaptability of an agent.

Workflow

A predefined, deterministic sequence of nodes. Every execution follows the same path. The flow cannot adapt based on intermediate results. Good for processes with known steps and stable logic.

Execution pathFixed at design time
BranchingConditional, but all branches pre-defined
LoopsNot supported (or explicit retry count)
AdaptabilityNone — same steps every run
DebuggingEasy — same path every execution
Research engine: always do query decomp → search → scrape → summarize → report. No deviations.

Agent

The LLM decides what to do next at each step. It can call different tools in different orders, loop back to earlier steps when results are unsatisfactory, and terminate when it judges the task complete.

Execution pathDecided dynamically by the LLM
BranchingLLM chooses from available tools/nodes
LoopsNatural: observe → decide → act → observe
AdaptabilityHigh — responds to tool results and failures
DebuggingHarder — path varies between runs
Research agent: decides whether to search more, refine queries, skip empty results, or generate the report based on what it has found so far.
💡

When to use agents vs workflows in production

Use workflows when: the task has a fixed structure, all steps are known in advance, determinism matters (compliance, billing), and debugging simplicity is important. Use agents when: the task requires adaptive planning, tool selection depends on intermediate results, self-correction is needed, or the number of steps is variable. Most production systems start as workflows and introduce agent capabilities only where the fixed structure fails.

02 · Agent Development Frameworks

LangGraph vs LangChain AgentExecutor
vs Building From Scratch

Several frameworks exist for building LLM agents. LangChain's AgentExecutor is the original, simpler option. LangGraph is the modern replacement with explicit state control. Custom implementations give maximum flexibility at maximum complexity. Choosing the right framework prevents months of re-engineering later.

FrameworkExecution modelState visibilityLoops & branchesBest for
LangChain AgentExecutorBlack-box loop: agent → tools → agent → ... until stop conditionHidden: cannot inspect or modify intermediate stateImplicit — loop continues until agent outputs final answerSimple single-agent tasks; rapid prototyping
LangGraph StateGraphExplicit graph: each node and edge is visible and modifiableFull: every field in state is typed and inspectable after each stepExplicit conditional edges that you define; human-in-the-loop checkpoints possibleProduction agents, multi-step workflows, human oversight, debugging
Custom (no framework)Pure Python: you write the observe-decide-act loop yourselfComplete — you own all stateAnything you implementMaximum control; avoid framework constraints; ML research
📌

Why LangGraph replaced AgentExecutor for production use

AgentExecutor's hidden loop is its core limitation: you cannot pause execution mid-loop, you cannot insert human approval before a tool call, you cannot save and restore agent state across sessions, and debugging requires reading verbose logs instead of inspecting structured state. LangGraph exposes every step as a named node with typed state, enabling human-in-the-loop, state persistence, and precise debugging. Anthropic, OpenAI, and the broader LangChain community now recommend LangGraph for all production agent work.

03 · LangGraph Basics

Graphs, Nodes, and Edges:
The Mental Model

A LangGraph application is a directed graph where nodes are Python functions and edges define what runs next. Every node reads from a shared state dict and writes partial updates back to it. Conditional edges call a routing function to decide which node to run next. The graph runs until it reaches the special END node.

The three primitives of every LangGraph application

🗂️ State

A TypedDict that is the shared memory of the graph. Every node reads from it and returns a partial update. LangGraph merges updates automatically. Fields can use reducers (e.g., operator.add for append-only lists).

Think of state as a shared whiteboard: every team member (node) can read everything on it and add new information.

⚙️ Nodes

Python functions (sync or async) that accept the current state and return a dict of updates. A node can call an LLM, invoke a tool, transform data, or make a routing decision. Nodes do NOT call each other directly.

Think of nodes as workers in an assembly line: each one takes the current state of the product, does their job, and passes it on.

→ Edges

Define what node runs after each node completes. Simple edges always go to the same next node. Conditional edges call a Python function on the state and return the name of the next node to run — enabling branching and loops.

Think of edges as the rules that say "after this step, go to that step" — or "decide where to go based on the current result."

Execution flow: how a LangGraph run works step by step

1

Graph is compiled: graph.compile() validates the graph structure, checks for unreachable nodes, and returns an executable app.

2

app.invoke(initial_state) is called. The initial_state dict must contain all required TypedDict fields.

3

The entry point node runs. It reads from state, performs work, returns a partial state update dict.

4

LangGraph merges the update into state. Simple fields are overwritten; annotated fields use their reducer function.

5

The edge from the completed node is evaluated. Simple edge: go to fixed next node. Conditional edge: call routing function with current state.

6

The next node runs with the updated state. Steps 3-5 repeat until a conditional edge returns "END" or the graph reaches the END node.

7

app.invoke() returns the final state dict. All fields set during the run are accessible in the return value.

04 · State Management and Typing

TypedDict State: Every Field
Typed, Visible, and Debuggable

The state TypedDict is the contract between nodes. Every field that any node reads or writes must be declared here. Fields without a reducer are overwritten on update. Fields annotated with Annotated and a reducer function have their updates merged — the most important reducer is operator.add for append-only message and document lists.

Defining state for the research engine agent

from typing import TypedDict, Annotated import operator class ResearchState(TypedDict): # Input fields question: str # user question max_sources: int # cap on URLs to scrape # Computed fields — overwritten each update queries: list[str] # generated search queries urls: list[str] # unique URLs found report: str # final report text # Append-only fields — reducer merges all updates summaries: Annotated[list[str], operator.add] errors: Annotated[list[str], operator.add] iteration: int # loop counter for guard

⚠️ Simple fields vs Annotated reducer fields

Understanding the difference is critical. Simple fields are overwritten: if two nodes both write to state["urls"], the second write replaces the first. Annotated reducer fields merge: if two nodes both append to state["summaries"], both lists are concatenated.

Simple field (overwrite)

queries: list[str]

Node A sets ["q1","q2"]. Node B sets ["q3"]. Result: ["q3"]. First write lost.

Reducer field (merge)

summaries: Annotated[list[str], operator.add]

Node A appends ["s1"]. Node B appends ["s2"]. Result: ["s1","s2"]. Both preserved.

Wrong: reducer for single value

report: Annotated[str, operator.add]

Multiple nodes write report → strings are concatenated, creating garbage output.

05 · Nodes, Edges, and Conditional Routing

Building the Graph:
Entry Points, Decisions, and END

Every LangGraph application is assembled from four operations: add_node() registers a function, add_edge() creates a simple fixed transition, add_conditional_edges() creates a decision point, and set_entry_point() defines where execution begins. The compile() call validates the graph and returns a runnable object.

⚙️ Node function signature

Every node is a Python function that accepts the current state and returns a dict of fields to update. The function can be sync or async. It does NOT return the full state — only the fields it changes.

# Sync node def generate_queries(state: ResearchState) -> dict: result = query_chain.invoke({"question": state["question"]}) return {"queries": result} # ONLY changed fields # Async node async def summarize_sources(state: ResearchState) -> dict: summaries = await summarize_chain.abatch( [{"url": u, "content": c} for u, c in state["scraped"]], config={"max_concurrency": 5} ) return {"summaries": summaries} # appended via reducer
↔ Conditional edge routing function

A routing function receives the current state and returns a string: the name of the next node to run, or "END" to terminate. This is where all agent decision logic lives.

def should_continue_research(state: ResearchState) -> str: # Guard: stop if too many iterations if state["iteration"] >= 3: return "synthesize" # force report # Need more sources? if len(state["summaries"]) < 3: return "search_more" # loop back return "synthesize" # enough sources, make report
🔧 Graph assembly: the four operations
from langgraph.graph import StateGraph, END graph = StateGraph(ResearchState) # Register nodes graph.add_node("decompose", generate_queries) graph.add_node("search", web_search_node) graph.add_node("scrape", scrape_and_summarize) graph.add_node("search_more", generate_queries) # reuse node graph.add_node("synthesize", generate_report) # Fixed edges graph.set_entry_point("decompose") graph.add_edge("decompose", "search") graph.add_edge("search", "scrape") graph.add_edge("synthesize", END) # Conditional edge: branch after scrape graph.add_conditional_edges( "scrape", should_continue_research, {"search_more": "search_more", "synthesize": "synthesize"} ) app = graph.compile() result = app.invoke({"question": "...", "max_sources": 10, "iteration": 0, "summaries": [], "errors": []})
⚠️

Always include a loop iteration guard

Any graph with a conditional edge that can loop back must have an explicit iteration counter in state plus a guard in the routing function. Without it, a bug in the search or summarization step can cause an infinite loop that burns API budget and never terminates. Convention: add iteration: int to state, increment it in the looping node, and return a forced exit node when iteration >= max_iter.

06 · LangChain Chains vs LangGraph

The Same Logic, Two Paradigms:
What Changes and What Gets Better

Converting from LangChain LCEL chains to LangGraph is not just a code refactor — it changes the operational properties of your system. The logic stays the same; the control, observability, and extensibility improve dramatically. Here is a precise comparison of what each approach gives you.

PropertyLangChain LCEL ChainLangGraph StateGraph
State visibilityState is implicit — lives in Python variables, not inspectable as a typed structureFull: every field in TypedDict is inspectable after each node; snapshot state at any step
Pause / resumeNot supported — chain runs to completion atomicallyNative: graph.compile(checkpointer=...) saves state to DB; resume from any step
Human-in-the-loopNot supported natively — requires wrapping entire chaininterrupt_before=["node_name"] pauses before a node; human approves, graph resumes
Loops and retryMust implement retry logic as recursive LCEL chain compositionNatural: conditional edge points back to earlier node; iteration counter guards infinite loops
Parallel executionchain.batch() — parallel but same path for all inputsSend API: fan out to multiple nodes in parallel from one node, merge results later
Debugging failed runsRead full output log; hard to pinpoint which step failedLangSmith shows each node as a named span; inspect state before and after each node
Multi-agentComplex: chain one full chain into another with glue codeFirst-class: Supervisor node routes between specialist sub-graphs; state shared across agents
💡

You do not have to choose: combine both

LangGraph nodes can contain LCEL chains internally. The typical pattern: use LangGraph for the outer workflow orchestration (which step to run, when to loop, when to stop) and LCEL chains inside individual nodes for the LLM-calling logic (prompt | llm | parser). This gives you LangGraph's control and LangSmith tracing at the workflow level plus LCEL's clean composition inside each node.

07 · Converting the Research Engine to LangGraph

From Linear Chain to
Controllable State Machine

The research engine from Module 3 was a linear async pipeline: query → search → scrape → summarize → report. Converting it to LangGraph introduces adaptive behavior: if the scraping step finds fewer than 3 usable sources, the agent loops back to generate more search queries and try again — a self-correction loop impossible in the original chain.

Side-by-side: what changes in the conversion

Before: LCEL async pipeline

async def research(question):
queries = await query_chain.invoke(...)
results = await asyncio.gather(*searches)
contents = await asyncio.gather(*scrapes)
summaries = await summarize_chain.abatch(...)
return await report_chain.invoke(...)
Problem: if scraping gets 0 usable sources,
pipeline produces empty report silently.

After: LangGraph state machine

graph nodes: decompose → search → scrape
↕ (conditional edge)
synthesize ← enough sources?
search_more ← too few sources?
State: {question, queries, urls,
summaries[], errors[], iteration}
Result: self-corrects on empty results.
Loops until enough sources or max iter.

Identified: 4 conversion steps

(1) Define ResearchState TypedDict with all fields. (2) Wrap each async function as a node that reads from state and returns updates. (3) Define the conditional edge routing function. (4) Assemble the graph with add_node, add_edge, add_conditional_edges.

New capability: self-correction loop

If scrape node finds <3 usable sources, the routing function returns "search_more" → decompose runs again with refined queries → new searches → new scrapes. The iteration counter prevents infinite looping.

New capability: error isolation

Each node appends to state["errors"] (reducer list). Failed scrapes are logged without crashing the pipeline. The synthesis node sees both summaries and errors, noting in the report which sources were unavailable.

08 · Production Code

Research Engine as a
LangGraph State Machine

research_graph.py

import asyncio, operator, requests
from typing import TypedDict, Annotated
from bs4 import BeautifulSoup
from langgraph.graph import StateGraph, END
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser, JsonOutputParser
from langchain_community.tools.tavily_search import TavilySearchResults

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)
search_tool = TavilySearchResults(max_results=5)

# ── State ─────────────────────────────────────────────────────
class ResearchState(TypedDict):
    question:  str
    queries:   list[str]
    urls:      list[str]
    summaries: Annotated[list[str], operator.add]   # append-only
    errors:    Annotated[list[str], operator.add]   # append-only
    report:    str
    iteration: int

# ── Chains (LCEL inside nodes) ────────────────────────────────
query_chain = (ChatPromptTemplate.from_messages([
    ("system", "Generate 4 diverse web search queries. Output ONLY a JSON array of strings."),
    ("human", "Question: {question}\nPrevious queries: {prev}")
]) | llm | JsonOutputParser())

summarize_chain = (ChatPromptTemplate.from_messages([
    ("system", "Extract 3 key facts from this web source. Only report what the source states."),
    ("human", "URL: {url}\nContent: {content}\n\n3 bullet points:")
]) | llm | StrOutputParser())

report_chain = (ChatPromptTemplate.from_messages([
    ("system", "Synthesize research findings into a structured report with Overview, Findings, and Conclusion."),
    ("human", "Question: {question}\n\nSources:\n{summaries}\n\nErrors: {errors}")
]) | llm | StrOutputParser())

# ── Nodes ────────────────────────────────────────────────────
async def decompose_node(state: ResearchState) -> dict:
    queries = await query_chain.ainvoke({
        "question": state["question"],
        "prev": ", ".join(state.get("queries", [])) or "none"
    })
    return {"queries": queries, "iteration": state["iteration"] + 1}

async def search_node(state: ResearchState) -> dict:
    tasks = [asyncio.to_thread(search_tool.invoke, q) for q in state["queries"]]
    results = await asyncio.gather(*tasks)
    urls = list({r["url"] for batch in results for r in batch})
    return {"urls": urls}

async def scrape_node(state: ResearchState) -> dict:
    def scrape(url):
        try:
            r = requests.get(url, timeout=8, headers={"User-Agent":"Mozilla/5.0"})
            soup = BeautifulSoup(r.text, "html.parser")
            for t in soup(["script","style","nav"]): t.decompose()
            return url, soup.get_text(" ", strip=True)[:5000]
        except Exception as e: return url, f"Error: {e}"

    scraped = await asyncio.gather(*[asyncio.to_thread(scrape, u) for u in state["urls"]])
    valid = [(u, c) for u, c in scraped if not c.startswith("Error") and len(c) > 200]
    errs  = [f"Failed: {u}" for u, c in scraped if c.startswith("Error")]

    new_summaries = await summarize_chain.abatch(
        [{"url": u, "content": c} for u, c in valid],
        config={"max_concurrency": 5}
    )
    return {"summaries": new_summaries, "errors": errs}

async def synthesize_node(state: ResearchState) -> dict:
    report = await report_chain.ainvoke({
        "question": state["question"],
        "summaries": "\n\n".join(state["summaries"]),
        "errors": ", ".join(state["errors"]) or "none"
    })
    return {"report": report}

# ── Routing function ─────────────────────────────────────────
def route_after_scrape(state: ResearchState) -> str:
    if state["iteration"] >= 3: return "synthesize"  # hard stop
    if len(state["summaries"]) < 3: return "decompose"    # need more
    return "synthesize"

# ── Graph assembly ───────────────────────────────────────────
g = StateGraph(ResearchState)
g.add_node("decompose",  decompose_node)
g.add_node("search",     search_node)
g.add_node("scrape",     scrape_node)
g.add_node("synthesize", synthesize_node)
g.set_entry_point("decompose")
g.add_edge("decompose", "search")
g.add_edge("search", "scrape")
g.add_conditional_edges("scrape", route_after_scrape,
    {"decompose": "decompose", "synthesize": "synthesize"})
g.add_edge("synthesize", END)
app = g.compile()

# ── Run ──────────────────────────────────────────────────────
result = asyncio.run(app.ainvoke({
    "question": "Latest breakthroughs in multimodal AI?",
    "queries": [], "urls": [], "summaries": [],
    "errors": [], "report": "", "iteration": 0
}))
print(result["report"])
09 · Assessment

Module 4 Quiz

1. A node in your LangGraph application writes {summaries: ["new_summary"]}. The state currently has summaries: ["old_summary"]. What will state["summaries"] contain after the update, and why?

Correct. The Annotated[list[str], operator.add] declaration tells LangGraph to use operator.add as the reducer for that field. When a node returns {"summaries": ["new_summary"]}, LangGraph calls operator.add(["old_summary"], ["new_summary"]) = ["old_summary", "new_summary"]. Without the Annotated reducer, the assignment would be a simple overwrite. This distinction is the most important thing to understand about LangGraph state.

2. Your LangGraph research agent has been running for 20 minutes and is still looping. LangSmith shows it has executed the "scrape" node 47 times. What is the missing mechanism and how do you add it?

Correct. The iteration guard is non-negotiable in any LangGraph application with loops. The iteration counter must be in state (so every node can see it), incremented in the looping node, and checked in the routing function as the first condition — before any other logic. A timeout at the Python/OS level is a poor substitute because it leaves the API calls mid-flight and cannot produce a partial result.

3. What is the fundamental reason LangGraph replaced LangChain AgentExecutor for production use?

Correct. The core limitation of AgentExecutor is the hidden loop. You pass it tools and a prompt, and it runs until it emits a final answer — but you cannot see the intermediate state, inject human decisions, or save progress. LangGraph trades that simplicity for explicit graph definition, typed state, and the operational capabilities that production systems require: debugging exact node states, pausing for human approval (interrupt_before), and persisting state to resume after failures.

4. You define a conditional edge with add_conditional_edges("scrape", router, {"A": "nodeA", "B": "nodeB"}). Your router function returns "C". What happens?

Correct. LangGraph validates routing function return values against the mapping dict at runtime. Any return value not in the dict raises an error. This is actually a safety feature: it forces you to explicitly handle every possible routing outcome. The fix is to ensure your routing function's return values and the mapping dict keys are identical sets. When adding new routing conditions, always update both the function and the mapping simultaneously.

5. You want to add human approval before the "synthesize" node runs — the report should be reviewed by an analyst before being sent to the user. How does LangGraph support this natively?

Correct. interrupt_before is LangGraph's native human-in-the-loop mechanism. It works in combination with a checkpointer (MemorySaver for testing, SqliteSaver or PostgresSaver for production) that saves the full graph state at the interruption point. The human can inspect state["summaries"] before approving. After approval, the graph resumes from exactly where it paused, with all state intact. This is architecturally simpler and more reliable than polling databases or separate approval APIs.
