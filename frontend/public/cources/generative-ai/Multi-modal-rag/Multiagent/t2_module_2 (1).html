Summarization and
the Map-Reduce Pattern

Every LLM has a context window limit. When your document exceeds it, a naive truncation silently destroys information. Map-Reduce is the production pattern for summarizing arbitrarily large documents: split into chunks, summarize each independently in parallel, then combine all summaries into one coherent final answer — scalable to any document length.

01 · The Context Window Problem

Why You Cannot Just Paste
a Long Document Into an LLM

Every LLM enforces a context window — the maximum tokens it can process in one call. Claude Sonnet 4: 200K tokens. GPT-4o: 128K. Gemini 2.5 Pro: 2M. For many tasks these are sufficient. But for quarterly report summarization, legal contract analysis, or synthesizing a hundred research papers, you need a strategy that scales beyond any single context window.

Failure ModeWhat HappensWhy It Is InvisibleSolution
Hard truncationDocument is cut to fit the window. Everything after the cutoff is permanently lost.The LLM returns a response. You see no error. The cut content just does not appear.Map-Reduce: process all content, no data loss
Lost-in-middleMiddle tokens (content between the first 25% and last 25%) receive weaker attention from the model.Summary looks plausible but quietly underrepresents the middle sections.Map-Reduce: each chunk gets its own full-attention context
Cost explosionSending 150K tokens to Gemini at $7/M costs $1.05 per query. At 10K queries/day that is $10,500/day.Individual query cost seems small; cumulative cost is catastrophic.Map-Reduce with smaller chunks: 500-token chunks at $3/M = $0.001/query
Rate limit hitsSingle requests with 50K+ tokens hit per-request token limits and are rejected.API returns 400 error with a confusing message about context length.Map-Reduce parallelizes into many small requests, each within limits

Naive approach (broken)

Document: 50,000 tokens
↓ Send entire document in one prompt
↓ Middle 30K tokens: half-attended
↓ LLM response: looks OK but is wrong
Cost: 50K × $3/M = $0.15/query

Map-Reduce approach (correct)

Document: 50,000 tokens
↓ Split into 100 chunks × 500 tokens
↓ 100 parallel map calls (full attention each)
↓ 1 reduce call: combine 100 summaries
Cost: same $0.15 but MUCH better quality
02 · The Map-Reduce Pattern

Split, Summarize, Combine:
Step by Step with a Worked Example

Map-Reduce for LLM summarization is borrowed from distributed computing. The core insight: you cannot fit the entire document in one prompt, but you can fit one chunk per prompt. Run all chunk prompts in parallel (the map step), collect the chunk summaries, then run one final prompt that combines them all (the reduce step).

Worked example: 20,000-token research report

STEP 1 — CHUNK

20,000 tokens ÷ 500 tokens/chunk = 40 chunks with 50-token overlap.

RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50) → 40 Document objects
↓

STEP 2 — MAP (parallel)

40 simultaneous LLM calls. Each receives one chunk and a "summarize this section" prompt.

Prompt: "Extract key findings in 3 bullets:\n{chunk}" → 40 bullet-point summaries (async)
↓

STEP 3 — REDUCE

Concatenate all 40 summaries (~4,000 tokens). One LLM call with a "combine" prompt.

Prompt: "Combine these section summaries into a 5-paragraph executive summary:\n{all_summaries}" → Final report
✓

Why parallel map is critical

Running 40 sequential map calls takes 40 × 1.5s = 60 seconds. Running them with asyncio.gather() or chain.abatch() takes ~1.5s total (the slowest single call). Always use async batch for the map step in production. LangChain's .abatch(inputs, config={"max_concurrency": 5}) handles this with a concurrency limit to respect API rate limits.

⚠️

When reduce step also overflows

500 chunks × 100 tokens per summary = 50,000 tokens in the reduce step — still exceeding many context windows. Solution: hierarchical reduce. Group chunk summaries in batches of 20, reduce each group to an intermediate summary, then reduce the intermediates. Repeat until the final input fits comfortably.

03 · Text Splitters: Chunking Without Losing Meaning

How to Split Documents Without
Breaking Sentences at Chunk Boundaries

The chunking strategy determines whether each map call sees a coherent piece of text or a truncated sentence fragment. Split at the wrong boundary and the LLM in the map step summarizes incomplete ideas. LangChain provides three primary splitters for different document types, plus chunk_overlap to preserve boundary context.

RecursiveCharacterTextSplitter Default choice

Tries to split at natural boundaries in priority order: \n\n (paragraphs) → \n (lines) → " " (words) → "" (characters). Falls back to the next separator only when the current level exceeds chunk_size. Respects prose structure without needing document-type-specific logic.

from langchain.text_splitter import RecursiveCharacterTextSplitter splitter = RecursiveCharacterTextSplitter( chunk_size=500, # max chars per chunk chunk_overlap=50, # chars shared between adjacent chunks separators=["\n\n","\n"," ",""] ) chunks = splitter.split_documents(docs) # chunks: List[Document] with metadata preserved

TokenTextSplitter Precise billing control

Splits by actual token count using tiktoken (OpenAI tokenizer) or HuggingFace tokenizers. Character-based splitters can create chunks that are either too large (multi-byte chars) or too small. Token splitting guarantees you never exceed the model's hard token limit per call.

from langchain.text_splitter import TokenTextSplitter splitter = TokenTextSplitter( encoding_name="cl100k_base", # GPT/Claude tokenizer chunk_size=400, chunk_overlap=20 )

HTMLHeaderTextSplitter Structured documents

Splits HTML documents at header boundaries (h1, h2, h3). Each resulting chunk inherits its ancestor headers as metadata. Ideal for web pages, HTML documentation, and reports where section structure carries meaning. The map step can then label each summary with its section name.

from langchain.text_splitter import HTMLHeaderTextSplitter splitter = HTMLHeaderTextSplitter( headers_to_split_on=[ ("h1", "Section"), ("h2", "Subsection") ] ) chunks = splitter.split_text_from_url(url) # metadata: {"Section": "Methods", "Subsection": "Data"}

💡 chunk_overlap: why and how much

Without overlap, a sentence that spans a chunk boundary is split in half. Neither chunk contains the complete thought. chunk_overlap copies the last N characters of chunk K into the beginning of chunk K+1, preserving boundary sentences.

Rule of thumb: 10-15% of chunk_size.
chunk_size=500 → chunk_overlap=50 to 75
chunk_size=1000 → chunk_overlap=100 to 150
Too little: broken sentences at boundaries.
Too much: duplicate content → wasted tokens.
💡

Which splitter to choose

Use RecursiveCharacterTextSplitter for all prose text (reports, articles, transcripts, emails). Use TokenTextSplitter when you need exact token counts for billing precision or you are hitting context length errors. Use HTMLHeaderTextSplitter for web pages and HTML documentation where you want summaries labeled by section name. For code files, use language-aware splitters (langchain.text_splitter.Language enum).

04 · Document Loaders

Ingesting Content From Any Source:
PDFs, URLs, Files, Wikipedia, CSV

Before splitting and summarizing, you need to load the document. LangChain's document loaders convert any source into a standardized list of Document objects. Every loader produces the same output format — page_content (text) and metadata (dict) — so your chunking and summarization pipeline works identically regardless of source type.

PDF
PyPDFLoader (PDF files)

Splits PDF by page. Each page becomes one Document. Handles text-layer PDFs well. For scanned PDFs (images), add pytesseract for OCR. Metadata includes page number and source filename.

loader = PyPDFLoader("report.pdf") docs = loader.load() # one Doc per page # docs[0].metadata = {"page": 0, "source": "report.pdf"}
URL
WebBaseLoader (URLs / web pages)

Fetches a URL, strips HTML tags, navigation, ads and boilerplate using BeautifulSoup. Returns cleaned article text. Metadata includes the URL. For multiple URLs, pass a list.

loader = WebBaseLoader("https://example.com/article") docs = loader.load() # metadata: {"source": "https://..."}
PLA
TextLoader (Plain text / Markdown)

Loads any .txt or .md file as a single Document. Simple and reliable. Pass encoding="utf-8" explicitly to handle international text. Chain with a splitter for files over 2,000 characters.

loader = TextLoader("transcript.txt", encoding="utf-8") docs = loader.load() # Single Document, full file content
ENT
DirectoryLoader (Entire folders)

Recursively loads all files matching a glob pattern from a directory. Pass loader_cls to specify which loader handles each file type. show_progress=True displays a progress bar for large archives.

loader = DirectoryLoader( "./reports/", glob="**/*.pdf", loader_cls=PyPDFLoader, show_progress=True) docs = loader.load()
WIK
WikipediaLoader (Wikipedia articles)

Fetches Wikipedia articles by search query. Returns full article text with section structure. Metadata includes Wikipedia URL and article summary. No API key required. Control max_docs to limit fetched articles.

loader = WikipediaLoader( query="Large language models", load_max_docs=3) docs = loader.load()
CSV
CSVLoader (CSV / spreadsheet data)

Converts each CSV row into a Document. Column values become page_content as "column: value" pairs. Row index and source filename become metadata. Useful for summarizing structured feedback datasets.

loader = CSVLoader( file_path="feedback.csv", source_column="id") docs = loader.load() # One Document per row
05 · Three Summarization Strategies

Stuff, Map-Reduce, Refine:
Choosing the Right Pattern for Your Task

LangChain supports three summarization strategies, each optimizing for a different tradeoff between quality, cost, and latency. The wrong choice for your document size or task type silently degrades quality or inflates cost. Here is when to use each.

StrategyHow It WorksLLM CallsQuality StrengthQuality WeaknessUse When
StuffConcatenate ALL document text into one prompt. One LLM call. Done.1 callMaximum coherence: model sees everything at onceFails silently on long docs; lost-in-middle on large inputsDoc fits in <50% of context window
Map-ReduceSplit → parallel map calls → one reduce call combining all chunk summaries.N+1 calls (N parallel)Scales to any length; fast with async; uniform section attentionCross-chunk context lost: chunk 3 cannot reference chunk 1 contentDoc exceeds context window; homogeneous structure
RefineChunk 1 summary → feed into Chunk 2 prompt → feed into Chunk 3 prompt → ... sequential.N sequential callsCross-chunk context preserved; progressive narrative refinementSlow (sequential); cost grows O(N²) with chunk countNarrative coherence critical: novels, legal contracts with dependencies

Stuff

Prompt: "Summarize the following document:\n\n{full_text}"

Best when: user feedback form (500 words), email thread, single article. Worst when: 300-page report, legal contract, quarterly filings.

Map-Reduce

Map: "Extract key points:\n{chunk_N}" Reduce: "Combine these summaries:\n{all_summaries}"

Best when: technical reports, research papers, meeting transcripts, customer feedback archives. Works on any length.

Refine

Step 1: "Summarize: {chunk_1}" Step 2: "Refine this summary given new info: {current_summary}\n\n{chunk_2}"

Best when: legal briefs (later clauses modify earlier ones), novels, policy documents with cross-references.

💡

Decision rule: start with Stuff, switch when it fails

Step 1: try Stuff. It is the simplest and produces the most coherent summaries. Step 2: if the document overflows (context length error or quality degrades due to size), switch to Map-Reduce. Step 3: if Map-Reduce summaries lack narrative coherence because of cross-chunk dependencies, switch to Refine. In practice, Map-Reduce handles 95%+ of production cases.

06 · Multi-Document Summarization

Summarizing Across Many Documents:
Two-Level Map-Reduce

Production summarization tasks often involve not one long document but many documents: all customer feedback forms for a month, all research papers on a topic, all Slack threads from a sprint. The same Map-Reduce pattern applies at the document level: one LLM call per document (level 1), then one synthesizing call across all document summaries (level 2).

Two-level Map-Reduce for 50 feedback forms

Input

50 text files, each 300-800 words. Cannot fit all in one prompt (would be ~200,000 tokens combined).

↓

Level 1 — Per-document Map-Reduce (parallel)

For each of the 50 forms: chunk → map → reduce to produce one 3-bullet summary per form. 50 independent async pipelines run simultaneously.

↓

Level 2 — Cross-document Reduce

Concatenate all 50 three-bullet summaries (~5,000 tokens). One final LLM call: Prompt: "Given summaries of 50 student feedback forms, identify the top 5 themes and rate each by frequency." Output: Thematic synthesis across all feedback.

🔍

Cross-document synthesis prompts need explicit instructions

In the level 2 reduce step, tell the model exactly what synthesis you need: "identify common themes", "find agreements and disagreements", "rank by frequency", "summarize the range of opinions". Without explicit synthesis instructions, the model may just re-concatenate the summaries rather than synthesizing across them. The synthesis prompt is where the analytical value of multi-document summarization is created.

07 · The Refine Pattern: Sequential Summarization

Carrying Context Across Chunks:
When Narrative Coherence Requires It

Map-Reduce treats each chunk as independent. This works for homogeneous documents (each section equally important, no cross-references). But legal contracts, novels, and policy documents have cross-chunk dependencies: a term defined in chunk 1 is used in chunk 7. The Refine strategy processes chunks sequentially, updating a running summary with each new chunk's information.

Refine chain: how the running summary evolves

Chunk 1 → Initial summary

Prompt: "Summarize:\n{chunk_1}" Output: [initial_summary]
↓

Chunk 2 → Refinement

Prompt: "Current summary:\n{initial_summary}\n\nNew info:\n{chunk_2}\n\nUpdate the summary if relevant." Output: [updated_summary]
↓

Chunk 3 → Refinement

Prompt: "Current summary:\n{updated_summary}\n\nNew info:\n{chunk_3}\n\nUpdate if relevant." Output: [final_summary]

⚠️ The cost growth problem

Each refine call includes the running summary as input. After N chunks, call N costs: initial_prompt + chunk_N_tokens + summary_of_chunks_1_to_N-1_tokens. Token cost grows approximately O(N²).

5 chunks~2,500 tokens total
20 chunks~15,000 tokens total
50 chunks~90,000 tokens total
100 chunks~350,000 tokens total + expensive

Verdict: use Refine only for <20 chunks AND when narrative coherence genuinely matters. Otherwise Map-Reduce.

08 · Production Code

Async Map-Reduce Summarizer
With Document Loaders and Hierarchical Reduce

map_reduce_summarizer.py

import asyncio
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.document_loaders import (
    PyPDFLoader, WebBaseLoader, DirectoryLoader, WikipediaLoader
)

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

# ── Map prompt: summarize one chunk ──────────────────────────
MAP_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "You are a precise summarizer. Extract key findings and specific data from this section."),
    ("human",
     "Summarize this section in 3-5 bullet points. Be specific. Include names and numbers:\n\n{chunk}")
])

# ── Reduce prompt: combine chunk summaries ───────────────────
REDUCE_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "You synthesize multiple document section summaries into one coherent output."),
    ("human",
     "Combine these section summaries into a {output_style}:\n\n{summaries}")
])

map_chain = MAP_PROMPT | llm | StrOutputParser()
reduce_chain = REDUCE_PROMPT | llm | StrOutputParser()

# ── Core Map-Reduce function ──────────────────────────────────
async def map_reduce_summarize(docs, chunk_size=800, output_style="5-paragraph executive summary"):
    # CHUNK
    splitter = RecursiveCharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=80)
    chunks = splitter.split_documents(docs)
    print(f"Summarizing {len(chunks)} chunks from {len(docs)} documents...")

    # MAP: all chunks in parallel (max 5 concurrent to respect rate limits)
    chunk_summaries = await map_chain.abatch(
        [{"chunk": c.page_content} for c in chunks],
        config={"max_concurrency": 5}
    )

    # Hierarchical reduce if summaries are too long
    combined = "\n\n---\n\n".join(
        f"[Section {i+1}]\n{s}" for i, s in enumerate(chunk_summaries))

    if len(combined) > 40000:  # hierarchical reduce needed
        batch_size = 20
        batches = [chunk_summaries[i:i+batch_size] for i in range(0, len(chunk_summaries), batch_size)]
        intermediate = await reduce_chain.abatch(
            [{"summaries": "\n\n".join(b), "output_style": "intermediate summary"} for b in batches],
            config={"max_concurrency": 3}
        )
        combined = "\n\n".join(intermediate)

    # REDUCE: final synthesis
    return await reduce_chain.ainvoke(
        {"summaries": combined, "output_style": output_style})

# ── Usage: single PDF ────────────────────────────────────────
async def summarize_pdf(path: str):
    docs = PyPDFLoader(path).load()
    return await map_reduce_summarize(docs, output_style="3-bullet executive briefing")

# ── Usage: multiple PDFs from folder ─────────────────────────
async def summarize_folder(folder: str):
    docs = DirectoryLoader(folder, glob="**/*.pdf", loader_cls=PyPDFLoader).load()
    return await map_reduce_summarize(
        docs, output_style="thematic analysis identifying top 5 issues with frequency")

# ── Usage: web pages ─────────────────────────────────────────
async def summarize_urls(urls: list[str]):
    docs = WebBaseLoader(urls).load()
    return await map_reduce_summarize(docs, output_style="comparative summary noting agreements and differences")

refine_summarizer.py — for narrative documents

# ── Refine chain: sequential context-preserving summarization ─
INITIAL_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "You create precise summaries of document sections."),
    ("human", "Create an initial summary of this section:\n\n{chunk}")
])

REFINE_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "You refine summaries as new document sections are processed."),
    ("human",
     """Current summary:\n{running_summary}\n\nNew section:\n{chunk}\n\nUpdate the summary if this section adds relevant new information. If not relevant, return the current summary unchanged.""")
])

initial_chain = INITIAL_PROMPT | llm | StrOutputParser()
refine_chain_step = REFINE_PROMPT | llm | StrOutputParser()

async def refine_summarize(docs, chunk_size=800):
    splitter = RecursiveCharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=80)
    chunks = splitter.split_documents(docs)

    # Step 1: initial summary from first chunk
    summary = await initial_chain.ainvoke({"chunk": chunks[0].page_content})

    # Steps 2+: refine with each subsequent chunk (sequential)
    for chunk in chunks[1:]:
        summary = await refine_chain_step.ainvoke({
            "running_summary": summary,
            "chunk": chunk.page_content
        })

    return summary  # final refined summary

# Warning: sequential — no parallelism. Best for docs <20 chunks.
09 · Assessment

Module 2 Quiz

1. You have a 90,000-token technical report. Claude Sonnet 4 supports 200,000 tokens. A teammate says: "it fits in the context window, just use Stuff." What is wrong with this reasoning?

Correct. The lost-in-the-middle phenomenon is well-documented: LLMs attend strongly to the beginning and end of their context window, but attention degrades for content in the middle. A 90K-token report occupies a wide middle zone. Map-Reduce eliminates this by giving each chunk its own dedicated, full-attention context window. Every section of the report receives the same quality of attention.

2. You are building a Map-Reduce summarizer with asyncio. The map step has 200 chunks. What happens if you run all 200 map calls simultaneously with asyncio.gather() and why should you use max_concurrency instead?

Correct. The max_concurrency parameter is the production-critical setting in Map-Reduce. Without it, you blast the API with hundreds of simultaneous requests, triggering 429 rate limit errors that break your pipeline. With max_concurrency=5, LangChain's .abatch() maintains a sliding window of 5 concurrent requests, completing all 200 in 200/5 = 40 batches × ~1.5s = ~60s total, vs 200 × 1.5s = 300s sequential. The sweet spot is typically 3-10 depending on your tier.

3. Your 100-chunk document produces 100 map summaries. When concatenated, they total 50,000 characters — exceeding your reduce prompt's effective context limit of ~40,000 characters. What is the correct architectural fix?

Correct. Hierarchical reduce is the standard solution to the "summaries overflow the reduce prompt" problem. It mirrors the same Map-Reduce insight applied recursively: if your input is too large for one step, split it and process in batches, then combine the batches. The intermediate reduce calls can run in parallel just like the original map calls. This approach scales to millions of tokens of source material with no architectural changes.

4. You need to select a text splitter for an HTML product documentation site. Each page has h1 (section), h2 (subsection), and h3 (topic) headers. Which splitter is most appropriate and what key benefit does it provide?

Correct. The key value of HTMLHeaderTextSplitter is metadata preservation. When each chunk knows it belongs to "Installation > Requirements", the map prompt can include section context: "Summarize this 'Installation > Requirements' section in 3 bullets." The resulting summaries are self-labeled by section, making the reduce step produce a structured, navigable final summary rather than a flat list of bullets without source attribution.

5. You have a 300-page legal contract where Section 12 explicitly modifies the liability terms defined in Section 3. After using Map-Reduce, the summary of Section 12 makes no mention of the Section 3 modification. Why does this happen and what is the fix?

Correct. This is the exact use case where Refine beats Map-Reduce: cross-section dependencies in legal and narrative documents. In Refine, by the time the model processes Section 12, the running summary contains the Section 3 liability definition, allowing it to write "Section 12 modifies the liability terms established in Section 3 by adding..." In Map-Reduce, Section 12's map call sees only Section 12 in isolation and cannot make this connection.
