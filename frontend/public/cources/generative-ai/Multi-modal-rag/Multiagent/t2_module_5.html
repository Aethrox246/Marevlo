Semantic Search and
RAG Foundations

Keyword search finds documents containing your exact words. Semantic search finds documents that mean the same thing — even when worded completely differently. This module builds from that insight to Retrieval-Augmented Generation: indexing your knowledge base as embeddings, retrieving the most relevant passages at query time, and grounding LLM answers in real documents.

01 · Keyword vs Semantic Search

Why "Exact Match" Fails for
Natural Language Questions

Keyword search (BM25, TF-IDF, full-text search) finds documents that contain the query words. It works well when users know the exact terminology in the knowledge base. It fails when users ask natural questions, use synonyms, or phrase the question differently from how the answer is written. Semantic search encodes meaning as vectors and finds documents that are semantically similar — regardless of word overlap.

Why keyword search fails: a concrete example

Knowledge base contains:

"Annual subscriptions are non-refundable after the 30-day cancellation window."

User asks:

"Can I get my money back if I paid for a year?"

Keyword search

0 results. No word overlap: "money" ≠ "non-refundable", "paid" ≠ "subscription", "year" ≠ "annual". Document is invisible to the query.

Semantic search

Top result: the refund policy document. Cosine similarity ~0.87. "Get money back" ≈ "non-refundable". "Paid for a year" ≈ "annual subscription".

02 · Embeddings From First Principles

What Embeddings Are and
Why They Capture Meaning

An embedding is a list of floating-point numbers that represents the meaning of a piece of text. The embedding model is trained to place semantically similar texts close together in this high-dimensional vector space — so "dog" and "puppy" have similar embeddings, "annual subscription" and "yearly plan" have similar embeddings, and "refund" and "money back" have similar embeddings. Distance in the space = semantic dissimilarity.

How embedding similarity works

"annual subscription"
[0.23, -0.41, 0.87, ... 1536 dims]
"yearly plan"
[0.25, -0.39, 0.84, ... 1536 dims]
"monthly billing"
[0.19, -0.35, 0.71, ... 1536 dims]
"pizza recipe"
[-0.82, 0.63, -0.14, ... 1536 dims]

Cosine similarity:

"annual subscription" · "yearly plan": 0.97 ← nearly identical meaning
"annual subscription" · "monthly billing": 0.71 ← related topic, different concept
"annual subscription" · "pizza recipe": 0.03 ← unrelated

💡

Use the same model for indexing and querying — always

Embeddings only compare meaningfully when produced by the same model. A document indexed with text-embedding-3-small and queried with bge-large will return random results — the vector spaces are incompatible. If you change embedding models, you must re-index the entire corpus. Version your embedding model name alongside your vector index so you know when a re-index is needed.

03 · Vector Stores: How They Work

Storing and Searching Embeddings
at Production Scale

A vector store has two jobs: store embeddings alongside their source text and metadata, and answer similarity queries ("find the K most similar vectors to this query vector") efficiently. Similarity search over millions of vectors using exact computation would take seconds — vector stores use Approximate Nearest Neighbor (ANN) algorithms to answer in milliseconds.

How a vector store answers a similarity query

1

Index time: embed all documents

Pass each text chunk through the embedding model → get a float vector. Store the vector alongside the original text and metadata in the vector index. Build the ANN graph (HNSW or IVF) for fast search. This is done once and updated incrementally.

↓
2

Query time: embed the question

Pass the user's question through the same embedding model → get a query vector. This takes 5-20ms.

↓
3

ANN search: find top-K similar vectors

Search the ANN index for the K vectors with highest cosine similarity to the query vector. Returns document IDs and similarity scores. HNSW search over 1M vectors takes ~5ms.

↓
4

Return: text + metadata + scores

Fetch the original text chunks for the top-K document IDs. Return them to the application as a ranked list. The application passes the top chunks to the LLM as context.

⚠️

Libraries vs databases: the key production distinction

FAISS and Chroma are libraries — they run in your Python process. This means: no network latency, but also no multi-process sharing, no persistence without manual save/load, and no real-time updates without rebuilding the index. Qdrant, Pinecone, and Weaviate are databases — they run as separate services. This adds network latency (~1-5ms) but gains real-time updates, multi-process sharing, and horizontal scaling. Use a library for local development; use a database for production.

04 · The RAG Design Pattern

Retrieval-Augmented Generation:
Two Phases, One Pipeline

RAG gives an LLM access to knowledge it was not trained on by retrieving relevant information at query time and injecting it into the prompt. The LLM generates an answer grounded in the retrieved text rather than in its training data alone. This solves the two most critical LLM reliability problems: hallucination (making up facts) and knowledge cutoffs (not knowing about recent events).

RAG: two phases explained

Phase 1: Ingestion (run once)

LoadPyPDFLoader, WebBaseLoader, TextLoader → List[Document]
SplitRecursiveCharacterTextSplitter → smaller chunks with overlap
Embedembedding_model.embed_documents(texts) → List[float vectors]
Storevector_store.add_documents(chunks) → indexed in ANN structure

Phase 2: Query (run per request)

Embed queryembedding_model.embed_query(question) → query vector
Retrievevector_store.similarity_search(query_vec, k=5) → top-5 chunks
Formatcontext = join([doc.page_content for doc in chunks])
Generatellm(prompt.format(context=context, question=question)) → answer

Eliminates hallucination

The LLM is instructed to answer only from the provided context. If the answer is not in the retrieved chunks, the model says "I don't have that information." Ground truth is the document, not the model's weights.

Solves knowledge cutoffs

The vector index is updated whenever your knowledge base changes. New documents are embedded and added in real time. No model retraining required — the freshest knowledge is always available at query time.

Enables source citations

Each retrieved chunk carries metadata (source URL, page number, document ID). The LLM can include "According to [Doc 1, page 3]..." in its answer. Users can verify the answer against the original source.

05 · Q&A Chatbot Over a Single Document

The Simplest RAG System:
One Document, One Vector Store, One Chain

Before building a full knowledge base, start with a single document. This reveals the core RAG pattern without the complexity of multi-document indexing, metadata filtering, or hybrid search. The pattern is: load → split → embed → store → retrieve → generate. Every more sophisticated RAG system extends this same foundation.

rag_single_doc.py — RAG from scratch

from langchain_community.document_loaders import WebBaseLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import Chroma
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# ── Phase 1: Ingestion ────────────────────────────────────────
# Load: fetch the document from a URL
loader = WebBaseLoader("https://docs.marevlo.com/refund-policy")
docs = loader.load()  # List[Document]

# Split: break into 500-char chunks with 50-char overlap
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)
print(f"Created {len(chunks)} chunks")

# Embed + Store: create Chroma vector store in memory
embedding_model = OpenAIEmbeddings(model="text-embedding-3-small")
vector_store = Chroma.from_documents(chunks, embedding_model)
# Chroma embeds all chunks and builds the search index in one call

# ── Phase 2: Retrieval chain ──────────────────────────────────
retriever = vector_store.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 3}  # return top-3 most similar chunks
)

RAG_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "Answer the question using ONLY the provided context.\n"
     "If the answer is not in the context, say 'I don't have that information.'\n"
     "Cite the relevant passage."),
    ("human", "Context:\n{context}\n\nQuestion: {question}")
])

def format_docs(docs):
    return "\n\n".join(d.page_content for d in docs)

# Chain: retrieve → format → prompt → LLM → parse
rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | RAG_PROMPT
    | ChatAnthropic(model="claude-sonnet-4-20250514")
    | StrOutputParser()
)

# ── Run ──────────────────────────────────────────────────────
answer = rag_chain.invoke("Can I get a refund after 30 days?")
print(answer)

# Inspect retrieved docs (for debugging):
retrieved = retriever.invoke("Can I get a refund after 30 days?")
for doc in retrieved:
    print(f"[score: ?] {doc.page_content[:100]}...")
    print(f"  source: {doc.metadata.get('source', 'unknown')}")
💡

RunnablePassthrough: the LCEL identity operator

In the chain {"context": retriever | format_docs, "question": RunnablePassthrough()}, both keys are evaluated in parallel. The retriever runs on the input question and formats the docs. RunnablePassthrough() passes the question through unchanged. The resulting dict feeds the RAG_PROMPT with both variables filled. This is the standard LCEL pattern for RAG chains.

06 · Expanding to a Knowledge Base

From One Document to
a Multi-Document Vector Index

A single-document RAG system is a proof of concept. A knowledge base RAG system indexes many documents — your entire documentation site, all product PDFs, historical support tickets — and retrieves from all of them simultaneously. The architecture is identical; only the ingestion step changes to handle multiple sources.

Ingesting multiple documents from a folder

from langchain_community.document_loaders import DirectoryLoader, PyPDFLoader from langchain_community.vectorstores import Qdrant # Load all PDFs from a folder recursively loader = DirectoryLoader( "./knowledge_base/", glob="**/*.pdf", loader_cls=PyPDFLoader ) all_docs = loader.load() # all pages from all PDFs # Split all documents chunks = splitter.split_documents(all_docs) print(f"{len(all_docs)} pages → {len(chunks)} chunks") # Build Qdrant index (production vector store) vector_store = Qdrant.from_documents( chunks, embedding_model, url="http://localhost:6333", collection_name="marevlo_kb", ) # Same rag_chain as before — no changes needed

Metadata filtering: retrieving from a subset

When your knowledge base has documents from multiple categories (pricing, technical docs, legal), metadata filters let you restrict retrieval to the relevant subset before doing similarity search. This dramatically improves precision.

# Add metadata at ingestion time splitter.split_documents(pricing_docs) # metadata already set # pricing_docs[0].metadata = {"category": "pricing", "source": "..."} # Filter at retrieval time retriever = vector_store.as_retriever( search_kwargs={ "k": 5, "filter": {"category": "pricing"} # Qdrant filter } ) # Only pricing documents are searched — much higher precision
⚠️

Adding documents after index creation: use add_documents()

Never rebuild the entire index from scratch when adding new documents. Use vector_store.add_documents(new_chunks) to incrementally add embeddings. For deletions, use vector_store.delete(ids=[...]) with the document IDs stored in metadata. Rebuilding from scratch requires re-embedding all documents (slow and expensive).

07 · RAG Terminology Reference

Every Term You Will Encounter
in Production RAG Systems

RAG documentation uses many terms with precise meanings. Misunderstanding even one — confusing "retriever" with "vector store", or "embedding" with "chunk" — causes hours of debugging. This reference section defines every core term precisely.

TermPrecise definitionRelated to
EmbeddingA float vector (list of numbers) representing text meaning. Example: [0.23, -0.41, 0.87, ...] with 768-3072 dimensions.Embedding model, vector store
Embedding modelThe neural network that converts text into an embedding vector. Must be the same at index time and query time.OpenAI, BAAI/bge, Cohere
ChunkA piece of text created by splitting a document. Usually 200-1000 tokens. The unit that gets embedded and stored.Text splitter, chunk_size, chunk_overlap
Vector storeA database optimized for storing embeddings and answering similarity queries. Chroma, Qdrant, Pinecone.ANN index, HNSW, cosine similarity
RetrieverA LangChain object that accepts a query string and returns a list of Document objects. Wraps a vector store.as_retriever(), search_kwargs
Context windowThe maximum tokens an LLM can process in one call. Determines how many chunks you can include in the prompt.chunk_size, top-k
GroundingThe property of an LLM answer being derived from specific source documents rather than from training data alone.Faithfulness, citation, hallucination
HallucinationWhen an LLM states something false as if it were true. RAG reduces (not eliminates) hallucination by providing context.Faithfulness metric, RAGAS
Top-kThe number of most similar chunks retrieved for a query. k=3 means the 3 closest chunks are returned as context.search_kwargs, precision vs recall
Cosine similarityThe measure of angle between two embedding vectors. 1.0 = identical direction (same meaning). 0.0 = perpendicular (unrelated). -1.0 = opposite.ANN search, score_threshold
08 · Production Code

Full RAG Chain With
Source Citations and Qdrant

production_rag.py

from langchain_community.document_loaders import DirectoryLoader, PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import Qdrant
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# ── Config ────────────────────────────────────────────────────
EMBED_MODEL = "text-embedding-3-small"
LLM_MODEL = "claude-sonnet-4-20250514"
QDRANT_URL = "http://localhost:6333"
COLLECTION = "knowledge_base"
CHUNK_SIZE, CHUNK_OVERLAP, TOP_K = 600, 60, 5

# ── Ingestion (run once to build index) ──────────────────────
def build_index(docs_folder: str):
    loader = DirectoryLoader(docs_folder, glob="**/*.pdf", loader_cls=PyPDFLoader)
    raw_docs = loader.load()
    print(f"Loaded {len(raw_docs)} pages from {docs_folder}")

    splitter = RecursiveCharacterTextSplitter(chunk_size=CHUNK_SIZE, chunk_overlap=CHUNK_OVERLAP)
    chunks = splitter.split_documents(raw_docs)
    print(f"Split into {len(chunks)} chunks")

    embeddings = OpenAIEmbeddings(model=EMBED_MODEL)
    store = Qdrant.from_documents(chunks, embeddings, url=QDRANT_URL, collection_name=COLLECTION)
    print("Index built ✓")
    return store

# ── Query chain ──────────────────────────────────────────────
def build_rag_chain(store):
    retriever = store.as_retriever(search_kwargs={"k": TOP_K})

    RAG_PROMPT = ChatPromptTemplate.from_messages([
        ("system",
         "Answer using ONLY the context below.\n"
         "Format: answer first, then Citations: [source: page].\n"
         "If not in context: 'I don't have that information.'"),
        ("human", "Context:\n{context}\n\nQuestion: {question}")
    ])

    def format_with_sources(docs):
        parts = []
        for i, d in enumerate(docs):
            src = d.metadata.get("source", "unknown")
            pg  = d.metadata.get("page", "?")
            parts.append(f"[Doc {i+1}, {src} p.{pg}]\n{d.page_content}")
        return "\n\n".join(parts)

    return (
        {"context": retriever | format_with_sources, "question": RunnablePassthrough()}
        | RAG_PROMPT
        | ChatAnthropic(model=LLM_MODEL, temperature=0)
        | StrOutputParser()
    )

# ── Usage ────────────────────────────────────────────────────
# store = build_index("./knowledge_base/")
# OR load existing index:
store = Qdrant(
    client=QdrantClient(QDRANT_URL),
    collection_name=COLLECTION,
    embeddings=OpenAIEmbeddings(model=EMBED_MODEL)
)
chain = build_rag_chain(store)
answer = chain.invoke("What is the refund policy for annual subscriptions?")
print(answer)
# Output: "Annual subscriptions are non-refundable after 30 days...
# Citations: [Doc 1, refund-policy.pdf p.3]"
09 · Assessment

Module 5 Quiz

1. A user asks "Can I get my money back?" but the knowledge base document says "Annual subscriptions are non-refundable after 30 days." Why does keyword search fail to find this document, and how does semantic search succeed?

Correct. This is the fundamental limitation of keyword search: it requires lexical overlap. "Money back" and "non-refundable" are semantic opposites that convey the same concept (refund eligibility), but they share zero words. The embedding model, trained on billions of text examples where these phrases appear in similar contexts, maps them to nearby vectors. Cosine similarity between the query embedding and document embedding will be high (~0.85+) despite zero word overlap.

2. You build a knowledge base using text-embedding-3-small (1536 dimensions). Six months later your team switches to BAAI/bge-large-en-v1.5 (1024 dimensions) to reduce costs. What must you do to maintain a working system?

Correct. Embedding model compatibility is a critical operational constraint. Different models are trained with different architectures and loss functions, producing embeddings in entirely different vector spaces. A cosine similarity computed across model boundaries is numerically meaningless. The re-indexing requirement is one of the most common RAG production mistakes — teams switch models without re-indexing and get quietly degraded retrieval quality that looks like a prompt engineering problem.

3. Your RAG chain's answers are accurate but users cannot verify them because the response contains no source information. What is the minimal code change to add citations?

Correct. Citations in RAG require two things: (1) including source metadata in the formatted context string so the LLM can see which chunk came from which document, and (2) instructing the LLM in the system prompt to cite sources in its answer. PyPDFLoader automatically populates metadata["source"] (filename) and metadata["page"] (page number) on every Document. The only missing piece is surfacing this metadata in the context string passed to the LLM.

4. You are choosing between Chroma (library) and Qdrant (database) for a production RAG system that serves 50 concurrent users. Which should you choose and why?

Correct. The library vs database distinction is the most important architectural decision in RAG infrastructure. Libraries (Chroma, FAISS) run inside the Python process — they cannot be shared across processes or servers. A FastAPI app with 4 workers and Chroma gives each worker its own separate index, causing stale reads when documents are updated. Qdrant as a separate service is the standard production choice: one source of truth, concurrent-safe writes, and horizontal scaling of the search capacity.

5. Your RAG chain is retrieving k=3 documents, but users report the answers sometimes miss relevant information that is clearly in your knowledge base. What are the two most likely causes and fixes?

Correct. Low recall (missing known-relevant documents) in RAG has two primary causes. First, too-small k: the relevant document exists but ranks outside the top-k. Increasing k with a reranker maintains precision while improving recall. Second, chunks that are too large: large chunks have embeddings that represent an average of all their content, which may not closely match a specific sub-question. Smaller chunks produce more focused embeddings that match specific queries more precisely. Both fixes are common in production tuning.
