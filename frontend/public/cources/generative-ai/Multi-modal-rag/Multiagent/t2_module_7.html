Track 2 · Module 7 · Advanced RAG

Advanced RAG:
Indexing Strategies

Basic RAG splits documents into fixed-size chunks, embeds them, and retrieves the closest match. Advanced RAG asks: what is the optimal unit to embed? Embedding a small child chunk increases precision. Returning the parent for context improves quality. Embedding a document summary captures the topic. Embedding hypothetical questions matches queries directly. This module covers all four strategies.

01 · Where Basic RAG Breaks

The Precision-Context Tradeoff:
Why Chunk Size Is Never Right

Basic RAG uses a single chunk size for both embedding and retrieval. Too small and the embedding captures a narrow fragment that may not match the query topic well. Too large and the embedding is a blurry average of many ideas, losing specificity. Advanced indexing strategies decouple the unit of embedding from the unit returned to the LLM — solving this tradeoff directly.

The fundamental tradeoff: small chunks vs large chunks

Small chunks (100-300 tokens)

Size: 100-300 tokens
Embedding quality: High precision — embedding closely captures the specific fact
Context quality: Incomplete context — answer fragments cut off mid-idea
Core problem: Retrieval is precise but the returned text is too short to be useful. LLM answers with a sentence fragment.

Large chunks (800-2000 tokens)

Size: 800-2000 tokens
Embedding quality: Low precision — embedding averages many ideas, matches many queries poorly
Context quality: Rich context — full paragraphs, complete arguments, proper continuity
Core problem: Retrieval is imprecise but returned text has enough context. LLM gets too much noise.

Advanced solution: decouple embedding unit from retrieval unit

Embed small child chunks (high precision) → when a child chunk matches a query, return its parent chunk (full context). Best of both worlds: precision of small chunks, context richness of large chunks. This is the ParentDocumentRetriever pattern.

02 · Advanced Splitting Strategies

Choosing the Right Boundary:
Four Splitting Approaches for Different Content

The splitting strategy determines whether chunks align with semantic boundaries (paragraph, section, topic) or arbitrary character counts. Semantic alignment is always better for retrieval quality — a chunk that contains one complete idea produces a more specific embedding than a chunk that cuts mid-sentence across two ideas.

RecursiveCharacterTextSplitter

Splits at natural boundaries in priority order: \n\n (paragraph) → \n (line) → " " (word) → "" (char). Respects prose structure without understanding content.

Use when: Use as the default for all prose content: reports, articles, books, emails, transcripts.

splitter = RecursiveCharacterTextSplitter( chunk_size=500, chunk_overlap=50)

HTMLHeaderTextSplitter

Splits at HTML header tags (h1, h2, h3). Each chunk inherits parent headers as metadata: {"Section": "Methods", "Subsection": "Data Collection"}. Preserves document hierarchy.

Use when: Web pages, HTML documentation, structured reports. When section names should appear in chunk metadata for filtering.

splitter = HTMLHeaderTextSplitter( headers_to_split_on=[("h1","H1"),("h2","H2")])

SemanticChunker (experimental)

Embeds every sentence, then splits where the cosine similarity between adjacent sentences drops below a threshold — at semantic topic boundaries rather than arbitrary character counts.

Use when: Long documents with multiple distinct topics per section. When chunk boundaries should align with genuine topic changes.

from langchain_experimental.text_splitter import SemanticChunker splitter = SemanticChunker(embeddings, breakpoint_threshold_type="percentile")

Child + Parent (manual two-level)

Explicitly create two levels: small child chunks (200-300 tokens) for embedding, and larger parent chunks (1000-2000 tokens) for retrieval. Gives full control over both levels.

Use when: When ParentDocumentRetriever default behavior doesn't fit your document structure. Gives precise control over child and parent sizes.

parent_splitter = RecursiveCharacterTextSplitter( chunk_size=2000) child_splitter = RecursiveCharacterTextSplitter( chunk_size=300)
💡

Factors that should guide your chunk_size choice

The ideal chunk_size depends on: (1) Average query length — queries of 10 words match best against chunks of 150-500 tokens; (2) Document structure — documents with short self-contained facts (FAQs) work with smaller chunks; narrative documents need larger chunks; (3) LLM context window — how many chunks fit in k × chunk_size tokens of context; (4) Retrieval precision requirements — smaller chunks produce more specific embeddings but require ParentDocumentRetriever to restore context.

03 · ParentDocumentRetriever

Embed Small, Return Large:
Best of Both Worlds

ParentDocumentRetriever is LangChain's built-in implementation of the child/parent pattern. It splits documents twice: into small child chunks for embedding (high precision) and larger parent chunks for retrieval (full context). The vector store contains only child chunk embeddings. When a child matches a query, the retriever fetches and returns the corresponding parent document from a docstore.

Architecture: two stores, one retriever

Vector Store (child chunk embeddings)

Contains embeddings of 200-300 token child chunks. Each child chunk knows its parent ID. Only child embeddings are stored here — never parent text.

Searched at query time using cosine similarity. Returns matching child chunk IDs.

DocStore (parent chunk text)

Contains full text of 1000-2000 token parent chunks. Keyed by parent ID. Not searched directly — only looked up by ID.

After child IDs are found, parent IDs are resolved and parent text is fetched from here.

1Query: "What is the refund window for enterprise plans?"
2Embed query → query vector
3Search vector store → find 3 most similar CHILD CHUNK embeddings
4Child result: "...refund window for enterprise..." (200 tokens, child_id=c47, parent_id=p12)
5Resolve parent_id → fetch parent chunk p12 from DocStore (1500 tokens)
6Return parent chunk p12 to LLM — full context, not just the 200-token fragment

parent_document_retriever.py

from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain.text_splitter import RecursiveCharacterTextSplitter

# Two splitters: small for embedding, large for context
child_splitter = RecursiveCharacterTextSplitter(chunk_size=300)
parent_splitter = RecursiveCharacterTextSplitter(chunk_size=2000)

# Vector store holds child chunk embeddings
vectorstore = Chroma(embedding_function=OpenAIEmbeddings())
# DocStore holds parent chunk full text (use RedisStore for production)
docstore = InMemoryStore()

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,  # omit to use full docs as parents
)

# Indexing: adds both child embeddings and parent text
retriever.add_documents(docs)  # docs = loaded List[Document]

# Retrieval: returns PARENT chunks despite matching on child embeddings
results = retriever.invoke("refund policy enterprise plans")
for doc in results:
    print(f"Length: {len(doc.page_content)} chars — parent chunk")
    print(doc.page_content[:200])

# Production docstore: persist with Redis
from langchain.storage import RedisStore
docstore = RedisStore(redis_url="redis://localhost:6379")
04 · MultiVectorRetriever

Multiple Vectors Per Document:
Summaries, Hypothetical Questions, and Both

MultiVectorRetriever is the general framework for storing multiple different vector representations per document. Where ParentDocumentRetriever stores one child embedding per chunk, MultiVectorRetriever lets you store many different embeddings — the chunk itself, its summary, and several hypothetical questions it answers — all pointing back to the same parent document in the docstore.

MultiVectorRetriever architecture

Document: "Enterprise Refund Policy" (full text)
├── DocStore: doc_id="ep_001" → full text (1,800 tokens)
├── VectorStore embedding 1: summary of doc
│ "Enterprise customers have custom refund terms..."
├── VectorStore embedding 2: hypothetical Q1
│ "How long do enterprise customers have to request a refund?"
├── VectorStore embedding 3: hypothetical Q2
│ "Can enterprise accounts get prorated refunds?"
└── VectorStore embedding 4: child chunk
   "Enterprise plan: refunds available within 60 days..."
Query → any of 4 vectors match → retrieve doc_id → return full text

Why multiple vectors dramatically improve recall

Raw chunk embedding

Matches queries that use similar terminology to the chunk text

e.g. ""60-day refund window enterprise""

Summary embedding

Matches thematic/overview queries about the document topic

e.g. ""What are enterprise refund terms?""

Hypothetical question

Matches queries that sound like user questions, not document prose

e.g. ""Can I get a refund after 2 months if I have enterprise?""

05 · Embedding Document Summaries

Topic-Level Retrieval:
When the Query Is About the Document Itself

Individual chunks are specific. They answer detail-level queries well. But topic-level queries ("What does your documentation say about enterprise plans?") may not match any individual chunk well because no chunk covers the whole topic — only the summary does. Embedding a summary generated by an LLM creates a single vector that captures the document's overall theme, enabling topic-level retrieval.

Generating and indexing document summaries

from langchain.retrievers import MultiVectorRetriever from langchain.storage import InMemoryStore from langchain_core.documents import Document import uuid # Generate summaries for each parent doc SUMMARY_PROMPT = ChatPromptTemplate.from_messages([ ("system", "Summarize this document in 2-3 sentences. Focus on the main topic."), ("human", "{doc}") ]) summarize = SUMMARY_PROMPT | llm | StrOutputParser() summaries = summarize.batch( [{"doc": d.page_content} for d in docs], config={"max_concurrency": 5} ) # Setup MultiVectorRetriever vectorstore = Chroma(embedding_function=OpenAIEmbeddings()) docstore = InMemoryStore() retriever = MultiVectorRetriever( vectorstore=vectorstore, docstore=docstore, id_key="doc_id" ) # Store: summary embeddings → full doc text doc_ids = [str(uuid.uuid4()) for _ in docs] summary_docs = [ Document(page_content=s, metadata={"doc_id": doc_ids[i]}) for i, s in enumerate(summaries) ] retriever.vectorstore.add_documents(summary_docs) # embed summaries retriever.docstore.mset(list(zip(doc_ids, docs))) # store full docs

When to use summary embeddings vs raw chunk embeddings

Query typeBetter withReason
"What is the refund policy?"Raw chunk embeddingPrecise term match in specific chunk
"What does your documentation say about refunds?"Summary embeddingMeta-question about the document's topic
"Give me an overview of enterprise features"Summary embeddingTopic-level question — no single chunk covers it
"What is the 30-day refund window?"Raw chunk embeddingSpecific fact retrieval
"Which documents are about pricing?"Summary embeddingDocument discovery, not fact retrieval
💡

Combining both: chunk embeddings + summary embeddings in one retriever

The best production setup uses MultiVectorRetriever with BOTH chunk embeddings and summary embeddings stored for each document. Add chunk embeddings with retriever.vectorstore.add_documents(chunk_docs) and summary embeddings with retriever.vectorstore.add_documents(summary_docs), both pointing to the same doc_ids in the docstore. When a query arrives, the ANN search finds whichever embedding type matches best — specific chunks for detail queries, summaries for topic queries.

06 · Embedding Hypothetical Questions

The Query-Answer Mismatch Problem:
Why Indexing Questions Beats Indexing Answers

User queries sound like questions. Document chunks sound like answers. Their embeddings often have low cosine similarity even when the document contains the answer — because question phrasing and answer phrasing use different vocabulary and sentence structure. Embedding hypothetical questions generated by an LLM bridges this gap: question embeddings match user query embeddings much more closely.

Why the mismatch happens

Document chunk (answer style)

"Enterprise plan subscribers are eligible for a refund within sixty calendar days of the subscription start date, subject to the conditions outlined in section 4.2 of the service agreement."

User query (question style)

"How long does an enterprise customer have to ask for their money back?"

Cosine similarity: ~0.58 — low, despite the document clearly containing the answer.

Hypothetical question generated by LLM for this document chunk

"How long does an enterprise subscriber have to request a refund after their subscription starts?"

Cosine similarity to user query: ~0.91 — high, because both are question phrasing in the same semantic space. This hypothetical question is embedded instead of the chunk text, and it points to the chunk in the docstore.

hypothetical_questions.py

from langchain.retrievers import MultiVectorRetriever
from langchain_core.output_parsers import JsonOutputParser
import uuid

# ── Generate hypothetical questions per chunk ─────────────────
HQ_PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "Generate 3 diverse questions that this document chunk answers.\n"
     "Write questions as a user would phrase them, not as document prose.\n"
     "Output ONLY a JSON array of 3 question strings."),
    ("human", "{chunk}")
])
hq_chain = HQ_PROMPT | llm | JsonOutputParser()

# Generate questions for all chunks in parallel
questions_per_chunk = hq_chain.batch(
    [{"chunk": d.page_content} for d in chunks],
    config={"max_concurrency": 5}
)

# ── Index: question embeddings → chunk text ───────────────────
chunk_ids = [str(uuid.uuid4()) for _ in chunks]

retriever = MultiVectorRetriever(
    vectorstore=vectorstore, docstore=docstore, id_key="doc_id"
)

# Add question Documents to vector store (embed questions)
question_docs = []
for chunk_id, questions in zip(chunk_ids, questions_per_chunk):
    for q in questions:
        question_docs.append(
            Document(page_content=q, metadata={"doc_id": chunk_id})
        )

retriever.vectorstore.add_documents(question_docs)  # embed questions
retriever.docstore.mset(list(zip(chunk_ids, chunks)))  # store original chunks

# ── Query: user question matches hypothetical question embedding
results = retriever.invoke("How long does enterprise have to get a refund?")
# Returns full chunk text, not the hypothetical question
for doc in results:
    print(doc.page_content)  # original chunk text
07 · Granular Expansion and Semi-Structured Content

Chunk Expansion and
Handling Tables, Code, and Mixed Content

Some documents mix structure and prose: a user manual with tables embedded in text, a codebase with docstrings, a product page with specs and descriptions. Standard text splitters break these poorly — a table's header ends up in one chunk, its data rows in another. Specialized strategies handle this content type correctly.

Granular chunk expansion (sentence-window retrieval)

Embed individual sentences (maximum precision) but return a window of surrounding sentences for context. The sentence embedding is specific enough to match exact queries. The window provides the LLM with enough surrounding text to formulate a coherent answer.

Document: "...Section 4.2. Enterprise refunds are processed within 5 business days. The refund amount is calculated prorated from the cancellation date. Partial months are not eligible for refund..."
Split into sentences → embed each sentence independently
Query matches: "The refund amount is calculated prorated..." (sentence 2)
Return: window of 2 sentences before + 2 after = 5-sentence context window
LLM receives: sentences 1-5 — full coherent context for the answer

Semi-structured content: tables and code

HTML tables

Use HTMLHeaderTextSplitter first (preserves table within its section), then handle each table as a unit. Consider asking an LLM to convert the table to prose: "The pricing table shows: Basic plan $9/month, Pro plan $29/month..." — prose embeds better than raw HTML.

Markdown tables

Unstructured.io library partitions documents and identifies table elements. Each table becomes one Document. Alternatively, use recursive character splitting with a table-aware separator that keeps rows together.

Code blocks

Use langchain.text_splitter.Language enum for code-aware splitting. Python splits at class/function boundaries. JavaScript splits at function declarations. Each function becomes a chunk — semantically meaningful boundaries for code search.

⚠️

Cost of advanced indexing: one-time but significant

Hypothetical question generation requires one LLM call per chunk (e.g. 3 questions per chunk × 1000 chunks = 3000 LLM calls). At $0.003 each = $9 per corpus indexing run. Summary generation: 1 call per document × 200 documents = 200 calls = ~$0.60. These are one-time costs paid at indexing time, not per query. Re-index only when documents change. Track which documents have been indexed with hypothetical questions to avoid re-generating them.

09 · Assessment

Module 7 Quiz

1. You set chunk_size=200 for your RAG system and retrieval precision is excellent, but LLM answers are incomplete — they end mid-sentence and lack context. What is the root cause and what is the recommended fix?

Correct. This is exactly the problem ParentDocumentRetriever solves. Small chunks (200 tokens) produce embeddings that closely match specific user queries — high precision. But 200 tokens is often too short for the LLM to provide a complete answer. ParentDocumentRetriever decouples the embedding unit (child chunk, 200 tokens) from the retrieval unit (parent chunk, 1500 tokens). The ANN search matches on child embeddings; the actual text returned is the parent.

2. Your RAG system works well for specific fact queries but fails on questions like "What does your documentation say about enterprise plans overall?" — it returns unrelated chunks. What strategy fixes this?

Correct. Topic-level queries ask about a document's overall theme, not a specific fact within it. Individual chunks — even large ones — cannot capture a document's overall theme because they contain detail-level content. A summary generated by an LLM ("This document describes enterprise refund policies, custom SLA terms, and dedicated account management features") encodes the document's theme in one embedding. When a user asks "what does your enterprise documentation say overall?", this summary embedding matches the query much better than any individual chunk.

3. A user queries "How long does an enterprise customer have to request a refund?" but the closest chunk has a cosine similarity of only 0.61, causing it to miss the score_threshold of 0.72. The chunk clearly contains the answer. What advanced strategy solves this?

Correct. The query-answer embedding mismatch is the core problem: user questions and document answers use structurally different language. Questions use interrogative patterns; answers use declarative prose. Their embeddings land in different parts of the semantic space despite being semantically related. Hypothetical questions bridge this gap: generate 3 questions per chunk that the chunk would answer, embed those questions, store them with the chunk ID. Now user queries match question embeddings (query ↔ question style similarity is high) instead of answer embeddings (query ↔ answer style similarity is low).

4. You need to split a document where important context spans multiple paragraphs — for example, a legal clause that references a definition from 5 paragraphs earlier. Neither RecursiveCharacterTextSplitter nor HTMLHeaderTextSplitter helps. What approach works?

Correct. SemanticChunker addresses the case where neither structural boundaries (HTML headers) nor arbitrary character counts produce semantically coherent chunks. By detecting when adjacent sentence embeddings diverge significantly, it creates boundaries that align with genuine topic shifts in the text. Legal documents with complex internal references often have long passages on the same topic (a definition + all clauses using that definition) — SemanticChunker keeps these together.

5. You want to use both summary embeddings and hypothetical question embeddings for a 500-document knowledge base. Each document has 5 chunks. You will generate 3 hypothetical questions per chunk. What is the approximate number of LLM calls required for indexing, and is this a one-time or per-query cost?

Correct. This is a critical distinction: advanced indexing costs are paid once at indexing time, not per query. The 8,000 LLM calls happen when you build or rebuild the index. After that, retrieval uses vector similarity search (no LLM calls) and only the final answer generation requires an LLM call. Track which documents have been indexed with which strategy (store in metadata) so incremental updates only process new or changed documents — not the entire corpus.
