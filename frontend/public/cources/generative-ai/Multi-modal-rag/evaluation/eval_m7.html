Multi-Agent Evaluation
Isolation · Routing Accuracy · Cross-Domain Testing · Synthesis · Overhead

Multi-agent systems fail at two levels: individual specialists and inter-agent coordination. Evaluation must cover both independently before testing the system as a whole. This module covers specialist isolation testing, coordinator routing accuracy, end-to-end task completion for cross-domain queries, synthesis quality, and the coordination overhead metric — with worked examples showing what each failure pattern looks like in LangSmith traces.

01 · The Two-Level Failure Problem

Specialists Fail Differently
Than Coordination Fails

A multi-agent system has two failure modes that require separate evaluation: (1) a specialist agent fails within its own domain — wrong tool selection, hallucination, incomplete answer; (2) the coordinator fails at dispatching — routes to the wrong specialist, misses required specialists, or synthesizes results incoherently. You cannot diagnose which level is failing with only end-to-end testing.

What end-to-end testing misses

User asks "Find hotel + book flight" → end-to-end test PASSES but accommodation specialist secretly called flight_search (wrong tool) and happened to get a correct hotel result from the wrong tool by coincidence
Coordinator routes correctly to accommodation specialist → but specialist returns a hallucinated price → synthesis creates a confident wrong answer → end-to-end test scores it as partial completion but does not identify which level failed
Multi-part query processed correctly by specialists → synthesis node drops the accommodation results → user gets flight info only → end-to-end test sees 50% completion but cannot tell if it was a coordinator or synthesis failure

The correct evaluation order

1
Specialist isolation tests: Test each specialist with domain queries (must use right tools) and off-domain queries (must refuse). Pass = specialist is reliable in isolation.
2
Coordinator routing accuracy: Test the router/supervisor classification independently. Given a query, does it select the right specialist(s)?
3
End-to-end tests: Only after passing 1 and 2. Test cross-domain queries requiring 2+ specialists. Now failures are unambiguously coordination/synthesis issues.
02 · Specialist Isolation Testing

Testing Each Agent
Before Connecting Them

Specialist isolation testing runs each specialist agent independently, disconnected from the coordinator. Tests verify: (1) domain queries use correct tools from the specialist's allowed set; (2) off-domain queries are refused or redirected gracefully; (3) output format is parseable by the coordinator. All three must pass before integrating.

The book-without-search failure is a critical safety issue

A specialist that books without searching first is dangerous: it may book a wrong hotel (hallucinated), book at a wrong price, or book without confirming with the user. This failure would pass an end-to-end test if the coordinator happened to never send a "Book [hotel name]" query directly — but in production, users ask these queries constantly. Isolation testing catches it before it costs a real booking. Fix: strengthen the specialist's system prompt with explicit "ALWAYS search before booking. NEVER call book_accommodation without having called hotel_search in the current conversation."

03 · Coordinator Routing Accuracy

Does the Router Send Queries
to the Right Specialists?

Routing accuracy measures whether the coordinator correctly identifies which specialist(s) to invoke for each query. This is tested independently of the specialists — by calling only the routing/classification component and checking its output against a labeled dataset of (query, expected_specialists) pairs.

04 · End-to-End Cross-Domain Testing

Queries That Require Multiple Specialists:
The True Integration Test

End-to-end tests for multi-agent systems must specifically test queries that require 2+ specialists working in sequence. Single-specialist queries only test coordination overhead, not coordination correctness. The integration test set should include queries designed to fail if any one specialist or the coordinator has a bug.

Three failure patterns from this test — three different fixes

Pattern 1 (flight not triggered): Supervisor terminates after accommodation result. Fix: supervisor prompt needs "For trip planning queries, always dispatch to both accommodation AND transport unless the user explicitly said they are driving." Pattern 2 (experience never called): Supervisor only dispatches to 2 specialists and considers task done. Fix: strengthen FINISH criteria — "Only output FINISH if ALL aspects of the user query have been addressed." Pattern 3 (synthesis drops results): Synthesizer receives 3 specialist results but only includes 2. Fix: bug in synthesis_node concatenation logic — likely a state merge error.

05 · Synthesis Quality and Coordination Overhead

How Well Does the Coordinator
Combine Specialist Results?

Synthesis quality evaluation

The synthesis node combines results from multiple specialists into one response. Quality failures: dropping specialist outputs, contradicting specialist data, presenting information in a confusing order, or failing to integrate results coherently.

Low synthesis quality (score: 2/5)
Accommodation: "Shinjuku Hotel ¥14,200 Dec 9-12"
Transport: "BA flight LHR→NRT £480 Dec 9"

Synthesized: "Here are the options: flight from London £480. Hotel available." (drops price, drops hotel name, misses date info)
High synthesis quality (score: 5/5)
Synthesized: "For your Tokyo trip Dec 9-12: ✈ Flight: BA from London Heathrow, £480 return, departing Dec 9. 🏨 Hotel: Shinjuku Hotel at ¥14,200/night (3 nights = ¥42,600). Total estimated budget: £480 + ~£220 hotel = £700."

Coordination overhead measurement

Coordination overhead = specialist LLM calls wasted by unnecessary dispatching. A supervisor that dispatches to all 3 specialists when only 1 is needed wastes 2 specialist calls + 2 extra supervisor routing calls.

06 · Analyzing Multi-Agent Failures in LangSmith

Reading Nested Traces to Diagnose
Exactly Which Layer Failed

Multi-agent systems produce hierarchical traces in LangSmith: the outer supervisor run contains spans for each specialist invocation, and each specialist span contains its own tool call spans. Reading these traces is the practical skill for diagnosing multi-agent failures in production.

LangSmith trace structure: reading a 3-specialist run

▶ SupervisorGraph [42.1s | $0.143 | PARTIAL COMPLETION]
  ▶ supervisor_node #1 [1.8s] → decision: "accommodation"
  ▶ accom_node [8.4s]
    ▶ hotel_search("Tokyo","Dec 9","Dec 12") [0.4s] → 5 results
    Final: "Shinjuku Hotel ¥14,200/night"
  ▶ supervisor_node #2 [1.9s] → decision: "transport"
  ▶ transport_node [9.1s]
    ▶ flight_search("London","Tokyo","Dec 9") [1.3s] → BA £480
    Final: "BA Flight LHR→NRT £480 return"
  ▶ supervisor_node #3 [2.1s] → decision: "FINISH" ← BUG: should dispatch "experience" first
  ▶ synthesize_node [4.2s]
    Missing: activities/restaurant recommendations not included
    Final synthesis covers hotel + flight only → PARTIAL COMPLETION
⚠️

Reading the trace: the FINISH at supervisor_node #3 is the failure point

The trace shows exactly where the system went wrong: supervisor_node #3 saw results from accommodation and transport, judged the task complete, and output FINISH — skipping the experience specialist. The user asked for a "full Tokyo trip plan" which implies activities too. Fix: add few-shot examples to the supervisor prompt showing full-trip queries requiring all 3 specialists. Or check if "experience" is missing from the supervisor's specialist list in that version.

07 · Specialist Confusion Rate

Did Each Specialist Stay
Within Its Domain?

Specialist Confusion Rate measures how often a specialist calls a tool outside its designated set. An accommodation specialist calling flight_search is a domain boundary violation — it undermines the purpose of specialist separation and can cause unpredictable behavior when the same query is handled by both accommodation and transport specialists.

Confusion rate by specialist across 100 multi-agent runs

💡

Confusion rate = 0.153 for experience specialist is the critical finding

15% of experience specialist calls are to out-of-domain tools. This tells you the experience specialist's system prompt is not clear enough about its boundaries — it is being triggered for queries that include travel logistics alongside activity planning, and it is trying to handle the full query instead of staying in its lane. Fix: add explicit NOT FOR instructions to the system prompt: "You handle activities, restaurants, and events ONLY. If the query asks about hotels or flights, respond with: 'That is outside my domain. The accommodation or transport specialist will handle that.'"

08 · Complete Multi-Agent Evaluation Script

Putting It All Together:
The Multi-Agent Evaluation Pipeline

multi_agent_evaluation.py

import pytest
from langchain_core.messages import HumanMessage
from langchain_anthropic import ChatAnthropic
from langchain_core.output_parsers import JsonOutputParser

llm = ChatAnthropic(model="claude-haiku-4-5-20251001")

SPECIALIST_TOOLS = {
    "accommodation": {"hotel_search", "bb_search", "book_accommodation"},
    "transport":     {"flight_search", "local_transport", "car_rental"},
    "experience":    {"activity_search", "restaurant_search", "events_search"},
}

# ── Specialist Isolation Tests ────────────────────────────────
def test_specialist_isolation(specialist_name: str, agent, test_cases: list[dict]) -> dict:
    allowed = SPECIALIST_TOOLS[specialist_name]
    results = []
    for tc in test_cases:
        result = agent.invoke({"messages": [HumanMessage(content=tc["query"])],
                               "iteration": 0})
        tool_calls = {tc["name"] for msg in result["messages"]
                      if hasattr(msg, "tool_calls") for tc in msg.tool_calls}
        out_of_domain = tool_calls - allowed
        results.append({"query": tc["query"], "out_of_domain": out_of_domain,
                        "pass": not out_of_domain and (tc.get("should_refuse", False)
                                                     == (not bool(tool_calls)))})
    pass_rate = sum(1 for r in results if r["pass"]) / len(results)
    confusion = sum(len(r["out_of_domain"]) for r in results)
    return {"specialist": specialist_name, "pass_rate": pass_rate,
            "confusion_calls": confusion, "per_query": results}

# ── Routing Accuracy ──────────────────────────────────────────
def evaluate_routing(routing_fn, routing_test_set: list[dict]) -> dict:
    correct, partial, wrong = 0, 0, 0
    for tc in routing_test_set:
        actual = set(routing_fn(tc["query"]))
        expected = set(tc["expected_specialists"])
        if actual == expected: correct += 1
        elif actual & expected: partial += 1  # some overlap
        else: wrong += 1
    n = len(routing_test_set)
    return {"exact_accuracy": correct/n, "partial_rate": partial/n,
            "wrong_rate": wrong/n}

# ── Synthesis Quality Judge ───────────────────────────────────
SYNTH_JUDGE = """Rate this synthesis 1-5.
Specialist results: {results}
Synthesized response: {synthesis}

Criteria: (1) includes all specialist results, (2) no contradictions,
(3) coherent narrative, (4) no dropped information.
Output JSON: {"score": 1-5, "missing": [...], "reason": "..."}"""

def score_synthesis(specialist_results: dict, synthesis: str) -> dict:
    from langchain_core.prompts import ChatPromptTemplate
    chain = ChatPromptTemplate.from_messages([("human", SYNTH_JUDGE)]) | llm | JsonOutputParser()
    return chain.invoke({"results": str(specialist_results), "synthesis": synthesis})
09 · Assessment

Module 7 Quiz

1. You run end-to-end tests on your multi-agent travel system and get 85% task completion rate. You assume the system is working well and ship it. Two weeks later, users report that "plan my full trip" queries always miss restaurant recommendations. What went wrong with your evaluation?

Correct. This is the test set stratification failure. An 85% overall TCR can hide systematic failures in specific query categories if those categories are underrepresented. "Full trip" queries requiring all 3 specialists may represent only 5-10 queries in a 200-query test set. If the specialist dispatch for experience is broken for this query type, those 5-10 queries fail but do not visibly impact the aggregate 85%. Always report TCR broken down by specialist requirements: single-domain TCR, two-domain TCR, three-domain TCR. A 50% three-domain TCR is catastrophic even when hidden by a high overall rate.

2. Specialist A passes isolation tests with 95% accuracy. Specialist B passes with 92% accuracy. You integrate them. End-to-end TCR for queries requiring both specialists is 0.71. Why is 0.95 × 0.92 = 0.874 not the correct expected TCR?

Correct. Failure independence is the key assumption behind the product rule — and multi-agent systems violate it systematically. Specialist A's output becomes specialist B's input context (through the coordinator state). A partial failure in A (incorrect format, missing field) propagates to B, to synthesis, and to the final response. Integration testing must account for these cascading dependencies. The 0.71 vs 0.874 gap (0.164 = 16.4 percentage points) represents the coordination failure overhead — failures that only emerge from specialist interaction, not visible in isolation.

3. Your accommodation specialist has a confusion rate of 0.038 (3.8% of calls are to out-of-domain tools). Your experience specialist has a confusion rate of 0.153. What specifically does the higher experience confusion rate tell you, and what is the most likely fix?

Correct. High confusion rates indicate unclear domain boundaries in the specialist's system prompt. The experience specialist is most often triggered for multi-domain queries (where the user asks about activities alongside accommodation) — and instead of staying in its lane, it tries to answer the full query by using whatever tools seem appropriate. The fix is always the same: explicit NOT FOR instructions with examples of what to delegate. "Do NOT call hotel_search even if the user mentions a hotel" is more effective than "You handle activities only" because it names the specific tools to avoid.

4. In your LangSmith trace, you see: supervisor_node #3 outputs FINISH after dispatching to accommodation and transport specialists. The user query was "Plan a full Tokyo trip including things to do." What does this trace tell you and how do you fix it?

Correct. The LangSmith trace is the diagnostic tool for supervisor logic failures. Seeing FINISH at supervisor_node #3 after only 2 specialist dispatches for a 3-domain query is a clear signal: the supervisor's judgment of task completion is wrong. The prompt fix (few-shot examples) teaches the supervisor the correct FINISH condition for different query types. The structural fix (completeness check node) adds a validation step that runs before FINISH and blocks premature termination. The trace made what would otherwise be a mysterious quality issue into a specific, fixable prompt engineering problem.

5. You want to measure coordination overhead. Your supervisor dispatches to 1.8 specialists on average for single-domain queries (minimum: 1). What is the overhead, what is its cost at scale, and what is the fix?

Correct. Coordination overhead has a direct cost: every unnecessary specialist dispatch = one full specialist agent LLM call (1-4 seconds, $0.005-0.02). At 10,000 queries/day with 80% over-dispatch on single-domain queries (which may represent 60% of total traffic = 6,000 queries), you are wasting 4,800 specialist calls/day. The fix (supervisor prompt improvement + query complexity pre-classification) reduces this without changing the system architecture. The pre-classification approach is particularly effective: if the query is labeled "single-domain: accommodation" before reaching the supervisor, the supervisor has a strong prior toward dispatching only to the accommodation specialist.
