01 · Why Cost and Latency Are Evaluation Metrics

Quality at Any Price Is
Not a Production System

A RAG system that achieves faithfulness = 0.95 at $0.50/query is not production-viable if your business model requires $0.02/query. Cost and latency are constraints within which quality must be maximized — not afterthoughts. Measuring them rigorously lets you find the operating point on the cost-quality frontier that your business can sustain.

02 · Latency Measurement and Percentiles

p50, p95, p99: Why the Average
Hides the User Experience

Average latency is misleading. If 95% of requests take 1 second and 5% take 30 seconds, the average might be 2.5 seconds — which sounds acceptable. But 5% of users are waiting 30 seconds, which is completely unacceptable. Percentile metrics reveal the tail latency that real users experience on their worst queries.

⚠️

At 10,000 requests/day, p99 = 11.4s affects 100 users daily

At 10,000 requests/day, the p99 latency affects 100 users — every single day. If your SLA is "responses under 10 seconds," you are violating it 100 times daily. The p99 failures cluster around specific query patterns: complex multi-hop reasoning, long retrieved contexts, and agent loops. Always investigate p99 cases separately — they almost always have a specific, fixable cause (usually too many tool calls or an unusually large context). Production targets: p50 < 2s, p95 < 5s, p99 < 10s for interactive applications.

latency_profiler.py

import time, statistics, json
from functools import wraps
from dataclasses import dataclass, field

@dataclass
class LatencyTracker:
    samples: list[float] = field(default_factory=list)
    
    def record(self, latency_s: float): self.samples.append(latency_s)
    
    def percentile(self, p: float) -> float:
        if not self.samples: return 0.0
        s = sorted(self.samples)
        idx = int(len(s) * p / 100)
        return s[min(idx, len(s)-1)]
    
    def report(self) -> dict:
        return {
            "count":  len(self.samples),
            "mean":   statistics.mean(self.samples),
            "p50":    self.percentile(50),
            "p95":    self.percentile(95),
            "p99":    self.percentile(99),
            "max":    max(self.samples),
            "sla_p95": self.percentile(95) < 5.0,
            "sla_p99": self.percentile(99) < 10.0,
        }

tracker = LatencyTracker()

def timed(fn):
    """Decorator to track latency of any function."""
    @wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = fn(*args, **kwargs)
        tracker.record(time.perf_counter() - start)
        return result
    return wrapper

# Decomposed latency by pipeline stage
@dataclass
class StageLatencyTracker:
    stages: dict = field(default_factory=dict)
    
    def record_stage(self, stage: str, latency: float):
        self.stages.setdefault(stage, []).append(latency)
    
    def report(self) -> dict:
        return {stage: {
            "mean": statistics.mean(vals),
            "p95":  sorted(vals)[int(0.95*len(vals))]
        } for stage, vals in self.stages.items()}

stage_tracker = StageLatencyTracker()

async def timed_rag_pipeline(query: str, retriever, llm) -> dict:
    t0 = time.perf_counter()
    
    docs = await retriever.aretrieve(query)
    stage_tracker.record_stage("retrieval", time.perf_counter() - t0)
    
    t1 = time.perf_counter()
    response = await llm.ainvoke({"query": query, "context": docs})
    stage_tracker.record_stage("generation", time.perf_counter() - t1)
    
    tracker.record(time.perf_counter() - t0)
    return {"response": response, "total_s": time.perf_counter() - t0}

System prompt compression: the easiest 30% cost cut

Most system prompts accumulate over iterations — examples get added, edge cases get addressed, clarifications pile up. Audit your system prompt quarterly: remove examples that are no longer needed, replace verbose explanations with concise rules, and use "chain-of-density" compression to say the same thing in fewer tokens. A 847-token system prompt can typically be compressed to 300 tokens with zero quality impact — saving $0.0016/turn or $16/day at 10,000 queries.

04 · Cache Hit Rate

Semantic Caching:
The Single Biggest Cost Reduction

Semantic caching stores LLM responses for queries and returns the cached response when a new query is semantically similar to a cached one. Unlike exact caching (which only matches identical strings), semantic caching handles paraphrases. Cache hit rates of 30-50% are common in production, reducing costs by the same percentage.

Semantic cache: mechanics and worked savings calculation

How semantic caching works:
1. Query arrives: embed query → compute cosine similarity against all cached query embeddings
2. If max similarity > threshold (e.g., 0.93): return cached response (no LLM call)
3. If max similarity < threshold: call LLM → store (query_embedding, response) in cache

Example cache hits at threshold 0.93:
"What is the refund policy?" → same as cached "What is your return policy?" (similarity: 0.94) → HIT
"How do I get my money back?" → cached "What is the refund policy?" (similarity: 0.91) → MISS (too different)
"Can I return this item?" → cached "What is your return policy?" (similarity: 0.95) → HIT

05 · Cost-Quality Frontier

Finding the Operating Point
Your Business Can Sustain

The cost-quality frontier maps every configuration of your system (model choice, k, system prompt size, caching) to a (cost, quality) point. The goal is to find the point on the efficient frontier — the configuration where you cannot improve quality without increasing cost, and cannot reduce cost without reducing quality. Everything below the frontier is waste.

The efficient frontier insight: Sonnet + k=5 + cache is the sweet spot

Moving from "Claude Sonnet + k=5 + no cache" to "Claude Sonnet + k=5 + cache 0.95" saves 39% cost (from $0.023 to $0.014/session) with only 0.01 faithfulness drop (0.88 → 0.87). This is an excellent tradeoff. Moving to Haiku saves 83% cost but drops faithfulness by 0.17 — a 19% quality drop that is likely unacceptable. The cost-quality frontier reveals that the Haiku configuration is not on the efficient frontier: you can get nearly the same cost by using Sonnet + aggressive caching while maintaining much higher quality.

07 · Instrumentation Code

Tracking Cost and Latency
Across Every Production Request

cost_latency_monitor.py

import time, json
from dataclasses import dataclass, field, asdict
from langchain_anthropic import ChatAnthropic
from langchain.callbacks.base import BaseCallbackHandler

PRICING = {  # $ per 1M tokens
    "claude-haiku-4-5-20251001":   {"input": 0.80,  "output": 4.00},
    "claude-sonnet-4-20250514":  {"input": 3.00,  "output": 15.00},
    "claude-opus-4-20250514":    {"input": 15.00, "output": 75.00},
}

@dataclass
class RequestMetrics:
    session_id: str
    query: str
    model: str
    input_tokens: int = 0
    output_tokens: int = 0
    cache_hit: bool = False
    latency_s: float = 0.0
    stage_latencies: dict = field(default_factory=dict)
    
    @property
    def cost_usd(self) -> float:
        if self.cache_hit: return 0.0001  # only embedding cost
        p = PRICING.get(self.model, PRICING["claude-sonnet-4-20250514"])
        return (self.input_tokens * p["input"] + self.output_tokens * p["output"]) / 1_000_000

class CostTrackingCallback(BaseCallbackHandler):
    def __init__(self, metrics: RequestMetrics):
        self.metrics = metrics
    
    def on_llm_end(self, response, **kwargs):
        usage = response.llm_output.get("usage", {})
        self.metrics.input_tokens  += usage.get("input_tokens", 0)
        self.metrics.output_tokens += usage.get("output_tokens", 0)

def tracked_rag_call(query: str, retriever, model_name: str, session_id: str,
                       semantic_cache=None) -> dict:
    metrics = RequestMetrics(session_id=session_id, query=query, model=model_name)
    t0 = time.perf_counter()
    
    # Check semantic cache first
    if semantic_cache:
        cached = semantic_cache.lookup(query, similarity_threshold=0.95)
        if cached:
            metrics.cache_hit = True
            metrics.latency_s = time.perf_counter() - t0
            log_metrics(metrics)
            return {"response": cached, "metrics": metrics}
    
    # Retrieval stage
    t1 = time.perf_counter()
    docs = retriever.invoke(query)
    metrics.stage_latencies["retrieval"] = time.perf_counter() - t1
    
    # Generation stage
    t2 = time.perf_counter()
    cb = CostTrackingCallback(metrics)
    llm = ChatAnthropic(model=model_name, callbacks=[cb])
    response = llm.invoke([{"role": "user", "content": f"Context: {docs}

Query: {query}"}])
    metrics.stage_latencies["generation"] = time.perf_counter() - t2
    metrics.latency_s = time.perf_counter() - t0
    
    if semantic_cache: semantic_cache.store(query, response.content)
    log_metrics(metrics)
    return {"response": response.content, "metrics": metrics}

def log_metrics(m: RequestMetrics):
    print(json.dumps({
        "session": m.session_id, "cost_usd": round(m.cost_usd, 6),
        "latency_s": round(m.latency_s, 3), "cache_hit": m.cache_hit,
        "stages": m.stage_latencies
    }))

09 · Assessment

Module 9 Quiz

1. Your RAG system's mean latency is 2.1s, which seems fine. But users are complaining about slow responses. You check p99 and find it is 14.2 seconds. What does this tell you and what do you investigate?

Correct. p99 tail latency represents a systematic problem affecting a specific user population, not random noise. Users experiencing 14-second responses are the heaviest users, adversarial queries, or users asking about topics where your knowledge base has poor coverage. These are not random outliers — they have a pattern that you can diagnose and fix. Stage decomposition is the key: if p99 retrieval time is 1.2s and p99 generation time is 13.0s, the LLM is generating very long responses or iterating many times for these queries — fix the agent's iteration limit or max_tokens. If p99 retrieval is 12s, the vector search is slow for certain query types — optimize the index or add filters.

2. You implement semantic caching at threshold 0.93 and measure a 40% cache hit rate. A week later, users report getting outdated answers about product pricing that changed. What went wrong and how do you fix it?

Correct. TTL management is the most common production semantic cache failure. Without TTL, a 40% cache hit rate means 40% of responses may be arbitrarily stale. The fix requires thinking about your data's temporal properties: pricing changes daily → TTL 24h for pricing queries. API documentation updates weekly → TTL 7 days. Legal policies update monthly → TTL 30 days. Topic-aware TTL (different policies for different content categories) is more sophisticated but more correct than a single global TTL. Cache invalidation on knowledge base update is the most accurate approach but requires integration between your content management system and cache layer.

3. Your system uses Claude Opus for all queries at $0.089/session. A consultant recommends switching to Claude Haiku at $0.004/session to cut costs 95%. What evaluation do you run before making this decision?

Correct. Model replacement decisions require rigorous quality evaluation before any production change. A 95% cost reduction sounds compelling until you realize it may come with a 24% quality reduction — and in domains like customer support, legal, or medical, that quality drop translates to wrong answers with real consequences. The model cascade approach is the production-optimal solution: classify query complexity before routing (simple factual queries → Haiku, complex multi-hop → Opus), measure the quality on each tier separately, and verify that the hard queries you route to Opus actually need it. This typically achieves 60-70% cost reduction with near-zero quality regression.

4. Token budget analysis reveals your system prompt is 847 tokens. After compression, you cut it to 320 tokens. How do you verify that prompt compression did not degrade quality?

Correct. Prompt compression is a system change that requires full regression testing. Even "minor" compression can accidentally remove implicit behavioral constraints that were embedded in verbose phrasing. "Never reveal the customer's account balance in the response" compressed to "privacy" loses the specific instruction. The behavioral test suite is as important as quality metrics for prompt compression validation — quality metrics measure output correctness, behavioral tests measure whether the system still follows its operational rules. Both must pass before shipping a compressed prompt.

5. At 10,000 queries/day, you are spending $230/day on LLM costs. You want to reduce to $100/day without quality regression. Given: cache hit rate 25%, system prompt 600 tokens, k=8, using Claude Sonnet, what is the optimal set of changes to reach your target?

Correct. Cost optimization is always layered — no single lever typically achieves a 57% cost reduction without quality impact. The right approach combines multiple low-risk optimizations (prompt caching, cache hit rate improvement, system prompt compression) before reaching for higher-risk changes (model downgrade, aggressive k reduction). Testing each change independently is critical — implementing all changes simultaneously makes it impossible to attribute quality regressions to a specific change. The prompt caching lever is particularly powerful and often underutilized: Anthropic's API caches the system prompt prefix at 90% discount, which is free to implement and has zero quality risk.
