LLM-as-Judge Patterns and Calibration
Positional Bias · Verbosity · Self-Preference · Swap Consistency · Calibration

LLM-as-Judge is the highest-impact automation in modern evaluation — but it comes with systematic biases that invalidate results if not accounted for. This module covers positional bias, verbosity bias, self-preference bias, calibration protocols, single-score vs multi-dimension judging, chain-of-thought vs direct scoring, and the four design patterns that make LLM judges reliable enough for production use.

01 · Why LLM-as-Judge Works and When It Fails

The Power and the Failure Modes
of Using LLMs to Evaluate LLMs

LLM-as-Judge uses a powerful language model (the "judge") to evaluate responses generated by your system. At its best, it approximates human judgment at scale: 1,000 evaluations per hour at $5, vs 1,000 human annotations at $500-2,000. At its worst, it systematically rewards the wrong things — longer responses, more confident-sounding text, outputs similar to its own training distribution. The difference between these outcomes is the quality of judge design.

When LLM judges work well

✓ Evaluating coherence, relevance, and fluency — tasks where LLM judgment aligns with human judgment (Spearman > 0.70)
✓ Pairwise comparisons between two similar-quality responses
✓ Screening at scale to identify the 10% of responses that need human review
✓ Faithfulness checking against retrieved context (NLI-equivalent judgment)

When LLM judges fail

✗ Factual verification — judges cannot verify facts they do not know
✗ Comparing responses of very different lengths — verbosity bias corrupts results
✗ Domain-specific quality in specialized fields (medical, legal, code) without domain-specific prompting
✗ Evaluating its own outputs (self-preference bias — judges prefer outputs similar to what they would produce)
02 · The Four Systematic Biases

What LLM Judges Get Wrong
Systematically and Predictably

LLM judge biases are not random noise — they are systematic. The same response will reliably score higher when presented first (positional bias), when it is longer (verbosity bias), when it was generated by the same model family as the judge (self-preference bias), and when it sounds more confident (sycophancy bias). Each bias can be measured, quantified, and partially corrected.

Bias 1: Positional Bias — measuring and correcting

Experiment: Present the same (A, B) pair in both orders to 100 pairs.

Round 1: [Response A first, Response B second] → A wins 64/100 times
Round 2: [Response B first, Response A second] → B wins 71/100 times

Positional bias magnitude = 0.64 + 0.71 - 1.0 = 0.35
A 35pp positional bias means the position advantage accounts for 35% of outcomes — nearly as large as the actual quality difference.

Correction: Run each pair in both orders. The true win rate = (wins in order 1 + wins in order 2) / (2 × total). In this case: if A wins in order 1 AND order 2 for 43 pairs → true win rate = 43/100 = 0.43. If A wins in order 2 but not order 1 for 21 pairs → these are positional artifacts.

Bias 2: Verbosity Bias

Judges rate longer responses higher on completeness and helpfulness even when the extra content is padding. Measured: compare scores for a "short correct answer" vs the same answer padded to 3× length. If padded version scores higher → verbosity bias present.

Bias 3: Self-Preference Bias

A Claude judge prefers Claude outputs by 5-15pp compared to GPT-4 outputs of equivalent quality. An OpenAI judge shows the reverse. Always use a judge from a different provider or family than the system being evaluated when possible.

Bias 4: Sycophancy Bias

Judges give higher scores to responses that include confident-sounding phrases ("Based on my analysis...", "Clearly...") vs the same content with hedged language ("I believe...", "It appears..."). Confident wrong answers score higher than uncertain correct ones.

03 · Swap Consistency Test

Detecting and Measuring
Positional Bias Systematically

The swap consistency test is the standard protocol for quantifying positional bias in a pairwise judge. Run every evaluation pair twice with swapped positions. A consistent judge should flip its preference when positions are swapped (if A was better in order 1, B is placed first in order 2 — the judge should still recognize A as better). Inconsistency = positional bias.

Swap consistency: worked calculation

Run N=100 pairs in both orders. Classify each pair:

Consistent-A: Judge picks A in both orderings = 35 pairs → genuinely prefers A
Consistent-B: Judge picks B in both orderings = 28 pairs → genuinely prefers B
Inconsistent (positional artifact): Judge picks first response regardless = 29 pairs
Consistent-Tie: Judge ties in both orderings = 8 pairs

0.29

35/(35+28+8) = 0.56 (not 0.64)

before trusting the judge

swap_consistency_test.py

from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

PAIRWISE_JUDGE = ChatPromptTemplate.from_messages([("system", """
Compare these two responses. Which is more helpful for the user's query?
Output JSON: {"winner": "A"|"B"|"tie", "reason": "one sentence", "confidence": "high"|"medium"|"low"}
Do NOT let response length influence your judgment.
"""), ("human", """Query: {query}
Response A: {response_a}
Response B: {response_b}""")])
judge_chain = PAIRWISE_JUDGE | llm | JsonOutputParser()

def swap_consistency_test(test_pairs: list[dict]) -> dict:
    """
    Run each pair in both orders and measure positional bias.
    test_pairs: [{"query": ..., "response_a": ..., "response_b": ...}]
    """
    consistent_a, consistent_b, inconsistent, tied = 0,0,0,0
    
    for pair in test_pairs:
        # Order 1: A first
        r1 = judge_chain.invoke({"query": pair["query"],
            "response_a": pair["response_a"], "response_b": pair["response_b"]})
        # Order 2: B first (swap)
        r2 = judge_chain.invoke({"query": pair["query"],
            "response_a": pair["response_b"], "response_b": pair["response_a"]})
        
        w1 = r1["winner"]
        w2 = "B" if r2["winner"]=="A" else ("A" if r2["winner"]=="B" else "tie")  # unswap
        
        if   w1=="A"   and w2=="A":   consistent_a += 1
        elif w1=="B"   and w2=="B":   consistent_b += 1
        elif w1=="tie" and w2=="tie": tied        += 1
        else:                              inconsistent += 1
    
    n = len(test_pairs)
    bias_rate = inconsistent / n
    consistency_rate = (consistent_a + consistent_b + tied) / n
    return {
        "consistency_rate": consistency_rate,
        "positional_bias_rate": bias_rate,
        "judge_reliable": consistency_rate > 0.80,
        "true_win_rate_a": consistent_a / (consistent_a + consistent_b + tied) if (consistent_a+consistent_b+tied) > 0 else 0
    }

05 · Reference-Guided Judging

Anchoring the Judge
to a Known-Good Answer

Reference-guided judging provides the judge with a gold standard reference answer alongside the two responses being compared. Instead of comparing A vs B (which is susceptible to positional and self-preference bias), the judge compares both A and B against the reference independently. The response closer to the reference wins. This approach is more reliable but requires a reference annotation for each query.

reference_guided_judge.py

from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser

REF_JUDGE = ChatPromptTemplate.from_messages([("system", """
You are an expert evaluator. Compare each response to the reference answer.
Score each response 1-5 on:
  Accuracy: How many key facts from the reference are covered correctly?
  Completeness: What fraction of the reference content is included?

Output JSON:
{"response_a": {"accuracy": 1-5, "completeness": 1-5, "overall": 1-5},
 "response_b": {"accuracy": 1-5, "completeness": 1-5, "overall": 1-5},
 "better": "A"|"B"|"tie"}

Reference answer (ground truth): {reference}
"""),
("human", """Query: {query}
Response A: {response_a}
Response B: {response_b}""")])

ref_judge = REF_JUDGE | ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0) | JsonOutputParser()

def reference_guided_compare(query: str, response_a: str, response_b: str, reference: str) -> dict:
    result = ref_judge.invoke({
        "query": query, "response_a": response_a,
        "response_b": response_b, "reference": reference
    })
    # Also run swapped for position robustness
    result_swapped = ref_judge.invoke({
        "query": query, "response_a": response_b,  # swapped
        "response_b": response_a, "reference": reference
    })
    # Winner must win in both orderings
    winner_1 = result["better"]
    winner_2 = "B" if result_swapped["better"]=="A" else ("A" if result_swapped["better"]=="B" else "tie")
    consistent_winner = winner_1 if winner_1 == winner_2 else "inconsistent"
    return {"order1": result, "order2_unswapped": result_swapped,
            "consistent_winner": consistent_winner}
06 · Calibration Protocol for LLM Judges

Validating Your Judge Before
Trusting It at Scale

Before using an LLM judge on thousands of responses, validate it against human judgments on a calibration set. A judge with Spearman correlation < 0.60 against human ratings is not reliable enough for production decisions — no matter how fast or cheap it is.

Judge calibration: 5-step protocol

01
Sample 200 examples from your test set, stratified across quality levels (40 poor, 60 fair, 60 good, 40 excellent). Stratification ensures all score levels are calibrated, not just the typical distribution.
02
Get 3 human annotators to rate each example with your rubric. Compute Fleiss' kappa — if < 0.60, improve the rubric before proceeding. Average human ratings to get ground truth.
03
Run your LLM judge on all 200 examples with the same rubric. For stability: run 3 times and average scores. Compute Spearman correlation between judge scores and human ground truth.
04
Analyze systematic errors: Find examples where judge and human disagree by 2+ points. These reveal prompt design issues. Typical findings: judge rates verbose wrong answers too high, judge ignores completeness in short correct answers.
05
Iterate prompt: Add few-shot examples of the failure cases to the judge prompt. Re-run calibration. Accept when Spearman > 0.70. This typically requires 2-3 iteration cycles.
07 · Production-Grade Judge Prompt

The Complete Judge Prompt
With All Bias Mitigations

production_judge.py — complete implementation

from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser
import statistics

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

PRODUCTION_JUDGE_PROMPT = """
You are an expert AI system evaluator. Your task is to rate an AI response.

CRITICAL INSTRUCTIONS:
1. Base your rating ONLY on content quality — NOT on response length.
   A short correct answer is better than a long incorrect one.
2. Think step by step before scoring.
3. Use the full 1-5 scale — avoid clustering all scores at 3-4.

DIMENSIONS (rate each independently):

FAITHFULNESS (1-5): Are all factual claims in the response supported by the context?
  5: Every claim traceable to context. No additions from outside context.
  4: One minor unsupported detail, all key claims supported.
  3: One significant unsupported claim.
  2: Multiple significant hallucinated claims.
  1: Mostly hallucinated or actively contradicts context.

RELEVANCE (1-5): Does the response address the specific question?
  5: Directly and completely answers the question asked.
  4: Mostly on-topic with minor tangential content.
  3: Partially answers the question.
  2: Mentions the topic but does not answer the question.
  1: Does not address the question at all.

COMPLETENESS (1-5): Does the response cover all aspects of the question?
  5: All aspects fully addressed, no relevant information omitted.
  4: One minor aspect missing.
  3: Some aspects covered, significant gaps.
  2: Only superficial coverage.
  1: Misses the core of the question entirely.

REASONING TRACE: Before scoring, for each dimension:
  1. Quote specific phrases from the response (max 20 words each).
  2. State whether each phrase supports or hurts the dimension score.
  3. Assign score.

Output JSON:
{"faithfulness": {"evidence": [...], "score": 1-5},
 "relevance": {"evidence": [...], "score": 1-5},
 "completeness": {"evidence": [...], "score": 1-5},
 "overall": 1-5}

Context provided: {context}
"""

judge_prompt = ChatPromptTemplate.from_messages([
    ("system", PRODUCTION_JUDGE_PROMPT),
    ("human", "Question: {question}
Response to evaluate: {response}")
])
judge_chain = judge_prompt | llm | JsonOutputParser()

def stable_judge_score(question: str, response: str, context: str, runs: int = 3) -> dict:
    """Run judge N times and average for stability."""
    all_runs = []
    for _ in range(runs):
        result = judge_chain.invoke({"question": question, "response": response, "context": context})
        all_runs.append(result)
    
    dims = ["faithfulness", "relevance", "completeness"]
    averaged = {}
    for dim in dims:
        scores = [r[dim]["score"] for r in all_runs]
        averaged[dim] = {"mean": statistics.mean(scores), "stdev": statistics.stdev(scores) if runs>1 else 0}
    averaged["overall"] = statistics.mean(averaged[d]["mean"] for d in dims)
    averaged["high_variance"] = any(averaged[d]["stdev"] > 1.0 for d in dims)
    return averaged  # high_variance=True → flag for human review

09 · Assessment

Module 11 Quiz

1. You run a pairwise study with Claude as judge comparing two response sets. System A (generated by Claude Sonnet) wins 63% of pairs vs System B (generated by GPT-4o). Should you conclude System A is better?

Correct. Self-preference bias is a documented, systematic effect in LLM-as-judge evaluation. Claude prefers Claude outputs; GPT-4 prefers GPT-4 outputs. A 63% win rate with Claude judging Claude vs GPT-4 may be entirely explained by self-preference bias — especially if the true quality difference is small. The multi-judge ensemble approach (Claude + GPT-4 + Gemini) cancels out individual provider biases. If all three judges agree A is better, the result is much more trustworthy than a single judge from the same provider as the evaluated system.

2. You implement a CoT judge that requires reasoning before scoring. The scores are more consistent, but the judge now always gives verbose responses scores of 4-5 and short responses scores of 2-3 regardless of content. What is happening?

Correct. CoT reasoning does not automatically eliminate verbosity bias — it can actually make the bias more systematic by providing the judge with a structured reasoning process that consistently references length. The CoT trace is useful precisely because it reveals this: the judge is explaining how it is applying verbosity as a completeness proxy. Calibration examples that explicitly violate the length-quality correlation are the most effective fix: force the judge to rate a short-but-complete answer as 5/5 and a long-but-incomplete answer as 2/5, with explicit rubric text saying "length does not determine completeness."

3. Your swap consistency test shows 0.55 consistency rate (55% of pairs produce the same winner in both orderings). Should you use this judge for a major model evaluation?

Correct. A consistency rate of 0.55 is dangerously close to the 0.50 you would get from a judge that randomly picks the first response every time (which would also give 0% consistency in the swap test since it always picks A in order 1 and B in order 2). The judge is barely more than random in its positional behavior. Statistical correction cannot fix this: if 45% of judgments are positional artifacts, correcting for them still leaves huge uncertainty about whether the remaining 55% are reliable quality judgments. The judge prompt must be revised and re-validated before any consequential model comparison.

4. You compute Spearman correlation between your LLM judge and 3 human annotators on 200 examples and get 0.48. You increase the judge's chain-of-thought verbosity and re-calibrate. The correlation improves to 0.64. Is the judge now ready for production?

Correct. Holdout validation is critical when iterating on a judge prompt against calibration data. Without a fresh holdout, you cannot distinguish genuine improvement (the judge is actually better) from overfitting (the prompt was optimized to score well on the specific 200 examples used, but will not generalize). This is identical to the train/test split principle in ML: calibration set is for development, holdout set is for final evaluation. A judge that achieves 0.64 on the calibration set may achieve 0.55 on a fresh holdout — which is not production-ready. Always validate on held-out data before concluding the judge is reliable.

5. You want to evaluate 50,000 responses per day for quality. You need reliability comparable to human judgment. What judge architecture do you recommend and why?

Correct. Evaluation at 50K responses/day requires a tiered architecture because no single approach achieves both coverage and depth within practical cost constraints. A Sonnet G-Eval on all 50K would cost ~$750/day ($0.015/response) for coverage that adds limited value on the 90% of responses that are clearly fine. The tier-1 fast screen directs evaluation effort where it matters most (the bottom 10%). This is the production evaluation pattern used by teams at scale: fast automated screening for 100% coverage, deep automated evaluation for flagged cases, human review for the long tail. Monthly calibration of tier-1 against tier-2 ensures the screening threshold remains accurate as response distribution shifts.
