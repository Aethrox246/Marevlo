01 · BLEU Score

Bilingual Evaluation Understudy:
N-Gram Precision, Step by Step

BLEU measures how many n-grams (sequences of N consecutive words) in the generated text also appear in the reference text. It was designed for machine translation in 2002 and remains widely used — often incorrectly, on tasks it was never designed for. Understanding its exact calculation reveals both its power and its severe limitations.

BLEU calculation: a worked example with real numbers

Inputs

Reference: "The refund policy allows cancellations within thirty days"
Hypothesis: "Cancellations are permitted within thirty days under the refund policy"

Step 1: Count n-gram matches

1-gram precision: 7/8 words match = 0.875 (refund✓ policy✓ cancellations✓ within✓ thirty✓ days✓ under? allows?)
2-gram precision: 3/7 bigrams match = 0.429 ("within thirty"✓, "thirty days"✓, "the refund"✓)
3-gram precision: 2/6 = 0.333
4-gram precision: 1/5 = 0.200
Step 2: Brevity penalty (BP)
Hypothesis length = 9, Reference length = 9 → BP = 1.0 (no penalty)

Step 3: BLEU-4 = BP × exp(0.25 × Σ log(pₙ))
= 1.0 × exp(0.25 × (log(0.875) + log(0.429) + log(0.333) + log(0.200)))
= 1.0 × exp(0.25 × (-0.133 + (-0.846) + (-1.099) + (-1.609)))
= 1.0 × exp(0.25 × (-3.687))
BLEU-4 = 1.0 × exp(-0.922) = 0.398

Interpretation: 0.40 is considered "good" for MT. Both sentences convey the same meaning.
❌ BLEU fails on this valid paraphrase
Reference: "Annual subscriptions cannot be refunded after thirty days"
Hypothesis: "You cannot get your money back on a yearly plan once a month has passed"
BLEU-4 = 0.07 — near zero despite perfect semantic equivalence.
Zero word overlap: "money back" ≠ "refunded", "yearly" ≠ "annual", "once a month has passed" ≠ "after thirty days"
✓ BLEU works well here
Reference: "Turn left at the traffic light"
Hypothesis: "At the traffic light, turn left"
BLEU-4 = 0.72 — high n-gram overlap, same meaning, same vocabulary.
Machine translation with similar source vocabulary: BLEU correlates well with human judgment here.
⚠️

When BLEU lies to you

BLEU was designed and validated for machine translation between close languages (English↔French). It assumes: (1) similar vocabulary between output and reference, (2) no valid paraphrases, (3) a short, complete answer. It fails for: open-ended QA, conversational responses, abstractive summarization, and any domain where paraphrasing is expected. Do not use BLEU as your primary metric for RAG or agent evaluation.

02 · ROUGE

ROUGE-1, ROUGE-2, ROUGE-L:
Recall-Oriented Evaluation for Summarization

ROUGE (Recall-Oriented Understudy for Gisting Evaluation) measures how much of the reference text appears in the generated text — it emphasizes recall over precision. Three variants exist: ROUGE-1 (unigram overlap), ROUGE-2 (bigram overlap), and ROUGE-L (longest common subsequence). Each captures different aspects of quality.

ROUGE variants: worked example

Reference summary: "The company reported record profits of $2.3B in Q3 driven by cloud services growth"
Generated summary: "Cloud services drove record Q3 profits of $2.3B for the company"
0.85
ROUGE-1 F1
11/13 words from reference appear in hypothesis
0.54
ROUGE-2 F1
5/12 bigrams match: "record profits", "$2.3B in", "the company", "driven by"...
0.77
ROUGE-L F1
LCS = "record profits 2.3B cloud services" = 6 tokens
💡

Which ROUGE variant to use?

ROUGE-1 is the most commonly reported single number. ROUGE-2 is more discriminative — bigram overlap captures phrase-level quality. ROUGE-L captures sentence structure. For summarization evaluation, report all three (ROUGE-1 R, ROUGE-2 R, ROUGE-L F) to give a complete picture. ROUGE-2 > 0.15 is generally considered acceptable; > 0.25 is strong for abstractive summarization.

rouge_evaluation.py

from rouge_score import rouge_scorer

scorer = rouge_scorer.RougeScorer(
    ['rouge1', 'rouge2', 'rougeL'],
    use_stemmer=True  # stemming: "running" matches "run"
)

reference = "The company reported record profits of $2.3B in Q3 driven by cloud services growth"
hypothesis = "Cloud services drove record Q3 profits of $2.3B for the company"

scores = scorer.score(reference, hypothesis)

for metric, score in scores.items():
    print(f"{metric}: P={score.precision:.3f} R={score.recall:.3f} F1={score.fmeasure:.3f}")

# Output:
# rouge1: P=0.917 R=0.786 F1=0.846
# rouge2: P=0.583 R=0.500 F1=0.538
# rougeL: P=0.833 R=0.714 F1=0.769

# Batch evaluation on a test set
def batch_rouge(predictions: list[str], references: list[str]) -> dict:
    all_scores = {m: [] for m in ['rouge1', 'rouge2', 'rougeL']}
    for pred, ref in zip(predictions, references):
        s = scorer.score(ref, pred)
        for m in all_scores: all_scores[m].append(s[m].fmeasure)
    return {m: sum(v)/len(v) for m, v in all_scores.items()}

03 · BERTScore

Semantic Similarity via
Contextual Embeddings

BERTScore fixes the core flaw in BLEU and ROUGE: it does not require word-level overlap. Instead it embeds every token in both the hypothesis and reference using BERT, then computes cosine similarities between all token pairs. "Refunded" and "money back" get high similarity because they share embedding space — even though they share zero characters.

BERTScore: step-by-step for the same paraphrase that broke BLEU

Reference: "Annual subscriptions cannot be refunded after thirty days"
Hypothesis: "You cannot get your money back on a yearly plan once a month has passed"
BLEU-4 = 0.07 (word overlap fails completely) vs BERTScore F1 = 0.81 (semantic similarity succeeds)

How: for each token in the hypothesis, BERTScore finds the reference token with the highest cosine similarity in embedding space. "money back" → "refunded" (similarity ~0.85). "yearly" → "annual" (similarity ~0.91). "once a month has passed" → "after thirty days" (similarity ~0.77). The average of these maximum similarities gives the recall score; averaging from reference→hypothesis gives precision.

bertscore_evaluation.py

from bert_score import score as bertscore

# Single pair
reference = ["Annual subscriptions cannot be refunded after thirty days"]
hypothesis = ["You cannot get your money back on a yearly plan once a month has passed"]

P, R, F1 = bertscore(
    hypothesis, reference,
    model_type="microsoft/deberta-xlarge-mnli",  # best model for English
    lang="en",
    verbose=True
)

print(f"Precision: {P.mean().item():.3f}")   # → 0.783
print(f"Recall:    {R.mean().item():.3f}")   # → 0.843
print(f"F1:        {F1.mean().item():.3f}")   # → 0.812

# Batch evaluation
def bert_score_batch(preds: list[str], refs: list[str]) -> dict:
    P, R, F = bertscore(preds, refs, lang="en")
    return {
        "precision": P.mean().item(),
        "recall":    R.mean().item(),
        "f1":        F.mean().item(),
        "per_sample_f1": F.tolist()  # score per example
    }

# BERTScore thresholds (DeBERTa-xlarge-mnli):
# F1 > 0.85: very similar meaning
# F1 0.75-0.85: related, some divergence
# F1 < 0.70: substantially different
⚠️

When BERTScore lies to you

BERTScore is not reliable when: (1) evaluating factual precision — "The accident killed 3 people" and "The accident killed 300 people" have high BERTScore (similar structure) but wildly different factual content; (2) evaluating code — token similarities in code embedding space do not reflect functional equivalence; (3) very short answers — a 2-word answer gets a high similarity to any 2-word answer in embedding space. BERTScore measures semantic similarity, not factual accuracy.

04 · METEOR

Beyond n-gram Overlap:
Stemming, Synonyms, and Recall

METEOR (Metric for Evaluation of Translation with Explicit ORdering) improves on BLEU by: (1) matching word stems ("running" matches "run"), (2) matching synonyms ("automobile" matches "car"), (3) weighting recall as importantly as precision, and (4) applying a chunk penalty that rewards word-order preservation. It correlates better with human judgment than BLEU on most tasks.

METEOR matching stages (in order)

Stage 1: Exact match

"profit" in hypothesis matches "profit" in reference exactly.

Stage 2: Stem match

"reported" in hypothesis matches "reporting" in reference via Porter stemmer (both → "report").

Stage 3: Synonym match

"yearly" in hypothesis matches "annual" in reference via WordNet synonyms.

Stage 4: Paraphrase match (METEOR 1.5+)

"get your money back" → "refund" matched via paraphrase tables.

METEOR vs BLEU on the same examples

05 · Perplexity

How Surprised Is the Model?
Intrinsic Fluency Measurement

Perplexity measures how confidently a language model predicts a text token-by-token. Lower perplexity means the model finds the text "less surprising" — the text is more consistent with patterns in training data. It measures fluency intrinsically (without a reference), but says nothing about factual accuracy.

Perplexity: the intuition with real numbers

Low perplexity (fluent) — does not mean correct

PPL = 12 ✓ Fluent + Correct
"The refund window is 30 days for all subscription tiers."
PPL = 14 ⚠ Fluent + Wrong
"The refund window is 90 days for all subscription tiers." (HALLUCINATION — but fluent)

High perplexity (disfluent) — does not mean wrong

PPL = 156 ✗ Disfluent + Wrong
"Refund the after thirty days subscription cannot annual is"
PPL = 89 ≠ Uncommon but correct
"The 30-day refund window applies to annual SKU-4892 subscribers only." (technical jargon → higher PPL)
⚠️

The fundamental limitation: confident hallucinations have LOW perplexity

A model that hallucinates fluently scores better on perplexity than a model that correctly expresses uncertainty. "The capital of France is London" has lower perplexity than "I believe the capital might be Paris, though I cannot verify this." Perplexity rewards stylistic consistency with training data, not factual accuracy. Never use perplexity as a proxy for correctness in RAG or factual QA evaluation.

perplexity_evaluation.py

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

def compute_perplexity(text: str, model_name: str = "gpt2") -> float:
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModelForCausalLM.from_pretrained(model_name)
    model.eval()
    
    encodings = tokenizer(text, return_tensors="pt")
    input_ids = encodings.input_ids
    
    with torch.no_grad():
        outputs = model(input_ids, labels=input_ids)
        loss = outputs.loss  # mean cross-entropy per token
    
    perplexity = torch.exp(loss).item()
    return perplexity

# Compare two model outputs
correct = "The refund window is 30 days for all subscription tiers."
hallucinated = "The refund window is 90 days for all subscription tiers."
incoherent = "Refund the after thirty days subscription cannot annual is"

print(f"Correct:      PPL = {compute_perplexity(correct):.1f}")      # ~12
print(f"Hallucinated: PPL = {compute_perplexity(hallucinated):.1f}")  # ~14 (nearly same!)
print(f"Incoherent:   PPL = {compute_perplexity(incoherent):.1f}")    # ~156

# Practical use: compare model checkpoints on a domain corpus
# Lower PPL on YOUR domain text → model better fits your vocabulary
# Use for: LLM selection, not quality evaluation of individual outputs
06 · Exact Match and F1-Token

Binary Correctness and
Token-Level Overlap for QA

Exact Match (EM) is the strictest metric: 1 if the generated answer exactly matches the reference (after normalization), 0 otherwise. Token-Level F1 is a softer version: it computes precision and recall of individual tokens between the hypothesis and reference. Both are standard for extractive QA benchmarks like SQuAD.

Worked example: SQuAD-style evaluation

Question: "How long is the refund window?"
Reference answer: "thirty days"
Hypothesis: "thirty days" → EM=1 | Token F1=1.00 ✓ Perfect
Hypothesis: "30 days" → EM=0 | Token F1=0.67 (after normalization: "30"≠"thirty" but "days" matches)
Hypothesis: "the refund window is thirty days long" → EM=0 | Token F1=0.50 (extra words reduce precision)
Hypothesis: "one month" → EM=0 | Token F1=0.00 (semantically correct, lexically zero)

Token F1 calculation

def normalize(text): # SQuAD normalization import re, string text = text.lower() text = re.sub(r"(a|an|the)", " ", text) text = "".join(c for c in text if c not in string.punctuation) text = " ".join(text.split()) return text def token_f1(pred: str, ref: str) -> float: pred_tokens = normalize(pred).split() ref_tokens = normalize(ref).split() common = set(pred_tokens) & set(ref_tokens) if not common: return 0.0 prec = len(common) / len(pred_tokens) rec = len(common) / len(ref_tokens) return 2 * prec * rec / (prec + rec) def exact_match(pred: str, ref: str) -> int: return int(normalize(pred) == normalize(ref)) # "thirty days" vs "30 days" print(exact_match("30 days", "thirty days")) # → 0 print(token_f1("30 days", "thirty days")) # → 0.667
07 · Side-by-Side Metric Comparison

Choosing the Right Metric
for Your Task

No single metric is universally best. The right choice depends on your task type, whether you have reference answers, and what failure modes matter most for your application.

MetricNeeds reference?Captures paraphrase?Captures facts?Best taskDo NOT use for
BLEUYesNo — word overlap onlyNoMachine translationOpen-ended QA, summarization
ROUGE-1/2/LYesNo — word overlapNoExtractive summarizationAbstractive generation, dialogue
METEORYesPartial (stem+synonym)NoTranslation, captionsLong-form generation, multi-hop QA
BERTScoreYesYes — embedding spaceNo (number errors missed)Open-ended QA, summariesCode, numeric precision tasks

💡

The recommendation: BERTScore for most GenAI evaluation, supplemented by human or LLM judge

For modern GenAI applications (RAG, chatbots, agents), BERTScore is the most appropriate reference-based metric because it handles paraphrase. But reference-based metrics alone are not enough — they require gold answers (expensive) and still cannot catch hallucination (BERTScore does not verify facts). For production RAG, use: BERTScore for semantic similarity, RAGAS Faithfulness for grounding, and LLM-as-judge for overall quality. Each covers the blind spots of the others.

08 · Production Evaluation Pipeline

Running All Metrics at Once
on a Test Set

llm_output_evaluation.py — complete pipeline

from rouge_score import rouge_scorer
from bert_score import score as bertscore
from nltk.translate.bleu_score import sentence_bleu, SmoothingFunction
from nltk.tokenize import word_tokenize
import json, statistics

def evaluate_outputs(
    predictions: list[str],
    references: list[str],
    include_bertscore: bool = True
) -> dict:
    """
    Run BLEU, ROUGE, BERTScore on a test set.
    Returns dict with all metrics + per-sample scores.
    """
    smoother = SmoothingFunction().method1
    rouge = rouge_scorer.RougeScorer(['rouge1','rouge2','rougeL'], use_stemmer=True)
    
    results = {'bleu':[], 'rouge1':[], 'rouge2':[], 'rougeL':[]}
    
    for pred, ref in zip(predictions, references):
        # BLEU
        ref_tokens = [word_tokenize(ref.lower())]
        pred_tokens = word_tokenize(pred.lower())
        results['bleu'].append(
            sentence_bleu(ref_tokens, pred_tokens, smoothing_function=smoother)
        )
        # ROUGE
        r = rouge.score(ref, pred)
        results['rouge1'].append(r['rouge1'].fmeasure)
        results['rouge2'].append(r['rouge2'].fmeasure)
        results['rougeL'].append(r['rougeL'].fmeasure)
    
    summary = {k: statistics.mean(v) for k, v in results.items()}
    
    if include_bertscore:
        P, R, F = bertscore(predictions, references, lang="en")
        summary['bertscore_f1'] = F.mean().item()
        results['bertscore_f1'] = F.tolist()
    
    # Find worst-performing examples
    bleu_with_idx = sorted(enumerate(results['bleu']), key=lambda x: x[1])
    summary['worst_5_bleu'] = [
        {'idx': i, 'score': s, 'pred': predictions[i], 'ref': references[i]}
        for i, s in bleu_with_idx[:5]
    ]
    
    return {'summary': summary, 'per_sample': results}

# Example usage:
preds = [
    "The refund window is 30 days.",
    "Cloud services drove record Q3 profits.",
    "You cannot cancel a yearly plan after one month.",
]
refs = [
    "The refund window is thirty days for all tiers.",
    "The company reported record profits in Q3 driven by cloud services growth.",
    "Annual subscriptions cannot be refunded after thirty days.",
]

report = evaluate_outputs(preds, refs)
print(json.dumps(report['summary'], indent=2))
# {
#   "bleu": 0.312, "rouge1": 0.634, "rouge2": 0.378,
#   "rougeL": 0.589, "bertscore_f1": 0.841
# }
09 · Assessment

Module 1 Quiz

1. Your RAG system generates "You cannot get your money back on a yearly plan once a month has passed" as the answer to a refund question. The reference is "Annual subscriptions cannot be refunded after thirty days." BLEU-4 = 0.07. What does this tell you, and what metric should you use instead?

Correct. This is the canonical BLEU failure case: correct paraphrase with zero vocabulary overlap. BLEU penalizes this maximally because its n-gram matching is purely lexical — "yearly" and "annual" share no characters. BERTScore handles this by computing cosine similarities in embedding space where synonyms are close together. METEOR handles it via WordNet synonym lookup. Neither penalizes a correct paraphrase as harshly as BLEU.

2. You measure perplexity on your chatbot's outputs and get an average of 18, which is low (fluent). A user reports the chatbot confidently told them the refund window is 90 days (the actual window is 30 days). How does perplexity miss this failure?

Correct. Perplexity is blind to factual accuracy. The number "90" is no more surprising than "30" in the sentence frame "The refund window is __ days." Both are common numbers following "is" in a temporal context. The model's training data contains many valid sentences with both numbers. Confident hallucinations often have lower perplexity than hedged correct answers because "I am confident the answer is X" is more fluent than "I believe it might be X though I cannot be certain."

3. You compute BERTScore F1 = 0.91 comparing two financial summaries: "The accident injured 3 workers" vs reference "The accident injured 300 workers." Why does BERTScore fail here?

Correct. This is BERTScore's most dangerous failure mode: numbers. "3" and "300" in BERT embedding space are neighbors — they frequently appear in the same syntactic contexts (quantifying nouns, following "approximately", etc.). The embedding model was not trained to distinguish their different values. For any evaluation where numeric precision matters — financial figures, medical quantities, dates, statistics — BERTScore is unreliable. Use exact match on numeric spans or a specialized verification step.

4. For which task would ROUGE-L be the most appropriate primary metric? Explain why.

Correct. ROUGE-L is designed for extractive summarization because the LCS metric specifically rewards preserving the sequential structure of the source text. An extractive summary that copies key sentences from the source will have high LCS overlap with the reference summary (which was also extracted from the same source). This property makes ROUGE-L useless for abstractive summarization, where rewriting in different vocabulary is the goal and would be penalized.

5. You are building a benchmark for a RAG system's QA accuracy. The test set has 500 questions with gold answers. A colleague suggests using only Exact Match. What is the problem and what additional metric would you combine it with?

Correct. EM's strictness is its main limitation for modern QA systems. A system that correctly says "thirty days" when the reference says "30 days" gets EM=0 despite being correct. A system that correctly says "customers can request a refund" when the reference says "refunds are available to customers" gets EM=0. The three-metric combination is standard: EM for strict correctness, Token F1 for partial credit, BERTScore for semantic similarity. Low EM + high BERTScore = the system is correct but paraphrasing. Low EM + low BERTScore = actual quality failure.
