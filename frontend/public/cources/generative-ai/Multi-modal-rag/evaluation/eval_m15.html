01 · Why Evaluation Must Be Continuous

Every Code Change Is a Risk:
Automated Gates That Never Sleep

A prompt change, a library update, an LLM provider model refresh, a new chunk in the knowledge base — any of these can silently degrade your system's quality. Manual evaluation before releases catches some regressions. But LLM providers update models silently. Library dependencies change behavior. Knowledge base updates shift retrieval distributions. The only protection against silent degradation is continuous automated evaluation that runs on every change and samples production traffic daily.

What continuous evaluation catches that manual review misses

Silent model updates: LLM providers update models without announcing it. Faithfulness can drop 0.05 overnight. Only daily eval catches this.
Dependency regressions: langchain 0.3.1 → 0.3.2 changes prompt formatting. System prompt truncated. Faithfulness drops. CI catches it on the version bump PR.
Knowledge base drift: New document added with conflicting information changes retrieval distribution. Context Precision drops on affected query cluster.
Query distribution shift: Users start asking new types of questions not in the eval set. Production monitoring with 10% sampling catches this 2-3 weeks before it becomes a user complaint pattern.

The three CI/CD evaluation layers

Layer 1: Per-PR gate (30-90 seconds)

Behavioral assertions on 20 critical test cases. Fails if any assertion breaks. Blocks PR merge.

Layer 2: On-merge quality gate (8-12 minutes)

Full RAGAS on 200-query eval set. Fails if any metric drops >0.05 from baseline. Blocks deployment.

Layer 3: Production monitoring (daily)

10% traffic sample → LLM judge → alert if 7-day rolling average drops >0.05. Catches silent degradation.

02 · GitHub Actions CI Workflow

Complete Working Workflow:
Behavioral Tests on Every PR

.github/workflows/llm-eval.yml

name: LLM Evaluation Gate

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]

env:
  ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  LANGCHAIN_API_KEY: ${{ secrets.LANGCHAIN_API_KEY }}
  LANGCHAIN_TRACING_V2: "true"
  LANGCHAIN_PROJECT: "ci-eval"

jobs:
  fast-behavioral-gate:
    name: "Behavioral Tests (per-PR, <90s)"
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.11"}
      - run: pip install -r requirements.txt deepeval

      - name: Run behavioral test suite
        run: |
          pytest tests/eval/behavioral/ -v             --timeout=80             --tb=short             -x  # stop on first failure

      - name: Upload results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: behavioral-test-results
          path: test-results.xml

  full-ragas-gate:
    name: "RAGAS Quality Gate (on-merge)"
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.11"}
      - run: pip install -r requirements.txt ragas langsmith

      - name: Run RAGAS evaluation
        run: python scripts/run_ragas_eval.py --output ragas_results.json

      - name: Check regression gate
        run: |
          python scripts/check_regression_gate.py             --results ragas_results.json             --baseline baselines/ragas_baseline.json             --max-drop 0.05             --fail-on-regression

      - name: Update baseline on success
        if: success()
        run: |
          cp ragas_results.json baselines/ragas_baseline.json
          git config user.email "ci@yourcompany.com"
          git config user.name "CI Bot"
          git add baselines/ragas_baseline.json
          git commit -m "chore: update eval baseline [skip ci]" || true
          git push

      - name: Post results to LangSmith
        if: always()
        run: python scripts/post_to_langsmith.py --results ragas_results.json
03 · Regression Gate Implementation

Thresholds, Baselines, and
Fail Conditions

scripts/check_regression_gate.py

import json, sys, argparse
from dataclasses import dataclass
from typing import Optional

@dataclass
class RegressionResult:
    metric: str
    baseline: float
    current: float
    drop: float
    failed: bool
    severity: str  # "warning" | "error"

THRESHOLDS = {
    # Metric: (max_allowed_drop, severity_if_exceeded)
    "faithfulness":       (0.05, "error"),    # block deployment
    "answer_relevancy":   (0.05, "error"),
    "context_recall":     (0.08, "error"),    # slightly more tolerant
    "context_precision":  (0.08, "warning"),  # warn but don't block
    "answer_correctness": (0.05, "error"),
}

def check_regression(baseline: dict, current: dict,
                      fail_on_regression: bool = True) -> list[RegressionResult]:
    results = []
    for metric, (max_drop, severity) in THRESHOLDS.items():
        b = baseline.get(metric)
        c = current.get(metric)
        if b is None or c is None: continue
        drop = b - c
        failed = drop > max_drop
        results.append(RegressionResult(metric, b, c, drop, failed, severity))
        
        status = "✓" if not failed else ("⚠" if severity=="warning" else "✗")
        print(f"{status} {metric}: baseline={b:.3f} current={c:.3f} drop={drop:+.3f} (max={max_drop})")
    
    errors = [r for r in results if r.failed and r.severity == "error"]
    if errors and fail_on_regression:
        print(f"
✗ REGRESSION GATE FAILED: {len(errors)} metric(s) regressed beyond threshold")
        print("  Failing metrics:", [r.metric for r in errors])
        sys.exit(1)
    elif not errors:
        print(f"
✓ REGRESSION GATE PASSED — all metrics within thresholds")
    return results

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--results", required=True)
    parser.add_argument("--baseline", required=True)
    parser.add_argument("--max-drop", type=float, default=0.05)
    parser.add_argument("--fail-on-regression", action="store_true")
    args = parser.parse_args()

    baseline = json.load(open(args.baseline))
    current  = json.load(open(args.results))
    check_regression(baseline, current, args.fail_on_regression)
04 · Production Sampling Pipeline

Monitoring 10% of Live Traffic
With Automated Quality Scoring

production_monitor.py — daily sampling and scoring

import random, json
from datetime import datetime, timedelta
from langsmith import Client
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser

ls_client = Client()
judge_llm = ChatAnthropic(model="claude-haiku-4-5-20251001", temperature=0)

QUICK_JUDGE = ChatPromptTemplate.from_messages([("system", """
Rate this RAG response on faithfulness (0-1) and relevance (0-1).
Output JSON: {"faithfulness": 0-1, "relevance": 0-1}
Context: {context}
"""), ("human", "Query: {query}
Response: {response}")])
judge_chain = QUICK_JUDGE | judge_llm | JsonOutputParser()

def fetch_production_samples(
    project: str = "production",
    hours_back: int = 24,
    sample_rate: float = 0.10
) -> list[dict]:
    """Fetch 10% sample of yesterday's production traces."""
    start = datetime.utcnow() - timedelta(hours=hours_back)
    runs = ls_client.list_runs(project_name=project, start_time=start, run_type="chain")
    all_runs = list(runs)
    sample_n = int(len(all_runs) * sample_rate)
    sampled = random.sample(all_runs, min(sample_n, len(all_runs)))
    print(f"Sampled {len(sampled)} from {len(all_runs)} total runs ({sample_rate*100:.0f}%)")
    return [r for r in sampled if r.inputs and r.outputs]

def score_samples(samples: list) -> dict:
    """Score sampled runs and compute daily quality metrics."""
    faith_scores, rel_scores = [], []
    for run in samples:
        try:
            scores = judge_chain.invoke({
                "query":    run.inputs.get("query", ""),
                "response": run.outputs.get("answer", ""),
                "context":  run.outputs.get("context", "N/A")
            })
            faith_scores.append(scores["faithfulness"])
            rel_scores.append(scores["relevance"])
        except: pass
    
    return {
        "date":               datetime.utcnow().date().isoformat(),
        "n_scored":           len(faith_scores),
        "faithfulness_mean":  sum(faith_scores) / len(faith_scores) if faith_scores else None,
        "relevance_mean":     sum(rel_scores) / len(rel_scores) if rel_scores else None,
        "low_faith_rate":     sum(1 for s in faith_scores if s < 0.7) / len(faith_scores) if faith_scores else None,
    }

def check_production_regression(daily_metrics: list[dict], window: int = 7) -> dict:
    """Check if today's metrics regressed vs 7-day rolling average."""
    if len(daily_metrics) < 2: return {"status": "insufficient_data"}
    recent = daily_metrics[-window:-1]  # past 7 days, excluding today
    today  = daily_metrics[-1]
    for metric in ["faithfulness_mean", "relevance_mean"]:
        baseline = sum(d[metric] for d in recent if d[metric]) / len(recent)
        drop = baseline - today.get(metric, baseline)
        if drop > 0.05:
            return {"status": "regression", "metric": metric,
                    "drop": drop, "baseline": baseline, "today": today[metric]}
    return {"status": "ok", "today": today}

# Run daily via cron: 0 8 * * * python production_monitor.py
if __name__ == "__main__":
    samples = fetch_production_samples()
    today_metrics = score_samples(samples)
    daily_history = json.load(open("monitoring/daily_metrics.json"))
    daily_history.append(today_metrics)
    json.dump(daily_history, open("monitoring/daily_metrics.json", "w"))
    regression = check_production_regression(daily_history)
    if regression["status"] == "regression":
        send_alert(regression)  # PagerDuty / Slack
        sys.exit(1)

06 · The Monthly Evaluation Cadence

What to Review and Update
Every 30 Days

Monthly evaluation review checklist

□
Review 30-day production metric trends. Plot faithfulness, relevancy, and cost/session over 30 days. Flag any trend (not just threshold crossings). A slow 0.002/day decline = 0.06 drop in 30 days — below alert threshold daily, significant monthly.
□
Human spot-check 50 production samples. 3 annotators, existing rubric. Check: kappa still >0.60 (rubric hasn't drifted). Spearman between human and automated judge still >0.70 (judge hasn't drifted). Update rubric and re-calibrate judge if either has drifted.
□
Mine new queries from production logs. Cluster this month's queries. Find top-10 clusters not represented in current eval set. Add 5-10 examples from each unrepresented cluster. Target: eval set grows 20-50 examples per month.
□
Update LLM judge calibration. Re-run Spearman on 100 examples (50 from the new human spot-check + 50 from existing calibration set). If Spearman dropped below 0.65, identify the diverging examples and add them as few-shot examples to the judge prompt.
□
Update regression gate baselines. If quality genuinely improved this month (not noise), update the baseline file. The gate should protect against regression from the current level, not from the level of 6 months ago.
□
Red-team update with novel attack patterns. Add 20-30 new attack prompts using techniques published in the last month. Re-run full 130+ attack suite. Update guardrails for any new failure category.
□
Review cost optimization opportunities. Token budget analysis: has system prompt grown? Is cache hit rate stable? Are mean tool calls/session trending up? Run cost-quality frontier analysis if considering model or k change.

09 · Final Assessment

Module 15 Quiz

1. Your CI pipeline has a RAGAS gate that runs on every PR. A developer submits a PR with a prompt compression change. The gate fails: faithfulness drops from 0.88 to 0.82 (6pp, above the 5pp threshold). The developer argues the failing tests are on obscure edge cases that never appear in production. Should you block the PR?

Correct. The right response to a failing CI gate is investigation, not threshold relaxation or skipping. Either the gate is wrong (eval set is stale) → fix the eval set. Or the change is genuinely harmful → revert or fix the prompt. Lowering the threshold to pass a failing gate defeats the purpose of the gate entirely — you have now permanently reduced your quality protection because one developer disagreed with a test result. The eval set update is the correct escalation path when specific tests are found to be non-representative.

2. Your production monitoring shows faithfulness has been slowly declining: 0.88 → 0.86 → 0.84 → 0.82 over 4 weeks. Each daily drop is only 0.005, below the 0.05 alert threshold. The system never triggered an alert. What went wrong with the alerting design?

Correct. Point-in-time threshold alerts are blind to gradual drift. A system that declines by 0.005/day never triggers a daily-delta alert while accumulating a significant quality problem over weeks. This is analogous to the boiling frog — each daily change is small, but the cumulative effect is not. The dual-alert architecture (daily-delta + rolling-window comparison) is the correct solution. Monthly trend reports that human reviewers read also catch this pattern — which is why the monthly human spot-check is in the evaluation playbook even when automated metrics look fine day-to-day.

3. You want to test a major new feature (multi-modal support) that changes the system architecture significantly. The current 200-query text-only eval set cannot evaluate the new capability. How do you structure the evaluation before shipping?

Correct. New capability development must be paired with new evaluation development. A 200-query text-only eval set provides zero signal about multi-modal quality — running it and passing tells you the old capability is not broken, but nothing about the new one. The three elements required: (1) new eval set for the new capability (before feature ships); (2) existing eval to verify no regression on old capability; (3) new CI tests covering the new behavioral requirements. Shipping without capability-specific evaluation means you have no quality baseline for the new feature — making any future regression undetectable.

4. After 6 months of operation, your production monitoring shows consistent metrics but user NPS has declined from 72 to 58. The automated eval has not flagged anything. What should you investigate and in what order?

Correct. Stable automated metrics + declining NPS is the most important evaluation system failure mode to understand: your metrics do not capture what users care about. The qualitative human review of low-NPS sessions is the fastest path to understanding the gap. In practice, the most common findings are: (1) the system became more conservative (more refusals) due to a guardrail update; (2) response length increased because a new prompt added context; (3) users started asking more conversational questions but the system responds in a formal tone; (4) a competitor raised the bar and user expectations shifted. None of these are captured by RAGAS metrics or behavioral tests — they require qualitative human investigation.

5. You are the first ML engineer at a startup. The system ships in 3 weeks. You have 1 developer-week to build evaluation infrastructure. What do you build first, second, and third?

Correct. The sequencing reflects the priority order for evaluation infrastructure: (1) baseline is the most critical — without it, you cannot detect regressions after launch; (2) CI gate is second — it protects the baseline from being degraded by future changes; (3) production monitoring is third — it catches silent degradation after launch. Safety (red-team) is critically important for safety-critical applications but can follow immediately after launch for a general application. Human annotation is the highest-quality evaluation but the highest-cost — it should be done in month 1 of production when you have real user queries to annotate. The minimum viable stack takes 5 developer-days and protects against the most common failure modes.
