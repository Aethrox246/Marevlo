RAG Pipeline Evaluation
RAGAS Triad · Faithfulness · Answer Relevance · Context Recall · Precision

The RAGAS framework decomposes RAG quality into three measurable dimensions: Faithfulness (are claims grounded?), Answer Relevance (does the answer address the question?), and Context Recall (did we retrieve all the relevant information?). This module covers the full math, worked examples with actual numbers, failure diagnosis, and a complete Python implementation.

01 · The RAGAS Framework

Why One Number Is Never Enough
for RAG System Quality

A RAG system can fail at two independent stages: retrieval (wrong documents) or generation (wrong answer from right documents). A single quality score cannot distinguish these failures. RAGAS provides a metric decomposition that pinpoints exactly where the system is failing and how to fix it — different failure patterns require completely different fixes.

The four failure modes and which RAGAS metric catches each

Failure 1: Retriever misses relevant documents

The knowledge base contains the answer but the retriever does not find the right chunks. The LLM has nothing to work with. Caught by: Context Recall (low = retriever missing relevant docs)

Failure 2: Retriever returns irrelevant noise

The retriever finds chunks but most are unrelated to the query. The LLM context is full of noise that confuses generation. Caught by: Context Precision (low = too much noise in retrieved set)

Failure 3: LLM hallucinates beyond retrieved context

The retriever found good documents, but the LLM adds claims not supported by any retrieved chunk. Caught by: Faithfulness (low = LLM is hallucinating)

Failure 4: Answer does not address the question

Retrieval and generation are fine, but the answer drifts off-topic — it answers a question the retrieved documents address, not the one the user asked. Caught by: Answer Relevance (low = off-topic answer)

02 · Faithfulness — Complete Deep Dive

Measuring Every Claim:
Formula, Examples, and Edge Cases

Faithfulness = (Number of claims in the answer that are supported by the retrieved context) ÷ (Total number of claims in the answer). Every factual statement in the answer is extracted as an atomic claim, then verified against the retrieved chunks individually. The score is between 0 and 1.

Full worked example — step by step

Query: "What are the conditions for getting a refund on an annual subscription?"

Retrieved context [Chunk 1]: "Annual subscribers are eligible for a full refund if the request is submitted within 30 calendar days of the subscription start date. Refund requests must be submitted through the Account Settings portal."

Retrieved context [Chunk 2]: "Refunds are processed within 5-7 business days. Partial refunds are not available for unused subscription periods."

Generated answer: "Annual subscription refunds are available within 30 days [✓C1] via the Account Settings portal [✓C2]. Processing takes 5-7 business days [✓C3]. Monthly subscribers can also get prorated refunds [✗C4 — not in context]. Customer support can expedite processing for VIP accounts [✗C5 — hallucinated]."

⚠️

What faithfulness 0.60 means operationally

With faithfulness = 0.60, 40% of claims in every answer are invented. If users make decisions based on these answers — cancellation timing, pricing, eligibility — 40% of the time they are acting on fabricated information. This is not a borderline failure. Production target: faithfulness > 0.85 minimum, > 0.90 for high-stakes domains.

Faithfulness edge cases — what RAGAS does with them

Edge case: "I don't have information on that"

The model refuses to answer. No claims to verify. Faithfulness = 1.0 by convention (no hallucinations possible). But the answer is incomplete. Faithfulness alone does not penalize appropriate refusals — this is correct behavior.

Edge case: claim is implied by context, not stated

Context: "Annual plans start at $99/month." Claim: "Annual plans cost more than $10/month." This is mathematically implied but not stated. NLI judges will typically NOT mark this as entailed (strict interpretation). LLM judges may. RAGAS typically uses strict entailment = not supported.

Edge case: claim is a negation of context

Context: "Refunds are available." Claim: "Refunds are not available." This contradicts the context. Faithfulness correctly marks this as 0 (not entailed). However NLI models sometimes confuse entailment with contradiction for negated claims.

Improving faithfulness: practical levers

Lever 1: Strengthen system prompt constraints
Add: "Answer ONLY using the provided context. If information is not in the context, say so explicitly. Do NOT add related information from general knowledge."
Lever 2: Reduce temperature
temperature=0 reduces creative invention. Models are less likely to "add helpful context" that isn't in the source.
Lever 3: Citation requirement
Require the model to cite which chunk supports each claim: "Answer with inline citations [Doc 1], [Doc 2]..." Models citing sources are less likely to add uncited hallucinations.
Lever 4: Improve retrieval precision
Paradoxically, high faithfulness with bad retrieval = confidently wrong. Fix retrieval first, then push faithfulness higher.
03 · Answer Relevance — Complete Deep Dive

Does the Answer Address
the Question? The Reverse-Question Method

Answer Relevance uses a clever reverse approach: generate N questions from the answer, then compute how similar those reverse questions are to the original question. If the answer is on-topic, the questions generated from it will be similar to the original question. If the answer drifts off-topic, the reverse questions will be different from what the user asked.

Answer Relevance: step-by-step calculation with real numbers

Original query: "What is the refund policy for annual plans?"

Generated answer: "Our company was founded in 2018. We offer monthly and annual plans. Annual plans renew automatically each year. Customer support is available 24/7."

Step 1: Generate 5 reverse questions from the answer
Q1: "When was the company founded?" → embedding similarity to original: 0.21
Q2: "What plan types are available?" → embedding similarity: 0.44
Q3: "How do annual plans renew?" → embedding similarity: 0.55
Q4: "When does annual plan billing occur?" → embedding similarity: 0.52
Q5: "How do I reach customer support?" → embedding similarity: 0.18

Answer Relevance = mean(0.21, 0.44, 0.55, 0.52, 0.18) = 0.38 — very low. The answer covered a different topic than refund policy.
High Answer Relevance (0.91) — same query
Answer: "Annual plans have a 30-day refund window from subscription start. Submit via Account Settings → Billing → Request Refund."

Reverse questions: "How long is the annual plan refund period?" (sim: 0.94) "How do I get a refund on an annual plan?" (sim: 0.92) "Where do I submit a refund request?" (sim: 0.88) → Mean similarity: 0.91 ✓
Low Answer Relevance (0.38) — drifted off-topic
Answer covers company history, plan types, renewal policy, support availability — all accurate but none answer the refund policy question.

Reverse questions are about founding year, plan types, renewals, support hours → Mean similarity to "refund policy for annual plans": 0.38 ✗
⚠️

When Answer Relevance gives misleading scores

Answer Relevance scores are artificially low for: (1) correct but very short one-word answers ("No" to "Can I pause?") — reverse questions from "No" do not capture the question well; (2) questions asking for comparisons — an answer comparing monthly vs annual plans generates questions about both, which may not align with the original question perfectly; (3) multi-part questions — the answer may be highly relevant to all parts but the reverse questions may only capture one part. Always review low-AR examples manually before optimizing for this metric.

04 · Context Recall

Did the Retriever Find
All the Relevant Information?

Context Recall measures the fraction of the ground-truth answer that can be attributed to the retrieved context. It requires a reference answer (gold standard) for each query — making it an expensive metric. But it is the most direct measurement of retriever completeness: did we give the LLM everything it needed?

Context Recall: attribution-based calculation

Query: "What are the refund conditions for annual plans?"

Gold reference answer: [S1] Annual subscribers can get a refund within 30 days. [S2] Submit via Account Settings portal. [S3] Processing takes 5-7 business days. [S4] Partial refunds are not available. [S5] Enterprise accounts have different terms — contact support.

Retrieved context: Contains information supporting S1 ✓, S2 ✓, S3 ✓. Does not contain information about S4 ✗ or S5 ✗.

Context Recall = 3 attributable sentences / 5 total sentences = 0.60
The retriever missed 2 important pieces of information: that partial refunds are unavailable and that enterprise accounts have different terms.

Context Recall = 0.60 — what you fix

The retriever is missing chunks that contain S4 and S5 information. Check: Are those chunks in the knowledge base at all? If not → document gap. If yes → retrieval failure (wrong k, wrong embedding, chunk too large).
Typical fix: increase k from 3 to 5-8. Add metadata filters. Use ParentDocumentRetriever for better context. Check if the missing info is in a separate section of a long document.

Context Recall = 1.0 — what it means

All sentences in the gold reference answer can be attributed to at least one retrieved chunk. The retriever found everything the LLM needed. If the final answer is still wrong, the failure is in generation (faithfulness or relevance), not retrieval. This decomposition is exactly the diagnostic value of RAGAS.
05 · Context Precision

How Much Noise Is in
the Retrieved Context?

Context Precision measures what fraction of retrieved chunks are actually useful for answering the query. Low precision means the LLM's context window is full of noise — irrelevant documents that may confuse generation and waste tokens. High precision means every retrieved chunk contributes to the answer.

Context Precision worked example

Query: "What is the refund window for annual plans?"

Retrieved chunks (k=5):
[C1] "Annual subscribers have a 30-day refund window" → Relevant ✓
[C2] "Submit refund requests via Account Settings portal" → Relevant ✓
[C3] "Our customer support team is available 24/7" → NOT Relevant ✗
[C4] "Monthly plans offer a 7-day cancellation window" → NOT Relevant ✗
[C5] "Refunds are processed in 5-7 business days" → Relevant ✓

💡

Low precision → LLM "lost in the middle"

Research shows LLMs perform worse when relevant information is surrounded by irrelevant context — the "lost in the middle" effect. A context with 5 chunks where 4 are irrelevant is worse than a context with just the 1 relevant chunk. High context precision directly improves generation quality by reducing the noise the LLM must filter through.

07 · Answer Correctness and Full RAGAS Suite

When You Have Ground Truth:
Answer Correctness

Answer Correctness is the most comprehensive RAGAS metric — it measures both semantic similarity and factual overlap between the generated answer and a ground truth reference. It requires annotation but gives the most direct measure of end-to-end quality. RAGAS computes it as a weighted combination of semantic similarity and factual precision/recall.

Answer Correctness: formula and worked example

Reference answer: "Annual plans have a 30-day refund window. Submit via Account Settings. Processing: 5-7 business days. Partial refunds not available."

Generated answer: "You can get a refund on an annual plan within 30 days. Go to Account Settings to submit. Takes about a week to process."

Semantic similarity (BERTScore F1) = 0.84
Factual precision: generated claims in reference = 3/3 = 1.0
Factual recall: reference claims in generated = 3/4 = 0.75 (missed: "partial refunds not available")
Factual F1 = 2×(1.0×0.75)/(1.0+0.75) = 0.857

Answer Correctness = 0.5 × semantic_sim + 0.5 × factual_f1 = 0.5×0.84 + 0.5×0.857 = 0.849
💡

Answer Correctness vs Faithfulness: when to use which

Use Faithfulness when you do not have ground truth (monitors production 100% of the time). Use Answer Correctness when you have ground truth and want the most precise quality measurement (periodic benchmark evaluation). Faithfulness catches hallucination relative to context; Answer Correctness catches errors relative to true knowledge. A system with perfect faithfulness but imperfect retrieval will have high Faithfulness but lower Answer Correctness — the two metrics are complementary.

08 · Full RAGAS Pipeline in Python

Running the Complete
RAGAS Evaluation Suite

ragas_evaluation_pipeline.py

from ragas import evaluate
from ragas.metrics import (
    faithfulness, answer_relevancy, context_recall,
    context_precision, answer_correctness
)
from ragas.metrics.critique import harmfulness
from datasets import Dataset
from langchain_anthropic import ChatAnthropic
from langchain_openai import OpenAIEmbeddings
import pandas as pd

# ── Configure LLM and embeddings for RAGAS judges ─────────────
from ragas.llms import LangchainLLMWrapper
from ragas.embeddings import LangchainEmbeddingsWrapper

ragas_llm  = LangchainLLMWrapper(ChatAnthropic(model="claude-sonnet-4-20250514"))
ragas_embs = LangchainEmbeddingsWrapper(OpenAIEmbeddings(model="text-embedding-3-small"))

# ── Prepare evaluation dataset ────────────────────────────────
# Required fields for different metrics:
# faithfulness:       question, contexts, answer
# answer_relevancy:   question, contexts, answer
# context_recall:     question, contexts, ground_truth
# context_precision:  question, contexts, ground_truth
# answer_correctness: question, answer, ground_truth

eval_data = [
    {
        "question": "What are the refund conditions for annual plans?",
        "answer": "Annual plans have a 30-day refund window. Submit via Account Settings. Monthly plans are also refundable.",
        "contexts": [
            "Annual subscribers may request a refund within 30 calendar days via Account Settings.",
            "Refunds are processed within 5-7 business days."
        ],
        "ground_truth": "Annual plans have a 30-day refund window. Submit via Account Settings. Processing: 5-7 days. Partial refunds not available."
    },
    # ... add more examples
]

dataset = Dataset.from_list(eval_data)

# ── Run full evaluation ───────────────────────────────────────
metrics = [faithfulness, answer_relevancy, context_recall, context_precision, answer_correctness]
for m in metrics:
    m.llm = ragas_llm
    if hasattr(m, 'embeddings'): m.embeddings = ragas_embs

results = evaluate(dataset=dataset, metrics=metrics)
df = results.to_pandas()

print(results)
# {'faithfulness': 0.50, 'answer_relevancy': 0.38,
#  'context_recall': 0.75, 'context_precision': 0.60,
#  'answer_correctness': 0.71}

# ── Diagnosis from scores ─────────────────────────────────────
def diagnose_ragas(scores: dict) -> str:
    faith = scores.get('faithfulness', 1.0)
    ar    = scores.get('answer_relevancy', 1.0)
    cr    = scores.get('context_recall', 1.0)
    cp    = scores.get('context_precision', 1.0)

    if faith < 0.7 and cr > 0.7:
        return "LLM is hallucinating: strengthen system prompt, add citation requirement"
    elif ar < 0.6 and cp < 0.6:
        return "Retriever returning off-topic chunks: improve embeddings, add score_threshold"
    elif cr < 0.6 and cp > 0.7:
        return "Retriever missing key documents: increase k, improve chunking"
    elif faith > 0.85 and ar > 0.8 and cr > 0.8:
        return "System performing well — continue monitoring"
    else:
        return "Multiple issues detected — run manual inspection on 20 low-score samples"

print(diagnose_ragas(results))
09 · Assessment

Module 3 Quiz

1. Your RAG system has: Faithfulness = 0.92, Answer Relevance = 0.88, Context Recall = 0.45, Context Precision = 0.91. Users report their questions are answered partially — they usually get part of the answer and have to ask follow-up questions. What is the root cause?

Correct. High Faithfulness + High Precision + Low Recall is the "partial answer" pattern. The model is correctly and relevantly answering only what is in its retrieved context — but the context is incomplete. With Context Recall = 0.45, the retriever finds less than half of the relevant information for each query. Users experience this as getting "part of the answer" that is accurate but incomplete. The fix is in retrieval: increase k, improve document chunking to keep related facts in the same chunk, or add hypothetical question indexing to improve retrieval of specific fact chunks.

2. You measure Answer Relevance for a query "Can I cancel anytime?" and get 0.35. The answer is "Yes, you can cancel at any time. Monthly billing stops at the next billing cycle. Annual subscribers cannot get a refund after 30 days." How does the Answer Relevance metric compute this low score?

Correct. Answer Relevance is sensitive to topic drift within an otherwise accurate answer. The response started well ("Yes, you can cancel at any time") but then added information about billing cycles and refund policy that, while related and accurate, is not what the user asked. The reverse-question method correctly detects this: questions generated from the full answer are about billing and refunds, not about cancellation eligibility. This reveals a prompt engineering opportunity: instruct the model to stay focused on the specific question rather than adding related but unasked information.

3. You run RAGAS with Faithfulness = 0.95, Answer Relevance = 0.91, Context Recall = 0.88, Context Precision = 0.45. What is the system doing wrong and what is the user experience?

Correct. High generation metrics + Low Context Precision is the "noisy retrieval" pattern. The system produces good outputs despite having a noisy context — the LLM is successfully filtering relevant information from a mix of relevant and irrelevant chunks. But this is wasteful and risky. Each query sends ~55% unnecessary context tokens to the LLM, inflating costs. And "lost in the middle" research shows LLM performance degrades with longer noisy contexts. Fix retrieval precision to improve cost efficiency and reduce hallucination risk from lost-in-middle effects.

4. Why does RAGAS compute Answer Relevance using reverse-generated questions rather than directly comparing the answer to the question?

Correct. This is the core insight behind the Answer Relevance metric design. A question embedding and its correct answer embedding are often dissimilar in the raw vector space — the vector for "What is the refund policy?" is in a different part of embedding space than "Annual plans have a 30-day refund window." But the question embedding for "What are the refund conditions for annual plans?" (generated from the answer) IS similar to "What is the refund policy?" — because both are questions about the same concept. The reverse-question trick converts the comparison from question↔answer (incompatible structures) to question↔question (comparable structures).

5. Your faithfulness score is 0.80. You strengthen the system prompt to "ONLY answer from the provided context" and faithfulness rises to 0.88. A colleague says this is sufficient improvement. What additional validation do you need?

Correct. Single-metric optimization in isolation is a classic evaluation trap. Strengthening the faithfulness constraint can hurt other dimensions: the model becomes more conservative (refuses more questions → lower completeness), becomes more literal (quotes chunks verbatim → lower conciseness), or becomes less helpful (says "not in context" more often → lower answer relevance). Always run the full metric suite before declaring an improvement. An increase in faithfulness accompanied by a decrease in answer relevance or completeness is not an improvement — it is a tradeoff that may make the system less useful overall.
