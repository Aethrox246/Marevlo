01 · The Evaluation Illusion

Why "It Feels Good" Is
Not a Measurement

Most GenAI teams ship systems they have never formally evaluated. They demo the system to stakeholders, it produces a good-looking output, and that becomes the quality bar. This is not evaluation — it is survivorship bias. The demo works because you chose a query that works. The user sees the queries you did not choose.

The Vibe Check Anti-Pattern

❌ What teams actually do
"I tried 10 queries and they all looked good. The system is ready."

Problems: (1) 10 queries is not statistically significant. (2) You chose familiar queries — not adversarial ones. (3) "Looked good" has no definition. (4) No baseline comparison. (5) Quality may degrade silently after code changes.
✓ What evaluation actually requires
Defined metrics with numerical targets. A test set of 200+ queries that is representative of real user distribution (not hand-picked). A baseline to compare against. Automated re-running on every change. Monitoring that catches silent regressions.

02 · What Evaluation Actually Measures

The Four Questions
Every Evaluation Answers

Evaluation is not a single thing. It is a set of questions about your system, each requiring a different measurement approach. Confusing these questions — asking "is the output accurate?" when you should be asking "did the retriever return relevant documents?" — leads to finding the wrong problems and missing the real ones.

#QuestionComponent being measuredMethods that answer itFailure looks like
Q1Is the retrieved context relevant to the query?Retriever / vector storePrecision@K, Recall@K, NDCG, Context PrecisionTop-5 chunks contain zero relevant information about the user's question
Q2Does the LLM answer stay within the retrieved context?LLM generation (faithfulness)RAGAS Faithfulness, NLI, FactScoreAnswer says "The return window is 60 days" but no retrieved chunk mentions this
Q3Does the answer actually address the question?LLM generation (relevance)RAGAS Answer Relevance, LLM judgeUser asks "Can I return this?" Agent gives accurate but off-topic refund policy history
Q4Did the agent take the right actions?Agent reasoning + tool useTask Completion Rate, Tool Sequence Accuracy, Trajectory AnalysisAgent calls weather API when it should call hotel search; user gets weather when they asked about hotels
💡

Most "hallucination problems" are actually retrieval problems

When an LLM gives a wrong answer in a RAG system, teams immediately blame the LLM. But if the retriever returned the wrong documents, the LLM had no correct information to work with — it hallucinated because it had nothing better to say. Always measure Q1 (retrieval quality) before blaming Q2 (generation faithfulness). In practice, fixing retrieval resolves ~60% of apparent hallucination issues.

03 · Metric Taxonomy

Reference-Based vs Reference-Free vs
Behavioral — Three Evaluation Regimes

Every evaluation metric belongs to one of three regimes. The regime determines what you need to run the evaluation, what failure modes it detects, and what it cannot detect. Choosing the wrong regime wastes effort and gives false confidence.

Reference-Based Metrics

Require a ground truth answer (reference) to compare against. Can objectively measure factual correctness. Require expensive annotation of a gold standard test set.

Examples: BLEU, ROUGE, BERTScore, Exact Match, Answer Correctness
Requires: (query, reference_answer) pairs — expensive to create
Blind spot: Penalizes valid paraphrases. Reference may itself be wrong.

Reference-Free Metrics

Evaluate quality without needing a ground truth answer. Use the model's own output + context. Cheaper to run but can be gamed by verbose, plausible-sounding text.

Examples: RAGAS Faithfulness, Answer Relevance, Perplexity, LLM-as-Judge
Requires: Only (query, response, context) — no annotation needed
Blind spot: Cannot verify factual correctness without a reference. Model may be confidently wrong.

Behavioral Metrics

Test what the system does, not what it says. Assert properties of behavior rather than scoring output quality. The standard approach for agents where outputs are non-deterministic.

Examples: Task Completion Rate, Tool Call Accuracy, Guardrail TPR/FPR, Refusal Rate
Requires: Test cases with expected behavior defined — no reference text
Blind spot: Says whether it did the right thing; not whether the output quality was good.
04 · The Evaluation Lifecycle

Before Launch, After Launch,
and Every Change in Between

Evaluation is not a checkpoint before you ship — it is a continuous process that runs at every stage of the development and production lifecycle. Each stage has different goals, different methods, and different cadences.

Evaluation by stage: what to measure when

Stage 1: Prototype (first 2 weeks)

Goal: does the approach work at all? Use synthetic test set (LLM-generated question-answer pairs from your documents). Run RAGAS triad on 50-100 queries. Accept if faithfulness > 0.6 and answer relevance > 0.6. This is a smoke test, not a quality bar.

Stage 2: Development (ongoing)

Goal: optimize quality while building. Expand to 200-query eval set. Mix synthetic + manually annotated. Run after each significant prompt or retrieval change. Track all metrics in LangSmith experiments. Target: faithfulness > 0.80, precision@5 > 0.70.

Stage 3: Pre-launch (1 week before)

Goal: certify readiness. Full 500+ query eval suite. Human spot-check of 50 examples. Safety adversarial testing (HarmBench + custom). Latency SLA verification (p99 < 10s). Guardrail effectiveness (TPR > 0.97, FPR < 0.02). All gates must pass.

Stage 4: Production (ongoing)

Goal: detect regressions and drift. Sample 10-20% of live traffic. LLM judge on sampled responses daily. Alert if quality drops >5% from baseline. Human review of low-scoring samples weekly. Full re-evaluation suite monthly.

05 · Building Your First Test Set

The Evaluation Dataset:
Synthetic, Annotated, or Both

You cannot evaluate without data. The hardest part of setting up evaluation is building the initial test set. There are three strategies — each with different cost, quality, and coverage tradeoffs. Most production teams use a hybrid: synthetic for breadth, annotated for depth.

Synthetic Generation

Use an LLM to generate question-answer pairs from your documents. Fast and cheap — 1000 QA pairs from 100 documents in under an hour. Covers your full knowledge base automatically.

from langchain_core.prompts import ChatPromptTemplate from langchain_anthropic import ChatAnthropic GEN_PROMPT = ChatPromptTemplate.from_messages([ ("system", "Generate 3 Q&A pairs from this text. Output JSON: [{question, answer, source_quote}]"), ("human", "{chunk}") ]) chain = GEN_PROMPT | ChatAnthropic(model="claude-sonnet-4-20250514") | JsonOutputParser() # Run on all chunks → instant test set
⚠ Bias: questions follow document structure, not user intent distribution

Manual Annotation

Domain experts write real questions a user would ask. They provide a gold standard answer and cite the relevant source passage. High quality but expensive: ~5 min/example = 500 examples costs 40+ hours.

Each annotation includes:
• Question (as a real user would phrase it)
• Gold answer (complete, accurate, citeable)
• Source passage (which chunk contains the answer)
• Difficulty tag (easy / medium / adversarial)
• Query type (factual / comparison / procedural)
✓ Highest quality. Captures real user intent. Ground truth you can trust.

Production Log Mining

Extract real queries from production logs. Label them with human or LLM judges. This is the most realistic distribution — actual user questions, not curated ones.

Process:
1. Sample 500 queries from last 30 days of logs
2. Remove duplicates (cluster by embedding similarity)
3. LLM judge scores each response 1-5
4. Human review bottom 20% (low-score examples)
5. Use as ongoing eval set with human-verified labels
✓ Most realistic. Catches long-tail failures your synthetic set misses.
⚠️

The minimum viable test set: start with 200

200 examples is the minimum for statistically meaningful evaluation. At 200 queries, a 5% quality difference between two system versions is detectable with 80% statistical power. Below 100, you cannot reliably distinguish real improvements from noise. Start with 100 synthetic + 100 annotated = 200 total. Grow to 500+ over the first month of production by mining real queries.

06 · The Metrics That Lie

When Good Numbers Mean
Nothing — and Why

Every metric has failure modes. BLEU-0.8 can mean excellent translation or a model that copies the reference word-for-word. Faithfulness-0.9 can mean a model that hedges everything with "the document mentions..." A high score on the wrong metric is worse than no metric — it gives false confidence that stops you looking for real problems.

PerplexityFactual accuracy evaluationLow perplexity (fluent-sounding output)Model generates fluent but completely fabricated text. A confident hallucination has lower perplexity than a hedged correct answer.
RAGAS FaithfulnessRetriever returns wrong documentsFaithfulness = 0.95Model is faithful to the wrong context. It stays within the retrieved documents — which themselves are wrong. High faithfulness + low context precision = confidently wrong answer.
Task Completion RateJudge uses LLM with verbose biasCompletion rate = 0.92LLM judge rates verbose answers as "complete" even when they miss the core question. Shorter, correct answers score lower because they are less impressive-looking.

09 · Assessment

Module 0 Quiz

1. Your RAG system has a RAGAS Faithfulness score of 0.95 but users are still reporting wrong answers. What is the most likely root cause?

Correct. Faithfulness is a conditional metric: it measures "is the answer grounded in the retrieved context?" not "is the answer factually correct?" A retriever returning wrong documents produces a high faithfulness score (the LLM faithfully reports what the wrong documents say) with factually incorrect answers. Always check Context Precision alongside Faithfulness.

2. A team evaluates their RAG system with 10 hand-picked queries and gets a faithfulness score of 0.90. They ship. What is the critical methodological flaw?

Correct. Two separate failures: (1) Statistical: 10 samples cannot distinguish real quality from noise. A 5% quality difference requires ~200 samples to detect reliably. (2) Selection bias: hand-picked queries exclude adversarial, ambiguous, and long-tail cases. Production users will hit all of these. The team shipped with false confidence from a best-case sample.

3. You measure your agent's task completion rate and get 0.88. A colleague says this is "good enough." What additional information do you need before agreeing?

Correct. A single number without context is meaningless. 0.88 could be excellent (up from 0.61 last version) or alarming (down from 0.96 last version). The definition of "completion" matters enormously — if the judge counts "partially answered the hotel query" as complete, the real success rate could be much lower. Always ask: compared to what, judged by what definition, on what test set.

4. Which evaluation regime should you use to catch "the agent called the wrong tool for this query type"?

Correct. Wrong tool selection is a behavioral property — you need to inspect what the agent did (tool_calls in state), not score the quality of its output. Reference-based metrics check output text quality. Reference-free metrics check coherence and relevance. Neither tells you whether the agent used hotel_search vs flight_search. Only behavioral tests that inspect the execution trace can catch this failure mode reliably.

5. You are building the first evaluation system for a RAG chatbot that has been in production for 3 months with no monitoring. What is the correct order of steps?

Correct. Starting from production logs is the right first step for a live system — it reveals what failure modes actually exist before you design your test set. If you build a synthetic test set first, it may miss the real failure modes users are experiencing. Human review of production failures identifies the error taxonomy that should drive your test set design. The baseline evaluation then establishes where you are before any changes.
