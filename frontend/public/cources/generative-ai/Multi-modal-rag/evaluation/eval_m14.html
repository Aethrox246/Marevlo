01 · The Core Decision Question

Start Here: What Are You
Trying to Learn?

The most common evaluation mistake is picking a metric first and then figuring out what question it answers. The right approach is the reverse: identify what specific question you are trying to answer about your system, then select the metric that most directly answers it. Different questions require completely different methods — and using the wrong metric gives you a confident wrong answer.

The five questions that drive metric selection

Q1
Is the answer grounded in what was retrieved? → RAGAS Faithfulness, NLI verification, FactScore. These measure whether every claim in the response can be traced to the retrieved context.
Q2
Did the retriever find the right documents? → Context Precision, Context Recall, Precision@K, Recall@K, NDCG. These measure the retriever in isolation, before generation.
Q3
Is Version A better than Version B? → Pairwise preference study with LLM-as-Judge (+ swap consistency) or human annotation (200+ pairs). Never compare with a single absolute score.
Q4
Did the agent do the right thing? → Behavioral assertions (tool_calls inspection), Task Completion Rate, Tool Selection Accuracy. Never use output-text metrics for agent trajectory evaluation.
Q5
Is the system safe to deploy? → ASR by attack category, Guardrail TPR/FPR, prompt injection test suite, PII leakage check. Safety evaluation is never optional before launch.

03 · Decision by Question Type

From Specific Diagnostic Question
to Specific Metric

The complete diagnostic-question-to-metric map

"Why is the answer wrong?"
Run RAGAS full suite. If Context Recall <0.7: retriever misses docs. If Faithfulness <0.8: LLM hallucinates. If Answer Relevancy <0.7: LLM answers wrong question. Each diagnosis = different fix.
"Did my prompt change help?"
Pairwise LLM-as-Judge on 200 queries with swap consistency. Win rate >0.55 with consistency >0.80 = genuine improvement. Use same eval set for both versions.
"Is the retriever good enough?"
Hit Rate@5, Precision@5, Recall@5 on labeled query set. Target: Hit Rate@5 >0.85, P@5 >0.60. Add NDCG if ranking matters. Build eval set from synthetic Q&A pairs first.
"Is my system safe to launch?"
Full red-team protocol: ASR <0.05 overall, <0.10 per category, multi-turn ASR <0.15. TPR >0.95, FPR <0.05. Zero P1 findings from human red-team.
"Why is the agent looping?"
Tool Call Efficiency ratio: actual_calls / minimum_calls. Inspect LangSmith traces on high-ratio queries. Efficiency >2.0 = looping. Root cause: ambiguous tool description or missing termination condition.
"Is cost growing unsustainably?"
Token budget analysis by component. Semantic cache hit rate. Cost/session trend. Mean tool calls/session trend. Check system prompt size: each 100 tokens = ~$30/day at 10K queries.
"Is my LLM judge trustworthy?"
Swap consistency test: run 100 pairs both orders, target consistency >0.80. Calibration: Spearman vs 200 human labels, target >0.70. Run both before trusting any judge-based evaluation.
"Which model should I use?"
Domain eval set (your queries, your KB) + cost-quality frontier mapping. Never rely on public benchmark scores alone. MMLU 91% vs 88% is noise; your domain score is signal.

05 · The Ten Most Common Evaluation Mistakes

Patterns That Lead to
False Confidence

The failure patterns — and how to fix each

Mistake 1: Evaluating on the training distribution. You test on the same kind of queries you used for prompt engineering. The system looks great. Users find failures on edge cases, adversarial inputs, and rare query types you never tested. Fix: always include adversarial and long-tail examples in every eval set.
Mistake 2: Single-metric optimization. You optimize faithfulness and it rises from 0.82 to 0.91. Answer relevancy drops from 0.85 to 0.70 (now answers the wrong question very faithfully). Always report and check all primary metrics together, not in isolation.
Mistake 3: Uncalibrated LLM judge. You use an LLM judge and trust its scores without checking swap consistency or Spearman correlation against humans. The judge has 0.29 positional bias rate. 29% of your A/B results are positional artifacts. Always run swap consistency + calibration before production use.
Mistake 4: Aggregate metrics hiding category failures. Overall TCR = 0.82 looks good. 3-specialist queries have TCR = 0.48 — a catastrophic failure hidden by the aggregate. Always report metrics by query category, not just overall.
Mistake 5: Known-attack-only safety testing. ASR = 0.01 on HarmBench attacks. You ship. Novel multi-turn attacks succeed 30% of the time because they were never in your test set. Always supplement known attack sets with LLM-generated novel attacks and human red-teamers.
Mistake 6: Too few examples for statistical conclusions. 50 pairwise comparisons showing 56% win rate for System A. You cannot reject the null hypothesis — the result is inconclusive. Never report improvement from an underpowered study. Use sample size calculators before running any human study.
Mistake 7: No baseline to compare against. Faithfulness = 0.84. Is this good? Without a previous version baseline, you do not know if this is up, down, or flat. Always establish and record your baseline before any changes.
Mistake 8: Using BLEU or ROUGE for open-ended QA. A perfectly correct paraphrased answer scores BLEU-4 = 0.07. Your system appears to have failed when it succeeded. Use BERTScore or LLM judge for any task where paraphrase is expected.
Mistake 9: Output-only evaluation for agents. All output-quality tests pass. The agent called the wrong tool, looped 4 times, and found the right answer by accident. The fragile behavior will fail in production on slightly different inputs. Always inspect tool_calls, not just final output.
Mistake 10: Evaluating only at launch, not continuously. The system passes all pre-launch gates. Three months later, the LLM provider silently updates the model. Faithfulness drops from 0.88 to 0.74. You find out from user complaints. Continuous production monitoring with automated alerts is the only protection against silent drift.

07 · The Complete Evaluation Playbook

End-to-End Protocol for
Any GenAI System

The 12-step evaluation playbook — from prototype to production

01
Define success criteria before writing any code. What does "good enough" look like? e.g., faithfulness >0.85, TCR >0.80, p95 latency <4s. These targets drive all evaluation design.
02
Build eval set (50 synthetic) before building the system. Generate from your documents. You need something to measure before you iterate.
03
Establish baseline scores on day one. Run RAGAS triad (RAG) or behavioral tests (agent) on your first working prototype. Record everything in LangSmith or Braintrust.
04
Add CI evaluation gate. 10-20 DeepEval behavioral tests + RAGAS on merge-to-main. Fail builds if metrics drop >0.05 from baseline.
05
Expand eval set to 200 queries as you collect real user data. Mine 100 real queries from logs. Add adversarial, edge-case, and failure examples. Human-label 50 of them.
06
Calibrate LLM judge against human labels. Spearman correlation on 200 examples. Target >0.70. Run swap consistency on 100 pairs. Target >0.80 before using judge for consequential decisions.
07
Run pre-launch red-team. 130+ attacks across 5 categories. Zero P1 findings required. Re-test after every guardrail change.
08
Run pre-launch human evaluation. 300 examples, 3 annotators, kappa >0.60. Pairwise vs previous version: win rate >0.55 on 200 pairs with p<0.05.
09
Launch with production monitoring. Sample 10-20% of traffic → LLM judge → store scores. Alert if quality drops >0.05 from baseline. Monitor cost/session and p99 latency daily.
10
Monthly: human spot-check 50 production samples. Catches quality drift that automated metrics miss. Re-calibrate LLM judge if Spearman drift detected.
11
Quarterly: update red-team with novel attacks. Add new jailbreak techniques discovered since last quarter. Re-run full attack suite. Update guardrails for new failure modes.
12
When metrics diverge from user satisfaction: Mine the specific user complaints. Add them to the eval set. Find which metric does not capture what users actually care about and either fix the metric or add a new one.

09 · Assessment

Module 14 Quiz

1. Your RAG system shows: Faithfulness=0.91, Answer Relevancy=0.88, Context Recall=0.65, Context Precision=0.82. Users report that answers are accurate but often incomplete. What is the root cause and the fix?

Correct. This is the canonical RAGAS diagnostic pattern: high faithfulness + high relevancy + low recall = accurate but partial answers. The LLM is doing its job correctly — it faithfully answers from what it has, and the answer is relevant to the question. But it only has 65% of the relevant information. The missing 35% is why users find answers incomplete. Context Precision=0.82 is acceptable. The entire problem is in the retriever's recall. This case demonstrates why single-metric evaluation is insufficient — only the pattern of all four RAGAS scores together reveals the correct diagnosis and fix.

2. You are comparing a new prompt (v2) to the old one (v1) using an LLM judge. v2 gets a 62% win rate in 100 pairwise comparisons. You run swap consistency and find consistency rate=0.61. What can you actually conclude?

Correct. A consistency rate of 0.61 means 39% of the outcomes changed when you swapped the positions of A and B — those outcomes are definitionally not reflecting quality judgments, they are reflecting which response appeared first. With 39% of 100 pairs being positional artifacts (39 pairs), the true quality-based win rate is determined by only 61 pairs — and on those 61 pairs, the result could easily be below 50%. The judge is not reliable enough for this comparison. Fix the judge first, then re-run the study. More pairs with a bad judge just gives you more bad data.

3. You improve your agent's Task Completion Rate from 0.78 to 0.87 by adding 5 new tools. Tool Selection Accuracy drops from 0.91 to 0.76. Should you ship this change?

Correct. This is a metric interaction effect: adding tools improved TCR but degraded tool selection accuracy. The TCR improvement on the test set may be masking a fragile behavior — the agent completes tasks by trying multiple tools until one works (higher TCR in the short run, higher efficiency ratio and unpredictable behavior in production). The right response is not binary accept/reject — it is investigation: understand which tools are causing selection confusion, improve their descriptions, and verify both metrics pass before shipping. A 15pp drop in tool selection accuracy cannot be dismissed as "secondary" — it predicts 15% more wrong-tool calls in production.

4. A competitor releases a model claiming to beat yours on MMLU, MT-Bench, and GSM8K. Your product manager asks if you should switch models. What evaluation do you run and what is your recommendation?

Correct. Model selection for production applications must be grounded in domain-specific evaluation, not public benchmark scores. MMLU 91% vs 88%, MT-Bench 8.9 vs 8.7, GSM8K 97% vs 96% — all of these differences are within noise for most production applications and tell you nothing about performance on your specific domain, query distribution, or evaluation criteria. Your domain eval set is the arbiter. The cost-quality frontier is the business decision filter: a model that is 5% better on your domain eval but costs 3× more per session may not be worth switching to.

5. Three months after launch, your automated evaluation shows all metrics within 2% of baseline, but user satisfaction scores have dropped 15%. What is the most likely cause and how do you diagnose it?

Correct. This is the metric coverage gap in production. Stable automated metrics + declining satisfaction is the clearest signal that your evaluation does not capture what users actually care about. Possible explanations: your eval set no longer represents the current query distribution (users have changed what they ask), your metrics measure the wrong dimensions (users care about tone but your metrics measure faithfulness), or users are experiencing something entirely unmeasured (the UI changed, response time feels different, comparison with a competitor shifted expectations). The qualitative human review of low-satisfaction samples is the fastest path to understanding the gap — humans will quickly identify patterns that automated metrics miss.
