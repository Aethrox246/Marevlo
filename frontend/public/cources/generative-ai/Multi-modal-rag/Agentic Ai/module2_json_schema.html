Section 01

What is JSON Schema?

JSON Schema is a vocabulary for annotating and validating JSON documents. Think of it as a contract — a machine-readable specification of exactly what valid data looks like.

Imagine you're building an AI agent that analyzes network devices. The agent returns a JSON report. But what if the agent hallucinates and returns "risk": "CRITICAL" when your system only understands "HIGH", "MED", or "LOW"? Your code crashes.

JSON Schema solves this. You write a schema that says exactly what the output must look like — and then you validate every response against it before using it.

A Simple Example

Here's the data we expect:

JSON — Expected Data
{
  "device_id": "JNP-001",
  "risk_level": "HIGH",
  "anomaly_score": 0.91
}

And here's the schema that describes the rules for that data:

JSON Schema
{
  "type": "object",
  "properties": {
    "device_id": {
      "type": "string",
      "description": "Device identifier"
    },
    "risk_level": {
      "type": "string",
      "enum": ["LOW", "MED", "HIGH"]
    },
    "anomaly_score": {
      "type": "number",
      "minimum": 0,
      "maximum": 1
    }
  },
  "required": ["device_id", "risk_level"],
  "additionalProperties": false
}
💡
Key insight: A JSON Schema is itself a JSON document. It uses special keywords like type, properties, required, and enum to describe what valid data looks like.

JSON Schema Draft Evolution

JSON Schema has multiple drafts. Most LLM providers support a subset of Draft 7 or Draft 2020-12. Knowing the differences prevents subtle bugs.

JSON Schema — Draft Comparison
// Draft-07 (most widely supported by LLM APIs)
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "$id": "https://marevlo.com/schemas/device-report",
  "type": "object",
  "definitions": {     // Draft-07 uses "definitions"
    "severity": { "type": "string", "enum": ["LOW", "MED", "HIGH"] }
  },
  "properties": {
    "risk": { "$ref": "#/definitions/severity" }
  }
}

// Draft 2020-12 (newer — $defs replaces definitions)
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$defs": {           // 2020-12 uses "$defs"
    "severity": { "type": "string", "enum": ["LOW", "MED", "HIGH"] }
  },
  "properties": {
    "risk": { "$ref": "#/$defs/severity" }
  }
}
⚠️
LLM API compatibility: Anthropic's tool input_schema is based on JSON Schema Draft-07. OpenAI Structured Outputs uses a subset of Draft 2020-12 but disallows some keywords like unevaluatedProperties. Always test your schema against the target provider.

Meta-Schema: Validating Schemas Themselves

At expert level, you write tooling that validates your schemas before deploying them. This prevents schema bugs from reaching production.

Python — Schema Registry with Meta-Validation
# pip install jsonschema
import jsonschema
from jsonschema import Draft7Validator
from pathlib import Path
import json

class SchemaRegistry:
    """Central registry for all agent output schemas."""

    def __init__(self, schema_dir: str = "schemas/"):
        self.schemas: dict[str, dict] = {}
        self.validators: dict[str, Draft7Validator] = {}
        self._load_all(schema_dir)

    def _load_all(self, schema_dir: str):
        for path in Path(schema_dir).glob("*.json"):
            with path.open() as f:
                schema = json.load(f)
            # Validate the schema against the meta-schema
            Draft7Validator.check_schema(schema)
            name = path.stem
            self.schemas[name] = schema
            self.validators[name] = Draft7Validator(schema)
            print(f"✓ Loaded schema: {name}")

    def validate(self, schema_name: str, data: dict) -> tuple[bool, list[str]]:
        validator = self.validators[schema_name]
        errors = list(validator.iter_errors(data))
        return len(errors) == 0, [e.message for e in errors]

    def get_tool_schema(self, schema_name: str) -> dict:
        """Export schema in Anthropic tool format."""
        schema = self.schemas[schema_name]
        return {k: v for k, v in schema.items()
                if k not in ("$schema", "$id")}

# Usage
registry = SchemaRegistry("schemas/")
valid, errors = registry.validate("device_report", llm_output)
if not valid:
    print(f"Schema errors: {errors}")
    # Trigger retry logic
Section 02

Schema Anatomy

Every JSON Schema keyword has a specific purpose. Master these building blocks and you can describe any data structure precisely.

Core Keywords

Keyword
type
Specifies the data type: string, number, integer, boolean, null, array, object
Keyword
properties
Defines the schema for each key in an object. Only applies when type is "object"
Keyword
required
Array of key names that must be present. Missing required keys fail validation
Keyword
enum
Restricts value to one of a fixed list. Ideal for status codes, categories, levels
Keyword
items
Defines the schema for each element in an array. All items must match
Keyword
description
Human-readable description. Critical for LLM tools — helps the model understand what to provide

Full Example with Annotations

JSON Schema — Annotated
{
  "type": "object",                    // Top-level must be an object
  "description": "Device health report",

  "properties": {

    "device_id": {
      "type": "string",               // Must be a string
      "minLength": 1,                 // Cannot be empty
      "maxLength": 20,                // Cannot be too long
      "pattern": "^JNP-\\d{3}$",      // Must match regex
      "description": "Juniper device ID"
    },

    "risk_level": {
      "type": "string",
      "enum": ["LOW", "MED", "HIGH"],  // Only these 3 values
      "description": "Assessed risk severity"
    },

    "anomaly_score": {
      "type": "number",
      "minimum": 0,                   // >= 0
      "maximum": 1,                   // <= 1
      "description": "0=normal, 1=anomalous"
    },

    "affected_components": {
      "type": "array",
      "items": { "type": "string" },    // Array of strings
      "minItems": 1,                  // At least one item
      "uniqueItems": true             // No duplicates
    },

    "timestamp": {
      "type": "integer",              // Unix timestamp
      "description": "Unix epoch seconds"
    }
  },

  "required": ["device_id", "risk_level", "anomaly_score"],
  "additionalProperties": false      // Reject unknown keys
}

Nested Objects, $ref, and Reusability

Real agent schemas are complex. Use $ref to reference reusable sub-schemas and avoid repetition — especially important when multiple tools share common types.

JSON Schema — $ref and Definitions
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "definitions": {

    // Reusable sub-schema for a device
    "Device": {
      "type": "object",
      "properties": {
        "id": { "type": "string", "pattern": "^JNP-\\d{3}$" },
        "hostname": { "type": "string" },
        "location": { "type": "string" }
      },
      "required": ["id"]
    },

    // Reusable severity enum
    "Severity": {
      "type": "string",
      "enum": ["LOW", "MED", "HIGH", "CRITICAL"]
    }
  },

  // Main schema references the definitions
  "type": "object",
  "properties": {
    "device": { "$ref": "#/definitions/Device" },
    "severity": { "$ref": "#/definitions/Severity" },
    "related_devices": {
      "type": "array",
      "items": { "$ref": "#/definitions/Device" }
    }
  },
  "required": ["device", "severity"]
}

Conditional Schemas with if/then/else

JSON Schema — Conditional Validation

oneOf, anyOf, allOf — Polymorphic Schemas

Agent outputs often vary by type. Use composition keywords to express "this field can be one of several shapes."

JSON Schema — Polymorphic Agent Actions
{
  "type": "object",
  "properties": {
    "action": {
      // Action must be exactly ONE of these types
      "oneOf": [
        {
          "type": "object",
          "properties": {
            "type": { "const": "alert" },
            "channel": { "type": "string", "enum": ["slack", "email", "pagerduty"] },
            "message": { "type": "string", "minLength": 5 }
          },
          "required": ["type", "channel", "message"],
          "additionalProperties": false
        },
        {
          "type": "object",
          "properties": {
            "type": { "const": "restart_service" },
            "service_name": { "type": "string" },
            "confirm": { "type": "boolean", "const": true }
          },
          "required": ["type", "service_name", "confirm"],
          "additionalProperties": false
        }
      ]
    }
  },
  "required": ["action"]
}
✅
oneOf vs anyOf: oneOf means exactly one must match (exclusive). anyOf means one or more can match. For discriminated union types (like action types), always use oneOf.

Section 03

Validation in Python

The jsonschema library makes it trivial to validate any JSON data against any schema. Here's how to use it at every level.

Python — Basic Validation
# pip install jsonschema
import jsonschema
from jsonschema import validate, ValidationError

schema = {
    "type": "object",
    "properties": {
        "device_id": {"type": "string"},
        "risk_level": {"type": "string", "enum": ["LOW", "MED", "HIGH"]},
        "anomaly_score": {"type": "number", "minimum": 0, "maximum": 1}
    },
    "required": ["device_id", "risk_level"]
}

# ✓ Valid data
valid_data = {"device_id": "JNP-001", "risk_level": "HIGH", "anomaly_score": 0.91}
validate(instance=valid_data, schema=schema)  # No error = valid!
print("✓ Valid data passed")

# ✗ Invalid — risk_level not in enum
try:
    bad_data = {"device_id": "JNP-001", "risk_level": "CRITICAL"}
    validate(instance=bad_data, schema=schema)
except ValidationError as e:
    print(f"✗ Validation failed: {e.message}")

# ✗ Invalid — missing required field
try:
    missing = {"device_id": "JNP-001"}  # risk_level missing
    validate(instance=missing, schema=schema)
except ValidationError as e:
    print(f"✗ Validation failed: {e.message}")

Collecting All Errors (Not Just the First)

Python — Collect All Validation Errors
from jsonschema import Draft7Validator

schema = {
    "type": "object",
    "properties": {
        "device_id": {"type": "string", "pattern": "^JNP-\\d{3}$"},
        "risk_level": {"type": "string", "enum": ["LOW", "MED", "HIGH"]},
        "anomaly_score": {"type": "number", "minimum": 0, "maximum": 1}
    },
    "required": ["device_id", "risk_level", "anomaly_score"]
}

validator = Draft7Validator(schema)

# Data with MULTIPLE errors at once
bad_llm_output = {
    "device_id": "invalid-id",   # Fails pattern
    "risk_level": "EXTREME",     # Not in enum
    "anomaly_score": 1.5          # Exceeds maximum
}

errors = list(validator.iter_errors(bad_llm_output))
print(f"Found {len(errors)} validation errors:")
for i, err in enumerate(errors, 1):
    path = " → ".join(str(p) for p in err.absolute_path)
    print(f"  {i}. [{path or 'root'}] {err.message}")

# Build a retry prompt with error details
def build_retry_prompt(original_output: dict, errors: list) -> str:
    error_lines = "\n".join(
        f"- {'.'.join(str(p) for p in e.absolute_path) or 'root'}: {e.message}"
        for e in errors
    )
    return f"""Your previous output failed validation:
{error_lines}

Please fix these errors and return a valid JSON object."""

Custom Validation Keywords

Python — Custom Validators
from jsonschema import Draft7Validator, validators
from jsonschema.exceptions import ValidationError

# Custom validator: "is_future_timestamp"
import time

def is_future_timestamp(validator, value, instance, schema):
    if value and instance <= int(time.time()):
        yield ValidationError(f"{instance} is not a future timestamp")

# Extend Draft7 with the custom keyword
CustomValidator = validators.extend(
    Draft7Validator,
    {"isFutureTimestamp": is_future_timestamp}
)

schema_with_custom = {
    "type": "object",
    "properties": {
        "schedule_at": {
            "type": "integer",
            "isFutureTimestamp": True   # Custom keyword!
        }
    }
}

v = CustomValidator(schema_with_custom)
try:
    v.validate({"schedule_at": 1000000000})  # Year 2001 — in the past
except ValidationError as e:
    print(f"Caught: {e.message}")

Schema Validation as an Agent Middleware Layer

Python — Validation Middleware with Retry
import json, anthropic
from jsonschema import Draft7Validator
from functools import wraps
from typing import Callable

def schema_validated(schema: dict, max_retries: int = 3):
    """Decorator: wraps any LLM call with schema validation + retry."""
    validator = Draft7Validator(schema)

    def decorator(fn: Callable):
        @wraps(fn)
        def wrapper(*args, **kwargs):
            last_errors = []
            for attempt in range(max_retries):
                result = fn(*args, feedback=last_errors, **kwargs)
                try:
                    data = json.loads(result) if isinstance(result, str) else result
                    validator.validate(data)
                    print(f"✓ Validated on attempt {attempt+1}")
                    return data
                except Exception as e:
                    last_errors = [str(e) for e in validator.iter_errors(data)]
                    print(f"✗ Attempt {attempt+1} failed: {len(last_errors)} errors")
            raise RuntimeError(f"Schema validation failed after {max_retries} retries")
        return wrapper
    return decorator

# Usage — wrap any LLM call
report_schema = {"type": "object", "properties": { ... }, "required": ["risk_level"]}

@schema_validated(report_schema, max_retries=3)
def analyze_device(device_id: str, feedback: list = []) -> str:
    prompt = f"Analyze device {device_id} and return JSON."
    if feedback:
        prompt += f"\n\nFix these errors from last attempt:\n" + "\n".join(feedback)
    # ... call LLM and return response

Python — JSON via Prompt
import anthropic, json

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": """Analyze device JNP-001 and return ONLY a JSON object

- device_id: string

Technique 2: Anthropic Tool Use for Structured Output

Define a tool with your output schema. The model must call the tool with valid arguments — effectively forcing structured output.

Python — Structured Output via Tool Use
import anthropic

client = anthropic.Anthropic()

# Define the "output tool" — the schema IS the output spec
output_tool = {
    "name": "report_device_analysis",
    "description": "Report the findings from device analysis",
    "input_schema": {
        "type": "object",
        "properties": {
            "device_id": {
                "type": "string",
                "description": "The device being analyzed"
            },
            "risk_level": {
                "type": "string",
                "enum": ["LOW", "MED", "HIGH"],
                "description": "Severity of the risk"
            },
            "anomaly_score": {
                "type": "number",
                "minimum": 0, "maximum": 1,
                "description": "Score from IsolationForest (0=normal, 1=anomalous)"
            },
            "root_cause": {
                "type": "string",
                "description": "Most likely cause of the anomaly"
            },
            "recommended_actions": {
                "type": "array",
                "items": {"type": "string"},
                "minItems": 1,
                "description": "List of concrete remediation steps"
            }
        },
        "required": ["device_id", "risk_level", "anomaly_score", "recommended_actions"]
    }
}

response = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    tools=[output_tool],
    tool_choice={"type": "tool", "name": "report_device_analysis"},  # Force this tool
    messages=[{
        "role": "user",
        "content": "Device JNP-001: CPU=94.2%, memory=67%, PFE errors=412. Analyze."
    }]
)

# Extract the structured output
tool_block = next(b for b in response.content if b.type == "tool_use")
report = tool_block.input  # This is already a typed Python dict!

print(f"Device: {report['device_id']}")
print(f"Risk: {report['risk_level']}")
print(f"Score: {report['anomaly_score']}")
print("Actions:")
for action in report["recommended_actions"]:
    print(f"  - {action}")
✅
Key trick: Using tool_choice: {"type": "tool", "name": "..."} forces the model to always call your specific tool. Combined with a well-designed schema, this is the most reliable way to get structured JSON from Claude.

Multi-Tool Orchestration with Schema Routing

Python — Schema-Driven Tool Router
import anthropic
from jsonschema import Draft7Validator

class SchemaRoutedAgent:
    """Agent that validates every tool output against registered schemas."""

    def __init__(self):
        self.client = anthropic.Anthropic()
        self.tool_schemas: dict[str, dict] = {}
        self.validators: dict[str, Draft7Validator] = {}
        self.tools: list[dict] = []

    def register_tool(self, name: str, description: str, schema: dict,
                       handler: callable):
        """Register a tool with its input schema and Python handler."""
        self.tool_schemas[name] = schema
        self.validators[name] = Draft7Validator(schema)
        self.tools.append({
            "name": name,
            "description": description,
            "input_schema": schema
        })
        setattr(self, f"_handler_{name}", handler)

    def run(self, user_message: str) -> str:
        messages = [{"role": "user", "content": user_message}]

        while True:
            response = self.client.messages.create(
                model="claude-opus-4-5", max_tokens=2048,
                tools=self.tools, messages=messages
            )

            if response.stop_reason == "end_turn":
                return response.content[0].text

            if response.stop_reason == "tool_use":
                tool_results = []
                for block in response.content:
                    if block.type == "tool_use":
                        # Validate tool INPUT against schema
                        errors = list(self.validators[block.name].iter_errors(block.input))
                        if errors:
                            result = f"Error: invalid input - {errors[0].message}"
                        else:
                            handler = getattr(self, f"_handler_{block.name}")
                            result = handler(**block.input)
                        tool_results.append({
                            "type": "tool_result",
                            "tool_use_id": block.id,
                            "content": str(result)
                        })
                messages += [{"role": "assistant", "content": response.content},
                             {"role": "user", "content": tool_results}]

Schema Versioning & Backward Compatibility

Python — Schema Version Manager
from jsonschema import Draft7Validator
from dataclasses import dataclass
import semver

@dataclass
class SchemaVersion:
    version: str
    schema: dict
    deprecated: bool = False
    migration: callable = None   # fn(old_data) -> new_data

class VersionedSchemaManager:
    def __init__(self):
        self.versions: dict[str, SchemaVersion] = {}

    def register(self, sv: SchemaVersion):
        self.versions[sv.version] = sv

    def validate_and_migrate(self, data: dict, from_version: str, to_version: str) -> dict:
        # Validate against source schema
        src = self.versions[from_version]
        errors = list(Draft7Validator(src.schema).iter_errors(data))
        if errors:
            raise ValueError(f"Invalid v{from_version}: {errors[0].message}")

        # Migrate up through versions
        current = data
        sorted_versions = sorted(self.versions.keys(), key=semver.Version.parse)
        migrating = False

        for v in sorted_versions:
            if v == from_version: migrating = True
            if migrating and v != from_version:
                sv = self.versions[v]
                if sv.migration:
                    current = sv.migration(current)
                if v == to_version: break

        # Validate against target schema
        tgt = self.versions[to_version]
        Draft7Validator(tgt.schema).validate(current)
        return current

Pydantic Integration

Pydantic models can auto-generate JSON Schemas and validate LLM outputs with Python type safety. The best of both worlds.

Pydantic lets you define data models in Python using type annotations. It automatically generates a JSON Schema from your model — so you write Python, and Pydantic gives you both validation and a schema for free.

Python — Pydantic Model + Auto Schema
# pip install pydantic
from pydantic import BaseModel, Field
from typing import Literal
import json

class DeviceReport(BaseModel):
    device_id: str = Field(description="Device identifier e.g. JNP-001")
    risk_level: Literal["LOW", "MED", "HIGH"]
    anomaly_score: float = Field(ge=0.0, le=1.0)
    recommendation: str

# Auto-generate JSON Schema
schema = DeviceReport.model_json_schema()
print(json.dumps(schema, indent=2))

# Validate data by constructing the model
try:
    report = DeviceReport(

from pydantic import BaseModel, Field
from typing import Literal, Optional

    """Alert generated when network anomaly is detected."""
    device_id: str = Field(description="Affected device ID")
    severity: Literal["LOW", "MED", "HIGH", "CRITICAL"]
    metric: str = Field(description="The metric that triggered the alert")
    current_value: float
    threshold: float
    suggested_action: str
    notify_oncall: bool = Field(default=False, description="Page the on-call engineer")

def pydantic_to_anthropic_tool(model: type[BaseModel], tool_name: str) -> dict:
    """Convert a Pydantic model into an Anthropic tool definition."""
    schema = model.model_json_schema()
    # Remove Pydantic-specific meta fields
    schema.pop("$defs", None)
    schema.pop("title", None)
    return {
        "name": tool_name,
        "description": model.__doc__ or "",
        "input_schema": schema
    }

tool = pydantic_to_anthropic_tool(NetworkAlert, "send_network_alert")

# Use with Anthropic API

    model="claude-opus-4-5", max_tokens=512,
    tools=[tool],
    tool_choice={"type": "tool", "name": "send_network_alert"},
    messages=[{"role": "user", "content": "JNP-001 CPU is 94%, threshold is 80%. Create an alert."}]
)

# Deserialize directly into Pydantic model!
tool_input = response.content[0].input
alert = NetworkAlert.model_validate(tool_input)

Dynamic Schema Generation for Adaptive Agents

Python — Runtime Pydantic Schema Builder
from pydantic import BaseModel, create_model
from pydantic.fields import FieldInfo
from typing import Literal, get_args

def build_agent_output_model(
    required_fields: list[tuple[str, type, str]],
    enum_fields: dict[str, list[str]] = None,
    model_name: str = "DynamicAgentOutput"
) -> type[BaseModel]:
    """Build a Pydantic model dynamically at runtime.

    Args:
        required_fields: List of (name, type, description) tuples
        enum_fields: Dict of field_name -> allowed_values for enums
    """
    field_definitions = {}
    annotations = {}

    for name, typ, desc in required_fields:
        if enum_fields and name in enum_fields:
            values = enum_fields[name]
            # Dynamically create Literal type
            lit_type = Literal[tuple(values)]
            annotations[name] = lit_type
        else:
            annotations[name] = typ
        field_definitions[name] = FieldInfo(description=desc)

    model = create_model(
        model_name,
        **{k: (annotations[k], v) for k, v in field_definitions.items()}
    )
    return model

# Example: build a model based on runtime config
DynamicReport = build_agent_output_model(
    required_fields=[
        ("device_id", str, "The device ID"),
        ("status", str, "Device status"),
        ("score", float, "Anomaly score 0-1"),
    ],
    enum_fields={"status": ["healthy", "degraded", "failed"]}
)

schema = DynamicReport.model_json_schema()
print(f"Built schema with {len(schema['properties'])} fields")

Section 07

Production Patterns

Hard-won lessons for using JSON Schema and structured outputs in real production AI systems.

Pattern 1 — Schema Strictness Gradient

Use strict schemas (additionalProperties: false) for tool inputs and final outputs. Use lenient schemas for intermediate chain-of-thought reasoning — overly strict schemas at every step causes models to over-focus on structure over reasoning quality.

Pattern 2 — Descriptions are Prompts

The description field in JSON Schema is not just documentation — it's an instruction to the LLM. Write descriptions as imperative prompts: "Return a score between 0 and 1 where 0 means completely normal and 1 means definitely anomalous" outperforms "Anomaly score" every time.

Pattern 3 — Schema-Driven Retry Budget

Cap retries at 3. After 3 failures, log the schema errors and the model output, then fail gracefully — don't retry infinitely. The most common cause of repeated failures is a schema/prompt mismatch, not model randomness.

Pattern 4 — Never Validate in Production with validate()

The jsonschema.validate() function raises on the first error. In production, always use Draft7Validator.iter_errors() to collect all errors — then send them all back to the model for self-correction in one retry call.

Python — Complete Production Pattern
import instructor, anthropic, json
from pydantic import BaseModel, Field
from typing import Literal
import logging

logger = logging.getLogger("agent.schema")

class DeviceAnalysisOutput(BaseModel):
    device_id: str = Field(description="Device ID in format XXX-000")
    risk_level: Literal["LOW", "MED", "HIGH"] = Field(
        description="Risk: LOW=monitor, MED=schedule maintenance, HIGH=immediate action"
    )
    anomaly_score: float = Field(
        ge=0, le=1,
        description="0.0=completely normal, 1.0=definite failure imminent"
    )
    root_cause: str = Field(
        description="Single most likely root cause in one sentence"
    )
    actions: list[str] = Field(
        min_length=1, max_length=5,
        description="Concrete remediation steps, ordered by priority"
    )

def analyze_device(
    device_id: str,
    telemetry: dict,
    max_retries: int = 3
) -> DeviceAnalysisOutput | None:
    """Production-grade device analysis with schema validation."""
    client = instructor.from_anthropic(anthropic.Anthropic())

    try:
        result = client.messages.create(
            model="claude-opus-4-5",
            max_tokens=1024,
            response_model=DeviceAnalysisOutput,
            max_retries=max_retries,
            messages=[{
                "role": "user",
                "content": f"Analyze device {device_id} with telemetry: {json.dumps(telemetry)}"
            }]
        )
        logger.info(f"Analysis complete: {device_id} → {result.risk_level}")
        return result

    except Exception as e:
        logger.error(f"Analysis failed for {device_id}: {e}")
        return None   # Fail gracefully
