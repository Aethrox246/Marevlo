// 03 — TOOL / FUNCTION SCHEMAS

Writing Schemas the LLM Trusts

A schema is a contract. Every field below is load-bearing. Get any of them wrong and the model will hallucinate, drop arguments, or pick the wrong tool.

tools/get_weather.json // LLM-FACING CONTRACT 
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Resolve the current weather for a city. Use whenever the user asks about temperature, conditions, rain, snow, or wind.",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "City name. May include country, e.g. 'Bhopal, IN'."
        },
        "units": {
          "type": "string",
          "enum": ["celsius", "fahrenheit"],
          "default": "celsius"
        }
      },
      "required": ["city"]
    }
  }
}
// FIELD GUIDE
NAME

Stable, snake_case, < 32 chars. The LLM emits this verbatim in tool_calls[i].function.name.

DESCRIPTION

Verbs + use-cases, not just nouns. Bad: "weather tool". Good: "Resolve current weather for a city. Use when the user asks about temperature…"

PARAMETERS

Always JSON Schema, type object. Use enum for closed sets — the model respects them. Use default for optional args.

REQUIRED

List the names that MUST be present. The runtime validates before calling. Anything not required is optional with a default.

DO
  • • Describe when to call, not just what it does.
  • • Constrain with enum where the answer is closed.
  • • Include format hints in arg descriptions ("ISO-8601", "URL", "snake_case").
  • • Keep the tool's effect idempotent when possible — the agent may retry.
DON'T
  • • Bundle 5 unrelated capabilities into one tool. Split them.
  • • Use ambiguous arg names like data or params.
  • • Forget required — the model will fabricate args.
  • • Expose internal IDs the user has no way to provide.
RULE OF THUMB

If a senior engineer can't pick the right tool from the registry by reading only the descriptions, the LLM can't either. Schemas are docs for a non-human reader who reads them every turn.

// 04 — MANUAL REACT LOOP

The Loop, in ~30 Lines

No frameworks. Just an SDK client, a while loop, and a dictionary of Python functions. This is what every agent library eventually boils down to.

// RUNTIME EXECUTION PIPELINE
USER MSG
LLM CALL
DECIDE
EXECUTE TOOLS
APPEND RESULTS
FINAL ANSWER
agent.py — the loop // PYTHON 3.11+ 
from openai import OpenAI
import json

client = OpenAI()

def run_agent(user_msg, tools, tool_impls, max_steps=10):
    messages = [
        {"role": "system", "content": "You are a careful assistant. Call tools when needed."},
        {"role": "user",   "content": user_msg},
    ]

    for step in range(max_steps):
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            tools=tools,
        )
        msg = resp.choices[0].message
        messages.append(msg)   # preserve assistant turn

        if not msg.tool_calls:
            return msg.content        # terminal answer

        for call in msg.tool_calls:
            name = call.function.name
            args = json.loads(call.function.arguments)
            result = tool_impls[name](**args)
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": json.dumps(result),
            })

    raise RuntimeError("step budget exceeded")
L02

Single import. No agent framework anywhere.

L06

tool_impls is a dict[str, Callable]. Name → Python function. This is the bridge between LLM intent and real execution.

L13

The while-loop with a step budget. Every framework wraps this same construct.

L22

If the model emits no tool_calls, it's done. Return the natural-language answer.

L25

Iterate over tool_calls — there can be multiple. We'll exploit this in the parallel section.

L29

Append a role="tool" message with the same tool_call_id. This is how the model correlates request and response.

weather_tool.py — Python implementation // 2 / 4 
import requests

def get_weather(city: str, units: str = "celsius") -> dict:
    """Wraps Open-Meteo. Returns {temp, conditions, wind_kph}."""
    # 1. Geocode
    geo = requests.get(
        "https://geocoding-api.open-meteo.com/v1/search",
        params={"name": city, "count": 1},
    ).json()
    if not geo.get("results"):
        return {"error": f"city not found: {city}"}
    lat, lon = geo["results"][0]["latitude"], geo["results"][0]["longitude"]

    # 2. Forecast
    wx = requests.get(
        "https://api.open-meteo.com/v1/forecast",
        params={
            "latitude": lat, "longitude": lon,
            "current": "temperature_2m,weather_code,wind_speed_10m",
            "temperature_unit": "celsius" if units == "celsius" else "fahrenheit",
        },
    ).json()
    cur = wx["current"]
    return {
        "temp": cur["temperature_2m"],
        "units": units,
        "wind_kph": cur["wind_speed_10m"],
    }

// MENTAL MODEL

Multi-step is not a special mode. It is the same loop running more iterations because the model keeps emitting tool_calls.

Conversation state is preserved in messages — appending each assistant turn and each tool result.

The model reads the entire trajectory every step. It "sees" all prior observations.

Step counts compound token usage quadratically — context grows with each appended observation.

The terminal step is whichever LLM call returns with tool_calls == None.

// 07 — PARALLEL TOOL CALLS

Concurrent Execution, Same Loop

Modern LLMs can emit N tool calls per turn. If they are independent, run them concurrently. The latency win is huge.

SEQUENTIAL (NAIVE)
SLOW
get_weather("Mumbai")  →  800ms
get_weather("Delhi")    →  800ms
get_weather("Bhopal")  →  800ms
2,400ms

Three independent calls, run one after another. Wasteful.

PARALLEL (CORRECT)
FAST
get_weather("Mumbai")  ║
get_weather("Delhi")    ║  ALL CONCURRENT
get_weather("Bhopal")  ║
~800ms

All three fire at once. Wall time = slowest call. 3× speedup.

parallel_exec.py — replacement for the inner for-loop // USE asyncio.gather OR concurrent.futures 
from concurrent.futures import ThreadPoolExecutor
import json

# Replace the per-call for-loop with this:
def execute_tool_calls(tool_calls, tool_impls):
    def _one(call):
        name = call.function.name
        args = json.loads(call.function.arguments)
        try:
            result = tool_impls[name](**args)
        except Exception as e:
            result = {"error": str(e)}    # surface to LLM, don't crash
        return {
            "role": "tool",
            "tool_call_id": call.id,
            "content": json.dumps(result),
        }

    with ThreadPoolExecutor(max_workers=8) as pool:
        return list(pool.map(_one, tool_calls))
CAVEAT 01

Parallelize only when calls are independent. If call B needs the output of call A, the model will simply not emit them together.

CAVEAT 02

Some tools are not thread-safe (shared connection pools, file handles). Use asyncio with async tools or isolate state per worker.

CAVEAT 03

Order of results doesn't matter — each carries its tool_call_id and the model matches them itself.

// 08 — ERROR RECOVERY

Failing Gracefully

Real tools fail. APIs time out. Arguments come back malformed. The agent must see the failure as an observation and try something else — not crash.

❌ NAIVE — TOOL EXCEPTION CRASHES LOOP 
for call in msg.tool_calls:
    args = json.loads(call.function.arguments)
    result = tool_impls[name](**args)   # 💥 raises → crash
    messages.append({...})

A single failed API call kills the entire trajectory. User sees a stack trace, not an answer.

✓ RESILIENT — ERROR BECOMES OBSERVATION 
for call in msg.tool_calls:
    try:
        args = json.loads(call.function.arguments)
        result = tool_impls[name](**args)
    except Exception as e:
        result = {"error": str(e), "hint": "retry with corrected args"}
    messages.append({"role": "tool", "content": json.dumps(result)})

The error becomes part of the trajectory. The LLM reads it and can re-plan — often it self-corrects on the next step.

// FOUR FAILURE MODES YOU HANDLE
Malformed arguments
LLM emits JSON the tool can't parse, or wrong types.
JSONDecodeError / TypeError
Return {"error": "..."}. Model re-emits corrected args next step.
Tool runtime exception
API down, timeout, 5xx, network hiccup.
requests.Timeout / 5xx
Catch broadly, return the error string. Add retries-with-backoff for known-transient codes.
Unknown tool name
Model hallucinates a tool that doesn't exist.
KeyError
Return {"error": "no such tool 'X'; available: [...]"}.
Step budget exceeded
Agent loops without converging on an answer.
RuntimeError
Raise to the caller. Hard cap is non-negotiable — protects cost & latency.

Principle: in an agent, errors are not failures — they are observations. As long as the loop survives, the LLM gets another chance. The runtime's job is to keep the loop alive and surface the error in plain text the model can reason about.

// 09 — WHY MANUAL MATTERS

Why You Did This By Hand

Track 2 hands you LangChain and LangGraph. Track 4 hands you LangGraph Platform. But the agents that survive production are debugged by people who know what the framework is doing underneath.

Frameworks present "agent" as a single class. In reality there are five things stacked: the SDK client, the message-building logic, the tool dispatcher, the loop controller, and the termination predicate. When the framework swallows an error or terminates early, you reach for the raw HTTP request and inspect what was actually sent. Without this module's mental model, that inspection is meaningless.
OpenAI returns tool_calls with stringified JSON args. Anthropic returns structured input dicts inside tool_use blocks. Some OSS models return XML. Frameworks abstract this — but the abstraction breaks when you switch providers or pin a niche model. Knowing the raw shape lets you write adapters in five minutes instead of waiting for the framework to support your stack.
Compressing context between steps, routing the cheap model for early steps and the expensive one for synthesis, summarizing old observations — all of these are interventions in the loop. Module 4.3 (Agent Cost Engineering) is built on the exact code you wrote here. Frameworks bury these levers; the raw loop exposes them.
Because you wrote the loop, you control the messages list. Persist it and you have a perfect replay artifact — the entire trajectory, deterministic up to the model. Track 3 (Agent Evaluation) and Module 4.2 (Agent Observability) both depend on this. The framework version of "tracing" is usually a watered-down subset of what you can do with raw messages.
