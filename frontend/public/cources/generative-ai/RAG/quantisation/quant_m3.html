01 · vLLM Internals — PagedAttention and Continuous Batching

The OS Memory Manager
Inside Your LLM Server

Traditional LLM serving pre-allocates a contiguous GPU memory block for each request's KV cache at request arrival — sized for the maximum possible output length. This wastes 40-60% of GPU memory: a request that generates 100 tokens but was allocated 2048 slots wastes 1948 slots of KV cache. PagedAttention (Kwon et al. 2023) borrows the OS virtual memory abstraction: KV cache is divided into fixed-size blocks (pages), mapped via a block table, allocated on-demand as tokens are generated, and freed immediately when the request completes. Combined with continuous batching, vLLM achieves 2-4× higher throughput than static batching approaches.

from vllm import AsyncLLMEngine, AsyncEngineArgs, SamplingParams
from vllm.engine.arg_utils import EngineArgs
import asyncio, time

# ── 1. ENGINE CONFIGURATION WITH QUANTIZATION ───────────────────────────────
def create_quantized_engine(
    model: str        = 'meta-llama/Meta-Llama-3-70B-Instruct',
    quantization: str = 'awq',          # 'awq'|'gptq'|'squeezellm'|None
    gpu_util: float   = 0.92,           # fraction of GPU memory for KV cache
    tp_size: int      = 2,               # tensor parallel across N GPUs
    max_model_len: int = 32768,          # max sequence length (context window)
    block_size: int   = 16,             # KV cache block size (tokens per page)
    enable_prefix_caching: bool = True,  # RadixAttention prefix cache
    kv_cache_dtype: str = 'fp8',        # 'auto'|'fp8'|'fp8_e5m2'
) -> AsyncLLMEngine:
    """
    Production vLLM engine setup for quantized LLM serving.

    Key configuration decisions:
    gpu_memory_utilization: controls KV cache size.
      KV_cache_bytes = GPU_memory × gpu_util − model_weights_bytes
      For LLaMA-3-70B AWQ-INT4 on 2×A100-80GB:
        model_weights = 35GB (INT4) across 2 GPUs = 17.5GB each
        KV_cache = (80 × 0.92) − 17.5 = 56.1GB per GPU = 112GB total
        At FP16 per token: 112GB / (2×96×128×2) = ~28K concurrent tokens

    block_size: must balance memory waste vs overhead.
      Too small (4): many block table entries, high metadata overhead
      Too large (64): up to 63 tokens wasted per request tail
      Default 16 is optimal for most workloads

    enable_prefix_caching: RadixAttention stores KV blocks by hash of token sequence.
      Requests sharing a system prompt (RAG) reuse the prefix KV blocks.
      Hit rate in RAG: 60–80%. Saves: hit_rate × prefix_len × KV_size per request.

    kv_cache_dtype='fp8': store KV cache in FP8 instead of FP16.
      2× memory reduction → 2× more concurrent requests.
      Accuracy: <0.3% perplexity degradation on standard benchmarks.
    """
    engine_args = AsyncEngineArgs(
        model=model,
        quantization=quantization,
        gpu_memory_utilization=gpu_util,
        tensor_parallel_size=tp_size,
        max_model_len=max_model_len,
        block_size=block_size,
        enable_prefix_caching=enable_prefix_caching,
        kv_cache_dtype=kv_cache_dtype,
        enforce_eager=False,           # CUDA graph for decode step
        max_num_batched_tokens=32768,   # max tokens across all concurrent seqs
        max_num_seqs=256,               # max concurrent requests
    )
    return AsyncLLMEngine.from_engine_args(engine_args)


# ── 2. CONTINUOUS BATCHING REQUEST HANDLER ───────────────────────────────────
async def handle_request(engine: AsyncLLMEngine, prompt: str,
                          request_id: str, max_tokens: int = 512) -> dict:
    """
    Async streaming generation with continuous batching.

    Continuous batching (Orca algorithm):
    vLLM processes tokens from MULTIPLE requests in each GPU kernel call.
    When request A finishes at step 50, request D (waiting) is immediately
    added to the batch at step 51 — no GPU idle time waiting for a full batch.

    Contrast with static batching: all requests in a batch must finish
    before new ones start. With varied output lengths, the GPU is idle
    waiting for the slowest request. Continuous batching eliminates this:
    GPU utilisation approaches 100% under load.

    Metrics to track:
      TTFT (Time To First Token): measures prefill latency
      TBT  (Time Between Tokens): measures decode throughput per token
      ITL  (Inter-Token Latency): same as TBT at application level
    """
    params = SamplingParams(
        temperature=0.7, top_p=0.9,
        max_tokens=max_tokens,
        stop=["</s>", "[INST]"],
    )
    t0 = time.perf_counter()
    first_token_time = None
    output_tokens = []

    async for request_output in engine.generate(prompt, params, request_id):
        if first_token_time is None:
            first_token_time = time.perf_counter() - t0   # TTFT
        if request_output.outputs:
            output_tokens = request_output.outputs[0].token_ids

    total_time = time.perf_counter() - t0
    n_out = len(output_tokens)
    return {
        'ttft_ms':      round(first_token_time * 1000, 2),
        'total_s':      round(total_time, 3),
        'output_tokens': n_out,
        'tbt_ms':       round((total_time - first_token_time) / max(n_out-1,1) * 1000, 2),
        'tokens_per_sec': round(n_out / total_time, 1),
    }


# ── 3. SPECULATIVE DECODING CONFIG ─────────────────────────────────────────
def create_speculative_engine(
    target_model: str = 'meta-llama/Meta-Llama-3-70B-Instruct',
    draft_model:  str = 'meta-llama/Meta-Llama-3-8B-Instruct',
    num_speculative_tokens: int = 5,
) -> AsyncLLMEngine:
    """
    Speculative decoding: draft model proposes K tokens, target verifies in parallel.

    Mechanism:
    1. Draft model (8B) generates K=5 candidate tokens autoregressively (~5× faster)
    2. Target model (70B) evaluates all K+1 positions in ONE forward pass
       (parallel evaluation — same cost as generating 1 token normally)
    3. Accept tokens where P_target(token) ≥ P_draft(token) (rejection sampling)
    4. On rejection, resample from target distribution and restart

    Expected speedup: K × acceptance_rate. For K=5 and rate=70%: 3.5×.
    Effective throughput: 70B speed × 3.5 = ~comparable to 8B alone.
    Accuracy: mathematically identical to target model (rejection sampling guarantee).

    When to use: latency-critical applications where target quality is required.
    Cost: extra GPU memory for draft model (8B AWQ ≈ 4GB).
    """
    engine_args = AsyncEngineArgs(
        model=target_model,
        speculative_model=draft_model,
        num_speculative_tokens=num_speculative_tokens,
        speculative_draft_tensor_parallel_size=1,
        use_v2_block_manager=True,
    )
    return AsyncLLMEngine.from_engine_args(engine_args)
🔑

Continuous batching: why GPU utilisation approaches 100%

Static batching: all requests in a batch must finish before new ones start. With mixed output lengths (some 50 tokens, some 500 tokens), the GPU idles waiting for the slowest request while the fast requests' slots sit empty. Continuous batching (Orca, 2022): the scheduler makes a decision at EVERY decode step — which sequences should participate in this step's forward pass? When request R finishes (outputs EOS token), its KV blocks are freed and a queued request S is immediately scheduled for the next step. The GPU sees a continuous stream of full-batch forward passes with no idle gaps. Practical improvement: 2-4× throughput at high load.

💡

Speculative decoding: parallelise the sequential bottleneck

Autoregressive decode is inherently sequential — each token depends on all previous. Speculative decoding breaks this: the small draft model (8B) generates K=5 candidate tokens in K sequential steps (fast). The large target model (70B) verifies all K+1 positions in ONE parallel forward pass (same cost as 1 token). Tokens are accepted via rejection sampling — mathematically identical to running the target alone. Expected speedup: 1.5-3× for K=5 at α=70-80% acceptance. Best for: single-request, latency-critical scenarios where batch_size=1.

02 · TensorRT-LLM and Benchmark Reality

Kernel Fusion vs System Scheduling:
Real Numbers

TensorRT-LLM (NVIDIA) and vLLM optimise at different layers of the stack. TRT-LLM pre-compiles fused CUDA kernels for each model architecture — QKV projection + rotary embedding + grouped query attention in a single kernel launch, eliminating memory round-trips between operations. vLLM optimises the request scheduling layer — PagedAttention, continuous batching, prefix caching, speculative decoding — using standard PyTorch kernels. The result: TRT-LLM wins on latency (single-request, fixed model), vLLM wins on throughput (multi-request, diverse models).

def measure_perplexity(model: AutoModelForCausalLM,
                       tokenizer: AutoTokenizer,
                       text_path: str = 'wikitext2_test.txt',
                       stride: int = 512,
                       max_tokens: int = 8192) -> float:
    """
    Compute perplexity on WikiText-2 test set — standard LLM benchmark.

    Algorithm: sliding window perplexity to handle long documents.
    Process in chunks of max_context with stride (overlap) to handle
    context boundary effects. Average NLL across all tokens.

    Standard values for reference:
      LLaMA-2-7B FP16:  5.47 ppl  (WikiText-2)
      LLaMA-2-7B INT8:  5.52 ppl  (+0.09% vs FP16)
      LLaMA-2-7B GPTQ4: 5.63 ppl  (+2.9% vs FP16)
      LLaMA-2-7B GGUF4: 5.58 ppl  (+2.0% vs FP16)

    Rule of thumb: <0.5 ppl increase → acceptable for most tasks.
    >2.0 ppl → noticeable quality degradation in generation.
    """
    encodings = tokenizer(open(text_path).read(), return_tensors='pt')
    input_ids = encodings.input_ids[0, :max_tokens]
    total_nll, total_tokens = 0.0, 0
    max_ctx = model.config.max_position_embeddings
    for start in range(0, len(input_ids) - 1, stride):
        end = min(start + max_ctx, len(input_ids))
        ids = input_ids[start:end].unsqueeze(0).to(model.device)
        target_len = end - start - stride if start > 0 else end - start - 1
        with torch.no_grad():
            loss = model(ids, labels=ids).loss
        total_nll += loss.item() * target_len
        total_tokens += target_len
    return math.exp(total_nll / total_tokens)


def benchmark_throughput(engine_url: str, n_requests: int = 100,
                          prompt_len: int = 512, output_len: int = 256) -> dict:
    """
    Measure serving throughput: send N concurrent requests, record metrics.

    Key metrics:
      throughput = total_output_tokens / total_wall_time
      p50/p95/p99 TTFT: distribution of time-to-first-token
      p50/p95/p99 TBT:  inter-token latency distribution
    """
    import httpx, asyncio
    prompt = " the" * prompt_len  # synthetic prompt of target length
    results = []
    async def send(client, req_id):
        t0 = time.perf_counter()
        async with client.stream('POST', f'{engine_url}/generate', json={
            'prompt': prompt, 'max_tokens': output_len, 'stream': True
        }, timeout=120) as resp:
            first, chunks = None, 0
            async for _ in resp.aiter_lines():
                if first is None: first = time.perf_counter() - t0
                chunks += 1
        results.append({'ttft': first, 'total': time.perf_counter()-t0, 'tokens': chunks})
    async def run_all():
        async with httpx.AsyncClient() as c:
            await asyncio.gather(*[send(c, i) for i in range(n_requests)])
    asyncio.run(run_all())
    ttfts = sorted(r['ttft'] for r in results)
    total_tok = sum(r['tokens'] for r in results)
    wall = max(r['total'] for r in results)
    return {'throughput_tps': round(total_tok / wall),
            'ttft_p50_ms': round(ttfts[n_requests//2]*1000),
            'ttft_p99_ms': round(ttfts[int(n_requests*.99)]*1000)}

The continuous batching multiplier — why AWQ+vLLM costs 4× less

AWQ INT4 single-request: 2700 tokens/sec. AWQ+vLLM under load: 6800 tokens/sec. The difference is continuous batching amortising fixed overhead (model weight reads, CUDA launch latency) across many concurrent requests. This directly reduces cost-per-token: the GPU serves 2.5× more tokens per unit time → cost/token drops proportionally. At $3/hr for an A100, FP16 single-request costs $0.17/1M tokens; AWQ+vLLM costs $0.04/1M — a 4.25× cost reduction. This is why model quantization + serving stack optimization together yield 10-15× cost reduction vs naïve FP16 single-request serving.

Question 1 of 8

A vLLM deployment of LLaMA-3-70B-Instruct (AWQ INT4, 2×A100-80GB, gpu_memory_utilization=0.92) receives 500 concurrent requests each with 512 input tokens and 256 output tokens. Why does throughput with vLLM's continuous batching massively exceed the naive HuggingFace approach, and what is the theoretical max concurrent tokens in flight?

Continuous batching mechanics: The critical insight is that 'batch' in vLLM is not fixed across decode steps. At each step, the scheduler checks: which sequences need a decode step? Those form the batch. When a sequence finishes (outputs EOS), it's immediately evicted from the KV cache and replaced by a queued request. This keeps the GPU maximally busy regardless of output length variance. The practical throughput improvement: 2-4× over static batching at high load, measured in tokens/second across all concurrent requests.
Question 2 of 8

PagedAttention uses a block table to map logical KV cache positions to physical GPU memory blocks. Explain how this enables prefix caching (RadixAttention) and calculate the memory saving for a RAG system with a 2048-token system prompt serving 10K requests per hour.

RadixAttention (vLLM v0.4+): The block table is the key enabler. Because logical and physical addresses are decoupled, multiple requests can have their logical positions 0-N pointing to the same physical blocks — this is shared-memory semantics, exactly like OS page sharing for shared libraries. The hash of a token sequence prefix uniquely identifies which physical blocks represent it. On cache hit: attach those blocks to the new request's logical table in O(1). On cache miss: allocate new blocks, compute KV, store by hash. Eviction: LRU, with recently-completed requests' unique blocks freed first.

Speculative decoding uses a small draft model to propose K tokens, which the large target model verifies in one forward pass. With a 70B target and 8B draft model, K=5 speculative tokens, and a token acceptance rate α=0.72: calculate the expected speedup and explain when speculative decoding fails to help.

Speculative decoding analysis: The correct speedup formula captures draft overhead. The key insight is that each target forward pass now produces ~E[accepted] ≈ 3 tokens instead of 1 — but costs slightly more than 1 target call due to draft inference. The batch_size=1 requirement is the most important practical limitation: at high throughput with many concurrent requests, the verification step must check all K+1 positions for each request independently, and the batch cannot mix different speculative positions. This is why speculative decoding is primarily used for latency-critical single-request scenarios (chatbots, coding assistants) not throughput-maximising serving (batch APIs).
Question 4 of 8

TensorRT-LLM achieves lower latency than vLLM for the same model and hardware. What architectural difference explains this, and under what deployment scenario would you choose vLLM over TensorRT-LLM despite the latency advantage?

The kernel vs scheduling dichotomy: TRT-LLM achieves 20-40% lower TTFT vs vLLM for single-request scenarios through kernel fusion and architecture-specific optimisations. But this comes at a cost: compilation takes hours, new model architectures require engineering effort, and the system is less flexible. vLLM's strength is its scheduler: continuous batching can improve throughput 4-10× over naive serving. The practical recommendation: use TRT-LLM for a fixed flagship model with strict latency SLAs (e.g. production coding assistant). Use vLLM for diverse model serving, rapid iteration, or when throughput > latency matters.
Question 5 of 8

A production RAG system serves 1000 QPS with mixed request types: 70% short queries (128 input, 128 output tokens) and 30% long context (4096 input, 512 output tokens). AWQ INT4 LLaMA-3-70B on 4×H100-80GB. Estimate the KV cache memory split and explain why continuous batching handles this workload better than static batching.

Mixed workload dynamics: The core challenge is that static batching treats all requests in a batch as atomic — the batch is only done when ALL requests finish. With 70% short requests that finish 4× faster, static batching wastes 70% of batch capacity for 75% of the execution time. Continuous batching's per-step scheduling means short requests never block new arrivals. The KV memory calculation shows the system is compute-bound (not memory-bound) at these parameters — 468K tokens in flight vs 836K capacity means 56% utilisation, leaving headroom for bursts.
Question 6 of 8

Your company's CI/CD pipeline needs to detect quantization quality regression automatically. You have access to: a held-out evaluation dataset (WikiText-2 + internal domain data), a baseline FP16 model, and any quantized model variant. Design a regression testing framework with thresholds, and explain what 'quantization drift' means in production.

Quantization drift in production: Fixed quantized weights don't change, but the input distribution does — and quantization quality is distribution-dependent. The scale factors s_j set during calibration assume the activation magnitudes follow a certain distribution. When production inputs shift (new language, new topic domain, seasonal events, user behaviour changes), activations may develop different outlier patterns than calibration data, causing previously-adequate scales to produce higher quantization error. This is analogous to covariate shift in ML but at the numerical precision level. The three-tier regression framework ensures: fast CI/CD gating, thorough quality validation, and continuous production monitoring.

Question 8 of 8

Comparing vLLM, TensorRT-LLM, and llama.cpp for deploying AWQ INT4 LLaMA-2-13B: throughput is 4800 tokens/sec (vLLM), 6200 tokens/sec (TRT-LLM), and 45 tokens/sec (llama.cpp CPU). Why is llama.cpp so much slower, and under what real business scenario would you choose it over the GPU options?

Memory bandwidth determines decode speed: This is the central insight of LLM serving. At batch_size=1, each forward pass reads every weight once — this is fully memory-bandwidth-bound. The 100× CPU-GPU gap maps almost exactly to the 100× memory bandwidth gap. llama.cpp on Apple M2 Max is a notable exception: M2 Max has 400GB/s unified memory bandwidth and achieves 60-70 tokens/sec for 13B models — 4-7× faster than CPU-only. The llama.cpp CPU path makes genuine business sense for privacy-critical on-premises deployments where $10K/year for a single GPU node is too expensive or not allowed by compliance requirements.
