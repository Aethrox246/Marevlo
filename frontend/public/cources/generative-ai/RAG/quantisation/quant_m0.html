01 · Foundations — The Mathematics of Quantization

From FP32 to INT4:
The Precision–Memory Equation

Quantization maps a continuous floating-point value x to a discrete integer q using a scale factor s: q = round(x/s), reconstructed as x̂ = s·q. This single equation, applied across billions of model weights and activation tensors, is what makes modern LLM deployment economically viable. Every design decision in the quantization stack — how to choose s, whether to use per-tensor or per-channel scales, symmetric vs asymmetric, when to calibrate — flows from understanding this fundamental trade-off: fewer bits means smaller scale steps, which means more rounding error, which means lower model accuracy.

quantization_toolkit.py — scalar, per-channel, symmetric/asymmetric + SmoothQuant

import torch
import torch.nn as nn

# ── 1. SCALAR QUANTIZATION FUNDAMENTALS ────────────────────────────────────
def quantize_symmetric(x: torch.Tensor, bits: int = 8) -> tuple:
    """
    Symmetric uniform scalar quantization.
    q = round(x / s)  where  s = max(|x|) / (2^(bits-1) - 1)
    Reconstruction: x̂ = s * q

    Why symmetric? Weights are approximately zero-centred — no zero-point needed.
    INT8 range: [-127, 127]  (exclude -128 to avoid asymmetry issues)
    INT4 range: [-7, 7]
    """
    n = 2 ** (bits - 1) - 1                   # 127 for INT8, 7 for INT4
    s = x.abs().max() / n                         # scale factor
    q = (x / s).round().clamp(-n, n).to(torch.int8)
    x_hat = s * q.float()
    err = (x - x_hat).abs().mean().item()
    return q, s, x_hat, err


def quantize_asymmetric(x: torch.Tensor, bits: int = 8) -> tuple:
    """
    Asymmetric quantization: includes zero-point offset z.
    q = round(x / s) + z   where s = (max-min) / (2^bits - 1), z = -round(min/s)
    Reconstruction: x̂ = s * (q - z)

    Why asymmetric? ReLU activations are non-negative — using full [0, 255] range
    is more efficient than centering at zero.
    """
    n = 2**bits - 1
    x_min, x_max = x.min().item(), x.max().item()
    s = (x_max - x_min) / n
    z = -round(x_min / s)
    q = ((x / s) + z).round().clamp(0, n).to(torch.uint8)
    x_hat = s * (q.float() - z)
    return q, s, z, x_hat


# ── 2. PER-CHANNEL QUANTIZATION (critical for weight matrices) ─────────────
def per_channel_quantize(W: torch.Tensor, bits: int = 8) -> tuple:
    """
    Each output channel has its own scale factor.
    W: (out_features, in_features) — scale per row.

    Why per-channel? Different channels of a weight matrix have very different
    value distributions. A single global scale wastes bits on small-magnitude
    channels while clipping large-magnitude ones.
    Accuracy improvement over per-tensor: ~1-3% on INT8, ~5-8% on INT4.
    """
    n = 2 ** (bits - 1) - 1
    # Per-row scale: shape (out_features, 1) for broadcasting
    s = W.abs().max(dim=1, keepdim=True).values / n
    q = (W / s).round().clamp(-n, n).to(torch.int8)
    W_hat = s * q.float()
    return q, s.squeeze(), W_hat


# ── 3. SMOOTHQUANT — KEY INSIGHT: migrate outliers from activations to weights
def smoothquant_transform(X: torch.Tensor, W: torch.Tensor,
                           alpha: float = 0.5) -> tuple:
    """
    SmoothQuant (Xiao et al., ICML 2023) — INT8 LLM inference without accuracy loss.

    The Problem: Activations X have HUGE outliers in certain channels (up to 1000×
    the typical value). Quantizing these destroys accuracy — the scale must cover
    the outlier, wasting bits on small values elsewhere.

    The Insight: The linear operation Y = X @ W is unchanged by:
        Y = (X @ diag(s)^-1) @ (diag(s) @ W)
    Move the hard-to-quantize part (outliers) from activations to weights.

    smoothing_factor: s_j = max(|X_j|)^alpha * max(|W_j|)^(1-alpha)
    - alpha=0.5: balanced migration
    - alpha→0: keep difficulty in activations (avoid if activations are hard)
    - alpha→1: migrate all difficulty to weights
    """
    # Compute per-channel smoothing factor
    act_max = X.abs().max(dim=0).values              # (in_features,)
    w_max   = W.abs().max(dim=0).values              # (in_features,)
    s = (act_max ** alpha) * (w_max ** (1 - alpha))
    s = s.clamp(min=1e-5)                            # prevent div/0
    X_smooth = X / s.unsqueeze(0)                    # (seq, in_features)
    W_smooth = W * s.unsqueeze(1) if W.dim() == 2 else W * s  # (out, in)
    # Now quantize the smoothed tensors — both have manageable ranges
    q_X, sX, _, _ = quantize_symmetric(X_smooth.float(), bits=8)
    q_W, sW,    _ = per_channel_quantize(W_smooth.float(), bits=8)
    return q_X, q_W, sX, sW, s


# ── 4. QUANTIZATION ERROR ANALYSIS ─────────────────────────────────────────
def quantization_snr(x: torch.Tensor, x_hat: torch.Tensor) -> float:
    """Signal-to-noise ratio in dB: higher = better quantization."""
    signal_power = (x**2).mean()
    noise_power  = ((x - x_hat)**2).mean()
    return 10 * torch.log10(signal_power / (noise_power + 1e-10)).item()
INT8 Symmetric

Weights

s = max(|W|) / 127. Best for zero-centred weight distributions. Hardware directly executes INT8 matmuls on A100/H100 Tensor Cores at 2–4× FP32 throughput.

INT8 Asymmetric

Activations

s = (max−min) / 255, z = −round(min/s). Required for ReLU outputs [0, ∞) — shifts the quantization window to cover only positive values, halving wasted bits.

Per-Channel

Accuracy Critical

One scale s_i per output channel. Each row of W has its own max → optimal range coverage. Improves INT4 accuracy by 5–8% on transformer weight matrices. Always use for weights.

🔑

The Quantization Error Equation

Quantization error ε = x − x̂ is bounded by the step size: |ε| ≤ s/2. With b bits, step size s = range / 2^b. Doubling bits halves the maximum error. But neural networks are surprisingly robust: averaging across millions of parameters means small per-element errors cancel. SNR = 6.02b + 1.76 dB for ideal quantization — each bit adds 6dB of SNR. INT8 gives ~49dB; INT4 gives ~25dB. Empirically, transformers tolerate INT4 weights with < 1% quality loss, but INT4 activations are harder — the outlier problem.

Getting INT4 right requires more than applying the scalar formula. Weights have outliers, activations have channel-wise structure, and fine-tuning requires gradient flow through discrete operations. Four methods have emerged as the production standard, each targeting a different failure mode of naïve quantization.

turboquant.py — TurboQuant KV cache compression: random rotation + sketch + sign

import torch
import torch.nn.functional as F
from dataclasses import dataclass

@dataclass
class TurboQuantState:
    """Compressed KV vector state — all you need to reconstruct."""
    q_coarse:   torch.Tensor    # INT4 quantized rotated vector
    scale:      float           # scalar quantization scale
    sign_sketch: torch.Tensor   # ±1 bit sketch of residual projection
    R:          torch.Tensor    # rotation matrix (shared across all KV vectors)
    S:          torch.Tensor    # sketch matrix (shared across all KV vectors)
    alpha:      float           # sketch reconstruction scale


class TurboQuantCompressor:
    """
    TurboQuant: Vector quantization for KV cache (Google Research, 2024).
    
    Key innovation over scalar INT4:
    - Scalar INT4 quantizes each element independently: treats 4096-dim KV
      vector as 4096 unrelated scalars. Misses inter-dimensional structure.
    - TurboQuant encodes the residual error as a random projection SIGN SKETCH,
      recovering correlation information scalar methods ignore.
    
    Bit budget (d=4096, m=256 sketch dimensions):
      INT4 coarse:    4 bits × 4096  =  16,384 bits
      Sign sketch:    1 bit  × 256   =     256 bits
      Scale:          16 bits (fp16) =      16 bits  
      Total:          ~16,656 bits / 4096 dims ≈ 4.06 bits/dim
    
    Compared to FP16: 16 bits → 4 bits = 4× compression
    Accuracy vs INT4 standalone: 20-40% lower perplexity degradation
    at same bit rate. Why? Residual sketch recovers systematic errors.
    """

    def __init__(self, dim: int, sketch_dim: int, bits: int = 4):
        """
        dim:        KV vector dimension (e.g. 4096 for LLaMA-2-70B)
        sketch_dim: residual sketch size (m << d, e.g. 256)
        bits:       coarse quantization bits (4 for INT4)
        """
        self.dim = dim
        self.m   = sketch_dim
        self.bits = bits
        self.n   = 2 ** (bits - 1) - 1   # 7 for INT4
        # Shared matrices: generated ONCE per model, reused for all KV vectors
        self.R = self._hadamard_rotation(dim)  # orthogonal rotation
        self.S = (torch.randn(sketch_dim, dim) / dim**0.5)  # random proj
        self.alpha = (dim / sketch_dim) ** 0.5   # JL lemma scaling

    def _hadamard_rotation(self, n: int) -> torch.Tensor:
        """Randomised Hadamard Transform — O(n log n) instead of O(n²)."""
        import math
        signs = (torch.randint(0, 2, (n,)) * 2 - 1).float()
        # Build Hadamard via butterfly operations (efficient, exact orthogonal)
        H = torch.eye(n)
        step = 1
        while step < n:
            H_new = torch.zeros_like(H)
            H_new[:, ::2*step] = (H[:, :step] + H[:, step:2*step]) / 2**0.5
            H_new[:, step:2*step::step] = (H[:, :step] - H[:, step:2*step]) / 2**0.5
            H = H_new; step *= 2
        return H * signs  # randomised signs break structure for better compression

    def compress(self, kv: torch.Tensor) -> TurboQuantState:
        """Compress one KV vector: (d,) float → TurboQuantState."""
        # Step 1: Random rotation — spreads outliers uniformly
        y = self.R @ kv                                     # (d,)
        # Step 2: Coarse scalar quantization
        s = y.abs().max().item() / self.n
        q = (y / s).round().clamp(-self.n, self.n)
        # Step 3: Residual (quantization error in rotated space)
        y_tilde = s * q
        r = y - y_tilde                                     # (d,)
        # Step 4+5: Random projection + sign compression
        z = self.S @ r                                      # (m,)
        b = z.sign()                                        # ±1, 1 bit each
        return TurboQuantState(
            q_coarse=q.to(torch.int8), scale=s,
            sign_sketch=b, R=self.R, S=self.S, alpha=self.alpha
        )

    def decompress(self, state: TurboQuantState) -> torch.Tensor:
        """Reconstruct KV vector from compressed state."""
        y_tilde = state.scale * state.q_coarse.float()
        r_hat   = state.alpha * (state.S.T @ state.sign_sketch)
        y_hat   = y_tilde + r_hat
        return state.R.T @ y_hat                          # inverse rotation

    def bits_per_dim(self) -> float:
        """Effective bits per dimension stored."""
        coarse_bits = self.bits * self.dim
        sketch_bits = 1 * self.m             # 1 bit per sign
        scale_bits  = 16                      # one fp16 scale factor
        return (coarse_bits + sketch_bits + scale_bits) / self.dim
💡

GPTQ — Second-Order Weight Quantization

Quantizes weights one-at-a-time, updating remaining weights to compensate via the OBQ algorithm. After quantizing w[i,j]: W[i,k:] -= (w[i,j] − wq[i,j]) × H⁻¹[j,k:] / H⁻¹[j,j]. The Hessian H captures how much the loss cares about each weight — high-curvature weights are compensated most aggressively. Result: INT4 that matches INT8 PTQ accuracy on most LLMs. Quantizes LLaMA-70B in ~4 GPU-hours.

💡

AWQ — Activation-Aware Scaling

AWQ identifies the 1% of weight channels that cause the most output change (high activation magnitude × weight magnitude product), and protects them with higher precision or a per-channel scale multiplier. Unlike GPTQ, AWQ is hardware-friendly: the scales are folded into preceding LayerNorm parameters, so inference requires no extra operations. AWQ achieves equivalent accuracy to GPTQ at INT4 with 30% less quantization compute.

Production stack: serving LLaMA-3-70B at scale

Weights: AWQ INT4 (model size: 35GB, fits on 2×A100 80GB or 1×H100 80GB with flash attn). Activations: FP16 (SmoothQuant for INT8 activations adds 1-2% throughput, acceptable quality). KV cache: FP16 for short contexts (<8K), GQA reduces from 64→8 heads (8× savings), INT8 for long contexts. Inference engine: vLLM with PagedAttention for multi-request batching. Hardware: H100 (FP8 Tensor Cores for forward pass, INT4 weight loading). Result: 70B model serving 100+ concurrent 8K-context users on 2 H100 nodes vs 8 nodes for naïve FP16.

03 · KV Cache Compression — The Long-Context Bottleneck

128K Tokens = 342GB:
Why KV Cache Needs Vector Quantization

Model weights are a fixed one-time cost. KV cache grows linearly with every token in every request — and at 128K context lengths, it dwarfs the model itself. Scalar INT4 helps, but still leaves tens of gigabytes per request. The fundamental insight of TurboQuant is that KV vectors are not random: they exhibit structured correlations across dimensions that scalar methods ignore completely. Vector quantization of the residual error captures this structure.

TurboQuant 7-step pipeline — random rotation + coarse INT4 + residual sign sketch → 3-4 bits/dim
⚠️

Why the KV cache problem is different from weight quantization

Weights are quantized once and stay fixed — calibration can be expensive and careful. KV vectors are generated dynamically for every token in every request — compression must happen in microseconds with no offline calibration. Weights are shared across requests — quantization error amortises. KV entries are per-token and per-request — reconstruction quality directly affects attention scores for every subsequent token. This is why TurboQuant uses a fixed random rotation R and sketch matrix S (shared, precomputed) rather than data-dependent codebooks.

📐

Math: TurboQuant bit budget

Setup: d=4096, m=256 sketch dims, INT4 coarse. Coarse: 4 bits × 4096 = 16,384 bits. Sketch: 1 bit × 256 = 256 bits. Scale: 16 bits (FP16). Total: 16,656 bits / 4096 dims ≈ 4.07 bits/dim. vs FP16 (16 bits/dim) → 3.9× compression. vs INT4 standalone (4.0 bits/dim) → nearly identical bit rate but 20-40% less perplexity degradation because the sign sketch captures residual structure that scalar INT4 misses entirely. At 128K context: 342GB FP16 → ~88GB TurboQuant.

Question 1 of 8

A vector x = [3.2, 0.01, 0.008, 0.003] is quantized to INT8 symmetrically. The tiny values 0.01, 0.008, 0.003 all quantize to 0. Why, and how does SmoothQuant fix this?

SmoothQuant's core insight: the problem is not that INT8 is too coarse — it's that outliers in one channel force the scale to be set too high, wasting all precision on covering the outlier while leaving small values underrepresented. The mathematical identity Y = (X·diag(s)⁻¹)·(diag(s)·W) lets us migrate the outlier magnitude from the hard-to-quantize activations to the easier-to-quantize weight side, leveling the difficulty across both.
Question 2 of 8

GPTQ quantizes a weight matrix W to INT4 by minimising ‖W − Wq‖_H where H is the approximate Hessian of the loss. What is the intuition behind using the Hessian here, and why is INT4 possible without QAT?

GPTQ (Frantar et al. 2022): The key algorithmic element is the OBC (Optimal Brain Compression) row update. After quantizing weight W[i,j], all remaining weights in row i are updated: W[i,k:] -= (W[i,j] − Wq[i,j]) × (H⁻¹[j,k:] / H⁻¹[j,j]). This error correction propagates the quantization mistake backward through the Hessian inverse, allowing INT4 to match INT8 PTQ quality on most LLMs. GPTQ quantizes a 175B model in ~4 hours on 1 GPU.
Question 3 of 8

The KV cache for a 70B model (L=80 layers, d=8192, FP16) at 128K sequence length is 342GB per request. A production system serves 64 concurrent users. With GQA reducing KV heads from 64 to 8 (8× reduction), plus INT4 quantization, what is the total KV memory per GPU required? Assume a single A100 80GB GPU.

Memory arithmetic: Always compute per-user first: Memory = 2 × L × T × d × bytes = 2 × 80 × 131072 × 8192 × 2 = 342GB. GQA with ratio r reduces this by r (KV heads, not query heads). INT4 is 0.5 bytes → ÷4 vs FP16. The 64-user multiplication shows why serving long-context models at scale requires careful planning: even with aggressive compression, multi-user KV cache dominates GPU memory. Options C and B give the same final number (≈9 GPUs for KV) — the key step is recognizing GQA and INT4 are independent multipliers applied sequentially.
Question 4 of 8

Product Quantization (PQ) with m=32 subvectors and k=256 entries per codebook compresses 1024-dim FP32 embeddings. What is the total storage (including codebook) for a database of 1M vectors, and why is approximate distance computation (ADC) O(m) rather than O(d)?

PQ compression math: The key formula: compressed_size = N × m × log₂(k) bits = 1M × 32 × 8 bits = 256Mb = 32MB. Codebook size = m × k × (d/m) × sizeof(float) = 32 × 256 × 32 × 4 = 1MB. The ADC efficiency comes from precomputing the partial distance table at query time (cost = m × k) once, then each DB vector lookup costs just m additions. This is why FAISS can search 1B vectors in milliseconds on a CPU — the bottleneck is the lookup table reads, not vector arithmetic.
Question 5 of 8

TurboQuant applies a random rotation y = Rx before quantization. Why does this improve INT4 accuracy, and what mathematical property of R is essential for reconstruction?

The orthogonality condition is load-bearing: R must satisfy RᵀR = I for two reasons. First, reconstruction: xhat = Rᵀŷ gives the exact inverse if ŷ were perfect. Second, distance preservation: ‖Rx - Ry‖ = ‖x - y‖ — quantization errors in the rotated space have the same L2 norm as in the original space. The Randomised Hadamard Transform (RHT) achieves O(d log d) vs O(d²) for a dense rotation, making it practical for d=4096. Theoretically, this is a Johnson-Lindenstrauss rotation — the outlier spreading follows from the JL lemma.
Question 6 of 8

QLoRA fine-tunes a 70B model by quantizing the base model to 4-bit NF4 (Normal Float 4) and adding LoRA adapters in BF16. Why is NF4 preferable to INT4 for weight quantization, and what happens computationally during the forward pass?

NF4 information theory: For a Gaussian weight distribution N(0,σ²), the optimal 4-bit quantizer minimises expected squared error E[(w - q(w))²]. This is achieved by quantile quantization: place boundaries at the 1/16, 2/16, ... quantiles of the distribution. NF4 tables these boundaries at initialization. The result: NF4 uses 0 bits on the weight's overall magnitude (handled by block-wise scaling) and all 4 bits on relative position within the distribution. Empirically, NF4 matches BF16 fine-tuning quality while using 4× less base model memory.
Question 7 of 8

Grouped Query Attention (GQA) with G groups and H query heads uses H/G KV heads. LLaMA-3-70B uses H=64 query heads and G=8 KV heads. A 128K context with this model at FP16: calculate the KV cache memory, and explain why GQA doesn't hurt quality as much as MQA (G=1).

GQA arithmetic: The formula is Memory(GQA) = 2 × L × T × G × d_head × bytes. Here G=8, d_head = d_model/H_total = 8192/64 = 128. Key conceptual point: GQA retains G independent KV projections, so each group of H/G queries can attend to different content aspects. MQA's single KV head creates a bottleneck where all 64 queries compete for the same attention pattern — quality suffers. GQA was introduced in the Ainslie et al. 2023 paper and is now standard in all major LLMs (LLaMA-2+, Mistral, Gemma).
Question 8 of 8

You are deploying a RAG system with 100M documents (1024-dim FP32 embeddings). Compare the total storage and query latency trade-off for: (A) exact FP32 FAISS flat index, (B) PQ with m=64, k=256, (C) HNSW exact index at M=32. Which do you choose for a latency-critical production system at <50ms p99?

Production vector search decision: The key insight is that latency budgets determine the algorithm. FP32 flat is trivially correct but impossibly slow at 100M scale. PQ is fast but introduces recall degradation (~90-95%) — acceptable for recommendation but risky for RAG where missing the right context is costly. HNSW gives 99%+ recall with sub-5ms queries. At 100M scale, HNSW storage (~10-30GB for M=32) fits on a single A100 80GB. For 1B+ vectors, IVFPQ (inverted file + PQ) or ScaNN are the right choices. Always benchmark recall@K and p99 latency together — optimising latency at the cost of recall destroys RAG answer quality.
