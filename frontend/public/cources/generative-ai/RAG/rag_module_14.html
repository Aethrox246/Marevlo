01 · Why RAG Evaluation Is Hard

The Oracle Problem:
No Ground Truth Without Human Effort

Evaluating a classifier is easy: you have ground truth labels. Evaluating RAG is hard because the "correct" answer is subjective, multi-dimensional, and context-dependent. A response can be technically accurate but unhelpful, completely faithful but off-topic, or perfect on one query type and terrible on another. Evaluation requires defining what "good" means before you can measure it.

The five reasons RAG evaluation is uniquely difficult

No single correct answer

For "What is the refund policy?", 50 different wordings are all correct. A string-match evaluation would score 49 of them as 0. You need semantic similarity or LLM-based grading.

Retrieval and generation fail independently

A retrieved-but-ignored context scores the same as a never-retrieved context in end-to-end evaluation. You need component-level metrics to diagnose which stage is failing.

Query distribution shift

Your golden test set was created when users asked about refunds. Users now ask about enterprise integrations. A static eval set gives false confidence on out-of-distribution queries.

Human evaluation is expensive and slow

Expert annotation of 100 RAG responses (relevance + faithfulness + helpfulness) takes 4-8 hours. You cannot run this after every deployment.

LLM judge bias

LLMs used as evaluators prefer longer answers, verbose explanations, and outputs from the same model family. An LLM judge that is the same model as your RAG generator has a conflict of interest.

02 · RAGAS Metrics Deep Dive

Four Orthogonal Metrics:
Each Measuring a Different Failure

RAGAS (Retrieval Augmented Generation Assessment) provides four automated metrics that together cover the main failure dimensions of a RAG system. Each metric is independent: you can score high on one while failing another. Together they form a diagnostic dashboard that tells you which pipeline component to fix.

FaithfulnessNLI-based claim verification

Decomposes the generated answer into atomic claims. For each claim, uses NLI to check if the claim is entailed by the retrieved context. Score = fraction of claims supported by context.

Input: answer: "Annual subs are non-refundable after 30 days [Doc 1]. Enterprise users get custom terms [Doc 2]."
Eval: Claim 1: "annual subs non-refundable after 30 days" → entailed by Doc 1 ✓ Claim 2: "enterprise users get custom terms" → entailed by Doc 2 ✓ Faithfulness = 2/2 = 1.0

Low = LLM is hallucinating (generating claims not in context). Fix: stronger grounding instructions.

Answer RelevancyQuestion reconstruction similarity

Asks an LLM to generate N questions that the answer would answer. Embeds those questions and computes cosine similarity to the original question. High similarity = the answer addresses the original question.

Input: answer: "Annual subscriptions are non-refundable after 30 days."
Eval: Generated: "What is the refund window for annual plans?" → cosine=0.94 ✓ Generated: "Are annual plans refundable?" → cosine=0.91 ✓ Answer Relevancy = mean(0.94, 0.91) = 0.925

Low = answer does not address the question despite being faithful. Fix: improve retrieval (wrong documents retrieved).

Context PrecisionFraction of retrieved chunks that are relevant

For each retrieved context chunk, asks an LLM: "Is this chunk relevant to answering the question?" Context Precision = fraction of retrieved chunks rated relevant.

Input: Retrieved: [Doc1: refund policy ✓, Doc2: pricing plans ✗, Doc3: enterprise terms ✓, Doc4: team features ✗, Doc5: refund process ✓]
Eval: Relevant chunks: 1, 3, 5 (3 of 5) Context Precision = 3/5 = 0.6

Low = retriever returning irrelevant documents. Fix: improve retrieval (better embeddings, metadata filtering).

Context RecallFraction of ground-truth answer supported by context

Given a reference answer, checks what fraction of its claims are supported by the retrieved context. Requires a reference answer (human-written). Measures retrieval completeness.

Input: Reference: "Annual plans non-refundable after 30 days. Enterprise has custom terms. Refund must be via email."
Eval: Claim 1: in context ✓ Claim 2: in context ✓ Claim 3: NOT in context ✗ Context Recall = 2/3 = 0.667

Low = retriever is missing relevant documents. Fix: improve recall (hybrid search, larger top-k).

03 · Building Golden Evaluation Sets

Human Annotation and
LLM-Assisted Generation

A golden evaluation set is a curated collection of (question, reference_answer, relevant_contexts) triples that represent your production query distribution. Building one requires effort but enables automated regression detection: if a code change breaks RAG quality, your golden set catches it before users do.

Method 1: Human annotation (highest quality)

1

Sample 200 representative queries from production logs

Query logs give real distribution. Cluster by topic to ensure coverage across all query types.

2

For each query: identify the correct source documents

Human annotator marks which documents in the corpus are relevant to this query.

3

Write reference answers using only those documents

Annotator writes a 2-3 sentence answer citing only the marked documents. No outside knowledge.

4

Quality review: second annotator verifies

Inter-annotator agreement on faithfulness and relevance. Resolve disagreements by consensus.

Method 2: LLM-assisted generation (faster, cheaper)

Generate QA pairs from your documents automatically, then filter by human review. Produces more diverse question types at lower cost.

System: "Given this document, generate 3 diverse test questions that can be answered using ONLY the document content. Include: 1 factual, 1 reasoning, 1 edge-case. For each question, write the reference answer and mark the relevant sentences."

Document: "Annual subscriptions are non-refundable after 30 days."

Q1 (factual): "Can I get a refund on an annual plan after 45 days?" A: "No, annual subscriptions are non-refundable after 30 days."
Q2 (reasoning): "If I bought an annual plan 25 days ago, can I still get a refund?" A: "Yes, since 25 days is within the 30-day window."
Q3 (edge): "What happens to the refund policy if I upgrade mid-subscription?" A: "The document does not address upgrade scenarios."
⚠️

Distribution monitoring: refresh your golden set quarterly

Production query distributions shift over time. Users who asked about basic refunds in Q1 may ask about enterprise integrations in Q3. Audit your golden set quarterly: compare the topic distribution of your current golden set vs recent production query logs. Add test cases for emerging query categories before they become blind spots.

04 · Unit Tests for RAG Components

Test Each Stage Independently
Before Testing the Full Pipeline

End-to-end evaluation tells you the system is failing but not why. Unit tests at the component level pinpoint exactly which stage introduced the regression. Test retriever, reranker, and generator independently with known inputs and expected outputs.

05 · End-to-End Evaluation Framework

From Single Run to
Systematic Score Tracking

A single RAGAS score on one day is not useful. A time series of scores across deployments reveals regressions, improvements, and drifts. Your eval framework must run automatically, store results, compare to baseline, and alert when quality drops.

Production eval framework components

1

Eval dataset registry

A versioned JSON/YAML file storing your golden set: {question, reference_answer, relevant_doc_ids}. Committed to git. Changes require PR review to prevent silent test set manipulation.

2

Eval runner

Script that: (1) loads the golden set, (2) runs each query through the full RAG pipeline, (3) computes RAGAS metrics per query, (4) aggregates to summary stats, (5) writes results to eval_results/{timestamp}.json.

3

Baseline tracking

The "baseline" is the eval result from the last successful deployment. Stored alongside the code. Each eval run compares current scores to baseline and reports delta.

4

Alert thresholds

Per-metric thresholds: Faithfulness < 0.85, AnswerRelevancy < 0.75, ContextPrecision < 0.6, ContextRecall < 0.7. Crossing any threshold fails the eval run.

5

Result dashboard

LangSmith eval runs UI provides a ready-made dashboard. Alternatively: write scores to a time-series DB (InfluxDB, Prometheus) and visualize in Grafana.

06 · Continuous Eval in CI/CD

Regression Detection Before
Bad Deployments Reach Users

Every code change that touches the RAG pipeline should trigger an automated evaluation run. If the change degrades any metric beyond its threshold, the deployment fails before users are affected. This is the RAG equivalent of unit tests in CI: it catches regressions before they ship.

GitHub Actions CI eval workflow

name: RAG Eval CI
on: [pull_request, push to main]

jobs:
eval:
runs-on: ubuntu-latest
steps:
- uses: actions/checkout@v4
- name: Setup Python + deps
run: pip install ragas langchain langchain-anthropic
- name: Run component unit tests
run: pytest tests/unit/ -v # retriever, reranker, prompt tests
- name: Run E2E RAGAS evaluation
run: python eval/run_eval.py --dataset golden_set_v3.json
env:
ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
LANGCHAIN_API_KEY: ${{ secrets.LANGSMITH_KEY }}
- name: Check thresholds and compare to baseline
run: python eval/check_thresholds.py --baseline eval/baseline.json
- name: Upload results as artifact
uses: actions/upload-artifact@v4
with: {name: eval-results, path: eval/results/}
⚠️

Eval CI cost management

Running RAGAS on a 100-query golden set with Claude Sonnet as the eval judge costs ~$0.50-$1.00 per CI run. On active repos with 20 PRs/day, this is $10-$20/day. Strategies: (1) run full eval only on PRs targeting main, run fast smoke test (10 queries) on feature branches; (2) use a cheaper eval model (Haiku) for screening, only run full Sonnet eval on merge; (3) cache eval results for identical pipeline configs.

08 · Production Code

RAGAS Eval Suite and
CI Regression Detection Script

eval_suite.py

from ragas import evaluate, EvaluationDataset
from ragas.metrics import (
    faithfulness, answer_relevancy,
    context_precision, context_recall
)
from langchain_anthropic import ChatAnthropic
from langchain_community.embeddings import HuggingFaceEmbeddings
import json, sys
from datetime import datetime

# ── Load golden set ───────────────────────────────────────────
def load_golden_set(path: str) -> list:
    with open(path) as f:
        return json.load(f)  # [{question, reference, contexts}]

# ── Run full RAG pipeline to get responses ───────────────────
def collect_responses(golden_set: list, rag_chain) -> list:
    samples = []
    for item in golden_set:
        result = rag_chain.invoke(item["question"])
        samples.append({
            "user_input": item["question"],
            "retrieved_contexts": result["retrieved_docs"],
            "response": result["answer"],
            "reference": item["reference"]  # for context_recall
        })
    return samples

# ── Run RAGAS evaluation ──────────────────────────────────────
def run_eval(samples: list) -> dict:
    dataset = EvaluationDataset.from_list(samples)
    llm = ChatAnthropic(model="claude-sonnet-4-20250514")
    embeddings = HuggingFaceEmbeddings(
        model_name="BAAI/bge-large-en-v1.5")
    results = evaluate(
        dataset=dataset,
        metrics=[faithfulness, answer_relevancy,
                 context_precision, context_recall],
        llm=llm,
        embeddings=embeddings
    )
    return results.to_pandas().mean().to_dict()

# ── Threshold check for CI ────────────────────────────────────
THRESHOLDS = {
    "faithfulness": 0.85,
    "answer_relevancy": 0.75,
    "context_precision": 0.60,
    "context_recall": 0.70,
}

def check_thresholds(scores: dict, baseline_path: str) -> bool:
    with open(baseline_path) as f:
        baseline = json.load(f)
    passed = True
    for metric, threshold in THRESHOLDS.items():
        score = scores.get(metric, 0)
        delta = score - baseline.get(metric, score)
        status = "PASS" if score >= threshold else "FAIL"
        print(f"{metric}: {score:.3f} (baseline: {baseline.get(metric,0):.3f}, delta: {delta:+.3f}) [{status}]")
        if score < threshold: passed = False
    return passed

# ── Main: run as CI step ─────────────────────────────────────
if __name__ == "__main__":
    golden_set = load_golden_set("eval/golden_set_v3.json")
    samples = collect_responses(golden_set, rag_chain)
    scores = run_eval(samples)
    timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    with open(f"eval/results/{timestamp}.json", "w") as f:
        json.dump(scores, f)
    passed = check_thresholds(scores, "eval/baseline.json")
    sys.exit(0 if passed else 1)  # non-zero exit fails CI step
09 · Final Assessment

RAG Masterclass
Final Quiz

1. RAGAS shows: Faithfulness=0.94, AnswerRelevancy=0.45, ContextPrecision=0.88, ContextRecall=0.91. What is broken and where do you focus your fix?

Correct. This unusual pattern (high faithfulness + high context quality + low answer relevancy) points to prompt design, not retrieval or grounding. The LLM is being faithful to good context but not producing answers that address the question. Common causes: the prompt asks for a summary ("describe the refund policy") when users want a direct answer ("yes/no, can I get a refund?"), or the LLM is producing verbose contextual information rather than the specific answer to the query.

2. You want to catch retrieval regressions before they reach production. What is the minimum viable CI eval setup?

Correct. Tiered eval matches cost to risk. Fast component tests (Recall@10 on a small subset) run in under a minute and catch retrieval regressions early and cheaply. The full RAGAS suite is expensive (~$1 per 100 queries) and slow (~5 min) but provides the authoritative quality signal for deployment decisions. Running full RAGAS on every commit is economically unsustainable on active repos.

3. Your golden test set was created 6 months ago from user queries about refund policies. Today, 40% of production queries are about enterprise integrations. What is the problem and how do you fix it?

Correct. A golden set is only as good as its coverage of the production distribution. 6-month-old test sets are a common source of false confidence: the system gets an "A" on the eval while users experience failures on queries the eval never covers. Regular golden set audits against production log topic distributions are the only defense against this.

4. Context Precision = 0.45 on your golden set. What does this tell you and what do you fix?

Correct. Context Precision measures the fraction of retrieved chunks that are relevant. 0.45 means more than half your retrieved context is noise. This is expensive (irrelevant tokens in the LLM context cost money and degrade generation quality) and a strong signal that retrieval precision needs improvement. The fixes are ordered by cost: metadata filtering is cheapest (zero additional compute), embedding model upgrade is moderate, adding hybrid search is more engineering work but often the highest-impact fix.

5. You are designing the evaluation strategy for a RAG system that will be used by doctors to look up drug interaction information. What evaluation requirements differ from a standard enterprise RAG use case?

Correct. High-stakes RAG (medical, legal, financial) requires qualitatively different evaluation standards. Automated RAGAS metrics are necessary but not sufficient: a faithfulness score of 0.97 means 3% of claims are hallucinated, which is unacceptable for drug interaction information. Human expert review, adversarial test cases, explicit refusal testing, and production response audits are all required additions to the standard automated eval suite.
