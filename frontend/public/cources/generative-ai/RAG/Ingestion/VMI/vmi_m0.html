The Multimodal Ingestion Problem

Container Formats · Demux · Frame Sampling · Mel Spectrogram · STFT · NVDEC · Throughput

A video is not a sequence of images with a soundtrack attached. It is a multiplexed container of three fundamentally different data types — compressed video frames, digital audio samples, and timed text — each requiring its own decoding pipeline, sampling strategy, and preprocessing chain before any model can touch it. This module builds the end-to-end ingestion pipeline: from MP4 container to three streams of encoder-ready tensors. Every decision made here — frame rate, audio sample rate, mel parameters, chunk size — propagates through every downstream model and must be matched precisely to what those models were trained on.

01 · The Container — Three Streams in One File

MP4 / MKV / WebM:
Not a Video, a Multiplexed Container

A video file is a container that multiplexes three independent bitstreams: a compressed video stream (H.264/HEVC/VP9), a compressed audio stream (AAC/Opus/MP3), and optional subtitle/metadata streams. Decoding these streams requires separate codecs and produces completely different data types: frame tensors, PCM samples, and text strings. The first step of any video ML pipeline is demuxing — separating the container into its constituent streams — using ffprobe for metadata and ffmpeg for decoding.

Video container demux pipeline — three modality streams to three encoder pathways

video_ingest.py — demux container, extract frames and audio streams

import subprocess, json, os
from pathlib import Path
from dataclasses import dataclass
import numpy as np

@dataclass
class VideoMeta:
    """Metadata extracted from container before any decoding."""
    path:         str
    duration_s:   float
    fps:          float
    width:        int
    height:       int
    has_audio:    bool
    audio_sr:     int     # sample rate Hz
    n_frames:     int     # total video frames
    codec_video:  str     # e.g. 'h264', 'hevc', 'vp9'
    codec_audio:  str     # e.g. 'aac', 'opus', 'mp3'


def probe_video(path: str) -> VideoMeta:
    """
    Use ffprobe to read container metadata without decoding any frames.
    Fast: reads only the container header — O(1) regardless of video length.
    """
    cmd = ['ffprobe', '-v', 'quiet', '-print_format', 'json',
           '-show_streams', path]
    meta = json.loads(subprocess.check_output(cmd))
    video = next(s for s in meta['streams'] if s['codec_type'] == 'video')
    audio = next((s for s in meta['streams'] if s['codec_type'] == 'audio'), None)
    fps_num, fps_den = map(int, video['r_frame_rate'].split('/'))
    fps = fps_num / fps_den
    return VideoMeta(
        path=path,
        duration_s=float(video.get('duration', 0)),
        fps=fps,
        width=int(video['width']),
        height=int(video['height']),
        has_audio=audio is not None,
        audio_sr=int(audio['sample_rate']) if audio else 0,
        n_frames=int(video.get('nb_frames', fps * float(video.get('duration', 0)))),
        codec_video=video['codec_name'],
        codec_audio=audio['codec_name'] if audio else '',
    )


def extract_frames(
    path:      str,
    strategy:  str  = 'fixed_fps',   # 'fixed_fps' | 'keyframe' | 'scene'
    target_fps: float = 1.0,           # for fixed_fps strategy
    out_dir:   str  = '/tmp/frames',
) -> list[str]:
    """
    Extract frames from video using ffmpeg.

    Strategies:
      fixed_fps:  sample at target_fps (e.g. 1 frame/sec for long videos,
                  8 fps for action recognition). Predictable, uniform.
      keyframe:   only decode keyframes (I-frames). Fast — no decoding of
                  P/B frames. Miss many frames but covers scene boundaries.
                  Use for rough scene understanding, not fine-grained motion.
      scene:      scene change detection (threshold-based). Extracts one
                  frame per detected scene cut. Best for content indexing.

    All strategies output JPEG frames to out_dir.
    Returns sorted list of output file paths.
    """
    os.makedirs(out_dir, exist_ok=True)
    filters = {
        'fixed_fps': f'fps={target_fps}',
        'keyframe':  'select=eq(pict_type\\,I)',
        'scene':     'select=gt(scene\\,0.3)',  # scene change threshold 0.3
    }
    vf = filters[strategy]
    cmd = ['ffmpeg', '-i', path, '-vf', vf,
           '-vsync', 'vfr',          # variable frame rate output
           f'{out_dir}/frame_%06d.jpg']
    subprocess.run(cmd, check=True, capture_output=True)
    return sorted(Path(out_dir).glob('frame_*.jpg'))
02 · Frame Sampling and Audio Preprocessing

Sampling Strategy Determines
What the Model Sees

A 60fps video has 3,600 frames per minute. No video encoder processes every frame — all video ML pipelines subsample. The sampling strategy defines what information the model sees, and the wrong strategy for your task destroys performance: uniform temporal sampling misses scene transitions; keyframe extraction misses within-scene motion; scene change detection misses fine-grained temporal dynamics.

audio_features.py — waveform → mel spectrogram for audio encoders

import numpy as np
import torch
import torchaudio
import torchaudio.transforms as T
import subprocess

def extract_audio_pcm(video_path: str,
                       sample_rate: int = 16000) -> torch.Tensor:
    """
    Demux audio stream from video container → mono PCM at target_sr.
    16kHz mono is the standard for most speech models (Whisper, Wav2Vec2).
    Returns (samples,) float32 tensor in range [-1, 1].
    """
    cmd = ['ffmpeg', '-i', video_path,
           '-ac', '1',               # mono
           '-ar', str(sample_rate),    # resample to target_sr
           '-f', 'f32le',             # raw float32 little-endian
           '-']                         # pipe to stdout
    raw = subprocess.check_output(cmd, stderr=subprocess.DEVNULL)
    return torch.frombuffer(raw, dtype=torch.float32)


def waveform_to_melspec(
    waveform:    torch.Tensor,    # (T,) mono float32
    sample_rate: int   = 16000,
    n_mels:      int   = 128,    # mel filterbank bins
    n_fft:       int   = 1024,   # FFT window size
    hop_length:  int   = 160,    # hop = 10ms at 16kHz
    f_min:       float = 0.0,
    f_max:       float = 8000.0,
) -> torch.Tensor:
    """
    Convert waveform to log-mel spectrogram.

    Pipeline:
      1. STFT: waveform → complex spectrogram (n_fft/2+1, T_frames)
         Each column = FFT of a 64ms window shifted by 10ms.
      2. Mel filterbank: map linear frequency bins → n_mels mel-scale bins.
         Mel scale compresses high frequencies (mirrors human hearing).
      3. Log compression: log(mel + 1e-8) — stabilises amplitude range,
         makes quiet sounds comparable to loud sounds.

    Output shape: (n_mels, T_frames) — treated as an image by audio encoders.
    Whisper uses n_mels=80, n_fft=400, hop=160 at 16kHz.
    CLAP, AudioCLIP use n_mels=64 or 128.
    """
    mel_transform = T.MelSpectrogram(
        sample_rate=sample_rate,
        n_fft=n_fft,
        hop_length=hop_length,
        n_mels=n_mels,
        f_min=f_min,
        f_max=f_max,
    )
    mel = mel_transform(waveform.unsqueeze(0))  # (1, n_mels, T_frames)
    log_mel = torch.log(mel + 1e-8)
    return log_mel.squeeze(0)                    # (n_mels, T_frames)


def chunk_audio(waveform: torch.Tensor,
                 sample_rate: int = 16000,
                 chunk_s: float = 30.0,
                 overlap_s: float = 1.0) -> list[torch.Tensor]:
    """
    Split long audio into overlapping chunks for model inference.
    Whisper processes 30s chunks. Overlap prevents boundary artefacts.
    """
    chunk_len = int(chunk_s * sample_rate)
    step_len  = int((chunk_s - overlap_s) * sample_rate)
    chunks = []
    for start in range(0, len(waveform), step_len):
        chunk = waveform[start:start + chunk_len]
        if len(chunk) < sample_rate:   # skip < 1s trailing chunks
            break
        chunks.append(chunk)
    return chunks
🔑

Mel spectrogram parameters must match the target model exactly

Whisper uses n_mels=80, n_fft=400, hop=160, sr=16000. CLAP uses n_mels=64, sr=48000. AudioCLIP uses n_mels=128, sr=22050. These parameters are baked into the model weights — using mismatched parameters produces embeddings that are completely uncorrelated with the model's training distribution. Always check the model card before computing spectrograms.

03 · Scale and Throughput Engineering

4K@60fps Ingestion:
Why CPU Decode Fails at Scale

⚠️

The 4K throughput bottleneck

4K@60fps = 3840×2160×3×60 ≈ 1.44 GB/s raw pixel throughput. CPU software decode (libavcodec) cannot sustain this — it saturates 8 CPU cores at ~30fps for 4K. Solution: NVDEC (NVIDIA hardware decoder) handles decode in dedicated silicon, delivering frames directly to GPU memory. One NVDEC unit handles 4K@60fps with zero CUDA core usage. PyNVDECO and PyAV+CUDA expose this from Python.

Production scenario: YouTube-scale video indexing

500 hours of video uploaded per minute (YouTube 2024 scale). At 30fps average, that is 900,000 frames per second across all uploads. Ingestion pipeline: NVDEC decode → GPU-resident resize (224×224) → 8-frame clip sampling → vision encoder (ViT-L/14 at 90ms per clip) → FAISS index. Critical path: NVDEC throughput limits to ~4K clips/sec per GPU. Scale to 1M clips/sec requires ~250 GPUs for ingestion alone — matching encoder throughput is the constraint, not storage or network.

Question 1 of 8

You are building a video understanding system for a 2-hour documentary. You need to extract representative frames for content indexing (one description per scene). Which frame sampling strategy produces the most semantically appropriate frame set?

Correct. Scene change detection is the right strategy when the goal is content indexing — you want one representative frame per scene, not one frame per fixed time interval. Fixed FPS at 1fps for a 2-hour film produces 7200 frames; most are near-duplicates within long scenes. Keyframes (I-frames) are fast but their positions are determined by the codec's compression schedule, not semantic content boundaries. Scene change detection at threshold 0.3 extracts exactly at visual transitions, producing a compact, semantically structured frame set.
Question 2 of 8

A mel spectrogram is computed with n_fft=1024, hop_length=160, sample_rate=16000, n_mels=128. What are the time resolution (ms per frame) and frequency resolution (Hz per FFT bin) of the raw STFT before the mel filterbank is applied?

Correct. Time resolution = hop_length / sample_rate = 160 / 16000 = 0.01s = 10ms per frame. Frequency resolution = sample_rate / n_fft = 16000 / 1024 = 15.625 Hz per FFT bin. The 10ms hop is the standard for speech processing (used by Whisper, Wav2Vec2, HuBERT). The mel filterbank then groups these 513 linear frequency bins into 128 mel-scale bins, compressing the high-frequency range where human speech has less perceptual information.
Question 3 of 8

You are demuxing an MP4 file with ffprobe and find: video stream codec='h264', r_frame_rate='30000/1001', nb_frames not present, duration='3723.5'. What is the total frame count and why is nb_frames absent?

Correct. The frame count estimate = duration × fps = 3723.5 × (30000/1001) ≈ 111,630. The 30000/1001 ≈ 29.97 fps is NTSC drop-frame rate — the standard for North American broadcast video. nb_frames is absent from many MP4 files because the container header only stores duration; the per-frame index (sample table) exists in the moov atom but ffprobe doesn't always expose the count without a full scan. This is a common source of off-by-one errors in video ingestion — always use duration-based estimates and verify with packet counting for critical applications.
Question 4 of 8

You are building a video ingestion pipeline for a medical imaging company. Videos are laparoscopic surgery recordings (30fps, 2-4 hours). You need to extract frames for surgical phase classification. Fixed FPS at 1fps produces 7200-14400 frames per video — too many for your encoder. What adaptive strategy reduces frame count while preserving surgical phase information?

Correct. Optical flow magnitude as a sampling trigger is the most domain-appropriate strategy for surgical video. Surgical phase transitions and critical events are defined by instrument motion: insertion, cutting, suturing, withdrawal. Sampling at high optical flow moments captures exactly the frames with the most relevant content — stationary frames (patient lying still, surgeon positioning) are skipped. Scene change detection (option C) is wrong because laparoscopic video lacks sharp visual cuts; the camera view is continuous. Hierarchical uniform sampling (option B) is reasonable but domain-agnostic — it captures motionless phases equally. The optical flow trigger is specifically tuned to surgical content.
Question 5 of 8

An audio encoder receives a 5-minute lecture video. After extracting PCM at 16kHz, you create a mel spectrogram with n_mels=80, hop_length=160, n_fft=400 (Whisper's parameters). What are the dimensions of the resulting spectrogram and how many 30-second Whisper input chunks does the audio split into?

Correct. Duration = 5 minutes = 300 seconds. Total samples = 300 × 16000 = 4,800,000. T_frames = samples / hop_length = 4,800,000 / 160 = 30,000. Shape = (80, 30,000). But wait — at hop=160 and sr=16000, 1 second = 100 frames. 300s = 30,000 frames. Each Whisper chunk is 30s = 3,000 frames. 300s / 30s = 10 chunks exactly. So the answer is (80, 30,000) total, split into 10 chunks of shape (80, 3,000) each. Whisper internally resamples each chunk to 3,000 frames via its log-mel frontend — exactly 1500 time steps after its 2× subsampling Conv layers, but the raw spectrogram before the model is (80, 3000) per chunk.
Question 6 of 8

You demux a video and find the audio stream has sample_rate=48000Hz but your audio encoder (Whisper) expects 16000Hz mono. In your ffmpeg command you use '-ar 16000 -ac 1'. What quality degradation risk does this resampling introduce and for which content types?

Correct. 16kHz resampling is appropriate for speech but lossy for music and audio events. Human speech intelligibility is fully preserved at 16kHz (Nyquist = 8kHz covers the full telephone bandwidth used for 100+ years of voice communication). The degradation is specific to high-frequency content: musical instruments with harmonics above 8kHz (cymbals, high strings), ambient soundscapes, and audio events used for scene understanding. For multimodal systems that need audio event classification (gunshot, music genre, crowd noise), use 22kHz or 44.1kHz input to CLAP/AudioCLIP and a separate 16kHz stream for Whisper ASR.
Question 7 of 8

What is the fundamental difference between a video encoder's challenge compared to an image encoder, and why do 3D convolutions address this while 2D convolutions (applied per-frame) do not?

Correct. The key distinction is joint spatiotemporal modelling. Per-frame 2D encoding is 'temporally blind' — it cannot distinguish a video from a randomly shuffled set of frames. 3D convolutions encode the shape of motion itself: the kernel response is high when pixels change in the expected spatiotemporal pattern. However, 3D convolutions are computationally expensive (O(t×h×w) per kernel vs O(h×w)). This is why modern video transformers (TimeSformer, VideoMAE) use factored space-time attention instead — separately attending to spatial patches and temporal positions before combining, achieving similar representation quality at lower cost.
Question 8 of 8

A 4K video (3840×2160) at 60fps is being ingested into a video encoder. The encoder accepts 224×224 clips of 8 frames. What preprocessing pipeline do you design, and what is the theoretical throughput bottleneck?

Correct. 4K video ingestion at 60fps requires GPU hardware decoding. The raw pixel throughput (1.44 GB/s) exceeds CPU decode+resize capacity. NVDEC (NVIDIA hardware decoder) handles this in dedicated silicon without using CUDA cores, delivering decoded frames directly to GPU memory. The resize (3840×2160 → 224×224) reduces data volume 294×, making subsequent encoder throughput the bottleneck at scale. In production systems, multiple NVDEC units run in parallel and the encoder queue is the rate-limiting factor — not decode, resize, or PCIe bandwidth.
