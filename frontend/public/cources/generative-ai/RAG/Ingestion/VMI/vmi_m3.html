Multimodal Fusion and Video-Language Models

Early/Mid/Late Fusion · Q-Former · Perceiver Resampler · Token Budget · Video-LLaVA · Flamingo · Temporal Grounding

You have three streams of encoded representations: visual tokens from a ViT, audio embeddings from CLAP or Whisper, and text tokens from a tokeniser. The challenge of multimodal fusion is getting these three streams — each in a different embedding space, at different temporal resolutions, and with different semantic densities — to inform a single coherent reasoning process. This module covers the architecture of that fusion: from simple early-late concat strategies, to Q-Former cross-modal compression, to the context-window arithmetic that constrains every design decision in production video-LLM systems.

01 · Fusion Strategies — Where Modalities Meet

Early, Mid, Late Fusion:
Three Different Points of Contact

Fusion strategy determines what information each modality can contribute to the joint representation. Early fusion operates on raw or lightly processed features — the modalities share parameters from the start, enabling low-level cross-modal interactions but requiring aligned input formats. Late fusion encodes each modality independently to a single vector and combines the vectors — simple and robust, but loses all temporal and spatial alignment between modalities. Mid fusion (cross-modal attention) is the state of the art: each modality is encoded by its own specialist encoder, then the encoded representations interact via attention, preserving rich spatial and temporal structure while allowing modality-specific preprocessing.

Q-Former: 2048 visual tokens compressed to 32 query tokens via cross-modal attention

qformer.py — Q-Former cross-modal compression (BLIP-2 style)

import torch
import torch.nn as nn

class QFormerLayer(nn.Module):
    """Single Q-Former block: self-attn among queries + cross-attn to visual + FFN."""
    def __init__(self, d: int, n_heads: int):
        super().__init__()
        self.self_attn  = nn.MultiheadAttention(d, n_heads, batch_first=True)
        self.cross_attn = nn.MultiheadAttention(d, n_heads, batch_first=True)
        self.ffn   = nn.Sequential(nn.Linear(d, d * 4), nn.GELU(), nn.Linear(d * 4, d))
        self.norm1 = nn.LayerNorm(d)
        self.norm2 = nn.LayerNorm(d)
        self.norm3 = nn.LayerNorm(d)

    def forward(self, q: torch.Tensor, v: torch.Tensor) -> torch.Tensor:
        # 1. Queries attend to each other
        q = q + self.self_attn(self.norm1(q), self.norm1(q), self.norm1(q))[0]
        # 2. Queries attend to visual tokens (cross-attention)
        q = q + self.cross_attn(self.norm2(q), v, v)[0]   # Q=queries, K=V=visual
        # 3. Feed-forward
        q = q + self.ffn(self.norm3(q))
        return q


class QFormer(nn.Module):
    """
    Q-Former: Querying Transformer for cross-modal compression (BLIP-2).

    The core problem:
    A ViT-L/14 encoder on T=8 frames produces T*256 = 2048 visual tokens at D=1024.
    Feeding 2048 tokens into a 7B LLM costs: 2048 * 4096 (LLM dim) = 8M params
    per attention layer, plus 2048 tokens consume most of a 4096-token context window.

    Q-Former compresses 2048 visual tokens → N_q=32 query tokens via cross-attention.
    Queries are LEARNED parameters — they start random and learn to extract the
    most language-relevant visual information from the full token set.

    Why cross-attention not pooling?
    Average pooling loses spatial detail — a 32-element average of 2048 tokens
    cannot distinguish 'a dog in the top-left' from 'a dog in the centre'.
    Cross-attention lets each query specialise: one query may attend to faces,
    another to text in the scene, another to background context. The 32 queries
    collectively cover the full visual content, weighted by what the LLM cares about.

    For video: visual tokens from all frames are concatenated before Q-Former.
    Queries attend to all T*N_patches tokens — implicitly learning temporal pooling.
    """
    def __init__(self, n_queries: int = 32, d_model: int = 768,
                 n_heads: int = 12, n_layers: int = 6, d_visual: int = 1024):
        super().__init__()
        self.queries     = nn.Parameter(torch.randn(n_queries, d_model) * 0.02)
        self.visual_proj = nn.Linear(d_visual, d_model) if d_visual != d_model else nn.Identity()
        self.layers      = nn.ModuleList([QFormerLayer(d_model, n_heads) for _ in range(n_layers)])
        self.norm        = nn.LayerNorm(d_model)

    def forward(self, visual_tokens: torch.Tensor) -> torch.Tensor:
        """
        visual_tokens: (B, T*N_patches, D_visual)   e.g. (2, 2048, 1024)
        Returns:       (B, N_q, D_model)             e.g. (2, 32, 768)
        """
        B = visual_tokens.size(0)
        v = self.visual_proj(visual_tokens)               # (B, T*N, D_model)
        q = self.queries.unsqueeze(0).expand(B, -1, -1)  # (B, N_q, D_model)
        for layer in self.layers:
            q = layer(q, v)
        return self.norm(q)   # (B, N_q, D_model) — ready to project to LLM dim
02 · Video-Language Models — The Full Pipeline

Frames + Audio + Transcript
Into One Context Window

A Video-LLM is a language model that can reason about video. Its inputs are three parallel streams — visual tokens from a video encoder, optional audio embeddings, and a text transcript from ASR — all interleaved into a single token sequence and fed to an autoregressive LLM. The binding constraint is the context window: every design decision in the pipeline ultimately comes down to how many tokens each modality is allowed to consume.

Video-LLM pipeline: three modality streams → token interleaving → LLM generation

video_llm_pipeline.py — Video-LLaVA style multimodal inference pipeline

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM
from dataclasses import dataclass

@dataclass
class VideoLLMInput:
    frame_tokens: torch.Tensor    # (T, N_patches, D_v) — CLIP ViT output per frame
    transcript:   str             # Whisper ASR transcript
    question:     str             # user query


class VideoLLMPipeline:
    """
    Video-LLaVA style: sampled frames → visual encoder → projector → LLM.

    Token budget (4096-token LLM context window, 8 frames):
      With Q-Former (32 queries/frame compressed to 32 total):
        Visual:     32 tokens
        Transcript: ~200 tokens (1-minute video, Whisper output)
        Question:   ~30 tokens   System: ~50 tokens
        Total:      ~312 tokens  →  Answer budget: 3784 tokens  ✅

      Without compression (MLP projector, 8 frames × 256 patches):
        Visual:     2048 tokens
        Transcript: ~200 tokens
        Total:      ~2278 tokens →  Answer budget: 1818 tokens  ⚠️

      Long video (32 frames, no compression):
        Visual:     32 × 256 = 8192 tokens → EXCEEDS 4096 LIMIT  ❌
        → Must use Q-Former or Perceiver Resampler for long video.

    Context window is the binding constraint for video LLMs.
    Q-Former solves it by compressing visual tokens before the LLM sees them.
    """
    def __init__(self, visual_encoder, projector,
                 llm_name: str = 'lmsys/vicuna-7b-v1.5', device: str = 'cuda'):
        self.visual_encoder = visual_encoder.to(device).eval()
        self.projector      = projector.to(device).eval()
        self.device    = device
        self.tokenizer = AutoTokenizer.from_pretrained(llm_name)
        self.llm       = AutoModelForCausalLM.from_pretrained(
            llm_name, torch_dtype=torch.float16, device_map='auto'
        )

    def encode_video(self, frame_tokens: torch.Tensor) -> torch.Tensor:
        """(T, N, D_v) → (N_q, D_llm) compressed visual tokens."""
        T, N, D = frame_tokens.shape
        flat = frame_tokens.view(1, T * N, D).to(self.device)  # (1, T*N, D_v)
        compressed = self.projector(flat)                          # (1, N_q, D_model)
        return compressed.squeeze(0)                              # (N_q, D_model)

    def generate(self, inp: VideoLLMInput, max_new_tokens: int = 256) -> str:
        with torch.no_grad():
            # 1. Compress visual frames to N_q tokens
            vis_tokens = self.encode_video(inp.frame_tokens)          # (N_q, D_model)
            # 2. Project to LLM embedding dimension
            vis_embeds = self.llm.get_input_embeddings().weight.new_zeros(
                1, vis_tokens.shape[0], self.llm.config.hidden_size
            )  # placeholder — real implementation uses a linear projection layer
            # 3. Build text prompt with transcript context
            text = (f"[Transcript: {inp.transcript[:400]}]
"
                    f"Q: {inp.question}
A:")
            text_ids    = self.tokenizer(text, return_tensors='pt').input_ids.to(self.device)
            text_embeds = self.llm.get_input_embeddings()(text_ids)   # (1, L, D_llm)
            # 4. Prepend visual tokens to text sequence
            inputs_embeds = torch.cat([vis_embeds, text_embeds], dim=1)
            # 5. Autoregressive generation
            out = self.llm.generate(
                inputs_embeds=inputs_embeds,
                max_new_tokens=max_new_tokens,
                do_sample=False,
            )
        return self.tokenizer.decode(out[0], skip_special_tokens=True)
03 · Context Window Arithmetic and Model Landscape

Token Budget:
The Binding Constraint of Video LLMs

🔑

Every design decision is a token budget decision

LLM context window (4K–128K tokens) is the hard ceiling. Visual tokens dominate: 8 frames × 256 patches = 2048 (MLP projector) vs 8 × 32 = 256 (Q-Former). ASR transcript adds ~100 tokens/minute. Question + system prompt: ~80 tokens. For videos longer than 5 minutes with a 4K context window and MLP projector, you mathematically cannot fit visual + audio + transcript. Q-Former or Perceiver Resampler is not optional — it is the only way to make long video work.

Context budget: 2-hour film, 32K context, Q-Former

Scene boundaries: ~100 scenes. Visual tokens: 100 × 32 = 3,200. ASR transcript (120 min × 100 tok/min): ~12,000. Speaker labels + timestamps: ~1,500. System prompt + question: ~300. Total input: ~17,000 tokens. Answer budget: 15,000 tokens — enough for a detailed film essay. Without Q-Former: 100 × 256 = 25,600 visual tokens alone exceed the context budget before any text is added.

Question 1 of 8

A Q-Former with N_q=32 queries processes visual tokens from a ViT-L/14 encoder applied to T=8 frames (256 patches each). What is the shape of the input to Q-Former's cross-attention (Key and Value), and what is the output shape after Q-Former?

Correct. The visual tokens from all T=8 frames are concatenated before Q-Former: 8 frames × 256 patches = 2048 tokens at D_v=1024. These 2048 tokens form the Key and Value in Q-Former's cross-attention. The 32 learned query vectors form the Query. After 6 Q-Former layers, the 32 queries emerge as (B, 32, D_model=768) — compressed visual tokens. This 64× compression (2048 → 32) is what makes the pipeline LLM-compatible.
Question 2 of 8

Early fusion, mid fusion, and late fusion differ in where modalities are combined. For a video QA task where the question is 'What does the speaker say right after showing the chart?', which fusion strategy best handles the temporal alignment between visual and speech modalities?

Correct. Cross-modal attention (mid fusion) is necessary for temporal alignment tasks. The question requires reasoning about a specific temporal relationship: visual event (chart shown) → immediately following speech. Cross-modal attention allows the audio encoder's temporal tokens to directly attend to the video encoder's temporal tokens at aligned timestamps. This produces a joint representation where the model can reason about which speech tokens temporally follow the chart-display visual tokens. Late fusion collapses temporal structure; early fusion cannot handle modality format incompatibility.
Question 3 of 8

The Perceiver Resampler (Flamingo) and Q-Former (BLIP-2) both compress visual tokens using learned queries and cross-attention. What is the key architectural difference, and when does it matter?

Correct. Self-attention among queries is Q-Former's key architectural advantage over Perceiver Resampler. Each Q-Former layer: self-attn(Q,Q) → cross-attn(Q,visual) → FFN. Each Perceiver layer: cross-attn(Q,visual) → FFN. The self-attention lets queries communicate — a query that has already extracted colour information can signal this to other queries, which then specialise in shape, motion, text, etc. Perceiver Resampler queries are independent across each layer — they only interact with visual tokens, not each other. Empirically, Q-Former produces better visual question answering results per query token; Perceiver Resampler scales better to larger N_q.
Question 4 of 8

Video-LLaVA uses a simple 2-layer MLP projector (no Q-Former). With T=8 frames and a CLIP ViT-L/14 encoder (256 patches/frame, D=1024), what is the visual token count fed to the LLM, and at what video length does the LLM context window (4096 tokens) become the bottleneck?

Correct. MLP projector does not compress the token count — it projects each patch embedding from D_v=1024 to D_llm (e.g. 4096) but keeps all 256 patches per frame. 8 frames × 256 = 2048 visual tokens. At T=16 frames: 16×256 = 4096 visual tokens alone — zero context remains for text, transcript, or question. This is why Q-Former or Perceiver Resampler is mandatory for long video: compressing 256 patches/frame to 32 queries/frame means T=16 uses only 512 visual tokens, leaving 3584 tokens for text. MLP projector is fine for short clips (≤8 frames); Q-Former is required for long video.
Question 5 of 8

Video-BLIP2 freeze the visual encoder (ViT-L/14) during Q-Former training. What is the rationale for freezing the visual encoder, and what risk does unfreezing it introduce?

Correct. Frozen ViT training is the key design choice that makes BLIP-2 (and Video-BLIP2) efficient and stable. The ViT's 307M parameters are expensive to update and already well-trained on 400M+ images. Q-Former (88M parameters) trains quickly on top of frozen ViT features. Stage 2 of BLIP-2 training does unfreeze the ViT, but with aggressive learning rate decay (~0.01× of Q-Former LR) and gradient clipping to prevent feature collapse. This staged training approach is now standard for video-LLM development.
Question 6 of 8

A Video-LLM is asked: 'At what point in the video does the presenter first mention the word revenue?' This is a temporal grounding task. Why do standard Video-LLM architectures (Video-LLaVA, VideoChat) fail at this and what architecture change enables it?

Correct. Standard Video-LLMs lack temporal awareness because visual compression (Q-Former, average pooling) collapses the temporal dimension. The fix requires three components working together: (1) temporally-indexed visual tokens so the LLM can associate visual content with specific timestamps; (2) Whisper word timestamps injected as structured text so speech timestamps are explicit; (3) training on temporal grounding tasks. This is an active research area — TimeChat (2023) and VTimeLLM (2023) are the current best approaches, but temporal grounding accuracy remains below human level on standard benchmarks.
Question 7 of 8

You are building a production Video-LLM for a 2-hour film analysis tool. Users ask questions spanning the entire film (plot summary, character arc analysis, thematic questions). The LLM context window is 32K tokens. How do you design the visual token budget and sampling strategy?

Correct. Scene-boundary sampling + Q-Former compression is the right design for long-form video analysis. Scene changes are semantically dense moments — the visual content transitions sharply, providing maximum information per sampled frame. Q-Former reduces each frame from 256 to 32 tokens. For 100 scene boundaries: 100 × 32 = 3,200 visual tokens. Add ASR transcript (~1,500 tokens/hour × 2 = 3,000) and metadata (timestamps, speaker labels) → ~7,000 total input tokens. Within a 32K context window, this leaves 25K tokens for the LLM to reason and generate a detailed film analysis. Option D (per-segment aggregation) loses cross-segment narrative coherence.
Question 8 of 8

Flamingo (Alayrac et al. 2022) interleaves visual tokens throughout the text sequence at positions corresponding to image/video references. Video-LLaVA prepends all visual tokens before the text. What advantage does Flamingo's interleaved approach provide for multi-image or long video tasks?

Correct. Proximity in the attention span matters. Transformer self-attention is theoretically global but practically weakens with distance — softmax normalisation over all positions dilutes attention weights for distant tokens. Flamingo's interleaved design keeps each frame's visual tokens adjacent to the text describing or questioning that frame. For a film with 100 scene-boundary frames, interleaving positions each scene's visual tokens next to the transcript text for that scene — temporal alignment is maintained in the token sequence itself. This is particularly important for temporal reasoning tasks where the LLM must correlate specific visual moments with specific textual references.
