Table Understanding Transformers

TATR Two-Stage Pipeline · DETR Detection · TAPAS Cell Selection · TEDS Metric · Spanning Cells

Tables are the densest information structures in documents — a single table might encode thousands of data points in a compact grid. Extracting that structure correctly requires two distinct operations: detecting where the table is on the page, then recognising its internal row-column structure. TATR (Table Transformer) performs both steps. TAPAS (Table Parser) enables natural language question answering directly over flattened table content. Together they form the table intelligence layer of a complete document AI system.

01 · TATR — Table Detection and Structure Recognition

Two DETR Models, Two Resolutions,
One Complete Table

Table extraction requires solving two separate detection problems at two different scales. Stage 1 detects where tables appear on the full page — a global layout problem. Stage 2 identifies rows, columns, and cells within each detected table — a local structure problem. TATR (Microsoft, 2022) uses the DETR object detection framework for both stages, making the architecture clean and composable.

🔑

TEDS — measuring table structure accuracy correctly

TEDS represents a table as a tree: table → rows → cells, with span attributes as node properties. The score is 1 - (tree edit distance / max tree size). A table where all cell positions are correct but all spans are wrong would score F1=1.0 (all cells found) but TEDS≈0.3 (massive structural errors). TEDS correctly penalises both: missing cells, extra cells, wrong row/column assignments, and incorrect spanning — because all of these increase the tree edit distance from ground truth.

02 · TAPAS — Natural Language Question Answering Over Tables

Cell Selection + Aggregation —
What to Select and How to Compute It

TAPAS extends BERT with row and column position embeddings, enabling the model to understand table structure through attention. Rather than generating an answer, TAPAS selects the relevant cells and classifies which aggregation operation to apply. This makes arithmetic answers (sums, averages, counts) reliable — the arithmetic itself is deterministic, only the cell selection and operation choice require neural inference.

Question 1 of 5

TATR uses a two-stage pipeline: first detect table regions, then run structure recognition on each crop. Why not run structure recognition directly on the full page without the detection stage?

Correct. The two-stage design solves a resolution-scope conflict. Detection requires global context (full page) at moderate resolution. Structure recognition requires local detail (table interior) at high resolution. These two requirements are incompatible in a single model pass — processing the full page at sufficient resolution for cell boundary detection would produce sequences too long for the transformer. The crop-and-zoom pattern is the standard solution for this class of resolution-scope conflict in visual transformers.
Question 2 of 5

TAPAS flattens a table into a token sequence and adds row and column embeddings to each cell token. A table has 5 rows and 4 columns (20 cells). Question: 'What is the average revenue across all quarters?' requires summing and dividing. How does TAPAS handle arithmetic that no single cell contains?

Correct. TAPAS's two-head design is the key insight: separate what (cell selection) from how (aggregation type). The model learns to identify relevant cells and classify the required operation from natural language, while the actual arithmetic is performed deterministically after prediction. This is more reliable than generating numeric answers autoregressively (which can produce incorrect numbers) and more flexible than pure cell selection (which cannot handle aggregation questions). The fixed aggregation vocabulary (SUM/COUNT/AVERAGE/MAX/NONE) is a practical design choice that covers the vast majority of table QA questions.
Question 3 of 5

TEDS (Tree Edit Distance based Similarity) is used to evaluate table structure recognition. A predicted table has the correct rows and columns but one cell that should span 2 columns is predicted as two separate cells. What TEDS score would you expect and why is TEDS preferred over simple cell-level F1?

Correct. TEDS captures structural fidelity that cell-level F1 cannot. A table where all cells are detected but all column spans are wrong would score F1=1.0 but TEDS≈0.3, correctly reflecting that the structure is unusable for downstream parsing. The tree representation captures the hierarchical relationship between table, rows, columns, and cells — including span attributes — so any structural error increases the tree edit distance. This is why TEDS is the standard evaluation metric for table structure recognition in all major TSR benchmarks (PubTables-1M, FinTabNet, SciTSR).
Question 4 of 5

You are extracting data from financial tables that contain merged header cells spanning multiple columns (e.g. 'Q1-Q4 Revenue' spanning 4 data columns). TATR structure recognition correctly identifies rows and columns but marks all cells as non-spanning. How do you detect and handle column-spanning headers?

Correct. The hybrid approach correctly identifies that TATR's column detection gives you column width information, and the OCR text bbox for header cells gives you the text span width. If a header text's bbox is wider than 1.5 columns, it must be spanning. The post-processing heuristic is robust for the header row where financial tables consistently place spanning cells. Fine-tuning on FinTabNet (option C) is also valid but requires retraining — the heuristic approach can be deployed immediately as post-processing on any TATR output.
Question 5 of 5

You need to extract a pivot table from a financial report. The table has both row headers and column headers, with data cells at their intersections. A question asks: 'What was the APAC region's revenue in Q3 from the products segment?' How should your system navigate this multi-dimensional lookup?

Correct. The pandas DataFrame representation is the key architectural decision. TATR gives you cell positions and text; converting this to a structured DataFrame makes all downstream queries into deterministic pandas lookups rather than neural inference problems. Multi-level column headers become MultiIndex in pandas — ('Q3', 'Products') as a column tuple. The hybrid approach (TATR → DataFrame → pandas lookup for structured queries, TAPAS for natural language questions) is the production pattern that combines the reliability of structured computation with the flexibility of neural table QA.
