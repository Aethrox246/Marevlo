01 · Production Inference Pipeline and Optimisation

From Research Accuracy to
Production Latency

A production document intelligence pipeline has a latency budget — the total time available from document receipt to structured output delivery. Each stage (pre-processing, OCR, layout detection, NER, validation) consumes part of that budget. Optimisation targets the largest consumers first. The rule: apply lossless optimisations (ONNX export, operator fusion) before lossy ones (quantisation, distillation), and stop once the latency target is met.

🔑

The stack-lossless-first principle

ONNX export removes Python overhead and enables operator fusion (LayerNorm + Linear into a single kernel). It has zero accuracy cost. Apply it first, always. Only then apply INT8 quantisation (small accuracy cost) or knowledge distillation (larger accuracy cost) if the latency target is still not met after ONNX. This ordering ensures you never pay an accuracy penalty you didn't need to.

Question 1 of 5

Your LayoutLMv3 NER model runs at 600ms/document on GPU. The SLA requires P95 < 300ms. You have four optimisation options: ONNX export (1.4× speedup), INT8 quantisation (2.5× speedup, -0.8 F1), dynamic batching (3× GPU utilisation, +200ms latency), knowledge distillation to 6-layer student (4× speedup, -2.5 F1). Which combination meets the SLA without unacceptable accuracy loss?

Correct. The stack-lossless-first principle is the right approach. ONNX export is always applied first — it reduces latency with zero accuracy cost (just removes Python overhead and fuses operations). Then INT8 is applied to close the remaining gap. The combined speedup of 3.5× brings 600ms to 171ms — 129ms headroom under the SLA. Dynamic batching adds latency (wrong direction for SLA improvement). Knowledge distillation has more accuracy cost than INT8 for comparable speedup. This stacking approach is the standard production optimisation recipe for transformer inference.
Question 2 of 5

You export a LayoutLMv3 model to ONNX for production. The exported model runs correctly on test documents but silently produces wrong NER predictions on 3% of production documents. Debugging reveals these documents have more than 256 tokens. What is the cause?

Correct. Static shape export is the most common ONNX deployment bug for NLP models. The model is exported with specific tensor shapes; documents exceeding those shapes are silently truncated rather than raising an error. Dynamic axes is the fix — it marks specific dimensions as variable, allowing ONNX Runtime to handle any length up to the model's actual maximum. Always test the exported ONNX model with inputs at the minimum, middle, and maximum lengths before production deployment.
Question 3 of 5

You are applying knowledge distillation to compress LayoutLMv3-base (12 layers, 125M params) to a 6-layer student. The teacher achieves F1=0.91 on FUNSD. After distillation, the student achieves F1=0.87. A colleague suggests 'just skipping every other layer' — using layers 1,3,5,7,9,11 of the teacher as the student. Would this achieve similar results to proper distillation?

Correct. Layer skipping alone (without subsequent fine-tuning) degrades performance significantly — the skipped layers' representations are calibrated for 12-layer depth, and using them in a 6-layer network without adaptation produces misaligned intermediate representations. The PKD approach that combines layer-wise initialisation with distillation training is the correct method. It achieves the best of both worlds: good initialisation from teacher weights plus adaptation through distillation training.
Question 4 of 5

You are monitoring a production LayoutLMv3 NER system with 50,000 documents/day. The model was deployed 3 months ago with F1=0.91. Validation F1 has drifted to 0.84. Your monitoring shows P95 GPU inference latency has also increased from 180ms to 340ms over the same period. What is the most likely cause of the latency increase and how do you diagnose it?

Correct. Distribution shift in document complexity is the most common cause of production latency increases in transformer inference systems. Transformer inference is not O(1) in input length — the full sequence is processed at every layer. If longer documents enter the pipeline, every forward pass takes longer. The diagnostic approach (comparing average token count over time vs latency over time) is the correct first step. The fixed-benchmark test isolates infrastructure changes from input distribution changes. This kind of monitoring — tracking both model accuracy and inference characteristics jointly — is essential for production DiT systems.
Question 5 of 5

You deploy two LayoutLMv3 models behind an A/B test: Model A (current, F1=0.91) serves 90% of traffic, Model B (new, F1=0.93) serves 10%. After 2 days you observe Model B has a 22% higher human review rate than Model A despite its higher F1. What explains this contradiction?

Correct. Confidence calibration is a frequent source of contradictions between benchmark metrics and production behaviour. A model with higher F1 may produce systematically lower confidence scores if it was trained with a different loss temperature, data augmentation strategy, or regularisation. Lower confidence scores trigger more human reviews under the same routing threshold, even if the actual extractions are correct. The fix is per-model confidence calibration (Platt scaling or temperature scaling on a held-out production sample) before setting the routing threshold. This is a canonical example of why production monitoring must track multiple metrics jointly — F1 alone does not predict human review rate.
