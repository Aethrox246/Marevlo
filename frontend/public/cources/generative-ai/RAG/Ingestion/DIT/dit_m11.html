01 · Architecture Decision Framework

Choosing the Right DiT Component
for Every Document Type

After eleven modules, you have a toolkit of specialised components: LayoutLMv3 for bbox-producing NER on structured documents, Donut for fixed-schema OCR-free extraction, TATR+TAPAS for table understanding, TrOCR for handwritten text, LayoutXLM for multilingual transfer, Longformer for long documents, ONNX+INT8 for production inference. The capstone skill is knowing when to reach for each one — and how to combine them into a coherent production architecture.

💡

The meta-lesson: models are the easy part

Every module in this track has focused on model architectures — attention mechanisms, pretraining objectives, evaluation metrics. But production document AI systems spend most of their engineering effort on everything around the models: annotation quality, pre-processing calibration, routing logic, validation rules, monitoring infrastructure, and retraining pipelines. The model is typically 20% of the total engineering effort. The surrounding system is 80%.

Question 1 of 5

You are building a document intelligence system for a global logistics company. Documents include: customs declarations (structured forms, 8 languages, requires bbox for audit), shipping manifests (dense tables with nested headers, variable row counts), handwritten waybills (HTR required, variable quality), and bills of lading (fixed 40-field schema, poor scan quality common). Propose the complete architecture — one architecture decision per document type.

Correct. The modular design routing each document type to its specialised architecture is the right production answer. Key decisions: LayoutXLM (not LayoutLMv3) for multilingual customs declarations because cross-lingual transfer is the primary constraint; TATR for shipping manifests because nested table structure requires specialised TSR, not NER; TrOCR for handwritten waybills because handwriting requires HTR-specific models; Donut for bills of lading because fixed small schema + poor scan quality is exactly Donut's design case. Each choice exploits the module's specific strength.
Question 2 of 5

Your LayoutLMv3 invoice NER system achieves F1=0.91 on your English invoice test set. Six months later, F1 drops to 0.79. The product team reports no code changes. Walk through the complete diagnosis and remediation process.

Correct. The five-step diagnosis process (decompose by vendor/type → per-stage metrics → failure examples → monitor validation → targeted remediation) is the correct production engineering response. The key principle: never retrain before diagnosing. A 12-point F1 drop in 6 months almost always has an identifiable cause (new vendor, format change, upstream component update) that targeted fine-tuning on 200-300 examples can fix. Full retraining without diagnosis wastes 2-4 weeks of compute on a problem that data analysis can localise in hours.
Question 3 of 5

You have trained a LayoutLMv3 model and a Donut model on the same invoice dataset. On your held-out test set: LayoutLMv3 F1=0.91, Donut ANLS=0.88. The product manager asks: 'Which model should we deploy?' What information is missing and how does it change your recommendation?

Correct. Metric incomparability is the core issue — F1 and ANLS cannot be directly compared because they measure fundamentally different things on the same task. A model could have F1=0.91 (near-perfect token classification) and ANLS=0.88 (some character-level errors in extracted strings) or F1=0.91 (all fields identified) and ANLS=0.72 (fields identified but value extraction noisy). The four missing dimensions (latency, bbox requirement, error types, scan quality) are the practical decision factors. This is a canonical example of why model selection requires application context, not just benchmark comparison.
Question 4 of 5

A junior engineer proposes: 'Instead of fine-tuning LayoutLMv3 on 2,000 annotated invoices, let's just prompt GPT-4 Vision with the invoice image and ask it to return the fields as JSON. It's faster to set up and doesn't require annotation.' Evaluate this proposal rigorously.

Correct. The rigorous three-dimension evaluation (accuracy, cost, reliability) is the correct framework. The hybrid approach — GPT-4V for annotation bootstrapping, LayoutLMv3 for production — is the practical synthesis. GPT-4V's value is in reducing annotation cost (use its outputs as noisy labels to bootstrap training), not in replacing a fine-tuned specialist model at scale. This is a common pattern in modern document AI: large generalist models for data generation, small specialist models for production inference.
Question 5 of 5

You have completed the DiT track. A company asks you to design a document intelligence system that processes 100,000 documents per day — a mix of invoices, contracts, medical records, and handwritten forms — across 6 languages, with a 500ms SLA and 95% field-level F1 target. What are the five highest-effort components that will consume the most engineering time?

Correct. The five highest-effort components — annotation, calibration, routing orchestration, validation logic, and monitoring infrastructure — are the ones consistently underestimated in project planning. Model training, which seems like the core ML work, is typically the shortest effort once these foundations are built. This is the central lesson of production document AI: the engineering around the model (data, infrastructure, validation, monitoring) requires more time than training the model itself. A realistic project plan allocates 3-4× more time to these surrounding components than to model development.
