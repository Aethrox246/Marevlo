01 · Full Pipeline Architecture

Seven Stages From Raw Document
to Structured JSON Output

A production document intelligence pipeline is not a monolithic function — it is a sequence of independently scalable stages, each with its own queue, worker pool, failure mode, and checkpoint. Each stage writes its output to S3 before enqueuing the next stage. If any stage fails, it retries from its own input, not from the beginning of the pipeline.

StageInputOutputCheckpoint key
1. IngestionRaw document uploadS3 raw key, DynamoDB job recordraw/{hash}/{file}
2. Pre-processingRaw documentDeskewed, enhanced image(s)preprocessed/{hash}/page_{n}.jpg
3. Layout detectionEnhanced pagesRegion bboxes + types per pagelayout/{hash}/page_{n}.json
4. Table structureTable region cropsCell grids per tabletsr/{hash}/table_{n}.json
5. OCRText region cropsText per regionocr/{hash}/page_{n}.json
6. UnderstandingLayout + OCR outputStructured fields (JSON)fields/{hash}/result.json
7. ValidationStructured fieldsValidated output or human review flagvalidated/{hash}/result.json

Why stage-by-stage checkpointing matters

At 80k documents/day, a 1% failure rate means 800 failures/day. Without checkpointing, each failure re-runs the full 1.4s pipeline from the beginning. With checkpointing, a Stage 6 failure retries only Stage 6 (400ms) using the already-computed layout and OCR outputs. At 80k/day, this saves 800 x (1400-400) = 800,000ms = 13 minutes of wasted compute per day — plus the cost of re-running the more expensive OCR stage.

02 · Pipeline Orchestrator

Stage Dispatch, Checkpoint Check,
and Confidence Routing

pipeline/orchestrator.py

import boto3, json
from celery import Celery

app = Celery("docpipeline", broker="redis://redis:6379/0")
s3  = boto3.client("s3")
ddb = boto3.resource("dynamodb").Table("doc_jobs")
BUCKET = "doc-pipeline"

CONFIDENCE_THRESHOLD = 0.75

def checkpoint_exists(key: str) -> bool:
    """Return True if stage output already exists in S3."""
    try:
        s3.head_object(Bucket=BUCKET, Key=key)
        return True
    except: return False

def load_checkpoint(key: str) -> dict:
    obj = s3.get_object(Bucket=BUCKET, Key=key)
    return json.loads(obj["Body"].read())

def save_checkpoint(key: str, data: dict) -> None:
    s3.put_object(Bucket=BUCKET, Key=key,
                  Body=json.dumps(data),
                  ContentType="application/json")

@app.task(bind=True, max_retries=3, default_retry_delay=30)
def run_stage(self, job_id: str, doc_hash: str,
               stage: str, prev_key: str) -> str:
    """
    Generic stage runner. Checks checkpoint first — if stage output
    already exists (from a prior attempt), skip the computation.
    Dispatches to the stage-specific function, saves output,
    then enqueues the next stage.
    """
    out_key = f"{stage}/{doc_hash}/output.json"
    if checkpoint_exists(out_key):
        result = load_checkpoint(out_key)
    else:
        try:
            prev_data = load_checkpoint(prev_key) if prev_key else {}
            result = STAGE_FNS[stage](doc_hash, prev_data)
            save_checkpoint(out_key, result)
        except Exception as exc:
            raise self.retry(exc=exc)

    next_stage = STAGE_ORDER.get(stage)
    if next_stage == "validate":
        conf = result.get("mean_confidence", 1.0)
        if conf < CONFIDENCE_THRESHOLD:
            route_to_human_review(job_id, doc_hash, result, conf)
            return out_key
    if next_stage:
        run_stage.apply_async(args=[job_id, doc_hash, next_stage, out_key])
    else:
        ddb.update_item(Key={"job_id":job_id},
            UpdateExpression="SET #s=:s, result_key=:r",
            ExpressionAttributeNames={"#s":"status"},
            ExpressionAttributeValues={":s":"complete",":r":out_key})
    return out_key

STAGE_ORDER = {
    "preprocess": "layout",
    "layout":     "tsr",
    "tsr":        "ocr",
    "ocr":        "understand",
    "understand": "validate",
    "validate":   None,
}
STAGE_FNS: dict = {}  # registered at worker startup

def route_to_human_review(job_id: str, doc_hash: str,
                            result: dict, conf: float) -> None:
    ddb.update_item(Key={"job_id":job_id},
        UpdateExpression="SET #s=:s, review_reason=:r, confidence=:c",
        ExpressionAttributeNames={"#s":"status"},
        ExpressionAttributeValues={":s":"review",
                                    ":r":f"Low confidence: {conf:.2f}",
                                    ":c":str(conf)})
03 · Content Deduplication

SHA-256 Hash at Ingestion —
Idempotent Submission and GSI Lookup

pipeline/deduplication.py

import hashlib, boto3
from datetime import datetime, timezone

ddb = boto3.resource("dynamodb").Table("doc_jobs")

def content_hash(data: bytes) -> str:
    return hashlib.sha256(data).hexdigest()

def check_duplicate(doc_hash: str) -> dict | None:
    """
    Look up existing completed job by content hash via DynamoDB GSI.
    GSI: doc_hash-index on doc_hash attribute.
    Returns the existing job record if found (status=complete), else None.
    O(1) lookup — critical for high-throughput ingestion without adding latency.
    """
    resp = ddb.query(
        IndexName="doc_hash-index",
        KeyConditionExpression="doc_hash = :h",
        ExpressionAttributeValues={":h": doc_hash},
        FilterExpression="#s = :s",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={":h": doc_hash, ":s": "complete"},
        Limit=1
    )
    items = resp.get("Items", [])
    return items[0] if items else None

def ingest_with_deduplication(data: bytes, filename: str,
                                priority: str = "standard") -> dict:
    """
    Idempotent ingestion:
    1. Hash the document content.
    2. Check DynamoDB for an existing completed job with the same hash.
    3. If found: return the existing result immediately (no reprocessing).
    4. If not found: upload to S3, create job record, enqueue task.
    """
    doc_hash = content_hash(data)
    existing = check_duplicate(doc_hash)
    if existing:
        return {"job_id": existing["job_id"], "status": "complete",
                "result_key": existing["result_key"],
                "deduplicated": True}
    # ... proceed with normal ingestion
    return {"doc_hash": doc_hash, "status": "queued", "deduplicated": False}

05 · Assessment

Module 6 Quiz

1. Your pipeline processes 80k documents/day. Layout detection takes 200ms/page, OCR takes 800ms/page, LayoutLMv3 inference takes 400ms/page. Total sequential latency: 1.4s/page. Your SLA is under 5 minutes per document. With 4 GPU workers, what is your maximum throughput in documents/day?

Correct. At 1.4s per document and 4 workers, theoretical throughput is ~246k docs/day against a target of 80k — comfortable headroom. The key insight is identifying OCR as the dominant latency component (800ms of 1400ms = 57%). Optimising OCR is the highest-ROI improvement before scaling worker count.

2. Your confidence router sends documents with layout confidence below 0.6 to human review. Currently 23% of documents are flagged. What does this tell you, and what is the correct investigation order?

Correct. Lowering the threshold without investigation converts human-caught errors into silent failures — worse than the current state. The investigation must first establish whether the model is wrong on flagged documents before any threshold change. If it is wrong, add those documents to training. If it is right, the threshold may be too conservative.

3. A document enters the pipeline at 14:03. Layout detection completes at 14:03:12. OCR completes at 14:04:05. LayoutLMv3 inference never completes — the Celery worker crashes with an OOM error at 14:05:30. What state is the document in, and what happens next?

Correct. task_acks_late + task_reject_on_worker_lost is the critical Celery configuration that prevents job loss on worker crash. The task is requeued, not resumed from the crash point — Celery tasks are not checkpointed. The full inference step re-runs. If OOM is systematic on this document, the DLQ captures it for investigation.

4. You add a document deduplication step at ingestion using SHA-256 content hashing. A customer submits the same invoice PDF twice with different filenames. What happens in the pipeline, and is this the correct behaviour?

Correct. Content-hash deduplication is most valuable when it returns existing results immediately for duplicate submissions. The key implementation detail: check DynamoDB for an existing completed job with the same doc_hash before enqueueing a new task. A GSI on doc_hash makes this check O(1). Without this check, the pipeline reprocesses identical documents, wasting compute.

5. Your pipeline is processing 60k documents/day normally. At 09:15 the queue depth for the standard queue spikes to 2,400. The autoscaler runs every 30s with TARGET_DEPTH=4 and MAX_WORKERS=20. At 09:15:30 it scales to 20 workers. By 09:45 queue depth is still 1,800. What is happening and what should you check?

Correct. Persistent queue depth growth at maximum workers is the canonical sign that incoming rate exceeds maximum throughput capacity. The three checks — incoming rate, per-document latency, DLQ depth — identify which of the three failure modes (volume spike, latency increase, worker failures) is responsible. Each requires a different fix.
