Document Graph and Knowledge Extraction
Entity Linking · Relation Extraction · Passive Normalization · Triple Store · Coreference

Individual document extraction produces flat facts. Document knowledge graphs connect those facts into a queryable network — companies linked to their acquisitions, drugs linked to their indications, contracts linked to their parties and obligations. This module covers the full knowledge graph construction pipeline: named entity recognition and linking to knowledge base URIs, relation extraction with passive-to-active normalization, coreference resolution for cross-sentence relation attribution, triple store indexing for query performance, and the confidence-tiered entity linking approach that prevents false edges from corrupting graph structure.

01 · Knowledge Graph Construction Pipeline

From Document Extractions
to a Queryable Triple Store

A document knowledge graph converts extracted facts into a structured network of (subject, predicate, object) triples. Each triple represents a relationship: (AstraZeneca, ACQUIRED, MedImmune), (metformin, TREATS, Type2Diabetes), (Contract_001, OBLIGATES, Supplier). The pipeline has four sequential stages: NER + entity linking (who/what are the entities?), relation extraction (how are they related?), coreference resolution (what do pronouns refer to?), and triple store ingestion with indexing.

knowledge_graph.py — entity linking and relation extraction

from dataclasses import dataclass
from sentence_transformers import SentenceTransformer
import numpy as np, spacy

@dataclass
class Triple:
    subject: str; predicate: str; obj: str
    subject_uri: str; obj_uri: str
    confidence: float; source_doc: str; source_sent: str

LINK_ASSERT    = 0.75  # assert the link as a fact
LINK_CANDIDATE = 0.50  # store as candidate with confidence
# Below 0.50: store as unlinked surface form

class EntityLinker:
    """
    Link entity surface forms to KB URIs using context-embedding similarity.
    Three-tier output: assert (>0.75), candidate (0.5-0.75), unlinked (<0.5).
    Prevents false edges from being asserted when context is ambiguous.
    """
    def __init__(self, kb_entities: list[tuple[str,str,str]],
                 model_name: str = "all-MiniLM-L6-v2"):
        self.model  = SentenceTransformer(model_name)
        self.uris   = [e[0] for e in kb_entities]
        self.labels = [e[1] for e in kb_entities]
        self.descs  = [e[2] for e in kb_entities]
        self.corpus_emb = self.model.encode(
            [f"{l}: {d}" for l,d in zip(self.labels, self.descs)])

    def link(self, surface: str, context: str) -> dict:
        query = self.model.encode(f"{surface}: {context}")
        sims  = np.dot(self.corpus_emb, query) / (
                np.linalg.norm(self.corpus_emb,axis=1)*np.linalg.norm(query)+1e-8)
        best_i = int(np.argmax(sims)); score = float(sims[best_i])
        if score >= LINK_ASSERT:
            return {"uri":self.uris[best_i],"status":"asserted","conf":score}
        elif score >= LINK_CANDIDATE:
            return {"uri":self.uris[best_i],"status":"candidate","conf":score}
        return {"uri":None,"status":"unlinked","conf":score}

PASSIVE_INDICATORS = {"acquired","was acquired","were acquired","is owned",
                      "was founded","was established"}

def normalise_passive(subj: str, pred: str, obj: str,
                       sentence: str) -> tuple[str,str,str]:
    """
    Normalise passive constructions to active voice direction.
    "X was acquired by Y" -> (Y, ACQUIRED, X)
    Prevents duplicate and contradictory edges in the graph.
    """
    import re
    if any(p in sentence.lower() for p in PASSIVE_INDICATORS):
        by_match = re.search(rr"by\s+([A-Z][a-zA-Z\s&]+)", sentence)
        if by_match:
            agent = by_match.group(1).strip()
            return agent, pred.upper(), subj
    return subj, pred.upper(), obj

graph_storage.py — Neo4j ingestion with labelled relationship types

from neo4j import GraphDatabase

class KnowledgeGraphStore:
    """
    Neo4j-backed knowledge graph with labelled relationship types.
    Labelled relationships are natively indexed by Neo4j — faster
    than generic RELATES_TO with a type property that requires
    explicit property index creation.

    Schema design:
    (:Entity {uri, label, type})-[:PREDICATE {confidence, source_doc}]->(:Entity)
    Each unique predicate is a separate relationship label (ACQUIRED, FOUNDED, TREATS).
    """
    def __init__(self, uri: str, user: str, password: str):
        self.driver = GraphDatabase.driver(uri, auth=(user, password))

    def upsert_triple(self, triple: Triple) -> None:
        with self.driver.session() as session:
            session.run("""
                MERGE (s:Entity {uri: $subj_uri})
                SET s.label = $subj, s.updated = datetime()
                MERGE (o:Entity {uri: $obj_uri})
                SET o.label = $obj
                WITH s, o
                CALL apoc.merge.relationship(s, $pred, {}, {
                    confidence: $conf,
                    source_doc: $doc,
                    source_sent: $sent,
                    asserted: $conf >= 0.75
                }, o) YIELD rel
                RETURN rel
            """, subj_uri=triple.subject_uri, subj=triple.subject,
                      obj_uri=triple.obj_uri,   obj=triple.obj,
                      pred=triple.predicate,     conf=triple.confidence,
                      doc=triple.source_doc,     sent=triple.source_sent)

    def create_indices(self) -> None:
        """Create indices for common query patterns."""
        with self.driver.session() as session:
            session.run("CREATE INDEX entity_uri IF NOT EXISTS FOR (e:Entity) ON (e.uri)")
            session.run("CREATE INDEX entity_label IF NOT EXISTS FOR (e:Entity) ON (e.label)")
            session.run("CREATE INDEX entity_type IF NOT EXISTS FOR (e:Entity) ON (e.type)")

    def query_acquisitions(self, start_year: int, end_year: int) -> list[dict]:
        """Example query — labelled relationship types enable native index use."""
        with self.driver.session() as session:
            result = session.run("""
                MATCH (acquirer:Entity)-[r:ACQUIRED]->(target:Entity)
                WHERE r.year >= $start AND r.year <= $end
                  AND r.asserted = true
                RETURN acquirer.label, target.label, r.year, r.confidence
                ORDER BY r.confidence DESC
            """, start=start_year, end=end_year)
            return [dict(record) for record in result]
03 · Assessment

Module 15 Quiz

1. Relation extractor finds both active and passive forms of the same acquisition event. How should the knowledge graph store them?

Correct. Passive-to-active normalization is required for relation extraction. Both directions as separate edges means queries for "who acquired MedImmune?" return both AstraZeneca and MedImmune as acquirers.

2. entity_linking() must link "Apple" in a document discussing both "Apple revenue" and "Apple orchard subsidies". How does the linker resolve the ambiguity?

Correct. Context-embedding disambiguation handles intra-document ambiguity that prior probability cannot. Storing the KB URI rather than the surface form is the key design decision for cross-document entity consistency.

3. A query over 2M triples for companies that acquired biotech firms 2015-2020 takes 45 seconds. Most likely cause and fix?

Correct. Missing predicate and property indices are the most common cause of slow graph queries. Labelled Neo4j relationships are natively indexed; relationship properties require explicit index creation.

4. A coreference chain incorrectly links "it" to "the competitor" instead of "the company". What is the downstream knowledge graph effect?

Correct. Coreference errors propagate silently into the knowledge graph as false edges between valid entities. Cross-document consistency checking is the primary detection mechanism. Confidence-flagged uncertain triples allow downstream consumers to filter by assertion confidence.

5. Your document KG has entity nodes for 50k companies. A new batch of financial reports mentions "Alphabet" 200 times. entity_linking() links 180 to Alphabet Inc. (Google parent) and 20 to "Alphabet" as a generic word for a letter sequence. How should the pipeline handle the 20 incorrect links?

Correct. A confidence threshold with three tiers (assert, candidate, unlinked) is the correct approach for entities with high surface form ambiguity. It prevents false edge creation while preserving information for review. The minimum similarity threshold of 0.75 for assertion is a starting point — calibrate against a held-out validation set of known links.
