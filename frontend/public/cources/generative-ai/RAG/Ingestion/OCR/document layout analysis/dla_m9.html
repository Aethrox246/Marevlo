Multilingual and Low-Resource Documents
Unicode BiDi · Script Detection · mBERT · XLM-RoBERTa · Cross-Lingual Transfer · Synthetic Data

Most document pipelines are built for one language on one script. Production reality is messier — invoices arrive in Arabic with bidirectional text, forms mix Hindi and English in the same field, low-resource languages have fewer than 200 annotated examples, and cross-lingual transfer must bridge German field labels to an English-trained extractor. This module covers Unicode bidirectional text handling, script detection and multi-script OCR configuration, multilingual pretrained models (mBERT, XLM-RoBERTa), cross-lingual transfer for document understanding, synthetic data generation for low-resource scripts, and the failure modes specific to non-Latin document pipelines.

01 · Unicode Bidirectional Text and Script Detection

Why BiDi Failure Silently Corrupts
Arabic and Hebrew Extraction

Unicode defines two text ordering conventions: logical order (the order characters are typed and stored, which matches semantic reading order) and visual order (the order characters appear on screen after bidirectional rendering). Arabic and Hebrew are right-to-left scripts — their logical order runs right-to-left, but they frequently appear on pages alongside left-to-right scripts. OCR engines that do not implement the Unicode BiDi algorithm return visual-order text that appears correct visually but is semantically inverted when consumed by an NLP model.

multilingual_ocr.py — BiDi handling and script detection

import unicodedata, re
from collections import Counter

def detect_script(text: str) -> dict:
    """
    Detect Unicode script blocks present in text.
    Returns a dict mapping script name to character fraction.
    Used to configure the correct Tesseract language combination.
    """
    script_ranges = {
        "Latin":      (0x0041, 0x024F),
        "Arabic":     (0x0600, 0x06FF),
        "Devanagari": (0x0900, 0x097F),
        "CJK":        (0x4E00, 0x9FFF),
        "Cyrillic":   (0x0400, 0x04FF),
        "Hebrew":     (0x0590, 0x05FF),
        "Ethiopic":   (0x1200, 0x137F),
        "Thai":       (0x0E00, 0x0E7F),
    }
    alpha = [c for c in text if c.isalpha()]
    if not alpha: return {}
    counts = Counter()
    for c in alpha:
        cp = ord(c)
        for name, (lo, hi) in script_ranges.items():
            if lo <= cp <= hi: counts[name] += 1; break
    total = len(alpha)
    return {k: round(v/total, 3) for k, v in counts.items()}

TESSERACT_LANG_MAP = {
    "Latin": "eng", "Arabic": "ara", "Devanagari": "hin",
    "CJK": "chi_sim", "Cyrillic": "rus",
    "Hebrew": "heb", "Ethiopic": "amh", "Thai": "tha",
}

def build_lang_string(scripts: dict, threshold: float = 0.05) -> str:
    """Build Tesseract lang string from detected scripts (threshold = min fraction)."""
    langs = [TESSERACT_LANG_MAP[s] for s, f in scripts.items()
             if f >= threshold and s in TESSERACT_LANG_MAP]
    return "+".join(langs) if langs else "eng"

def fix_bidi(visual_text: str) -> str:
    """
    Convert OCR visual-order text to Unicode logical order.
    Apply when OCR engine returns RTL text in visual (LTR scan) order.
    Requires: pip install python-bidi
    """
    from bidi.algorithm import get_display
    return get_display(visual_text, base_dir="R")
02 · Multilingual Pretrained Models

mBERT and XLM-RoBERTa for
Cross-Lingual Document Understanding

mBERT (multilingual BERT) and XLM-RoBERTa are transformer models pretrained on 100+ languages simultaneously. Their multilingual embedding space encodes cross-lingual representations — semantically similar text in different languages maps to nearby embedding positions. This allows fine-tuning on high-resource languages and zero-shot or few-shot transfer to low-resource languages without additional data collection.

multilingual_classifier.py — XLM-RoBERTa for multilingual document classification

from transformers import (AutoTokenizer, AutoModelForSequenceClassification,
                           Trainer, TrainingArguments)
from torch.utils.data import Dataset
import torch

class DocDataset(Dataset):
    def __init__(self, texts, labels, tokenizer, max_len=512):
        self.enc = tokenizer(texts, truncation=True, padding=True,
                             max_length=max_len, return_tensors="pt")
        self.labels = torch.tensor(labels)
    def __len__(self): return len(self.labels)
    def __getitem__(self, i):
        return {k: v[i] for k, v in self.enc.items()} | {"labels": self.labels[i]}

def build_multilingual_classifier(
        train_texts: list[str], train_labels: list[int],
        num_classes: int,
        model_name: str = "xlm-roberta-base") -> Trainer:
    """
    Fine-tune XLM-RoBERTa for multilingual document classification.
    Works across 100+ languages using a single shared model.
    For low-resource languages (< 500 examples): freeze all encoder layers
    except the last 3 and fine-tune only those layers + classification head.
    This prevents overfitting on small datasets while retaining cross-lingual
    representations from multilingual pre-training.
    """
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModelForSequenceClassification.from_pretrained(
        model_name, num_labels=num_classes)

    # Freeze most encoder layers for low-resource fine-tuning
    for name, param in model.named_parameters():
        layer_num = re.search(r"encoder\.layer\.(\d+)", name)
        if layer_num and int(layer_num.group(1)) < 9:  # freeze first 9 of 12
            param.requires_grad = False

    dataset = DocDataset(train_texts, train_labels, tokenizer)
    args = TrainingArguments(
        output_dir="./xlmr_doc_classifier",
        num_train_epochs=5, per_device_train_batch_size=16,
        learning_rate=2e-5, warmup_ratio=0.1,
        evaluation_strategy="epoch", save_strategy="epoch",
        load_best_model_at_end=True)
    return Trainer(model=model, args=args, train_dataset=dataset)

from jinja2 import Template
import subprocess, tempfile, os, json, random

INVOICE_TEMPLATE = """
<!DOCTYPE html><html><head>
<meta charset="utf-8">
<style>
  body { font-family: {{ font }}; font-size: {{ font_size }}pt; }
  .header { font-weight: bold; font-size: {{ header_size }}pt; }
  table { border-collapse: collapse; width: 100%; }
  td { padding: 4px 8px; border: {{ border }}; }
</style></head><body>
<div class="header">{{ company_name }}</div>
<p>{{ address }}</p>
<table>
  <tr><td>{{ field_labels.date }}</td><td>{{ date }}</td></tr>
  <tr><td>{{ field_labels.invoice_no }}</td><td>{{ invoice_no }}</td></tr>
  <tr><td>{{ field_labels.total }}</td><td>{{ total }}</td></tr>
</table>
</body></html>
"""

AMHARIC_FIELDS = {
    "date":       "ቀን",
    "invoice_no": "የደረሰኝ ቁጥር",
    "total":      "ጠቅላላ",
}

def generate_synthetic_invoice(fields: dict, lang_config: dict) -> tuple[str, dict]:
    """
    Generate a synthetic invoice image and its field annotations.
    fields: {date, invoice_no, total, company_name, address}
    lang_config: {font, font_size, header_size, border, field_labels}
    Returns: (html_path, annotation_dict)
    """
    tmpl  = Template(INVOICE_TEMPLATE)
    html  = tmpl.render(**fields, **lang_config)
    with tempfile.NamedTemporaryFile(suffix=".html", delete=False, mode="w") as f:
        f.write(html); html_path = f.name
    annotations = {"date": fields["date"], "invoice_no": fields["invoice_no"],
                   "total": fields["total"]}
    return html_path, annotations

def render_to_image(html_path: str, output_png: str, dpi: int = 150) -> None:
    """Render HTML to PNG using headless Chrome (wkhtmltoimage as alternative)."""
    subprocess.run(["chromium-browser", "--headless", "--disable-gpu",
                     f"--screenshot={output_png}",
                     f"--window-size=794,1123", html_path], check=True)

05 · Assessment

Module 9 Quiz

1. Your pipeline receives Arabic invoices. OCR returns text in visual order (RTL characters stored LTR as they appear visually). NLP extraction trained on logical order fails. Root cause and fix?

Correct. Unicode BiDi failure is the root cause for most Arabic/Hebrew OCR pipeline failures. The fix is BiDi-aware OCR at source, or the Unicode BiDi algorithm as post-processing. Both are valid — choose based on whether you control the OCR engine.

2. Multilingual document classifier across 12 languages: 5,000 annotated documents for 8 languages, only 200 per language for 4 low-resource languages. Most effective strategy for low-resource languages?

Correct. Cross-lingual transfer from multilingual pretrained models (mBERT, XLM-RoBERTa) is the standard approach for low-resource languages. The shared multilingual embedding space allows representations from high-resource languages to transfer. 200 examples is sufficient for fine-tuning a classification head on a frozen multilingual encoder.

3. detect_script() finds mixed Hindi (Devanagari) and English (Latin) text. Your pipeline runs Tesseract with lang="hin". What goes wrong and what is the fix?

Correct. Tesseract lang combination (lang="hin+eng") is the correct fix for mixed-script documents. Using only one language model garbles the excluded script. Combine only the scripts actually detected in the document to balance accuracy and latency.

4. Generating synthetic training data for low-resource Amharic (Ethiopic script) document extraction. You have 50 real annotated Amharic invoices. Two most effective strategies?

Correct. Template-based synthesis and document-specific augmentation are the two highest-ROI strategies for low-resource image document extraction. Template synthesis provides structural diversity; augmentation provides scan-quality diversity. Translation-based approaches help text models but do not address image distribution coverage.

5. LayoutLMv3 is fine-tuned on English invoices and must now extract fields from German invoices without retraining. Zero-shot performance is 0.54 F1. What are the two most likely causes of the gap, and what is the fastest fix?

Correct. Vocabulary mismatch (German field labels as rare tokens) and spatial layout drift are the two root causes of cross-lingual transfer gaps in document extraction. Few-shot fine-tuning on 50-100 target-language examples is the fastest fix — it is faster and cheaper than collecting hundreds of examples and retraining from scratch.
