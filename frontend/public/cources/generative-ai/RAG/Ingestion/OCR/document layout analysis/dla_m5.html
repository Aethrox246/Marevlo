Document Understanding Models
LayoutLM v1/v2/v3 · Donut · Document VQA · OCR-Free vs OCR-Dependent · Fine-Tuning Strategies

Classical and deep learning layout models identify where regions are. Document understanding models reason about what those regions mean — extracting structured fields, answering questions, and producing clean JSON from raw document images. This module covers the LayoutLM family (v1, v2, v3) and their multi-modal pre-training approach, Donut as an OCR-free end-to-end alternative, document VQA as a task formulation, the trade-offs between OCR-dependent and OCR-free architectures, and fine-tuning strategies for domain-specific document types.

01 · The LayoutLM Family

Text, Layout, and Image:
Progressive Multi-Modal Pre-Training

LayoutLM extends BERT with 2D spatial position embeddings — adding (x1, y1, x2, y2) bounding box coordinates to each text token. LayoutLMv2 adds image patch embeddings via a CNN, enabling cross-modal attention between text tokens and visual features. LayoutLMv3 replaces the CNN with a linear projection of image patches and applies unified masking objectives across both modalities, achieving state-of-the-art on DocVQA, information extraction, and document classification tasks.

layoutlmv3_inference.py — document field extraction

from transformers import LayoutLMv3Processor, LayoutLMv3ForTokenClassification
import torch
from PIL import Image

LABELS = ["O","B-HEADER","I-HEADER","B-QUESTION","I-QUESTION",
          "B-ANSWER","I-ANSWER"]

def extract_fields(image_path: str, ocr_words: list[str],
                    ocr_boxes: list[list[int]],
                    model_path: str = "microsoft/layoutlmv3-base") -> dict:
    """
    Extract structured fields using LayoutLMv3 token classification.

    ocr_words: list of word strings from OCR
    ocr_boxes: list of [x1,y1,x2,y2] normalised to [0,1000] per LayoutLM convention
    Returns: dict mapping field_type -> list of extracted text spans
    """
    processor = LayoutLMv3Processor.from_pretrained(model_path)
    model = LayoutLMv3ForTokenClassification.from_pretrained(
        model_path, num_labels=len(LABELS))
    model.eval()

    image = Image.open(image_path).convert("RGB")
    inputs = processor(image, ocr_words, boxes=ocr_boxes,
                       return_tensors="pt", truncation=True)

    with torch.no_grad():
        outputs = model(**inputs)

    predictions = outputs.logits.argmax(dim=-1).squeeze()
    word_ids = inputs.word_ids()

    fields = {"HEADER":[], "QUESTION":[], "ANSWER":[]}
    current_field, current_tokens = None, []
    for idx, word_id in enumerate(word_ids):
        if word_id is None: continue
        label = LABELS[predictions[idx].item()]
        if label.startswith("B-"):
            if current_field: fields[current_field].append(" ".join(current_tokens))
            current_field = label[2:]; current_tokens = [ocr_words[word_id]]
        elif label.startswith("I-") and current_field:
            current_tokens.append(ocr_words[word_id])
        else:
            if current_field: fields[current_field].append(" ".join(current_tokens))
            current_field, current_tokens = None, []
    return fields
02 · Donut: OCR-Free Document Understanding

Swin Encoder + Autoregressive Decoder
End-to-End Without an OCR Step

Donut (Document Understanding Transformer) eliminates the OCR dependency entirely. A Swin Transformer encoder converts the document image into patch embeddings. A BART-style autoregressive decoder generates structured output (JSON, key-value pairs, or free-form answers) directly from those embeddings — no text extraction, no bounding boxes, no intermediate representation. This removes the error accumulation of multi-stage OCR pipelines at the cost of a fixed-resolution input constraint.

donut_inference.py — end-to-end document field extraction

from transformers import DonutProcessor, VisionEncoderDecoderModel
import torch, re
from PIL import Image

def load_donut(model_name: str = "naver-clova-ix/donut-base-finetuned-cord-v2"):
    processor = DonutProcessor.from_pretrained(model_name)
    model = VisionEncoderDecoderModel.from_pretrained(model_name)
    model.eval()
    return processor, model

def extract_with_donut(image_path: str, processor, model,
                         task_prompt: str = "<s_cord-v2>") -> dict:
    """
    Run Donut on a document image.
    task_prompt: task-specific start token that conditions the decoder.
    Each fine-tuned Donut model has a task-specific prompt token.
    Output: parsed JSON dict of extracted fields.
    """
    image = Image.open(image_path).convert("RGB")
    pixel_values = processor(image, return_tensors="pt").pixel_values

    decoder_input_ids = processor.tokenizer(
        task_prompt, add_special_tokens=False, return_tensors="pt").input_ids

    with torch.no_grad():
        outputs = model.generate(
            pixel_values, decoder_input_ids=decoder_input_ids,
            max_length=model.decoder.config.max_position_embeddings,
            early_stopping=True, pad_token_id=processor.tokenizer.pad_token_id,
            eos_token_id=processor.tokenizer.eos_token_id, use_cache=True,
            num_beams=1, bad_words_ids=[[processor.tokenizer.unk_token_id]])

    sequence = processor.batch_decode(outputs)[0]
    sequence = sequence.replace(processor.tokenizer.eos_token, "").                        replace(processor.tokenizer.pad_token, "")
    return processor.token2json(sequence)

def donut_resolution_check(image_path: str, target_h: int = 1280,
                             target_w: int = 960,
                             min_text_px: int = 10) -> dict:
    """
    Check whether text will be readable after Donut downscaling.
    Estimates the minimum text pixel height after rescaling.
    If below min_text_px, warn that small text may be unreadable.
    """
    import cv2
    img = cv2.imread(image_path)
    orig_h, orig_w = img.shape[:2]
    scale = min(target_h/orig_h, target_w/orig_w)
    # Assume minimum body text height = 10pt at 96 DPI = ~13px
    min_src_text_h = 13
    scaled_text_h  = min_src_text_h * scale
    return {"scale": round(scale, 3),
            "scaled_text_h_px": round(scaled_text_h, 1),
            "readable": scaled_text_h >= min_text_px,
            "recommendation": "OK" if scaled_text_h >= min_text_px
                               else f"Increase Donut resolution or use LayoutLMv3"}
03 · Document VQA as a Task Formulation

Answering Questions Over Documents —
Extractive vs Abstractive Answers

Document VQA frames information extraction as question answering: given a document image and a natural language question, produce an answer. Extractive VQA (the DocVQA standard) produces answers that are exact spans from the document text. Abstractive VQA allows generated answers that are not literal spans. The distinction matters for evaluation — extractive systems use ANLS (Average Normalised Levenshtein Similarity) which tolerates minor OCR errors; abstractive systems require generation-aware metrics like ROUGE or BERTScore.

docvqa_inference.py — LayoutLMv3 extractive VQA

from transformers import LayoutLMv3Processor, LayoutLMv3ForQuestionAnswering
import torch
from PIL import Image

def answer_question(image_path: str, question: str,
                     ocr_words: list, ocr_boxes: list,
                     model_path: str = "impira/layoutlm-document-qa") -> dict:
    """
    Extractive document VQA using LayoutLMv3.
    Returns the answer span and its confidence score.
    ocr_boxes: normalised to [0, 1000] per LayoutLM convention.
    """
    processor = LayoutLMv3Processor.from_pretrained(model_path)
    model = LayoutLMv3ForQuestionAnswering.from_pretrained(model_path)
    model.eval()

    image = Image.open(image_path).convert("RGB")
    encoding = processor(image, question, ocr_words, boxes=ocr_boxes,
                         return_tensors="pt", truncation=True)

    with torch.no_grad():
        outputs = model(**encoding)

    start = outputs.start_logits.argmax(dim=-1).item()
    end   = outputs.end_logits.argmax(dim=-1).item()
    tokens = processor.tokenizer.convert_ids_to_tokens(
        encoding["input_ids"].squeeze())
    answer = processor.tokenizer.convert_tokens_to_string(
        tokens[start:end+1])
    conf = float(torch.softmax(outputs.start_logits, dim=-1).max() *
                 torch.softmax(outputs.end_logits, dim=-1).max())
    return {"answer": answer, "confidence": round(conf, 3),
            "start_token": start, "end_token": end}

05 · Assessment

Module 5 Quiz

1. LayoutLMv3 takes image patches and text tokens. A colleague says to skip image patches on clean PDFs. When correct, when wrong?

Correct. Image patches are a robustness mechanism for imperfect OCR and visual-only elements. On clean born-digital PDFs the text and position embeddings carry the signal. Start with text-only LayoutLM on high-quality PDFs and add image patches when accuracy gaps appear on specific document types.

2. Donut achieves document understanding without OCR. How does it process a document image, and what is the main production limitation?

Correct. Donut eliminates OCR dependency but trades it for a resolution-vs-compute constraint. Use Donut for structured forms with large text; use LayoutLMv3 plus explicit OCR for dense multi-column documents.

3. LayoutLMv3 fine-tuned on DocVQA achieves 89% ANLS on DocVQA test but 61% on internal invoices. Two most likely causes?

Correct. Question distribution mismatch and missing entity types are the two most actionable root causes. Measuring per-question-type ANLS on the invoice test set confirms which failure mode dominates before investing in data collection.

4. Choosing between LayoutLMv3 and Donut for invoice extraction at 50k per day with variable scan quality. Which is more appropriate?

Correct. Donut is not immune to scan quality — it is brittle in a different way. Low-resolution images produce illegible image patches at Donut input resolution. LayoutLMv3 with OCR preprocessing is more robust in production because each step can be independently optimised and monitored.

5. Fine-tuning LayoutLMv3 for NER on purchase orders: training NER F1=0.91 but test F1=0.67 after 10 epochs on 800 annotated documents. Two most effective fixes?

Correct. Layer freezing and token-level augmentation address overfitting from opposite sides: freezing reduces the adapted parameter space; augmentation expands the effective training distribution. Both have stronger empirical support than CRF or model downsizing for LayoutLM fine-tuning on small annotated sets.
