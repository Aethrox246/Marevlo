01 · Benchmark Construction

Three Pillars of a
Trustworthy Evaluation Dataset

A benchmark that overestimates production performance is worse than no benchmark — it produces confident deployment decisions based on misleading evidence. Three design choices determine whether a benchmark is trustworthy: test set isolation, annotation quality, and distribution representativeness. All three must be correct before any F1 number from the benchmark can be trusted.

benchmark_construction.py

from datetime import datetime
from sklearn.metrics import cohen_kappa_score
import numpy as np

def time_based_split(documents: list[dict],
                      test_cutoff_date: str,
                      stratify_by: list[str] = None) -> tuple[list, list]:
    """
    Split documents into train/test by date to prevent temporal leakage.
    Documents before test_cutoff_date go to train; after go to test.
    This also naturally tests temporal generalisation —
    the model must handle future document formats it was not trained on.

    stratify_by: list of metadata fields (e.g. ['doc_type', 'vendor'])
    to check distribution balance after split.
    """
    cutoff = datetime.fromisoformat(test_cutoff_date)
    train = [d for d in documents if datetime.fromisoformat(d["date"]) < cutoff]
    test  = [d for d in documents if datetime.fromisoformat(d["date"]) >= cutoff]
    if stratify_by:
        for field in stratify_by:
            train_dist = {d[field] for d in train}
            test_dist  = {d[field] for d in test}
            missing    = test_dist - train_dist
            if missing:
                print(f"WARNING: test set contains {field} values not in train: {missing}")
    return train, test

def measure_iaa(annotations_a: list[dict],
                annotations_b: list[dict],
                fields: list[str]) -> dict:
    """
    Measure inter-annotator agreement per field using Cohen Kappa.
    Annotators must label the same documents independently.
    IAA below 0.85 on any key field means the ground truth for that
    field is unreliable — do not use it in the benchmark.
    """
    results = {}
    for field in fields:
        a = [ann.get(field, "") for ann in annotations_a]
        b = [ann.get(field, "") for ann in annotations_b]
        kappa = cohen_kappa_score(a, b)
        results[field] = {"kappa": round(kappa, 3),
                          "reliable": kappa >= 0.85}
    results["benchmark_ready"] = all(v["reliable"] for v in results.values()
                                     if isinstance(v, dict))
    return results

pipeline_metrics.py — rolling validation monitor

from collections import deque
import numpy as np

class RollingValidationMonitor:
    """
    Samples recently-processed documents and computes rolling F1.
    Triggers a retraining alert when rolling F1 drops 3+ points from baseline.
    Uses reservoir sampling to ensure representative coverage of all document types.
    """
    def __init__(self, baseline_f1: float, window: int = 500,
                 alert_threshold: float = 0.03):
        self.baseline = baseline_f1
        self.window   = window
        self.alert    = alert_threshold
        self.buffer   = deque(maxlen=window)

    def add_sample(self, predicted: dict, ground_truth: dict) -> None:
        """Add a validated sample to the rolling window."""
        correct = predicted == ground_truth
        self.buffer.append(correct)

    def current_f1(self) -> float:
        if not self.buffer: return None
        return sum(self.buffer) / len(self.buffer)

    def check_alert(self) -> dict:
        f1 = self.current_f1()
        if f1 is None: return {"alert": False, "reason": "Insufficient samples"}
        drop = self.baseline - f1
        return {"rolling_f1": round(f1, 3),
                "baseline_f1": self.baseline,
                "drop": round(drop, 3),
                "alert": drop >= self.alert,
                "recommendation": "Trigger retraining pipeline" if drop >= self.alert
                                    else "Within acceptable range"}
03 · Distribution Shift Detection

Detecting When Your Production Data
Has Drifted from Training Data

drift_detection.py

from scipy.stats import ks_2samp, chi2_contingency
from collections import Counter
import numpy as np

def detect_text_drift(train_texts: list[str],
                       prod_texts: list[str],
                       n_features: int = 1000) -> dict:
    """
    Detect vocabulary drift between training and production text distributions.
    Uses TF-IDF feature distribution comparison via Kolmogorov-Smirnov test.
    A significant KS statistic (p < 0.05) indicates distribution shift.
    """
    from sklearn.feature_extraction.text import TfidfVectorizer
    vect = TfidfVectorizer(max_features=n_features)
    vect.fit(train_texts)
    train_means = np.array(vect.transform(train_texts).mean(axis=0)).flatten()
    prod_means  = np.array(vect.transform(prod_texts).mean(axis=0)).flatten()
    stat, pvalue = ks_2samp(train_means, prod_means)
    return {"ks_statistic": round(stat, 4), "p_value": round(pvalue, 4),
            "drift_detected": pvalue < 0.05,
            "severity": "high" if stat > 0.3 else "medium" if stat > 0.1 else "low"}

def detect_doc_type_drift(train_labels: list[str],
                           prod_labels: list[str]) -> dict:
    """
    Detect shifts in document type distribution using chi-squared test.
    A significant chi-squared (p < 0.05) means the class distribution
    in production differs from training — a common cause of F1 degradation
    on under-represented classes.
    """
    all_classes = sorted(set(train_labels) | set(prod_labels))
    train_counts = [Counter(train_labels)[c] for c in all_classes]
    prod_counts  = [Counter(prod_labels)[c]  for c in all_classes]
    contingency  = np.array([train_counts, prod_counts])
    chi2, pvalue, _, _ = chi2_contingency(contingency)
    return {"chi2": round(chi2, 2), "p_value": round(pvalue, 4),
            "drift_detected": pvalue < 0.05,
            "class_distribution": {c: prod_counts[i] for i,c in enumerate(all_classes)}}

05 · Assessment

Module 8 Quiz

1. Pipeline extraction F1 drops from 0.91 to 0.83 over 6 weeks with no code changes. Three most likely causes and correct investigation order?

Correct. F1 drift without code changes is almost always distribution shift in the input documents or ground truth labels. Checking the input distribution by week is the fastest first step. Per-stage metric monitoring then isolates which pipeline component is responsible.

2. A/B testing new LayoutLMv3-large vs current base: 10% traffic for 2 weeks, new model F1=0.93 vs 0.91. Sufficient evidence to deploy?

Correct. Statistical significance and segment-level regression analysis are both required before deploying. Average F1 improvement can hide per-segment regressions that matter more to the business than the aggregate metric suggests.

3. Internal test set F1=0.92 but client reports 20% extraction errors on their documents. Most likely cause?

Correct. High internal F1 with poor client performance is the canonical sign of test set distribution mismatch or annotation guideline misalignment. The fix is to build a client-representative test set with aligned guidelines — not to adjust model hyperparameters.

4. Which metric should trigger an automatic model retraining job, and why not the others?

Correct. Retraining should be triggered by measured quality degradation in production, not by time or training dynamics. Human review rate and rolling validation F1 are the two metrics closest to the extraction quality that matters to the business.

5. Constructing a benchmark from 5,000 invoices. Three most critical design decisions that determine benchmark trustworthiness?

Correct. Test set isolation, annotation IAA, and distribution representativeness are the three pillars of a trustworthy benchmark. A benchmark that fails any of these three will produce F1 numbers that do not predict production performance — leading to deployment decisions based on misleading evidence.
