Real-Time and Streaming Document Pipelines
Kafka Manual Commit · Consumer Lag Autoscaling · GPU Batch Sizing · Flink Checkpointing · Priority Tiers

Batch document pipelines process documents after they arrive. Real-time pipelines must extract results while documents are still arriving — within seconds, not minutes. This module covers Kafka-based streaming document ingestion with manual offset commit for exactly-once semantics, consumer group lag as the primary autoscaling metric, GPU batch sizing to reduce per-document OCR latency, parallel stage execution within a document, Flink checkpoint-based fault tolerance for stateful aggregations, and priority-tier resource isolation using separate Kafka topics with dedicated consumer groups.

01 · Kafka-Based Streaming Ingestion

Manual Offset Commit and
Exactly-Once Processing Semantics

streaming_consumer.py — manual offset commit with idempotent writes

from kafka import KafkaConsumer
import boto3, json, time

def build_consumer(topic: str, group_id: str,
                    bootstrap_servers: list[str]) -> KafkaConsumer:
    """
    Manual offset commit consumer for exactly-once semantics.
    enable.auto.commit=False: offset only advances after S3 write succeeds.
    auto.offset.reset=earliest: replay from last committed offset on restart.
    max.poll.records: tune to GPU batch size for throughput-latency balance.
    """
    return KafkaConsumer(
        topic,
        bootstrap_servers=bootstrap_servers,
        group_id=group_id,
        enable_auto_commit=False,      # manual commit only
        auto_offset_reset="earliest",
        max_poll_records=8,             # batch up to 8 pages per poll
        value_deserializer=lambda m: json.loads(m.decode()),
        session_timeout_ms=30000,
        heartbeat_interval_ms=10000)

def process_batch(consumer: KafkaConsumer, s3, bucket: str,
                   layout_fn, ocr_fn) -> None:
    """
    Process a batch of messages with manual offset commit.
    Offset committed only after all S3 writes in the batch succeed.
    Idempotent S3 key: doc_hash + page_num ensures retries are safe.
    """
    while True:
        records = consumer.poll(timeout_ms=100, max_records=8)
        if not records: continue
        batch_ok = True
        for tp, messages in records.items():
            for msg in messages:
                doc = msg.value
                try:
                    layout = layout_fn(doc["image_key"])
                    ocr    = ocr_fn(layout)
                    # Idempotent key: same content always writes to same key
                    out_key = f"streaming/{doc['doc_hash']}/p{doc['page']}.json"
                    s3.put_object(Bucket=bucket, Key=out_key,
                                  Body=json.dumps({"layout":layout,"ocr":ocr}))
                except Exception as e:
                    batch_ok = False
                    print(f"Processing failed: {e}"); break
        if batch_ok:
            consumer.commit()  # only commit after all writes succeed
02 · Autoscaling and Latency Optimisation

Lag-Based Autoscaling and
GPU Batch Sizing for Sub-10s Latency

streaming_autoscaler.py — lag-based consumer scaling

from kafka.admin import KafkaAdminClient
import boto3, time

def get_consumer_lag(bootstrap_servers: list[str],
                      group_id: str, topic: str) -> int:
    """
    Measure consumer group lag: total messages behind across all partitions.
    Lag is the primary autoscaling metric for document streaming pipelines —
    more reliable than CPU utilisation for I/O-bound OCR workloads.
    """
    admin = KafkaAdminClient(bootstrap_servers=bootstrap_servers)
    offsets = admin.list_consumer_group_offsets(group_id)
    lag = 0
    for tp, offset_meta in offsets.items():
        if tp.topic != topic: continue
        end_offsets = admin.list_offsets({tp: "latest"})
        lag += max(0, end_offsets[tp].offset - offset_meta.offset)
    admin.close()
    return lag

def autoscale_consumers(lag: int, current: int,
                          min_c: int = 2, max_c: int = 20,
                          target_lag_per_consumer: int = 50) -> int:
    """Desired consumer count = ceil(lag / target_lag_per_consumer)."""
    import math
    return max(min_c, min(max_c, math.ceil(lag / target_lag_per_consumer) if lag > 0 else min_c))

# Latency optimisation: GPU batch sizing
# batch_size=1:  GPU processes 1 page → high scheduling overhead → P95=12s
# batch_size=8:  GPU processes 8 pages per forward pass → P95=2-3s
# Buffer window: hold up to 50ms for a full batch before firing
# Trade-off: 50ms added latency for all documents vs 8x throughput increase

# Parallel stage execution within a document:
# Sequential:   layout(p1) → ocr(p1) → layout(p2) → ocr(p2) → ... (slow)
# Pipelined:    layout(p1) | layout(p2) running while ocr(p1) is running
# Savings:      ~40-50% reduction in per-document end-to-end latency
03 · Assessment

Module 16 Quiz

1. A Kafka consumer crashes after committing the offset but before writing layout output to S3. The document is lost. What Kafka configuration prevents this?

Correct. Manual offset commit with offset advancement only after successful downstream write is the standard pattern for exactly-once document processing on Kafka. Idempotent S3 writes using content-derived keys ensure retries do not create duplicates.

2. Your streaming pipeline processes 8 docs/sec with 12 consumers. A news event triggers 10,000 documents in 30 seconds (333 docs/sec incoming). What happens and what should you pre-configure?

Correct. Consumer group lag is the correct autoscaling metric for Kafka-based document pipelines. The four pre-configurations (lag-based scaling, batch sizing, retention, DLT) together handle burst traffic without data loss.

3. Real-time extraction must complete within 10 seconds. Current P95=18 seconds with OCR bottleneck at P95=12 seconds. Two most effective fixes?

Correct. GPU batch sizing and parallel stage execution are the two highest-ROI latency reductions for real-time document pipelines. Both address the OCR bottleneck without requiring new infrastructure.

4. A Flink task manager crashes during stateful windowed aggregation. What happens to in-flight documents and how is state recovered?

Correct. Flink checkpoint-based recovery is the standard fault tolerance mechanism for stateful stream processing. The checkpoint includes both operator state and Kafka consumer offsets. Idempotent downstream writes convert at-least-once to exactly-once.

5. Real-time pipeline must process express documents within 5 seconds and standard within 60 seconds. Both share the same GPU pool. How do you implement priority-aware resource allocation?

Correct. SLA isolation requires physical resource isolation — separate Kafka topics with dedicated consumer groups. Kafka does not implement message-level priority within a topic. This is the same multi-queue pattern as the M6 production pipeline.
