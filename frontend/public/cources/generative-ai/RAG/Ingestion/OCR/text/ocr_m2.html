01 · How Tesseract's LSTM Engine Works

From a Line Image to Text:
Inside the Tesseract 4/5 Architecture

Tesseract 4 (2016) replaced the legacy HMM-based engine with a bidirectional LSTM that processes text line images from left-to-right and right-to-left simultaneously, producing character probabilities at each position. This context-awareness is what allows it to resolve ambiguous glyphs — "rn" vs "m" is disambiguated by the characters before and after. Understanding this architecture explains why certain inputs succeed and others fail.

The Tesseract 5 pipeline: step by step

① Page Layout Analysis

Tesseract first analyses the entire page to detect text blocks, columns, and reading order (controlled by PSM — see Section 2). It identifies individual text line bounding boxes using pixel projection profiles — horizontal scans that find the white gaps between text lines.

↓

② Line Normalisation

Each text line is scaled to a fixed height (typically 48 pixels in Tesseract 5), making the LSTM input resolution-independent. This is why Tesseract performance is relatively stable across DPI values above 150 — the normalisation step compensates for varying scale.

↓

③ Bidirectional LSTM Recognition

The normalised line image is passed through a bidirectional LSTM: one LSTM processes left-to-right, another right-to-left. Their outputs are concatenated and passed to a dense layer, producing a probability distribution over the character set at each x-position in the image.

↓

④ CTC Decoding

Connectionist Temporal Classification (CTC) collapses the per-position character probability sequence into a text string, handling the alignment between image positions and character positions (characters are wider than a single pixel position).

↓

⑤ Word Dictionary Lookup (optional)

In legacy mode (OEM 0) and partially in LSTM mode, Tesseract applies a dictionary lookup to prefer valid English words over equally-probable character sequences. This can be disabled with the parameter dict_basenames.

💡

Why context matters: the "rn" vs "m" problem

The letter "m" and the two-character sequence "rn" are visually nearly identical at low resolution or with serif fonts. In the legacy HMM engine, these were frequently confused based on character-level probability alone. The LSTM engine sees the full line and can use context: "modern" would produce a high probability for "rn" (because the surrounding characters "mode" and "" form a common word), while "farm" would correctly prefer "m". This contextual disambiguation is the primary quality improvement of Tesseract 4/5 over Tesseract 3.

02 · Page Segmentation Modes (PSM): All 14 Explained

The Most Misconfigured Tesseract Setting:
Choosing the Right PSM

PSM controls what Tesseract assumes about the layout of the input image before it begins recognition. Using the wrong PSM is the most common cause of Tesseract producing garbage on well-prepared images. PSM 3 (the default "auto") works on most full-page documents but fails silently on cropped regions, single words, and rotated text.

03 · OCR Engine Modes (OEM)

Which Tesseract Engine to Use
and When

Tesseract has maintained two parallel recognition engines since version 4: the legacy character-classifier engine (inherited from Tesseract 3) and the new LSTM engine. OEM controls which engine is used and whether both can be combined.

OEM 0 — Legacy engine only

Uses the pre-Tesseract-4 character classifier. Generally lower accuracy on most documents. However, for specific font types (very large fonts, monospace code) and certain domain configurations, legacy mode can be faster and more predictable.

Use when: processing monospace code blocks; when LSTM mode produces worse results after trying both; for character-level bounding box output (LSTM bounding boxes are less precise).

OEM 1 — LSTM engine only (recommended)

The bidirectional LSTM engine. Best accuracy on standard printed text, mixed fonts, and degraded documents. The default for Tesseract 5. Run with OEM 1 + PSM 3/6/7 for production document processing.

Use when: everything, unless you have a specific reason to use OEM 0. Start here for any new project.

OEM 2 — Legacy + LSTM combined

Both engines vote; combined result used. Occasionally slightly higher accuracy than OEM 1 alone on certain document types, but roughly 2× slower. Rarely worth the overhead.

OEM 3 — Default (Tesseract decides)

Tesseract automatically selects the best available engine for the installed data files. In practice equivalent to OEM 1 in Tesseract 5 if LSTM data is installed. Use this if you are not sure.

04 · Character Whitelists and Blacklists

Eliminating Entire Error Classes
by Restricting the Character Set

One of the most powerful and underused Tesseract features is character set restriction. By specifying a whitelist of valid output characters, you tell Tesseract to only ever output characters from that set — eliminating all substitution errors that fall outside it. For structured fields (dates, amounts, phone numbers, IDs), this alone can improve field-level accuracy from 85% to 99%.

Whitelist worked example: invoice amount extraction

Field being extracted: Invoice total amount, e.g. "£12,345.67"

Without whitelist — Tesseract output examples:
"£l2,345.67" → lowercase 'l' instead of '1'
"£12,34S.67" → 'S' instead of '5' (common serif confusion)
"£I2,345.67" → uppercase 'I' instead of '1'
"£12,345,67" → comma instead of period (common OCR error)

With whitelist = "0123456789.,£$€":
Only digits, comma, period, and currency symbols can appear in output.
"£l2,345.67" → "£12,345.67" (l→1 forced by whitelist constraint)
"£12,34S.67" → "£12,345.67" (S→5 forced)
"£I2,345.67" → "£12,345.67" (I→1 forced)
Field-level accuracy improvement: 85% → 98%+

tesseract_config.py — whitelists, PSM, OEM

import pytesseract
from PIL import Image
import numpy as np, cv2

# ── Common config strings ─────────────────────────────────────
CONFIGS = {
    # Full document, best accuracy
    "full_page":    "--oem 1 --psm 3",
    
    # Pre-cropped single line field
    "single_line":  "--oem 1 --psm 7",
    
    # Numeric field: amounts, quantities
    "numeric":      '--oem 1 --psm 7 -c tessedit_char_whitelist=0123456789.,£$€-',
    
    # Date field: DD/MM/YYYY or MM-DD-YYYY
    "date":         '--oem 1 --psm 7 -c tessedit_char_whitelist=0123456789/-',
    
    # Uppercase letters only (ID codes, invoice numbers)
    "uppercase_id": '--oem 1 --psm 7 -c tessedit_char_whitelist=ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789-',
    
    # Mixed alphanumeric (VIN, serial numbers)
    "alphanumeric": '--oem 1 --psm 8 -c tessedit_char_whitelist=ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789',
    
    # Blacklist: remove characters that are never valid
    "no_specials":  '--oem 1 --psm 3 -c tessedit_char_blacklist=@#^&*~`|<>{}[]',
}

def ocr_field(crop: np.ndarray, field_type: str = "single_line") -> str:
    """OCR a pre-cropped field region with appropriate config."""
    config = CONFIGS.get(field_type, CONFIGS["single_line"])
    pil_img = Image.fromarray(crop)
    result = pytesseract.image_to_string(pil_img, config=config)
    return result.strip()

def ocr_full_page(image: np.ndarray, lang: str = "eng") -> str:
    """OCR a full page document."""
    pil_img = Image.fromarray(image)
    return pytesseract.image_to_string(
        pil_img,
        lang=lang,
        config=CONFIGS["full_page"]
    )

# Usage examples:
# amount_text = ocr_field(amount_crop, "numeric")    → "£12,345.67"
# date_text   = ocr_field(date_crop,   "date")       → "15/03/2024"
# inv_num     = ocr_field(id_crop,     "uppercase_id") → "INV-2024-0042"
05 · Extracting Confidence Scores

Word and Character Level Confidence:
Knowing When to Trust the Output

Tesseract produces a confidence score (0–100) for each recognised word. These scores are not perfectly calibrated (a word with confidence 40 is not necessarily correct 40% of the time), but they are highly effective for identifying which words need human review or LLM correction. Words below ~60 confidence are disproportionately likely to contain errors.

confidence_extraction.py

import pytesseract
from PIL import Image
import pandas as pd
import numpy as np

def ocr_with_confidence(image: np.ndarray,
                         config: str = "--oem 1 --psm 3",
                         low_conf_threshold: int = 60) -> dict:
    """
    Run Tesseract and return text with per-word confidence scores.
    Flags words below threshold for human review.
    """
    pil_img = Image.fromarray(image)
    
    # image_to_data returns bounding boxes + confidence for each word
    data = pytesseract.image_to_data(
        pil_img,
        config=config,
        output_type=pytesseract.Output.DATAFRAME
    )
    
    # Filter to actual word rows (confidence != -1)
    words_df = data[(data["conf"] != -1) & (data["text"].str.strip() != "")].copy()
    
    words_df["low_confidence"] = words_df["conf"] < low_conf_threshold
    
    # Build structured output
    full_text = " ".join(words_df["text"].tolist())
    mean_conf = words_df["conf"].mean()
    flagged   = words_df[words_df["low_confidence"]]
    
    return {
        "text":            full_text,
        "mean_confidence": round(mean_conf, 1),
        "word_count":      len(words_df),
        "low_conf_words":  flagged[["text", "conf", "left", "top"]].to_dict("records"),
        "low_conf_count":  len(flagged),
        "review_needed":   mean_conf < 75 or len(flagged) > len(words_df) * 0.15
    }

# Example output:
# {
#   "text": "Invoice Total: £12,345.67 Due: 15/03/2024",
#   "mean_confidence": 82.4,
#   "low_conf_words": [{"text": "£l2,345.67", "conf": 43, "left": 340, "top": 220}],
#   "review_needed": False  ← only 1 low-conf word out of 8
# }

def get_word_bboxes(image: np.ndarray) -> list[dict]:
    """Get each word with its bounding box — useful for field localisation."""
    pil_img = Image.fromarray(image)
    data = pytesseract.image_to_data(pil_img, output_type=pytesseract.Output.DICT)
    words = []
    for i, text in enumerate(data["text"]):
        if text.strip() and data["conf"][i] > 0:
            words.append({
                "text": text,
                "conf": data["conf"][i],
                "bbox": (data["left"][i], data["top"][i],
                          data["width"][i], data["height"][i])
            })
    return words
06 · Custom Word Lists and Language Packs

Teaching Tesseract Your Domain:
Word Lists, Dictionaries, and Tessdata

Tesseract uses a word frequency dictionary during recognition to prefer common words over rare ones. When processing domain-specific documents (medical, legal, technical), the standard English dictionary penalises valid domain terms — "metformin", "polyethylene", "GAAP" — causing them to be corrected to more common but wrong words. Custom word lists and user-defined dictionaries solve this.

Adding domain words to Tesseract

advanced_config.py — disabling dictionaries for codes

import pytesseract
from PIL import Image

# Config for product codes, part numbers, technical identifiers
# These look like noise to Tesseract's dictionary — disable it
CODE_CONFIG = """--oem 1 --psm 7
-c load_system_dawg=0
-c load_freq_dawg=0
-c tessedit_char_whitelist=ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789-/."""

# Without disabling dawg: "PROD-X7K2-AB" might become "PROD-X7KZ-AB"
# (Z closer to Z in dictionary vs 2 which is rare in English words)

# With disabled dawg + whitelist: all 10-90 digit characters valid,
# no dictionary pressure toward "word-like" sequences

# Config for scientific notation / numbers
SCIENTIFIC_CONFIG = """--oem 1 --psm 7
-c load_system_dawg=0
-c load_freq_dawg=0
-c tessedit_char_whitelist=0123456789.eE+-×x"""
# Correctly reads: "3.14×10⁻⁶" without dictionary interference

text = pytesseract.image_to_string(Image.fromarray(crop), config=CODE_CONFIG)
print(text.strip())  # → "PROD-X7K2-AB"

09 · Assessment

Module 2 Quiz

1. A pre-cropped date field (format DD/MM/YYYY) returns "08/l3/l994" — lowercase l instead of digit 1. Which Tesseract configuration change is most targeted at eliminating this specific error class?

Correct. The character whitelist is the most targeted fix because it attacks the root cause at the output level: l/1 ambiguity arises when the LSTM assigns nearly equal posterior probability to both characters. Without a whitelist, Tesseract selects whichever has the marginally higher probability (sometimes 'l' due to English dictionary frequency). With whitelist=0123456789/, 'l' is excluded from the output vocabulary entirely — the probability mass is redistributed to '1' by elimination. This requires no retraining and takes effect immediately. The word list approach (D) would not work because dates are not dictionary words and Tesseract's word frequency model does not apply to numeric strings.

2. You pass a 400×50 pixel crop containing "Total: £12,345.67" to Tesseract with PSM 3 (default). The output is an empty string. What is the cause?

Correct. PSM 3's layout analysis was designed for full-page documents. When given a 400×50 crop, it attempts to identify paragraph structure, column boundaries, and text block hierarchies — none of which exist at that scale. The segmenter finds insufficient layout evidence and returns nothing rather than recognising the obviously-present text. PSM 7 skips layout analysis entirely and treats the whole image as one text line, which is exactly what a pre-cropped field region is. This is the single most impactful PSM selection decision in form field extraction pipelines.

3. You OCR a chemistry paper containing "Fe₂O₃" and "CH₃COOH". Tesseract returns "FezO3" and "CHsCOOH". Disabling dictionaries (-c load_system_dawg=0 -c load_freq_dawg=0) partially helps. What additional change most improves subscript digit recognition?

Correct. Subscript digit errors arise from two compounding causes: small pixel size (making digits visually ambiguous with letters) and dictionary pressure (making 'z' more probable than '2' in English word context). Disabling dictionaries addresses the second cause. Upscaling subscript regions addresses the first — at 8–12 pixels, '2' and 'z' share very similar pixel topology; at 24–36 pixels after 3× scaling, the distinctive shape difference becomes reliably classifiable. For production chemistry OCR, the most robust approach combines upscaling + disabled dictionaries + a custom whitelist including digits and element symbols. TrOCR or GPT-4 vision handles subscripts more robustly than any Tesseract configuration.

4. image_to_data() returns mean confidence 71, with 3 of 50 words below 60. Should you flag this invoice for human review?

Correct. Flat confidence thresholds without field-position awareness produce two failure modes: false positives (routing clean documents for review because boilerplate text has low confidence) and false negatives (auto-approving documents where critical financial fields have low confidence but mean is acceptable). The correct design routes on field-level confidence: identify which words correspond to amount/date/ID fields using their bounding box coordinates relative to known field positions, then apply strict thresholds only to those critical fields. Re-running OCR (D) does not help — if the character is visually ambiguous, the LSTM will assign the same probability distribution both times.

5. You process 200,000 invoice PDFs per month. Each has a text layer plus a vendor logo image. You want to extract the vendor name from the logo. What is the most efficient architecture?

Correct. The hybrid architecture applies the minimum necessary processing to each component. Text-layer content needs no OCR — PyMuPDF extracts it exactly. The logo image needs OCR, but only the logo region needs to be rendered and processed, not the entire page. At 200,000 invoices/month: full-page render + PaddleOCR at ~1.5s/page = 83 CPU-hours/month. Hybrid: PyMuPDF (near-instant) + logo-only OCR at ~0.2s/invoice = ~11 CPU-hours/month. The 7× compute reduction comes from OCRing a 200×100 pixel logo crop instead of a 2480×3507 page. LLM vision (D) at $0.01/call × 200,000 = $2,000/month is not justified for logo text that Tesseract handles well.
