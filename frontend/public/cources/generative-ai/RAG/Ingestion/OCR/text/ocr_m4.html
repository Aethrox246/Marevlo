01 · Why Transformers Changed OCR

From LSTM Lines to
Image-Wide Attention

Tesseract's LSTM processes a text line from left to right, maintaining a hidden state that carries context from earlier characters. Transformer-based OCR applies attention across the entire image simultaneously — every patch can attend to every other patch when computing character probabilities. This global attention enables recognition of characters whose identity depends on distant context, making transformers dramatically more robust to degraded images, unusual fonts, and complex scripts.

LSTM vs Transformer: the key architectural difference

LSTM (Tesseract) — sequential context

To recognise character at position 47, the LSTM has a hidden state that summarises characters 1-46. Context from position 1 has been exponentially discounted over 46 timesteps. Distant context is effectively lost. Long-range dependencies (e.g., a word completing a phrase seen 10 words earlier) are weakly captured.

Transformer (TrOCR) — global attention

To recognise a character at any position, the attention mechanism computes similarity between that position and all other positions simultaneously. Character at position 47 can directly attend to character at position 1 or position 200. Distant context has zero decay. Especially useful for resolving ambiguous characters using full-line context.

02 · TrOCR: Architecture Deep Dive

Vision Transformer Encoder +
Language Model Decoder

TrOCR (Li et al., 2021) is an encoder-decoder transformer. The encoder is a Vision Transformer (ViT) pre-trained on image classification. The decoder is a GPT-2 style language model pre-trained on text generation. The two are fine-tuned jointly on line-image to text pairs. This architecture leverages the strengths of both: ViT's visual feature extraction and the language model's text generation and linguistic context.

TrOCR step-by-step: how a line image becomes text

① Patch embedding

The input image is resized to 384×384 pixels. It is divided into 16×16 pixel patches (24×24 = 576 patches). Each patch is flattened to a 768-dimensional vector and linearly projected. Position embeddings are added to preserve spatial relationships between patches.

↓

② Transformer encoder (ViT-large)

12 or 24 layers of multi-head self-attention. Each patch computes attention scores against all other patches. The output is a sequence of 576 context-aware feature vectors — one per image patch — that encode the visual content of each region in context of the whole image.

↓

③ Cross-attention decoder (GPT-2 style)

The decoder generates the output text token by token. At each step, the decoder attends to: (a) previously generated tokens (self-attention), and (b) all encoder image features (cross-attention). The cross-attention lets each output character look at any part of the image.

↓

④ Token-by-token generation with beam search

The decoder outputs a probability distribution over the vocabulary at each step. Beam search (beam width = 4-8) keeps the top-k partial sequences at each step, producing the globally best text sequence rather than greedily selecting the highest-probability character at each step.

trocr_inference.py

from transformers import TrOCRProcessor, VisionEncoderDecoderModel
from PIL import Image
import torch, numpy as np

# Available TrOCR checkpoints:
# microsoft/trocr-base-printed   — fast, good for clean printed text
# microsoft/trocr-large-printed  — best accuracy on printed text (slower)
# microsoft/trocr-base-handwritten  — handwritten text (IAM dataset)
# microsoft/trocr-large-handwritten — best handwriting accuracy
# microsoft/trocr-base-stage1    — general pre-trained (fine-tune yourself)

class TrOCREngine:
    def __init__(self, checkpoint: str = "microsoft/trocr-base-printed"):
        self.processor = TrOCRProcessor.from_pretrained(checkpoint)
        self.model = VisionEncoderDecoderModel.from_pretrained(checkpoint)
        self.device = "cuda" if torch.cuda.is_available() else "cpu"
        self.model.to(self.device)
        self.model.eval()
        print(f"TrOCR loaded: {checkpoint} on {self.device}")
    
    def recognise_line(self, line_image: np.ndarray) -> str:
        """
        Recognise text in a single line image crop.
        Input: numpy array (H, W) greyscale or (H, W, 3) RGB.
        Output: recognised text string.
        """
        if line_image.ndim == 2:
            pil = Image.fromarray(line_image).convert("RGB")
        else:
            pil = Image.fromarray(line_image)
        
        with torch.no_grad():
            pixel_values = self.processor(
                images=pil, return_tensors="pt"
            ).pixel_values.to(self.device)
            
            generated_ids = self.model.generate(
                pixel_values,
                max_length=64,       # max output tokens
                num_beams=4,         # beam search width
                early_stopping=True
            )
        
        return self.processor.batch_decode(
            generated_ids, skip_special_tokens=True
        )[0]
    
    def recognise_document(self,
                             line_crops: list[np.ndarray],
                             batch_size: int = 8) -> list[str]:
        """Batch recognition for efficiency — process multiple lines at once."""
        results = []
        for i in range(0, len(line_crops), batch_size):
            batch = line_crops[i:i+batch_size]
            pils = [Image.fromarray(c if c.ndim==3 else np.stack([c]*3, axis=-1)) for c in batch]
            with torch.no_grad():
                pixel_values = self.processor(images=pils, return_tensors="pt").pixel_values.to(self.device)
                ids = self.model.generate(pixel_values, num_beams=4, max_length=64)
            results.extend(self.processor.batch_decode(ids, skip_special_tokens=True))
        return results

# text = engine.recognise_line(line_crop)  # → "Invoice Total: £12,345.67"
03 · CRAFT Text Detection

Finding Text Regions Before Recognition:
Character Region Awareness

TrOCR and most transformer recognition models operate on pre-cropped text line images — they do not detect text regions themselves. For natural scene images or documents without prior layout analysis, CRAFT (Character Region Awareness For Text detection) produces per-character and per-word heatmaps, enabling precise text region cropping before recognition. CRAFT + TrOCR is the state-of-the-art combination for complex real-world documents.

CRAFT output: region scores and affinity scores

Region score map:
Per-pixel Gaussian heatmap peaked at the centre of each character. High values (0.8-1.0) at character centres; low values (0.0) between characters and in background.

Affinity score map:
Per-pixel heatmap peaked between adjacent characters in the same word. Links characters together into words and words into text lines. High affinity between 'h' and 'e' in "hello", zero affinity between words.
Post-processing:
1. Threshold region map at 0.4 → get character blobs
2. Threshold affinity map at 0.4 → get inter-character links
3. Group linked character blobs → words
4. Group nearby words → text lines
5. Compute minimum rotated bounding box per line → crop for recognition

Result: Axis-aligned or rotated crops of each text line, correctly segmented regardless of perspective or curved text.

craft_detect.py

import easyocr  # EasyOCR includes CRAFT detector internally
import numpy as np
import cv2

# CRAFT is built into EasyOCR's detection pipeline
# For standalone CRAFT: github.com/clovaai/CRAFT-pytorch
reader = easyocr.Reader(["en"], gpu=False)

def detect_and_crop_lines(image: np.ndarray) -> list[dict]:
    """
    Use CRAFT (via EasyOCR) to detect text regions.
    Returns list of {"bbox": [[x1,y1],[x2,y1],[x2,y2],[x1,y2]], "crop": np.ndarray}
    """
    # detail=1 → returns bounding boxes without recognition
    results = reader.readtext(image, detail=1)
    
    line_crops = []
    for (bbox, text, confidence) in results:
        # bbox: [[x1,y1],[x2,y1],[x2,y2],[x1,y2]] (quadrilateral)
        pts = np.array(bbox, dtype=np.int32)
        x, y, w, h = cv2.boundingRect(pts)
        
        # Crop from original image using bounding box
        x, y = max(0, x), max(0, y)
        crop = image[y:y+h, x:x+w]
        
        line_crops.append({
            "bbox":       bbox,
            "crop":       crop,
            "easyocr_text": text,       # EasyOCR's built-in recognition
            "confidence": confidence
        })
    
    return line_crops

# For higher accuracy: detect with CRAFT/EasyOCR, recognise with TrOCR:
def craft_detect_trocr_recognise(image: np.ndarray,
                                    trocr_engine) -> list[dict]:
    crops = detect_and_crop_lines(image)
    for item in crops:
        item["trocr_text"] = trocr_engine.recognise_line(item["crop"])
    return crops
04 · PaddleOCR PP-OCRv4: Production Speed

The Fastest Complete OCR System
With GPU and CPU Optimisation

PaddleOCR's PP-OCRv4 (released 2023) is a three-stage pipeline: DB++ text detection, text line rectification, and SVTR (Scene Text Recognition Transformer) recognition. It achieves near-TrOCR accuracy at 10-50× the throughput by using lightweight CNN-Transformer hybrid models optimised for inference. On GPU, PP-OCRv4 processes 100+ pages per minute.

PP-OCRv4 three-stage pipeline

Stage 1: DB++ Detection

Differentiable Binarisation (DB++) produces a probability map where each pixel's value indicates the probability of belonging to a text region. Compared to CRAFT, DB++ is 5× faster while achieving comparable detection quality. Outputs bounding polygon per text instance.

↓

Stage 2: Text Rectification (TPS-based)

For detected text regions that are not axis-aligned (curved, rotated), Thin Plate Spline (TPS) transformation warps the region to a canonical horizontal rectangle. This allows the recognition model to work on normalised input regardless of text orientation.

↓

Stage 3: SVTR Recognition

Scene Text Vision Transformer (SVTR) is a lightweight transformer that processes the rectified line crop. Unlike TrOCR (encoder-decoder), SVTR is an encoder-only model that directly predicts character sequences using CTC loss — much faster than autoregressive decoding.

paddleocr_pipeline.py

from paddleocr import PaddleOCR
import numpy as np, json

# Initialise PP-OCRv4
ocr = PaddleOCR(
    use_angle_cls=True,     # detect and correct text angle
    lang="en",               # language: en, ch, fr, de, es, ja, ko, ar, ...
    use_gpu=False,           # True for GPU (10× faster)
    det_model_dir=None,      # auto-download PP-OCRv4 det model
    rec_model_dir=None,      # auto-download PP-OCRv4 rec model
    show_log=False
)

def paddle_ocr_document(image_path: str) -> dict:
    """
    Full PP-OCRv4 pipeline: detect + classify angle + recognise.
    Returns structured output with bboxes, text, and confidence.
    """
    result = ocr.ocr(image_path, cls=True)
    
    parsed = []
    for page_result in result:
        if page_result is None: continue
        for line in page_result:
            bbox = line[0]            # [[x1,y1],[x2,y1],[x2,y2],[x1,y2]]
            text, conf = line[1]     # (text_string, confidence_float)
            parsed.append({
                "text":       text,
                "confidence": round(conf, 3),
                "bbox":       bbox
            })
    
    full_text = " ".join(p["text"] for p in parsed)
    mean_conf = sum(p["confidence"] for p in parsed) / len(parsed) if parsed else 0
    
    return {
        "full_text":   full_text,
        "mean_conf":   round(mean_conf, 3),
        "lines":       parsed,
        "line_count":  len(parsed)
    }

# Performance tuning for high-throughput:
def batch_paddle_ocr(image_paths: list[str], workers: int = 4) -> list[dict]:
    from concurrent.futures import ThreadPoolExecutor
    with ThreadPoolExecutor(max_workers=workers) as ex:
        return list(ex.map(paddle_ocr_document, image_paths))
# On GPU: ~0.3s per page → 200 pages/min
# On CPU: ~1.5s per page → 40 pages/min
05 · EasyOCR: Breadth and Simplicity

80+ Languages, One API,
Five Lines of Code

EasyOCR trades some accuracy for extreme language coverage and a simple API. It uses CRAFT for detection and a custom LSTM-based recogniser for 80+ languages including Arabic, Hebrew, Thai, and 29 Indian scripts. For projects requiring rapid prototyping or multilingual support without domain-specific fine-tuning, EasyOCR is often the fastest path to working OCR.

Decision guide: which engine for which use case

Standard office documents (invoices, letters, reports) at scale: PaddleOCR PP-OCRv4. Best balance of speed and accuracy for high-volume clean-document processing.
Handwriting, degraded historical documents, maximum accuracy: TrOCR-large. Significantly better than all other options on difficult inputs. Worth the compute cost.
Structured fields, fixed-layout forms, whitelist-restricted output: Tesseract with PSM 7 + whitelist. Whitelist eliminates the accuracy gap for structured fields and runs on any CPU without a model download.
Multilingual documents or rapid prototyping: EasyOCR. Broadest language support, minimal setup, acceptable accuracy for most use cases.
07 · Fine-Tuning TrOCR on Domain Data

Adapting a Pre-trained Model
to Your Specific Document Type

trocr_finetune.py — HuggingFace fine-tuning

from transformers import (TrOCRProcessor, VisionEncoderDecoderModel,
                          Seq2SeqTrainer, Seq2SeqTrainingArguments)
from torch.utils.data import Dataset
from PIL import Image
import torch

class OCRDataset(Dataset):
    """
    Custom dataset: list of (image_path, ground_truth_text) pairs.
    Minimum for fine-tuning: 500-1000 annotated line images.
    """
    def __init__(self, samples: list[tuple[str, str]],
                 processor: TrOCRProcessor):
        self.samples = samples
        self.processor = processor
    
    def __len__(self): return len(self.samples)
    
    def __getitem__(self, idx):
        img_path, text = self.samples[idx]
        image = Image.open(img_path).convert("RGB")
        
        # Process image
        pixel_values = self.processor(
            image, return_tensors="pt"
        ).pixel_values.squeeze()
        
        # Process label text
        with self.processor.as_target_processor():
            labels = self.processor(
                text, return_tensors="pt"
            ).input_ids.squeeze()
        
        labels[labels == self.processor.tokenizer.pad_token_id] = -100
        return {"pixel_values": pixel_values, "labels": labels}

def finetune_trocr(
    train_samples: list[tuple[str, str]],
    output_dir: str = "./trocr-finetuned",
    epochs: int = 10,
    batch_size: int = 8
):
    processor = TrOCRProcessor.from_pretrained("microsoft/trocr-base-printed")
    model = VisionEncoderDecoderModel.from_pretrained("microsoft/trocr-base-printed")
    
    # Configure decoder
    model.config.decoder_start_token_id = processor.tokenizer.bos_token_id
    model.config.pad_token_id = processor.tokenizer.pad_token_id
    model.config.vocab_size = model.config.decoder.vocab_size
    model.config.max_length = 128
    model.config.num_beams = 4
    
    n = int(len(train_samples) * 0.9)
    train_ds = OCRDataset(train_samples[:n], processor)
    eval_ds  = OCRDataset(train_samples[n:], processor)
    
    args = Seq2SeqTrainingArguments(
        output_dir=output_dir,
        num_train_epochs=epochs,
        per_device_train_batch_size=batch_size,
        per_device_eval_batch_size=batch_size,
        predict_with_generate=True,
        evaluation_strategy="epoch",
        save_strategy="epoch",
        load_best_model_at_end=True,
        fp16=torch.cuda.is_available(),
        learning_rate=5e-5,
        warmup_steps=500,
    )
    
    trainer = Seq2SeqTrainer(model=model, args=args,
                             train_dataset=train_ds, eval_dataset=eval_ds)
    trainer.train()
    trainer.save_model(output_dir)
    print(f"Fine-tuned model saved to {output_dir}")
# Minimum viable: 500 annotated samples, 10 epochs → typically 20-40% CER improvement
08 · Hybrid Pipeline: Best of All Worlds

Route Each Document Region
to the Optimal Engine

hybrid_ocr.py — confidence-routed engine selection

import pytesseract
from PIL import Image
import numpy as np

class HybridOCR:
    """
    Route each text region to the best engine based on:
    - Region type (field → Tesseract+whitelist, body → PaddleOCR)
    - Initial confidence (low confidence → upgrade to TrOCR)
    - Document type (handwritten → TrOCR-handwritten)
    """
    def __init__(self, use_trocr: bool = True):
        from paddleocr import PaddleOCR
        self.paddle = PaddleOCR(lang="en", use_gpu=False, show_log=False)
        if use_trocr:
            from transformers import TrOCRProcessor, VisionEncoderDecoderModel
            self.trocr_proc  = TrOCRProcessor.from_pretrained("microsoft/trocr-base-printed")
            self.trocr_model = VisionEncoderDecoderModel.from_pretrained("microsoft/trocr-base-printed")
        self.use_trocr = use_trocr
    
    def ocr_field(self, crop: np.ndarray, whitelist: str = "") -> str:
        """Structured field → Tesseract with whitelist."""
        config = f"--oem 1 --psm 7"
        if whitelist: config += f" -c tessedit_char_whitelist={whitelist}"
        return pytesseract.image_to_string(Image.fromarray(crop), config=config).strip()
    
    def ocr_body(self, image_path: str,
                 low_conf_threshold: float = 0.7) -> list[dict]:
        """Body text → PaddleOCR first, upgrade low-confidence to TrOCR."""
        paddle_result = self.paddle.ocr(image_path, cls=True)
        
        results = []
        for page in (paddle_result or []):
            for line in (page or []):
                bbox, (text, conf) = line
                
                if conf < low_conf_threshold and self.use_trocr:
                    # Low confidence → upgrade to TrOCR
                    import torch, cv2
                    img = cv2.imread(image_path)
                    pts = np.array(bbox, np.int32)
                    x,y,w,h = cv2.boundingRect(pts)
                    crop = img[y:y+h, x:x+w]
                    pil = Image.fromarray(cv2.cvtColor(crop, cv2.COLOR_BGR2RGB))
                    with torch.no_grad():
                        ids = self.trocr_model.generate(
                            self.trocr_proc(images=pil, return_tensors="pt").pixel_values,
                            num_beams=4, max_length=64
                        )
                    text = self.trocr_proc.batch_decode(ids, skip_special_tokens=True)[0]
                    conf = 0.99  # mark as upgraded
                
                results.append({"text": text, "conf": conf, "bbox": bbox})
        return results
09 · Assessment

Module 4 Quiz

1. TrOCR uses beam search with beam width 4. Explain the key difference from greedy decoding and give a concrete OCR example where beam search recovers the correct output that greedy decoding would get wrong.

Correct. The "rn" vs "m" example is exactly the scenario beam search was designed for. At position 4 of "modern", the pixel evidence for "rn" and "m" is nearly identical at typical OCR resolution. Greedy decoding picks "m" (marginally higher single-step probability) and produces "modem" — a valid word that locks in the error. Beam search keeps both "mode-rn" and "mode-m" as active candidates and evaluates the joint probability of the remaining characters. "modern" produces higher joint probability (both "r" and "n" have high posterior given the image pixels) than "modem", so beam search recovers the correct output. This is why beam search is standard for sequence OCR models.

2. PaddleOCR achieves CER=1.2% and runs at 40 pages/min on CPU. TrOCR-large achieves CER=0.8% and runs at 7 pages/min. Your target is 500 clean printed invoices per day. Which should you deploy and why?

Correct. Model selection requires evaluating the full context: volume, document quality, downstream validation, and cost. At 500 invoices/day with clean printed input and post-processing validation, the 0.4pp CER gap between PaddleOCR and TrOCR has minimal practical impact — validation catches the errors that CER predicts. The 6× throughput difference is irrelevant at this volume. TrOCR's advantage materialises on degraded, handwritten, or unusual font documents where the CER gap widens and validation cannot easily catch errors. Option D is a reasonable architecture but adds engineering complexity (the quality classifier) without meaningful accuracy gain for clean printed invoices.

3. You fine-tune TrOCR-base on 600 pharmaceutical label images. After 10 epochs, CER on the validation set is 13.9%, improved only slightly from 14.8% before fine-tuning. What is the most likely root cause?

Correct. A 1% CER improvement after 10 epochs on 600 samples indicates the model learned something but not enough. The likely cause is training data distribution mismatch: if all 600 samples are easy instances, the model excels on easy validation examples but the hard cases (rare polysyllabic names, low-contrast labels) were never seen. 600 samples is actually sufficient for domain adaptation when correctly stratified — research shows that even 200–500 well-chosen examples can produce 40–60% CER improvement on the hard cases. The fix is data curation: mine the validation failures, understand which word types they represent, and ensure those types appear proportionally in training data.

4. EasyOCR returns "étre" instead of "être" on a French document. This is a diacritic substitution (circumflex ê → acute é). Is this an encoding issue, a language pack issue, or a visual recognition issue?

Correct. EasyOCR produces correct Unicode — the problem is it produced the wrong character, not the wrong byte representation. The circumflex ^ and acute ´ accent marks differ by only a few pixels at OCR resolution: ^ has a symmetric inverted-V shape while ´ is a simple diagonal stroke. On slightly blurred or low-contrast text, these become nearly indistinguishable to the recognition model. Post-processing with a French spell checker (language-tool-python) is the most practical fix because "étre" fails French dictionary lookup immediately, prompting correction to "être". This is a case where linguistic validation catches visual ambiguity that the OCR model cannot reliably resolve.

5. CRAFT returns a quadrilateral bounding box for curved text: [[100,200],[350,190],[360,240],[90,250]]. The recognition model expects a rectangular input. What transformation is required and what is wrong with simply cropping the axis-aligned bounding box?

Correct. The perspective transformation is mathematically required, not optional. A homography H maps the four source quadrilateral corner points to four destination rectangle corners — warpPerspective then resamples all pixels through this mapping, producing a rectangular crop where the text is horizontal and undistorted. The axis-aligned bounding box fails on both counts: the triangular background pixels corrupt the recognition model's input (the model has not been trained on crops with diagonal background regions), and the text appears at the quadrilateral's slope angle rather than horizontal. Rotation (A) only works for small angles and cannot handle perspective distortion from camera angle. TPS (used by PaddleOCR) extends this to handle curved text that a planar homography cannot correct.
