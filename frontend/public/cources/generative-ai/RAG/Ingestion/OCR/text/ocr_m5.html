Handwriting Recognition (HTR)
CRNN · CTC Loss · IAM Dataset · Slant Correction · Rejection Thresholds

Handwriting recognition (HTR) is the hardest OCR problem: infinite style variation, connected strokes that cross character boundaries, inconsistent spacing, and ink pressure variation that changes stroke width mid-character. This module covers CRNN architecture and CTC loss from first principles, the IAM benchmark dataset, pre-processing specific to handwriting, TrOCR fine-tuning on custom handwritten forms, and confidence-based rejection to know when to ask for human review.

01 · Why Handwriting Is Orders of Magnitude Harder

The Seven Challenges That Make HTR
a Fundamentally Different Problem

Printed text recognition assumes fixed glyphs — the letter "a" in Arial always looks like "a" in Arial. Handwriting recognition has no such invariance. The same writer produces different "a" shapes on different days, different lines, and different moods. Different writers produce shapes that would be misread by a model trained only on other writers. This variability is not noise to be removed — it is the inherent structure of handwritten language.

The seven HTR challenges and their engineering implications

Style variation The same letter can have 100+ visually distinct forms across writers. A model trained on 100 writers fails on writer 101. Solutions: large diverse training sets (10,000+ writers), writer-adaptive methods, domain fine-tuning on target writer samples.
Connected strokes In cursive writing, "m" and "n" share strokes. Character boundaries are ambiguous — segmenting into individual characters before recognition produces artificially broken inputs. CTC-based models avoid explicit segmentation entirely.
Variable spacing Word boundaries vary: some writers space words by 5px, others by 30px. The same writer may vary spacing within a line. Models must learn word boundaries from context, not fixed pixel gaps.
Ink pressure Stroke width varies from 1 to 8+ pixels depending on pen pressure and angle. A thin stroke and a thick stroke of the same character look visually very different in pixel space, even at identical resolution.
Baseline wander Handwritten lines do not stay horizontal — they slope up, slope down, or curve. Classical baseline normalisation (required for LSTM-based models) fails when the baseline wanders more than 2-3 degrees.
Crossing strokes The dot of "i", the cross of "t", and ascenders/descenders from adjacent lines physically cross into each other's vertical territory, breaking projection-based line segmentation.
Domain vocabulary A doctor's handwritten prescription uses medical terminology not in standard language model vocabularies. Form fields contain abbreviations, codes, and jargon that standard language models do not weight correctly.
02 · CRNN Architecture

Convolutional Recurrent Neural Network:
The Classical HTR Architecture

CRNN (Shi et al., 2015) is the foundational architecture for sequence recognition without explicit character segmentation. It combines a CNN for visual feature extraction with a bidirectional LSTM for sequence modelling, and CTC for output decoding. Despite being a 2015 model, CRNN variants remain competitive for on-device and low-latency HTR due to their small size.

CRNN layers: from image to text

① CNN Feature Extractor (7 layers, VGG-style)

Takes the H×W×1 greyscale line image. Produces feature maps of shape H/32 × W/4 × 512. The spatial reduction in height (÷32) folds the character height into feature depth. The spatial reduction in width (÷4) maintains horizontal character resolution — each horizontal position in the feature map corresponds to approximately 4 pixels in the original image, preserving character sequence information.

↓

② Column-wise Feature Extraction

The feature maps (H/32 × W/4 × 512) are reshaped to a sequence of W/4 feature vectors, each of dimension H/32 × 512. Each feature vector corresponds to one "slice" of the original image — a column of ~4 pixels width. This converts the 2D feature map into a 1D sequence ordered left-to-right.

↓

③ Bidirectional LSTM (2 layers)

The sequence of W/4 feature vectors is processed by a BiLSTM. The forward LSTM accumulates left-to-right context; the backward LSTM accumulates right-to-left. Their concatenated outputs give each position context from the full line — essential for disambiguation ("rn" vs "m" requires seeing neighbouring characters).

↓

④ CTC Output Layer + Decoding

A dense layer maps each position's BiLSTM output to a probability distribution over the character vocabulary (plus the CTC blank token). CTC decoding collapses the sequence of per-position character predictions into a text string without requiring explicit segmentation of the image into individual character regions.

03 · CTC Loss: Why It Solves the Segmentation Problem

Connectionist Temporal Classification:
Aligning Characters Without Knowing Where They Are

The fundamental challenge in sequence-from-image recognition: the image has a fixed pixel width, but the output text has a variable number of characters. A 200-pixel-wide line image might contain 5 characters or 50, and we do not know where each character starts and ends. CTC is a loss function that trains the model to emit the correct text without requiring a mapping between image positions and character positions.

CTC: step-by-step intuition with a worked example

Input: Image of the word "cat" — 60px wide. Model produces 15 time-steps (60÷4).
Vocabulary: {a, b, c, ..., z, —} where — is the CTC "blank" token (separator)

One possible alignment (many are valid):
Steps: [—, c, c, —, a, a, a, —, t, t, —, —, —, —, —]
CTC decoding rule: merge consecutive duplicates, remove blanks
→ [—, c, -, —, a, -, -, —, t, -, —, ...] → "cat" ✓

Another valid alignment for the same output "cat":
[c, —, c, a, a, a, a, t, t, t, —, —, —, —, —]
→ CTC collapses → "cat" ✓ (duplicate c with blank separator → single c; consecutive a's → single a)

CTC loss = -log(sum of probabilities over ALL valid alignments for "cat")
Training maximises this probability — the model learns to concentrate mass on positions that produce the correct text without being told exactly where each character appears.
💡

Why the blank token is essential

The blank token allows the model to output "aa" (two separate 'a' characters) by emitting [a, —, a] — without the blank, consecutive identical characters collapse to one. For handwriting, where a character's stroke might span 10+ time steps, the blank also allows the model to "park" between characters while maintaining temporal coherence. The blank appears at ~60-70% of positions in a typical CTC alignment, absorbing the uncertainty about exactly where characters start and end.

04 · The IAM Handwriting Dataset

The Standard Benchmark:
What It Contains and What Its Scores Mean

IAM (Institute of Applied Mathematics, Bern) is the standard benchmark for English handwriting recognition. It contains 13,353 text lines from 657 writers, covering all styles from neat to barely legible. Understanding the IAM benchmark structure is essential for interpreting published HTR accuracy claims and deciding what accuracy to expect from your own system.

What IAM CER means for real-world HTR

IAM CER of 2.8% (TrOCR) sounds excellent. But IAM writers knew they were being recorded — they wrote relatively clearly. Real-world handwriting includes: hasty physician prescriptions (CER often 20-40% with any model), student exam answers (10-20%), medical history forms (8-15%), historical census records (15-30%). Always test your specific document population — do not assume IAM benchmark performance translates to your use case without validation.

Word Error Rate vs Character Error Rate

IAM is evaluated on both CER and WER. The conversion is non-linear: CER 2.8% → WER ~8-12% depending on word length distribution. For short words like "of", "the", "and" — any character error makes the entire word wrong. For long words like "representation", one character error still leaves most of the word readable. WER is typically 3-4× CER for English text.

05 · Pre-processing for Handwriting

Different Pre-processing Needs
Than Printed Text

Handwriting pre-processing shares some steps with printed text (greyscale, denoise, binarise) but has critical differences. Skew correction is more aggressive (handwriting can slope 5-10°, not just 1-3°). Morphological operations must be avoided — they easily break the connecting strokes that are essential to handwriting recognition. Contrast normalisation requires special handling for variable-pressure ink.

Key differences: printed vs handwriting pre-processing

StepPrinted textHandwriting
BinarisationOtsu or adaptive, works wellSauvola always — ink pressure variation requires local thresholds
DeskewCorrect to ≤ 0.5°Correct aggressively — handwriting can slope ±15°. Use text baseline fitting, not Hough lines.
Morphology2×2 closing occasionally helpfulNever — connecting strokes are distinguishing features, not artefacts
DenoisingMedian 3×3 safeVery gentle (median 3×3 only) — stroke variation is signal, not noise
NormalisationFixed height normalisationNormalise to cap height only (not full line height — descenders vary)
Slant correctionNot neededShear correction for right-leaning cursive improves LSTM accuracy

Slant correction for cursive

Cursive handwriting often has a consistent rightward slant (15-30°). This slant causes the LSTM to associate the slanted form of each character with its identity. Shear (horizontal) transformation corrects the slant by shifting each row by a proportional amount, bringing vertical strokes closer to vertical.

import numpy as np, cv2 def correct_slant(binary: np.ndarray, slant_angle: float = 15.0) -> np.ndarray: """ Apply horizontal shear to correct cursive slant. slant_angle: measured clockwise from vertical (typical: 10-25°) """ h, w = binary.shape shear = np.tan(np.radians(slant_angle)) M = np.float32([[1, shear, 0], [0, 1, 0]]) corrected = cv2.warpAffine(binary, M, (w + int(h * shear), h), flags=cv2.INTER_LINEAR, borderValue=255) return corrected def estimate_slant(binary: np.ndarray) -> float: """Estimate cursive slant using Hough lines on thinned image.""" thinned = cv2.ximgproc.thinning(cv2.bitwise_not(binary)) lines = cv2.HoughLinesP(thinned, 1, np.pi/180, 50, 20, 5) if lines is None: return 0.0 angles = [np.degrees(np.arctan2(l[0][3]-l[0][1], l[0][2]-l[0][0])) for l in lines] return 90.0 - abs(np.median(angles)) # convert to slant from vertical
06 · TrOCR for Handwriting: Fine-Tuning on Custom Forms

Adapting TrOCR-Handwritten
to Your Writer Population

TrOCR-base-handwritten achieves CER 4.2% on IAM out of the box. For domain-specific handwriting (medical prescriptions, exam scripts, census forms), fine-tuning on 200-1000 annotated lines from the target population typically reduces CER by 30-60% compared to the general pre-trained model. The fine-tuning process is identical to the printed text case in M4, but requires additional data augmentation strategies specific to handwriting variability.

htr_data_augmentation.py — handwriting-specific augmentation

import numpy as np, cv2, random
from PIL import Image

def augment_handwriting_line(image: np.ndarray) -> np.ndarray:
    """
    Apply random augmentations that simulate real handwriting variation.
    These are DIFFERENT from printed text augmentations — they target
    handwriting-specific variability: slant, stroke width, ink pressure.
    """
    aug = image.copy()
    
    # 1. Random slant variation (±5°)
    if random.random() > 0.5:
        slant = random.uniform(-5, 5)
        h, w = aug.shape[:2]
        shear = np.tan(np.radians(slant))
        M = np.float32([[1, shear, 0], [0, 1, 0]])
        aug = cv2.warpAffine(aug, M, (w + int(h * abs(shear)), h),
                               borderValue=255)
    
    # 2. Random stroke width variation (dilate/erode by 0-1 px)
    if random.random() > 0.5:
        op = cv2.MORPH_DILATE if random.random() > 0.5 else cv2.MORPH_ERODE
        k = cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (2, 2))
        inv = cv2.bitwise_not(aug)
        inv = cv2.morphologyEx(inv, op, k)
        aug = cv2.bitwise_not(inv)
    
    # 3. Random elastic deformation (simulates pen movement variation)
    if random.random() > 0.5:
        h, w = aug.shape[:2]
        amplitude = 2.0  # pixels; keep small to preserve character shapes
        dx = np.random.randn(h, w).astype(np.float32) * amplitude
        dy = np.random.randn(h, w).astype(np.float32) * amplitude
        dx = cv2.GaussianBlur(dx, (11, 11), 5)
        dy = cv2.GaussianBlur(dy, (11, 11), 5)
        map_x = (np.meshgrid(np.arange(w), np.arange(h))[0] + dx).astype(np.float32)
        map_y = (np.meshgrid(np.arange(w), np.arange(h))[1] + dy).astype(np.float32)
        aug = cv2.remap(aug, map_x, map_y, cv2.INTER_LINEAR, borderValue=255)
    
    # 4. Random contrast variation (ink pressure simulation)
    if random.random() > 0.5:
        alpha = random.uniform(0.8, 1.2)  # contrast multiplier
        aug = np.clip(aug.astype(float) * alpha, 0, 255).astype(np.uint8)
    
    return aug

# Fine-tuning recipe for handwriting:
# 1. Start: microsoft/trocr-base-handwritten (NOT trocr-base-printed)
# 2. Collect: 300-500 annotated line images from your target writers
# 3. Augment: 5× each sample with the augmentor above → 1500-2500 effective samples
# 4. Train: 20 epochs, lr=2e-5, batch=4 (handwriting needs smaller batch)
# 5. Validate: hold out 20% of writers (not just 20% of lines) for true generalization test
⚠️

The writer-independent validation split is non-negotiable

The most common HTR fine-tuning mistake: splitting 80/20 by line while keeping all lines from a writer in both train and test. A model that sees 80% of writer A's lines in training will perform extremely well on the remaining 20% of writer A's lines — it has effectively memorised writer A's style. A true generalization test uses entirely unseen writers in the validation set. Reported accuracy on same-writer validation overstates real-world performance by 30-50% relative.

07 · Confidence Scores and Rejection Thresholds

Knowing When to Ask:
The Human-in-the-Loop HTR Strategy

For HTR in production, the goal is not to minimise CER on all input — it is to maximise throughput of correctly processed documents while routing genuinely hard cases to human review. A well-calibrated rejection strategy can achieve 99%+ accuracy on auto-processed documents while routing only 15-25% to humans, rather than attempting 95% accuracy on everything or routing everything to humans.

Confidence thresholding: CER vs automation rate tradeoff

TrOCR mean sequence confidence on 1,000 HTR lines:
Mean conf > 0.90: 540 lines → auto-process → CER = 1.8%
Mean conf 0.70-0.90: 320 lines → auto-process with caution → CER = 7.3%
Mean conf < 0.70: 140 lines → route to human review → CER would be ~24.1% (avoided)

Strategy: auto-process if conf > 0.85 (722 lines, 72.2%) — CER = 2.9%
Route to human: conf < 0.85 (278 lines, 27.8%) — these are the hard cases

Result: 72% automation rate, 2.9% CER on automated output — acceptable for most applications

htr_confidence.py — confidence extraction and routing

import torch
from transformers import TrOCRProcessor, VisionEncoderDecoderModel
from PIL import Image
import numpy as np

class HTRWithConfidence:
    def __init__(self, checkpoint: str = "microsoft/trocr-base-handwritten"):
        self.processor = TrOCRProcessor.from_pretrained(checkpoint)
        self.model     = VisionEncoderDecoderModel.from_pretrained(checkpoint)
        self.model.eval()
    
    def recognise(self, line_image: np.ndarray,
                  auto_threshold: float = 0.85) -> dict:
        """
        Recognise handwritten line with confidence scoring.
        Returns: text, mean_confidence, action (auto/review)
        """
        pil = Image.fromarray(line_image).convert("RGB")
        
        with torch.no_grad():
            pixel_values = self.processor(images=pil, return_tensors="pt").pixel_values
            
            # Generate with scores to get per-token probabilities
            outputs = self.model.generate(
                pixel_values,
                num_beams=4,
                max_length=128,
                output_scores=True,
                return_dict_in_generate=True
            )
            
            sequences    = outputs.sequences
            token_scores = outputs.scores  # tuple of (vocab_size,) per step
        
        # Decode text
        text = self.processor.batch_decode(sequences, skip_special_tokens=True)[0]
        
        # Compute per-token confidence (softmax of score at chosen token)
        token_confidences = []
        for step, score_tensor in enumerate(token_scores):
            probs = torch.softmax(score_tensor[0], dim=-1)
            chosen_token = sequences[0, step + 1]  # +1 for decoder start token
            token_confidences.append(probs[chosen_token].item())
        
        mean_conf = np.mean(token_confidences) if token_confidences else 0.0
        min_conf  = min(token_confidences) if token_confidences else 0.0
        
        # Routing decision
        action = "auto" if mean_conf >= auto_threshold and min_conf >= 0.5                  else "human_review"
        
        return {
            "text":            text,
            "mean_confidence": round(mean_conf, 3),
            "min_confidence":  round(min_conf, 3),
            "action":         action,
            "token_count":    len(token_confidences)
        }
08 · HTR for Specific Form Fields

Handwritten Field Extraction:
Combining Layout Analysis with HTR

form_htr_pipeline.py — handwritten form field extraction

import cv2, numpy as np
from dataclasses import dataclass
from typing import Optional

@dataclass
class FormField:
    name: str
    bbox: tuple             # (x, y, w, h) — fixed template coordinates
    field_type: str         # "text" | "numeric" | "date" | "checkbox"
    expected_pattern: Optional[str] = None  # regex for validation

class HandwrittenFormExtractor:
    """
    Extract handwritten field values from a fixed-template form.
    Template: known field locations (can be detected or pre-defined).
    """
    
    def __init__(self, fields: list[FormField], htr_engine):
        self.fields = fields
        self.htr = htr_engine  # HTRWithConfidence instance
    
    def extract(self, form_image: np.ndarray) -> dict:
        results = {}
        for field in self.fields:
            x, y, w, h = field.bbox
            # Add padding around field for better HTR context
            pad = 5
            crop = form_image[
                max(0, y-pad):min(form_image.shape[0], y+h+pad),
                max(0, x-pad):min(form_image.shape[1], x+w+pad)
            ]
            
            if field.field_type == "checkbox":
                # Checkbox: check if region is mostly dark (checked) or light (unchecked)
                inv = cv2.bitwise_not(crop)
                dark_ratio = inv.sum() / (crop.size * 255)
                results[field.name] = {"value": dark_ratio > 0.15,
                                       "confidence": 0.99, "action": "auto"}
            else:
                # Text/numeric/date: run HTR
                ocr_result = self.htr.recognise(crop, auto_threshold=0.80)
                
                # Validate against expected pattern
                import re
                if field.expected_pattern:
                    match = re.fullmatch(field.expected_pattern, ocr_result["text"].strip())
                    if not match: ocr_result["action"] = "human_review"
                
                results[field.name] = ocr_result
        
        return results

PRESCRIPTION_FIELDS = [
    FormField("patient_name", (180, 120, 400, 40), "text"),
    FormField("dob",          (180, 170, 200, 40), "date",
              expected_pattern=r"\d{1,2}/\d{1,2}/\d{4}"),
    FormField("medication",   (50,  280, 600, 50), "text"),

09 · Assessment

Module 5 Quiz

1. A CRNN model trained on 500 lines from 10 writers achieves CER=4.2% when evaluated on held-out lines from the same 10 writers. A colleague says this evaluation is invalid. Who is correct and why?

Correct. Writer-independent evaluation is the gold standard for HTR. A model that sees 80% of writer A's lines during training has effectively adapted to writer A's stroke style, letter morphology, and spacing habits. Its performance on the remaining 20% of writer A's lines is optimistic — closer to "recognition with prior knowledge of the writer" than "recognition of a new handwriting sample". Production systems encounter new writers continuously. The writer-independent split reveals true generalisation performance. Studies consistently show same-writer CER is 30–50% better (lower) than writer-independent CER for models without explicit writer adaptation mechanisms.

2. Why is CTC-based recognition essential for cursive handwriting, and what would go wrong if you tried to segment cursive text into individual characters before recognition?

Correct. The absence of physical character boundaries in cursive is what makes segmentation-free methods essential, not merely convenient. In printed text, each character is a distinct isolated object with white space separating it from neighbours — segmentation by connected component analysis works reliably. In cursive, the connecting strokes between characters produce continuous ink: the transition from 'n' to 'g' in "language" is a curved stroke that belongs to neither character exclusively. Threshold-based cuts create fragments that the recognition model has never been trained to classify. CTC's blank token absorbs these transitions: in the sequence [l,l,—,a,—,—,n,g,—,u,—,—,a,g,e], the blanks align with the inter-character connecting regions.

3. Your HTR pipeline shows stable confidence scores (31% below 0.85 threshold, consistent week over week) but CER on auto-processed outputs rises from 2.1% to 5.8% by week 3. What is happening?

Correct. Stable routing rate + rising CER = confidence calibration drift. A well-calibrated model routes the hard cases (low confidence → human review) and auto-processes the easy cases (high confidence → auto). When calibration drifts, the model assigns high confidence to cases it gets wrong — these slip through the routing filter into auto-processing, raising CER without changing the routing rate. This is distinct from true accuracy degradation (which would raise CER and likely change the distribution of confidence scores). The diagnostic test: compare CER on auto-processed cases vs all cases. If auto-processed CER is rising while the distribution of confidence scores is unchanged, confidence calibration has drifted.

4. You apply morphological closing (2×2 kernel) to a handwritten line image before TrOCR. Accuracy decreases. Why does this happen specifically for handwriting when the same operation helps for printed text?

Correct. The fundamental difference is that printed character shapes are defined by font design and are robust to minor morphological changes — thickening a printed 'a' by 1–2px does not change its recognisability. Handwritten character shapes are defined by the writer's strokes, and the thin connecting strokes, loop openings, and gap widths between near-touching characters are primary recognition features. Closing fills gaps indiscriminately: the same operation that repairs a legitimately broken stroke in one character also closes the open loop of an adjacent 'c' or 'e', changing its topology. This is why the module states "never apply morphology to handwriting" — the risk of destroying discriminative features outweighs the benefit of repairing broken strokes.

5. TrOCR returns "Take 2 tablets daily" with mean confidence 0.92 and minimum token confidence 0.71 (on the word "daily"). Should this prescription line be auto-processed with threshold=0.85?

Correct. The routing decision for high-stakes medical text must be semantically aware. "Take 2 tablets" (dose and administration) and "daily" (frequency) have different clinical risk profiles: an error in the dose number has immediate patient safety implications; an error in a clearly-invalid frequency string is caught by vocabulary validation. The dual-threshold approach (mean + minimum) plus semantic field classification is the production-correct architecture for prescription OCR. Single flat thresholds either over-route (flagging every prescription with any uncertain token) or under-route (missing dose errors when mean confidence looks acceptable). The vocabulary validation step for frequency tokens provides a calibration-independent safety layer.
