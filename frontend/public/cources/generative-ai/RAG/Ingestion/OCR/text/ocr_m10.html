LLM-Augmented OCR
Confidence Routing · Vision API · Cost-Accuracy · Prompt Failures · Hallucination · GDPR

Large language models do not replace OCR — they extend it. A well-engineered hybrid pipeline routes low-confidence regions to an LLM only when the cost is justified, uses structured prompts to extract typed JSON fields directly from document images, cross-validates LLM output against OCR, and applies GDPR and PCI DSS compliance rules before any data leaves your infrastructure. This module covers the seven scenarios where LLMs help vs hurt, confidence-gated routing architecture, Claude vision API for structured extraction, cost-accuracy tradeoff tables, prompt engineering failure modes, hallucination risk on structured identifiers, and production hybrid pipeline design.

01 · When LLMs Help and When They Hurt

Seven Scenarios for Each Side:
A Decision Framework

The question is never "should we use LLMs for OCR?" — it is "for which specific failure modes does the cost of LLM inference justify the accuracy gain?" LLM vision models excel at semantic understanding but are slower, more expensive, and introduce hallucination risk. Tesseract and PaddleOCR are fast, free, and deterministic — they should always be the primary engine.

7 scenarios where LLMs help

1. Handwriting on degraded paper. OCR sees pixel noise; LLM uses global document context to disambiguate.
2. Complex merged-cell tables. TATR and morphological detection fail; LLM reasons about visual structure.
3. Mixed-script inline text. "Invoice No. فاتورة 2024-001" — LLM handles both scripts in one pass.
4. Heavily annotated / corrected forms. Strikethrough, margin notes, correction fluid — LLM identifies the canonical intended value.
5. Low-contrast scene text. Colour gradients, textured backgrounds, perspective distortion in real-world photos.
6. Rare abbreviations and domain jargon. LLM resolves "HTN" → hypertension, "ISDA CSA" → credit support annex from context.
7. Implicit structure inference. "The following applies to all parties" — LLM determines which subsequent fields share this constraint.

7 scenarios where LLMs hurt

1. Serial numbers and reference codes. LLM hallucinates plausible-looking but wrong identifiers — "A3F9X1" becomes "A3F9X2".
2. High-volume clean documents. 50,000 clear printed invoices/day — LLM adds latency and cost for zero accuracy gain over Tesseract.
3. Exact numeric extraction. Currency amounts, quantities — LLM rounds, normalises, or "corrects" values that should be verbatim.
4. GDPR/HIPAA-restricted data. Sending patient records to an external LLM API may violate DPA Article 28 without a signed DPA with the provider.
5. Real-time latency requirements. <100ms SLA — LLM API adds 800ms–3s per call depending on image size and response length.
6. Offline/air-gapped environments. Regulatory or security requirements prohibit external API calls entirely.
7. Consistent format enforcement. LLM may normalise dates, currencies, or names unpredictably. Regex-based extraction is deterministic.
02 · Confidence-Gated Routing

Tesseract Primary, LLM Escalation
Only Below Confidence Threshold

The correct architecture is not "Tesseract or LLM" — it is "Tesseract always, LLM only when confidence is insufficient for the field's accuracy requirement." Confidence thresholds must be calibrated per field type: a postcode with wrong character has no fallback; a vendor name with low confidence can be reviewed later. Routing must be field-level, not document-level.

confidence_gated_router.py

import pytesseract
from PIL import Image
from dataclasses import dataclass
from typing import Optional
import numpy as np, cv2

FIELD_THRESHOLDS = {
    "serial_number":  (95, None),   # never LLM — hallucination risk
    "amount":         (90, None),   # never LLM — rounding risk
    "date":           (80, "llm"),  # LLM ok — formats vary
    "vendor_name":    (70, "llm"),  # LLM ok — context disambiguates
    "address":        (65, "llm"),  # LLM ok — multi-line tolerates inference
    "description":    (55, "llm"),  # LLM ok — semantic field
}

@dataclass
class FieldResult:
    value:      str
    confidence: float
    method:     str         # "tesseract" | "llm" | "human_review"
    escalated:  bool = False

def ocr_field_crop(crop: np.ndarray) -> tuple[str, float]:
    """Run Tesseract on a pre-cropped field image, return (text, mean_conf)."""
    data = pytesseract.image_to_data(
        Image.fromarray(crop), config="--oem 1 --psm 7",
        output_type=pytesseract.Output.DICT)
    confs  = [c for c in data["conf"] if c > 0]
    text   = " ".join(t for t, c in zip(data["text"], data["conf"])
                       if c > 0).strip()
    conf   = min(confs) if confs else 0   # use min — weakest char limits trust
    return text, conf

def route_field(crop: np.ndarray, field_type: str,
                llm_fn=None) -> FieldResult:
    """
    Route a field crop through Tesseract, escalating to LLM if confidence
    falls below the threshold for this field type.
    llm_fn: callable(crop) -> str  — your LLM extraction function.
    """
    text, conf = ocr_field_crop(crop)
    threshold, escalate_to = FIELD_THRESHOLDS.get(field_type, (70, "llm"))
    if conf >= threshold:
        return FieldResult(text, conf, "tesseract")
    if escalate_to == "llm" and llm_fn:
        llm_result = llm_fn(crop)
        return FieldResult(llm_result, conf, "llm", escalated=True)
    # Null escalation (serial_number, amount) → human review
    return FieldResult(text, conf, "human_review", escalated=True)
03 · Structured Field Extraction via Vision API

JSON Schema Prompting With
Claude Vision API

llm_structured_extract.py

import anthropic, base64, json, io, numpy as np
from PIL import Image

client = anthropic.Anthropic()

SCHEMA = {
    "vendor_name": "string",
    "invoice_number": "string — exact as printed, no normalisation",
    "invoice_date": "string — ISO 8601 YYYY-MM-DD",
    "due_date": "string — ISO 8601 or null",
    "currency": "string — ISO 4217 (GBP, USD, EUR)",
    "subtotal": "number — float, no currency symbol",
    "tax_amount": "number — float or null",
    "total_amount": "number — float",
    "payment_terms": "string or null",
    "line_items": "array of {description, quantity, unit_price, total}"
}

def encode_image(img: np.ndarray) -> str:
    buf = io.BytesIO()
    Image.fromarray(img).save(buf, format="PNG")
    return base64.b64encode(buf.getvalue()).decode()

SYSTEM = """You are a precise document extraction engine.
Extract fields exactly as printed — never normalise, paraphrase, or infer values
that are not visible in the image. If a field is absent, output null.
Output ONLY valid JSON matching the schema. No markdown, no commentary."""

def extract_invoice_fields(img: np.ndarray,
                             schema: dict = SCHEMA) -> dict:
    prompt = (
        f"Extract all fields from this invoice image.
"
        f"Required schema:
{json.dumps(schema, indent=2)}

"
        f"Critical rules:
"
        f"1. invoice_number: copy character-by-character. No guessing.
"
        f"2. All amounts: float only, no symbols.
"
        f"3. Verify: subtotal + tax_amount must equal total_amount.
"
        f"4. If you cannot read a field clearly, output null.
"
        f"Output ONLY the JSON object."
    )
    resp = client.messages.create(
        model="claude-sonnet-4-20250514", max_tokens=1500,
        system=SYSTEM,
        messages=[{"role":"user", "content":[
            {"type":"image","source":{"type":"base64",
             "media_type":"image/png","data":encode_image(img)}},
            {"type":"text","text":prompt}
        ]}]
    )
    raw = resp.content[0].text.strip()
    raw = raw.replace("```json","").replace("```","").strip()
    try:
        data = json.loads(raw)
        # Cross-validate arithmetic
        s, t, tot = (data.get(k) for k in ("subtotal","tax_amount","total_amount"))
        if all(v is not None for v in [s,t,tot]):
            data["_tax_check"] = abs((s + t) - tot) < 0.05
        return {"ok":True, "data":data}
    except json.JSONDecodeError as e:
        return {"ok":False, "error":str(e), "raw":raw}

cost_router.py — tiered cost routing by document quality

import cv2, numpy as np

def image_quality_score(grey: np.ndarray) -> dict:
    """
    Estimate scan quality to inform routing tier.
    Returns sharpness (Laplacian variance) and contrast (pixel std).
    Thresholds empirically calibrated on invoice datasets.
    """
    sharpness = cv2.Laplacian(grey, cv2.CV_64F).var()
    contrast  = grey.std()
    snr       = sharpness / (max(contrast, 1))
    tier = (
        "tesseract"  if sharpness > 300 and contrast > 50
        else "paddleocr" if sharpness > 100 and contrast > 30
        else "llm"
    )
    return {"sharpness": round(sharpness,1),
            "contrast":  round(contrast,1),
            "snr":       round(snr,2),
            "tier":      tier,
            "est_cost":  {"tesseract":0,"paddleocr":0,"llm":0.015}[tier]}

def route_by_quality(image_path: str) -> dict:
    img  = cv2.imread(image_path, cv2.IMREAD_GRAYSCALE)
    qual = image_quality_score(img)
    print(f"[ROUTER] tier={qual['tier']} sharpness={qual['sharpness']}"
          f" contrast={qual['contrast']}")
    if qual["tier"] == "tesseract":
        import pytesseract
        from PIL import Image as PILImage
        return {"text": pytesseract.image_to_string(PILImage.fromarray(img)),
                "method": "tesseract", "cost": 0}
    if qual["tier"] == "paddleocr":
        from paddleocr import PaddleOCR
        r = PaddleOCR(show_log=False).ocr(image_path)
        return {"text": "
".join(i[1][0] for p in r for i in (p or [])),
                "method": "paddleocr", "cost": 0}
    img_bgr = cv2.imread(image_path)
    result  = extract_invoice_fields(img_bgr)
    return {"data": result, "method": "llm", "cost": 0.015}

llm_guardrails.py — post-extraction validation

import re
from datetime import datetime

def validate_llm_extraction(data: dict) -> dict:
    """
    Validate LLM extraction output against type and format rules.
    Returns data with added _errors list and _valid bool.
    """
    errors = []

    # invoice_number: no empty strings, no whitespace-only
    inv_no = data.get("invoice_number", "")
    if not inv_no or not inv_no.strip():
        errors.append("invoice_number: empty")

    # invoice_date: must parse as ISO 8601
    date_str = data.get("invoice_date", "")
    try:
        datetime.strptime(date_str or "", "%Y-%m-%d")
    except:
        errors.append(f"invoice_date: not ISO 8601 ({date_str!r})")

    # All amount fields: must be float or null, not strings
    for field in ("subtotal", "tax_amount", "total_amount"):
        v = data.get(field)
        if v is not None and not isinstance(v, (int, float)):
            errors.append(f"{field}: expected float, got {type(v).__name__} ({v!r})")
        elif isinstance(v, str):
            if re.search(r"[£$€,]", v):
                errors.append(f"{field}: contains currency symbol/separator — strip before returning")

    # currency: must be ISO 4217 3-letter code
    ccy = data.get("currency", "")
    if ccy and not re.match(r"^[A-Z]{3}$", ccy):
        errors.append(f"currency: not ISO 4217 ({ccy!r})")

    # arithmetic cross-check
    s, t, tot = (data.get(k) for k in ("subtotal","tax_amount","total_amount"))
    if all(isinstance(v,(int,float)) for v in [s,t,tot]):
        if abs((s + t) - tot) > 0.05:
            errors.append(f"arithmetic: subtotal({s})+tax({t})={s+t:.2f} ≠ total({tot})")

    data["_errors"] = errors
    data["_valid"]  = len(errors) == 0
    return data
06 · LLM Hallucination on Structured Identifiers

Plausible-Wrong: The Worst Kind
of Extraction Error

A CER of 0.3% sounds excellent. But for structured identifiers — invoice numbers, serial numbers, ISIN codes, NHS numbers — a single wrong character produces a value that passes format validation, passes regex checks, and fails silently in production. "INV-2024-A3F9X1" extracted as "INV-2024-A3F9X2" is undetectable from the OCR output alone.

Why LLMs hallucinate identifiers

LLMs are trained to predict plausible next tokens. For free text, plausibility correlates with correctness. For structured identifiers with no semantic meaning, the model has no ground truth signal — "X1" and "X2" are equally plausible completions.

The model does not know whether "A3F9X1" refers to a real invoice. It generates a token sequence that looks like a plausible identifier given its training distribution. The error is undetectable from the output.

Rule: Never use LLM extraction for fields where wrong values pass format checks silently: serial numbers, reference codes, account numbers, ISINs, NHS numbers, VINs, barcodes. Use OCR + regex for these fields, route to human review on low confidence.

Safe vs unsafe LLM extraction fields

Safe — semantic meaning: vendor name, description, address, payment terms, notes. Errors are visible, contextually implausible, or caught by human review.
Safe — constrained format: date (ISO 8601), currency (ISO 4217). Format validation catches hallucinations.
Unsafe — opaque identifiers: invoice/PO numbers, serial numbers, ISIN, NHS number, account number. Wrong values pass format checks.
Unsafe — exact numerics: amounts, quantities, tax rates. LLM may round or normalise silently.
07 · Production Hybrid Pipeline

OCR Primary, LLM Fallback,
Cross-Validation Safety Net

hybrid_ocr_pipeline.py

from dataclasses import dataclass, field
from typing import Optional
import cv2, numpy as np

@dataclass
class ExtractionResult:
    fields:        dict
    methods:       dict   # field_name -> "tesseract"|"llm"|"human_review"
    review_needed: bool
    review_reasons: list
    cost_usd:      float

def hybrid_extract_document(image_path: str,
                              field_config: dict,
                              llm_enabled: bool = True) -> ExtractionResult:
    """
    Full hybrid extraction:
    1. Image quality routing (decide primary engine)
    2. Per-field OCR with confidence
    3. LLM escalation for low-confidence semantic fields
    4. Hard block on LLM for identifier/amount fields
    5. Cross-validation across all extracted fields
    6. Review routing for failures
    """
    img   = cv2.imread(image_path)
    grey  = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
    qual  = image_quality_score(grey)
    fields, methods, reasons = {}, {}, []
    cost  = 0.0

    for fname, cfg in field_config.items():
        x, y, w, h = cfg["bbox"]
        crop = grey[y:y+h, x:x+w]
        threshold, escalate_to = FIELD_THRESHOLDS.get(fname, (70, "llm"))

        result = route_field(crop, fname,
                              llm_fn=lambda c: extract_invoice_fields(img) if llm_enabled else None)
        fields[fname]  = result.value
        methods[fname] = result.method
        if result.method == "llm": cost += 0.012

    # Cross-validation: amounts
    s, t, tot = (fields.get(k) for k in ("subtotal","tax_amount","total_amount"))
    try:
        if all(v for v in [s,t,tot]):
            if abs((float(s)+float(t))-float(tot)) > 0.05:
                reasons.append("arithmetic_mismatch")
    except: reasons.append("amount_parse_error")

    # Required field check
    required = [f for f in ["total_amount","invoice_date","vendor_name"]
                if not fields.get(f,"").strip() if isinstance(fields.get(f,""),str)]
    reasons.extend([f"missing:{f}" for f in required])

    return ExtractionResult(fields, methods,
                             review_needed=bool(reasons),
                             review_reasons=reasons, cost_usd=cost)

09 · Assessment

Module 10 Quiz

1. A field confidence gate routes "serial_number" fields with conf < 95 to LLM extraction. After deployment, 3 serial numbers per 1,000 documents are extracted incorrectly — they pass regex validation but cause downstream lookup failures. What is the architectural error?

Correct. Null escalation for opaque identifier fields is a hard architectural requirement, not a threshold tuning problem. When a field has no semantic meaning — the character "1" vs "2" in position 6 of a serial number is equally plausible to any language model — LLM escalation introduces hallucination risk without any accuracy benefit. Cross-validation between two engines (C) provides false confidence: both Tesseract and LLM can independently produce the same wrong value from an ambiguous image. Fine-tuning (D) reduces but cannot eliminate hallucination on genuinely ambiguous characters. Only human review provides ground truth for opaque identifier fields where image quality is insufficient.

2. An invoice extraction prompt returns "total_amount": "£12,345.67" as a string. validate_llm_extraction() flags an error. The value is correct — the LLM just included the currency symbol. What prompt addition prevents this at the source?

The correct answer is D — few-shot examples are the most reliable prompt engineering technique for consistent output format. Abstract schema descriptions ("number — float only") are frequently overridden by the model's prior training on reading text that includes currency symbols. A concrete input-output example showing exactly the transformation expected (£12,345.67 → 12345.67) is interpreted unambiguously. B is also good practice (explicit schema annotation) but alone is less reliable than an example. C (post-processing) is the right safety net but not a source fix — it silently corrects errors rather than teaching the model the expected format. D combined with B is the production-grade approach.

3. An accounts payable pipeline using the hybrid architecture processes 5,000 invoices/day. The LLM escalation rate is 40% (2,000 calls/day at $0.015 each = $30/day). Your budget is $5/day for LLM calls. Without reducing accuracy on genuinely hard documents, what is the most principled reduction approach?

Correct. The root-cause-first approach is the only principled cost reduction. Options A (lower thresholds) and D (random cap) reduce LLM calls by accepting higher error rates — they trade accuracy for cost. Option C reduces cost by accepting lower LLM accuracy. Only B reduces LLM calls by fixing the upstream quality issues that are causing unnecessary escalations. If 15% of your invoices are phone-photographed thermal receipts that could be fixed with CLAHE pre-processing, fixing that pre-processing eliminates LLM escalation for those 750 documents/day at zero cost — savings of $11.25/day before touching any thresholds.

4. You are launching a healthcare invoice extraction service in Germany. Patient names and NHS-equivalent (Krankenkassennummer) appear on invoices. You plan to use Claude API for LLM escalation. What GDPR controls are mandatory before the first production call?

Correct. All three controls are mandatory, not optional. A signed DPA is required before any personal data is transmitted to an external processor under Article 28 — this is not a best practice, it is a legal prerequisite. A DPIA is required because health insurance numbers constitute sensitive personal data warranting a systematic privacy risk assessment before any new processing activity begins. Data residency verification is required because even with a signed DPA, transfers to countries without an EU adequacy decision require additional safeguards under Articles 44–49. Pseudonymisation (A) is risk mitigation, not a GDPR exemption — if the invoice still contains enough information to identify the patient, GDPR still applies.

5. Your hybrid pipeline shows: Tesseract CER=1.4% on clean invoices, LLM CER=0.4% on escalated invoices. Overall pipeline CER=1.1% on the full dataset. Is the LLM escalation providing value and how do you know?

Correct. Aggregate CER comparisons across different subsets of documents are confounded by document quality distribution. The escalated subset contains the hardest documents — those where Tesseract already showed low confidence. The comparison must be within-subset: LLM CER on escalated docs vs Tesseract CER on the same escalated docs. The A/B holdout approach (disable LLM escalation on a random 20% of escalation-eligible documents) provides the cleanest measurement by controlling for document quality. Option A makes the exact error of comparing LLM performance on a hard subset against Tesseract performance on the full (easier) dataset.
