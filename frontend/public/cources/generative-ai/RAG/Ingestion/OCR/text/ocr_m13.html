Production OCR Pipeline
FastAPI · Celery · Auto-scaling · S3 Architecture · DLQ · Prometheus · Cost Modelling · SLA

A model that achieves 0.8% CER in a notebook is not a production OCR system. Production means async task queues that absorb traffic spikes without dropping documents, worker pools that auto-scale on queue depth, GPU vs CPU routing decisions that balance cost against latency SLAs, S3-backed document storage with structured output versioning, dead-letter queues for failure isolation, Prometheus metrics with Grafana alerting, and a cost model that predicts infrastructure spend at 100k documents/day before you deploy. This module builds all of it — from FastAPI ingestion endpoint to Celery worker fleet to monitoring dashboard.

01 · Architecture Overview

Five Layers of a Production
OCR Pipeline

Production OCR is an async pipeline problem, not a synchronous request-response problem. A client submits a document and gets a job ID. The document moves through ingestion, queuing, processing, post-processing, and storage layers asynchronously. Each layer is independently scalable and failure-isolated. No layer blocks another.

LayerComponentResponsibilityScale unit
1. IngestionFastAPIValidate, store to S3, enqueue jobHorizontal (stateless)
2. QueueRedis + CeleryJob dispatch, priority routing, backpressureRedis cluster
3. ProcessingCelery workersOCR, post-processing, validationWorker replicas (GPU/CPU)
4. StorageS3 + DynamoDBRaw docs, structured output, job stateManaged (S3) / provisioned (DDB)
5. MonitoringPrometheus + GrafanaLatency, error rate, queue depth, costSingle Prometheus + Grafana

Why async, not sync?

Synchronous OCR: client waits 2-8 seconds per document. At 100 concurrent clients, you need 100 threads blocked on I/O. Async OCR: client gets a job ID in under 50ms. FastAPI handles the next request immediately. OCR runs in a separate worker process. Client polls /status/{job_id} or receives a webhook. Ingestion and processing layers scale independently.

Queue depth as the scaling signal

Queue depth is the primary autoscaling metric for OCR. When depth exceeds N times worker_capacity (TARGET_DEPTH typically 3-5), spin up workers. When depth falls below 1 times capacity for 5 minutes, scale down. More responsive than CPU-based autoscaling for I/O-bound OCR workloads because OCR workers can be idle (waiting for S3) while CPU is low.

02 · FastAPI Ingestion Layer

Async Document Submission,
S3 Upload, and Job Queuing

api/ingestion.py

from fastapi import FastAPI, UploadFile, File, HTTPException
from fastapi.responses import JSONResponse
import boto3, uuid, hashlib
from datetime import datetime, timezone

app = FastAPI(title="OCR Pipeline API")
s3  = boto3.client("s3")
ddb = boto3.resource("dynamodb").Table("ocr_jobs")

MAX_BYTES      = 50 * 1024 * 1024
ALLOWED_TYPES  = {"application/pdf","image/png","image/jpeg","image/tiff"}

@app.post("/v1/documents")
async def submit_document(
    file: UploadFile = File(...),
    priority: str    = "standard",
    webhook: str     = None
) -> JSONResponse:
    if file.content_type not in ALLOWED_TYPES:
        raise HTTPException(415, f"Unsupported: {file.content_type}")
    data = await file.read()
    if len(data) > MAX_BYTES:
        raise HTTPException(413, "File exceeds 50MB limit")

    doc_hash = hashlib.sha256(data).hexdigest()
    job_id   = str(uuid.uuid4())
    s3_key   = f"raw/{doc_hash[:4]}/{doc_hash}/{file.filename}"

    s3.put_object(Bucket="ocr-documents", Key=s3_key, Body=data,
                  ContentType=file.content_type,
                  Metadata={"job_id": job_id})

    now = datetime.now(timezone.utc).isoformat()
    ddb.put_item(Item={"job_id":job_id, "status":"queued",
                        "s3_key":s3_key, "priority":priority,
                        "webhook":webhook or "", "created_at":now})

    queue = {"express":"ocr.express","standard":"ocr.standard",
             "bulk":"ocr.bulk"}[priority]
    prio  = {"express":9,"standard":5,"bulk":1}[priority]
    from workers.tasks import process_document
    process_document.apply_async(args=[job_id, s3_key],
                                   queue=queue, priority=prio)
    return JSONResponse({"job_id":job_id,"status":"queued",
                          "poll_url":f"/v1/jobs/{job_id}"}, status_code=202)

@app.get("/v1/jobs/{job_id}")
async def get_job(job_id: str):
    resp = ddb.get_item(Key={"job_id":job_id})
    if "Item" not in resp: raise HTTPException(404, "Not found")
    item = resp["Item"]
    return {"job_id":item["job_id"],"status":item["status"],
            "result_key":item.get("result_key",""),
            "error":item.get("error","")}
03 · Celery Workers, Retry Logic, and Dead-Letter Queue

Three Queues, GPU/CPU Routing,
Late ACK, and DLQ on Permanent Failure

workers/tasks.py

from celery import Celery
import boto3, json, time, cv2, numpy as np

app = Celery("ocr", broker="redis://redis:6379/0",
             backend="redis://redis:6379/1")
app.conf.update(
    task_acks_late=True,              # ACK only after task completes
    task_reject_on_worker_lost=True,  # requeue if worker crashes mid-task
    task_serializer="json",
    result_expires=86400,
)
s3  = boto3.client("s3")
ddb = boto3.resource("dynamodb").Table("ocr_jobs")

def update_job(job_id: str, **kw) -> None:
    ddb.update_item(Key={"job_id":job_id},
        UpdateExpression="SET "+",".join(f"#k{i}=:v{i}" for i in range(len(kw))),
        ExpressionAttributeNames={f"#k{i}":k for i,k in enumerate(kw)},
        ExpressionAttributeValues={f":v{i}":v for i,v in enumerate(kw.values())})

@app.task(bind=True, max_retries=3, default_retry_delay=30,
          queue="ocr.standard")
def process_document(self, job_id: str, s3_key: str) -> dict:
    t0 = time.time()
    try:
        update_job(job_id, status="processing")
        obj  = s3.get_object(Bucket="ocr-documents", Key=s3_key)
        data = np.frombuffer(obj["Body"].read(), dtype=np.uint8)
        img  = cv2.imdecode(data, cv2.IMREAD_COLOR)
        grey = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
        use_gpu = _gpu_available() and cv2.Laplacian(grey,cv2.CV_64F).var() < 200
        result  = _run_ocr(img, use_gpu=use_gpu)
        out_key = s3_key.replace("raw/","results/") + ".json"
        s3.put_object(Bucket="ocr-documents", Key=out_key,
                      Body=json.dumps(result), ContentType="application/json")
        elapsed = round(time.time()-t0, 2)
        update_job(job_id, status="complete", result_key=out_key,
                   processing_secs=elapsed, gpu=use_gpu)
        return {"job_id":job_id, "elapsed":elapsed}
    except Exception as exc:
        if self.request.retries >= self.max_retries:
            update_job(job_id, status="failed", error=str(exc))
            app.send_task("workers.dlq.handle_dlq",
                          args=[job_id, s3_key, str(exc)], queue="ocr.dlq")
            raise
        raise self.retry(exc=exc)

def _gpu_available() -> bool:
    try: import torch; return torch.cuda.is_available()
    except: return False

# DLQ handler — isolates permanent failures for forensics and replay
@app.task(queue="ocr.dlq", max_retries=0)
def handle_dlq(job_id: str, s3_key: str, error: str) -> None:
    s3.put_object(Bucket="ocr-documents", Key=f"dlq/{job_id}.json",
                  Body=json.dumps({"job_id":job_id,"s3_key":s3_key,"error":error}),
                  ContentType="application/json")
    boto3.client("sns").publish(
        TopicArn="arn:aws:sns:eu-west-2:ACCT:ocr-alerts",
        Message=f"DLQ: job {job_id}
{error[:400]}",
        Subject="OCR DLQ Alert")
04 · Auto-scaling Workers

Queue-Depth Scaling:
Scale Up Immediately, Scale Down With Cooldown

infra/autoscaler.py

import redis, boto3, math, time

rc  = redis.Redis(host="redis", port=6379, decode_responses=True)
ecs = boto3.client("ecs")

MIN_W  = {"ocr.express":2, "ocr.standard":2, "ocr.bulk":1}
MAX_W  = {"ocr.express":10,"ocr.standard":20,"ocr.bulk":8}
TARGET_DEPTH = 4     # target pending jobs per worker
COOLDOWN_S   = 300   # 5-min scale-down cooldown

last_scale_down = {q:0 for q in MIN_W}

def autoscale(queue: str) -> dict:
    depth   = rc.llen(queue)
    svc     = f"ocr-worker-{queue.split('.')[1]}"
    current = ecs.describe_services(cluster="ocr-cluster",
                  services=[svc])["services"][0]["runningCount"]
    desired = max(MIN_W[queue], min(MAX_W[queue],
                  math.ceil(depth / TARGET_DEPTH) if depth > 0 else 0))
    action  = "none"
    if desired > current:
        ecs.update_service(cluster="ocr-cluster",service=svc,desiredCount=desired)
        action = "scale_up"
    elif desired < current and time.time() - last_scale_down[queue] > COOLDOWN_S:
        ecs.update_service(cluster="ocr-cluster",service=svc,desiredCount=desired)
        last_scale_down[queue] = time.time()
        action = "scale_down"
    return {"queue":queue,"depth":depth,"current":current,
            "desired":desired,"action":action}
05 · S3 Storage Layout and Output Versioning

Hash-Prefix Sharding, Output Schema,
and Lifecycle Policies

storage/s3_schema.py

import boto3, json
from datetime import datetime, timezone

# S3 key layout
# raw/      {hash[:4]}/{hash}/{filename}         raw uploads
# results/  {hash[:4]}/{hash}/{filename}.json    structured output
# previews/ {hash[:4]}/{hash}/preview.jpg        annotated image (30d TTL)
# dlq/      {job_id}.json                        failure records
# audit/    {YYYY}/{MM}/{DD}/{job_id}.jsonl       append-only audit log
#
# hash[:4] sharding creates 65536 possible prefixes — distributes S3
# partition pressure across all prefix buckets at high request rates.

def store_result(s3, bucket: str, doc_hash: str, filename: str,
                  job_id: str, fields: dict, meta: dict) -> str:
    p       = doc_hash[:4]
    out_key = f"results/{p}/{doc_hash}/{filename}.json"
    version = 1
    try:
        prev = json.loads(s3.get_object(Bucket=bucket, Key=out_key)
                            ["Body"].read())
        version = prev.get("version", 1) + 1
    except: pass
    payload = {
        "schema_version": "1.0",
        "version":        version,
        "job_id":         job_id,
        "doc_hash":       doc_hash,
        "processed_at":   datetime.now(timezone.utc).isoformat(),
        "fields":         fields,
        "pipeline":       meta,
    }
    s3.put_object(Bucket=bucket, Key=out_key,
                  Body=json.dumps(payload, indent=2),
                  ContentType="application/json")
    return out_key

# Lifecycle policies:
# raw/        Standard → Glacier after 90 days
# results/    Retain indefinitely (structured output)
# previews/   Expire after 30 days
# dlq/        Retain 1 year for forensics

Three highest-ROI cost levers

1. LLM escalation rate. 10% to 5% LLM escalation halves LLM spend. Upstream CLAHE/Sauvola pre-processing reduces escalations at zero API cost — highest ROI investment in the pipeline.

08 · Assessment

Module 13 Quiz

1. At 50k docs/day, queue depth hits 800 at 14:00. TARGET_DEPTH=4, current workers=6, MAX_WORKERS=20, each doc takes 45s. What does the autoscaler do, and is the queue draining?

Correct. The key insight is that MAX_WORKERS caps throughput, and when incoming rate exceeds that cap, the queue never drains during a sustained spike. The autoscaler does the right thing (scales to max), but max is insufficient. The two correct fixes are: (1) capacity planning — set MAX_WORKERS to handle peak load at target occupancy; (2) backpressure — rate-limit ingestion to match processing capacity rather than letting the queue grow unboundedly, which introduces unbounded latency for late-arriving jobs.

2. A document fails three times with OOM errors. What happens step by step after the third exception inside process_document()?

Correct. The full failure path is deterministic and traceable at every layer: DynamoDB reflects terminal status, Prometheus captures the event via DOCS_FAILED counter, S3 preserves failure context for forensics, SNS triggers paging. task_acks_late=True combined with task_reject_on_worker_lost=True is the critical Celery configuration that prevents job loss on worker crash — without it, a crash between task start and ACK would silently discard the job.

3. A colleague proposes simplifying S3 keys from raw/{hash[:4]}/{hash}/{filename} to raw/{filename}. At what volume does the current sharding become necessary, and what specific S3 behaviour does it prevent?

Correct. The S3 partition throughput limit is the primary motivation for hash-prefix sharding in high-volume document pipelines. Note that S3 automatically partitions when it detects sustained high request rates to a prefix, but this can take 15-30 minutes — during which you hit 503 SlowDown errors. Proactive hash sharding avoids this entirely. Flat raw/{filename} also breaks the deduplication logic: the SHA-256 hash in the key path ensures the same document always maps to the same S3 key regardless of submission filename, enabling content-addressable deduplication at zero cost.

4. Your Prometheus alert fires: histogram_quantile(0.95, rate(ocr_processing_seconds_bucket{priority="express"}[5m])) > 60. Express SLA is P99 < 60s. What does this alert tell you, and what are the three most likely root causes?

Correct. P95 exceeding the P99 SLA threshold is a strong signal of SLA breach — if 5% of documents exceed 60s at P95, then P99 is substantially above 60s. The three root causes (worker starvation, S3 latency, GPU memory pressure) represent the three distinct resource bottlenecks in the pipeline: compute, I/O, and accelerator memory. Each has a different diagnostic signal and fix. Priority queue isolation — never allowing express workers to drain into other queues — is the most impactful architectural safeguard for SLA compliance.

5. You need to replay all failed jobs from the DLQ after fixing a bug that caused systematic OOM errors on documents larger than 15MB. There are 847 jobs in the DLQ. What is the correct replay procedure?

Correct. Rate-limited replay is the critical discipline that distinguishes a safe DLQ drain from a second incident. Replaying 847 jobs simultaneously creates a queue depth spike that can overload workers and produce a second wave of failures. Verifying the fix before replay is the first and most important step — a deploy gate check prevents the replay from re-triggering the original bug. The audit trail via the _replayed_ suffix S3 copy is important for compliance: it records exactly which jobs were manually replayed and when, supporting incident post-mortems and SLA reporting.
