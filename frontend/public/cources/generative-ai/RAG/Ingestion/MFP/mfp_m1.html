MFP Algorithms Track · Module 1

Probabilistic Filtering and Seed Generation

Count-Min Sketch · FNV-1a · 8-bit Counters · 99.9999% Rejection · Seed Ranking · Ψ(S)

A corpus of 1.7 million documents might contain 843 million unique 5-grams. Counting the document frequency of every one would require hundreds of gigabytes of memory. The MFP algorithm solves this with probabilistic pre-filtering: a Count-Min Sketch (CMS) with 8-bit counters and FNV-1a hashing estimates n-gram frequencies in under 2GB of RAM, rejecting 99.9999% of candidates before any exact computation. The ~100 survivors become seeds for greedy expansion. This module explains how the CMS works, why the minimum estimator is correct, and how seed ranking by Ψ(S) prioritises the most promising expansion starting points.

01 · The Count-Min Sketch — Approximate Counting in Fixed Memory

d Hash Functions × w Counters —
Always Overestimates, Never Underestimates

The Count-Min Sketch (CMS) is a probabilistic data structure that estimates item frequencies using a d×w matrix of counters. Each counter is only ever incremented — never decremented. The minimum across d independent hash rows gives the best upper bound on the true count. For the MFP problem: populate the CMS with all n-grams in one corpus pass, then query estimated df for candidate seeds in O(d) time — no hash map, no exact counting, sub-2GB memory for any corpus.

Count-Min Sketch — d=4 hash rows, each hashing to one counter column, estimate = minimum of highlighted cells

count_min_sketch.py — probabilistic n-gram frequency estimation with FNV-1a

import numpy as np

class CountMinSketch:
    """
    Count-Min Sketch for approximate n-gram document frequency estimation.

    Structure: d hash functions × w counters per row (d×w matrix).
    Each hash function maps a phrase → one column index per row.
    To estimate df(phrase): hash it d times, take the MINIMUM counter value.

    Why minimum? Hash collisions only INCREASE a counter (never decrease).
    The minimum across d independent hash functions gives the best lower
    bound on the true count. With d=4, w=2^28 (≈256M counters × 1 byte = 256MB),
    the over-estimation error is bounded: P(est > true + ε·n) ≤ (1/e)^d.

    The MFP paper uses 8-bit counters capped at 255 (saturating arithmetic)
    and FNV-1a hash to minimise collision correlation across rows.
    Total memory: d × w bytes — configurable to stay under 2GB.
    """
    def __init__(self, width: int = 1 << 24,  # 16M slots per row
                 depth: int = 4):             # 4 hash rows
        self.w = width
        self.d = depth
        # 8-bit counters: max value 255 (saturating)
        self.table = np.zeros((depth, width), dtype=np.uint8)
        # Independent seeds for each row's hash function
        self.seeds = [0x811c9dc5 + i * 0x01000193 for i in range(depth)]

    def _fnv1a(self, key: tuple[int, ...], seed: int) -> int:
        """
        FNV-1a hash (32-bit) of an integer tuple.
        FNV-1a has excellent avalanche properties and minimal
        correlation between row hashes for the same input.
        """
        h = seed
        for token in key:
            h ^= token & 0xFF
            h = (h * 0x01000193) & 0xFFFFFFFF
            h ^= (token >> 8) & 0xFF
            h = (h * 0x01000193) & 0xFFFFFFFF
        return h % self.w

    def add(self, ngram: tuple[int, ...]):
        """Increment counters for ngram in all d rows (saturating at 255)."""
        for row, seed in enumerate(self.seeds):
            col = self._fnv1a(ngram, seed)
            if self.table[row, col] < 255:   # saturate at max
                self.table[row, col] += 1

    def estimate(self, ngram: tuple[int, ...]) -> int:
        """
        Estimate df(ngram) = minimum counter across all d rows.
        This is an upper bound: estimate ≥ true_count always.
        Typical over-estimation: < 1% for high-frequency n-grams.
        """
        return int(min(
            self.table[row, self._fnv1a(ngram, seed)]
            for row, seed in enumerate(self.seeds)
        ))

    def memory_bytes(self) -> int:
        return self.d * self.w  # 1 byte per counter
02 · Seed Generation — From 843M n-grams to 100 Candidates

99.9999% Rejection Rate —
From Universe to Tractable Set

After the CMS is populated, every unique n-gram in the corpus is queried. If estimated df < σ, it is immediately rejected. The 99.9999% rejection rate reduces 100M unique n-grams to approximately 100 survivors for a 1.7M-document corpus. These survivors are deduplicated, scored by Ψ(S) = est_df × length, and ranked into the seed expansion queue — highest-Ψ first, so the most prevalent boilerplate is identified first.

Seed generation pipeline — four stages from raw n-gram enumeration to ranked expansion queue

seed_generation.py — n-gram enumeration, CMS filtering, seed ranking

import heapq
from dataclasses import dataclass, field

@dataclass(order=True)
class Seed:
    """A candidate seed phrase ranked by estimated df."""
    neg_df:  int            # negative df for max-heap via heapq
    tokens:  tuple = field(compare=False)
    est_df:  int   = field(compare=False)

    def score(self) -> float:
        """
        Ψ(S) — seed quality score from the paper.
        Higher df → higher priority for expansion.
        In practice: simply rank by est_df descending.
        Ties broken by seed length (longer preferred: more specific).
        """
        return self.est_df * len(self.tokens)


def generate_seeds(
    corpus:    list[list[int]],    # tokenised documents
    cms:       CountMinSketch,     # pre-populated CMS
    n:         int   = 5,          # seed n-gram length
    sigma:     int   = 100,        # minimum df threshold
    max_seeds: int   = 100_000,   # cap on seeds to expand
) -> list[Seed]:
    """
    Generate and rank candidate seed n-grams.

    Two-phase pipeline:
    Phase 1 — Enumerate: slide an n-gram window over every document,
      query the CMS for estimated df. If est_df ≥ σ, add to candidate set.
      Memory: O(unique n-grams surviving the threshold), typically << 1M.

    Phase 2 — Deduplicate and rank: use a min-heap to keep the top
      max_seeds candidates by score Ψ(S). This is the sort-merge step
      the paper mentions for corpora that exceed RAM.

    Key insight: CMS rejection rate is ~99.9999% — the vast majority of
    n-grams are unique or rare and are rejected immediately. Only a tiny
    fraction reach Phase 2.
    """
    seen: dict[tuple, int] = {}   # ngram → best est_df seen

    # Phase 1: scan corpus, CMS filter
    for doc in corpus:
        for i in range(len(doc) - n + 1):
            gram = tuple(doc[i:i+n])
            if gram in seen:
                continue                    # skip if already queued
            est = cms.estimate(gram)
            if est >= sigma:
                seen[gram] = est            # candidate survives

    # Phase 2: rank by Ψ(S), keep top max_seeds
    heap: list[Seed] = []
    for gram, est_df in seen.items():
        seed = Seed(neg_df=-est_df, tokens=gram, est_df=est_df)
        if len(heap) < max_seeds:
            heapq.heappush(heap, seed)
        elif seed < heap[0]:        # better than worst in heap
            heapq.heapreplace(heap, seed)

    # Return sorted best-first
    return sorted(heap, key=lambda s: s.neg_df)


def populate_cms_from_corpus(
    corpus: list[list[int]],
    n:      int = 5,
    width:  int = 1 << 24,
    depth:  int = 4,
) -> CountMinSketch:
    """
    First pass over corpus: add all n-grams to the CMS.
    This is the only full corpus scan — all subsequent steps
    use the inverted index or the CMS, not the raw corpus.
    """
    cms = CountMinSketch(width=width, depth=depth)
    for doc in corpus:
        for i in range(len(doc) - n + 1):
            cms.add(tuple(doc[i:i+n]))
    return cms
03 · Memory Budget and Scale

Under 2GB for Any Corpus —
The Paper's Design Constraint

🔑

Memory components

CMS table: d=4 rows × w=2²⁸ = 256M slots × 1 byte = 1GB. Inverted index (for exact verification): O(corpus × avg_length) — may require external sort-merge if > RAM. Bitmask (Module 2): O(total_tokens / 8) bytes — 1 bit per token position. Total: typically 1.5–2GB for a 1.7M-document corpus.

Scenario: 1.7M government document corpus, σ=1000

500 tokens per document on average → 850M total token positions → 850M/8 = 106MB bitmask. CMS: 1GB at w=2²⁸. Inverted index (5-grams, external sort-merge): 12GB on disk, 2GB in RAM chunks. Seeds found: ~80 candidate phrases. Expansion time: minutes. Total memory peak: 3GB (within server RAM budget). Without CMS pre-filtering: exact counting would require a 60GB hash map.

Question 1 of 8

A Count-Min Sketch with d=4 hash rows and w=2²⁸ counters uses 8-bit saturating counters. The n-gram ("all","rights","reserved","copyright","2024") is added to the sketch 850 times across the corpus. The four hash functions map it to cells with current values [847, 851, 839, 843]. What is the CMS estimate, and can the estimate ever be LESS than the true count?

Correct. The CMS estimate is always the minimum across all d rows. The key property: CMS counters are monotone-increasing — they can only be incremented. Any collision with another n-gram can only add to a counter, never subtract. Therefore, every counter is ≥ true count. The minimum across d independent hash rows gives the tightest upper bound. The estimate is ALWAYS ≥ true count — it is a guaranteed upper bound, never an under-estimate.
Question 2 of 8

The MFP paper uses 8-bit counters (max 255) in the CMS with "saturating arithmetic." Why is this choice for high-frequency boilerplate phrases problematic, and how does the paper address it?

Correct. Saturation at 255 is the key trade-off of 8-bit counters. For boilerplate detection, this is acceptable because: (1) the σ threshold (100–1000) is always below 255, so saturated counters still correctly indicate "frequent enough"; (2) the relative ranking of very high-frequency phrases is lost, but since all heavily saturated phrases enter the expansion queue anyway, this does not affect algorithm correctness. The benefit of 8-bit counters is memory efficiency: 256M counters × 1 byte = 256MB per row vs 1GB per row with 32-bit counters.
Question 3 of 8

The MFP paper reports a seed n-gram length of n=5 for corpora of 500K–1.7M documents. Why would n=3 produce too many false positive seeds, and why would n=8 produce too few seeds?

Correct. Seed length n trades off precision (longer = fewer false positives) vs recall (shorter = captures more variants). n=5 is the empirical optimum for the paper's corpora: a 5-gram appearing in 1000+ documents is almost certainly boilerplate, not coincidence. The paper notes that boilerplate phrases are typically 10–50 tokens long, so a 5-gram seed provides a stable anchor for expansion in both directions without committing to specific long-phrase variants.
Question 4 of 8

The CMS is populated in a single corpus pass that adds every n-gram to the sketch. After this pass, why can't the CMS be used for exact df verification of seed candidates — and what data structure is used for exact verification instead?

Correct. The CMS and inverted index serve complementary roles. CMS: approximate, memory-efficient, fast — used for the first filter (reject the 99.9999% of non-frequent n-grams). Inverted index: exact, memory-intensive, used for final exact df verification and for the greedy expansion step (looking up which documents contain a given phrase). The CMS is never used for expansion — only for pre-filtering. This two-phase design is the key to MFP's memory efficiency.
Question 5 of 8

Seed ranking uses the score Ψ(S) = est_df(S) × length(S). Two seeds: S1 = ("home","about","contact","privacy","policy") with est_df=38,700, and S2 = ("all","rights","reserved","copyright","2024","acme","corp") with est_df=12,400. Which has higher Ψ(S) and which should be expanded first?

Correct. Ψ(S1) = 38,700 × 5 = 193,500 > Ψ(S2) = 12,400 × 7 = 86,800. S1 is expanded first. The length multiplier reflects the intuition that longer seeds are more specific and thus more likely to be genuine boilerplate, but a very large df difference can override this. In practice, the top seeds in the expansion queue tend to be common site-wide phrases (navigation menus, legal disclaimers) that appear in a large fraction of the corpus with df in the tens of thousands.
Question 6 of 8

The MFP paper reports that for a corpus of 1.7M documents, the CMS with 8-bit counters and d=4 rows achieves a 99.9999% rejection rate at the seed filtering stage. What does this mean concretely, and what are the implications for the memory budget of the subsequent exact counting stage?

Correct. The 99.9999% rejection rate is the key to MFP's scalability. Without pre-filtering, exact df computation over all unique n-grams in a 1.7M-document corpus would require an enormous hash map (hundreds of gigabytes). The CMS reduces this to a tiny set of survivors, making the inverted index and exact counting stages computationally trivial. The CMS itself requires only 1–2GB of memory, and the survivors require negligible memory.
Question 7 of 8

You are applying MFP to a corpus of academic papers to detect boilerplate in journal article footers. You set σ=500 (a paper must appear in at least 500 papers). After running MFP, you find the phrase "The authors declare no conflict of interest" is NOT in the output MFP set, despite appearing in 2,400 papers. What is the most likely explanation?

Correct. MFP outputs only maximal phrases — a sub-phrase that is covered by a longer MFP will not appear in the output. If "The authors declare no conflict of interest. Funding: This work was supported by NSF grant…" appears with the same df=2,400, then the shorter phrase is not maximal and is bitmask-suppressed. This is the intended behaviour: outputting the longest consistent boilerplate phrase is more useful for corpus cleaning than outputting every sub-phrase separately.
Question 8 of 8

The CMS uses FNV-1a as its hash function with different seeds for each row. Why is using k different seeds of the SAME hash family better than using k completely different hash families?

Correct. FNV-1a with different seed values produces practically independent hash functions for the same input. The seed changes the initial state of the FNV accumulator, cascading through the hash computation to produce uncorrelated outputs. This is the standard approach in Count-Min Sketch implementations — using a single, well-understood hash function family with seed variation is simpler, faster, and empirically as effective as using k distinct hash algorithms.
