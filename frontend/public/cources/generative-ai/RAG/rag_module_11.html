Structured RAG extends retrieval to cover SQL databases, CSV tables, self-querying metadata filters, and knowledge graph traversal — and shows how to combine structured and unstructured retrieval in a single pipeline.

01 · When Documents Are Not Enough

Enterprise Data Lives in
Tables, Databases, and Graphs

A typical enterprise has two classes of knowledge: unstructured (policies, documentation, emails, reports — well-served by vector RAG) and structured (sales data, user records, product inventory, event logs — not served at all by vector RAG). Users ask questions that cross both boundaries: "How many users on annual plans have submitted refund requests in the last 90 days?" No document answers this. You need SQL.

Questions that require structured retrieval

SQL / database query"How many users upgraded from Starter to Teams in Q3 2024?"

Aggregation query over user_events table. Vector RAG returns documentation pages about plans, not actual counts.

CSV / table QA"Which course has the highest completion rate among enterprise users?"

Requires filtering course_completions table by plan_tier=enterprise and computing a ratio. No document contains this answer.

Knowledge graph traversal"What courses are prerequisites for the Advanced RAG certificate?"

Requires traversing a graph: Certificate → has_prerequisite → Course nodes. Entity relationships, not document text.

Metadata self-querying"Show me Python tutorials from 2024 for intermediate learners."

Structured constraints (year=2024, level=intermediate, topic=python) need pre-filtering before semantic search.

💡

The right architecture: route to the right retriever

A production enterprise RAG system routes queries to the appropriate retriever based on the question type: SQL generator for aggregation/filter queries over databases, vector store for semantic document search, knowledge graph for relationship queries, and a hybrid combiner when the answer requires both. The LLM then synthesizes results from whichever retrievers returned relevant context.

02 · SQL Generation from Natural Language

Architecture, Schema Linking,
and Prompt Design

Natural language to SQL (NL2SQL) is a three-stage process: schema linking (identify which tables and columns the query needs), SQL generation (write the query), and validation (check syntax, check for dangerous operations, run in a sandbox). The schema linking stage is the most important and most frequently broken.

NL2SQL pipeline architecture

Stage 1: Schema linking: Given the NL query, identify: which tables are needed, which columns are referenced, which JOIN keys are required. Done by passing the query + schema summary to an LLM and asking it to list relevant tables/columns.
↓
Stage 2: SQL generation: Pass relevant schema subset (not the full schema) + NL query to the LLM. Ask for SQL only. Include examples of correct queries for your dialect (PostgreSQL, SQLite, BigQuery). Request a step-by-step reasoning trace before the SQL.
↓
Stage 3: Validation + execution: Parse the generated SQL for syntax errors. Check for dangerous operations (DROP, DELETE, UPDATE without WHERE). Execute in read-only mode with a timeout. If error: send error message back to LLM for self-correction (max 3 retries).
↓
Stage 4: Result formatting: Convert SQL result (list of rows) to a structured summary. If > 100 rows, ask LLM to aggregate. Pass formatted result to generation stage alongside original question.
⚠️

Schema injection: less is more

Never inject the full database schema. A schema with 50 tables and 400 columns overloads the LLM's attention and causes it to confuse column names across tables. Schema linking first identifies the 3-5 relevant tables, then only those tables' CREATE TABLE statements are injected into the SQL generation prompt. This dramatically improves accuracy.

Schema linking prompt

System: "Given the following question, identify which tables and columns from the schema are needed to answer it. Output as JSON: {tables: [...], columns: {...}}"

Schema summary:
- users(id, email, plan_tier, signup_date, status)
- subscriptions(id, user_id, plan, start_date, end_date)
- refund_requests(id, user_id, amount, status, created_at)

Question: "How many users on annual plans submitted refunds in Q3 2024?"

Output: {tables: ["users","refund_requests"], columns: {users: ["id","plan_tier"], refund_requests: ["user_id","created_at"]}}

SQL generation prompt

System: "Write a PostgreSQL SELECT query. Read-only. Explain your reasoning step by step, then output SQL inside ```sql``` block."

Schema (relevant tables only):
CREATE TABLE users(id INT, plan_tier VARCHAR, ...);
CREATE TABLE refund_requests(id INT, user_id INT, created_at TIMESTAMP, ...);

Question: "How many users on annual plans submitted refunds in Q3 2024?"

Reasoning: I need to JOIN users with refund_requests on user_id, filter plan_tier='annual', filter created_at to Q3 2024, COUNT distinct users.
```sql
SELECT COUNT(DISTINCT u.id) FROM users u JOIN refund_requests r ON u.id=r.user_id WHERE u.plan_tier='annual' AND r.created_at BETWEEN '2024-07-01' AND '2024-09-30';
```
03 · Worked SQL Example

NL → SQL → Result → Answer:
Every Step Annotated

Let's trace a complete NL2SQL execution for a realistic enterprise query, showing every decision the system makes at each stage.

1

Input query

"Which Marevlo course has the highest refund rate among Teams-plan users in 2024?"
2

Schema linking

Tables identified: enrollments(user_id, course_id, enrolled_at), refund_requests(user_id, course_id, status, created_at), users(id, plan_tier). Columns: plan_tier, course_id, status, created_at.
3

SQL generation reasoning

Need to: JOIN enrollments with refund_requests on (user_id, course_id), filter users.plan_tier='teams', filter year=2024, count refunds per course, count total enrollments per course, compute ratio, ORDER BY ratio DESC, LIMIT 1.
4

Generated SQL

SELECT e.course_id, COUNT(r.id) AS refunds, COUNT(e.id) AS enrollments, ROUND(100.0*COUNT(r.id)/COUNT(e.id),1) AS refund_rate FROM enrollments e LEFT JOIN refund_requests r ON e.user_id=r.user_id AND e.course_id=r.course_id AND r.status='approved' AND EXTRACT(YEAR FROM r.created_at)=2024 JOIN users u ON e.user_id=u.id WHERE u.plan_tier='teams' AND EXTRACT(YEAR FROM e.enrolled_at)=2024 GROUP BY e.course_id ORDER BY refund_rate DESC LIMIT 1;
5

SQL result

[(course_id=42, refunds=87, enrollments=340, refund_rate=25.6)]
6

Answer generation

The course with the highest refund rate among Teams-plan users in 2024 is Course ID 42, with a 25.6% refund rate (87 refunds out of 340 enrollments). This is significantly above the platform average, which may warrant investigation into course quality or expectations.
04 · Self-Querying Retriever

LLM Extracts Metadata Filters
From Natural Language

A self-querying retriever uses an LLM to parse structured constraints out of a natural language query and then applies them as metadata filters before or alongside vector search. The LLM does the parsing; the vector store does the filtering. No special syntax required from the user.

Self-querying decomposition

User query

"Show me intermediate Python tutorials released after January 2024"

LLM parses to

semantic_query: "Python tutorials"
filters: {level: "intermediate", date: {$gte: "2024-01-01"}, topic: "Python"}

Vector search with filters

Run dense search for "Python tutorials" ONLY on documents where level=intermediate AND date >= 2024-01-01. Returns semantically relevant Python content that also satisfies the structured constraints.

LangChain SelfQueryRetriever setup

from langchain.retrievers.self_query.base import SelfQueryRetriever
from langchain.chains.query_constructor.base import AttributeInfo

metadata_field_info = [
  AttributeInfo(name="level", description="Course difficulty",
    type="string"), # "beginner","intermediate","advanced"
  AttributeInfo(name="date", description="Release date",
    type="string"),
  AttributeInfo(name="topic", description="Primary topic",
    type="string"),
]
retriever = SelfQueryRetriever.from_llm(
  llm=llm, vectorstore=vectorstore,
  document_contents="ML course content",
  metadata_field_info=metadata_field_info,
  verbose=True)

What the LLM generates internally

# For query: "intermediate Python tutorials after Jan 2024"
# LLM generates a structured query object:

{   "query": "Python tutorials", # semantic part
  "filter": "and(eq('level','intermediate'), gte('date','2024-01-01'), eq('topic','Python'))" }

# Qdrant translates this to:
# Filter({level: "intermediate", date: {$gte: "2024-01-01"}})
# + ANN search with "Python tutorials" embedding
05 · Knowledge Graph RAG

Entity Relationships That
Documents Cannot Express

A knowledge graph stores facts as (subject, predicate, object) triples: (Course:RAG_Masterclass, has_prerequisite, Course:ML_Fundamentals). These relationship facts are impossible to retrieve with vector search because no document explicitly states all the prerequisite chains. Graph traversal finds them in one query.

Knowledge graph patterns for Marevlo

ENTITY TRIPLES (stored in graph)

(RAG_Masterclass, has_prerequisite, ML_Fundamentals)
(RAG_Masterclass, has_prerequisite, Python_Basics)
(ML_Fundamentals, has_prerequisite, Statistics_101)
(RAG_Certificate, requires_course, RAG_Masterclass)
(RAG_Certificate, requires_course, Vector_DB_Course)
(Alice, enrolled_in, RAG_Masterclass)
(RAG_Masterclass, taught_by, Instructor:Siddhish)

CYPHER QUERY (Neo4j)

// What are ALL prerequisites for RAG Certificate?
MATCH (cert:Certificate {name:"RAG_Certificate"})
-[:requires_course]->(c:Course)
-[:has_prerequisite*1..3]->(prereq:Course)
RETURN DISTINCT prereq.name

// Returns: ML_Fundamentals, Python_Basics, Statistics_101, Vector_DB_Course
💡

When to use graph RAG vs vector RAG

Use graph RAG when the answer requires traversing relationships across multiple entities: "What prerequisite chain do I need for certificate X?", "Which users have completed course A but not course B?", "What instructors teach courses related to topic T?" Use vector RAG when the answer requires semantic understanding of document text. Use both together when queries span relationship facts AND document content.

06 · Table QA

CSV and Spreadsheet Reasoning
with Pandas Query Generation

Table QA handles questions over structured tabular data (CSV files, Excel sheets, database result sets) that do not require a full SQL database. The LLM generates Python pandas code to answer the question, which is executed in a sandboxed environment.

Table QA pipeline: NL → pandas → answer

Input table (courses.csv)

course_id | name | completions | refunds
---------|--------------------|-----------|---------
42 | RAG Masterclass | 340 | 87
15 | ML Fundamentals | 892 | 54
31 | Python Basics | 1204 | 23
67 | LLMOps Production | 156 | 41
88 | Vector DB Mastery | 287 | 67

Generated pandas code

# Q: "Which course has worst completion-to-refund ratio?"
df["refund_rate"] = df["refunds"] / df["completions"]
worst = df.nlargest(1, "refund_rate")
# Result: RAG Masterclass (25.6% refund rate)
# Passed back to LLM for answer generation
⚠️

Sandboxing is non-negotiable

The LLM generates arbitrary Python code. Execute it only in a sandboxed environment with no filesystem access, no network access, and a hard execution timeout (5 seconds). Never execute LLM-generated code directly in your production Python environment. Use RestrictedPython, Docker, or a subprocess with resource limits.

07 · Hybrid Structured + Unstructured Pipeline

Combining SQL, Vector, and Table
in a Single Query Router

Most production questions cannot be classified perfectly as "structured" or "unstructured." "Show me the refund policy and tell me how many refunds were processed last month" requires both a vector document lookup AND a SQL aggregate query. A query router classifies the question and dispatches to the appropriate retrieval path, then a synthesis prompt combines the results.

Query router: LLM classifies query as: DOCUMENT (policy/documentation questions), SQL (aggregation/filter over database), TABLE (CSV analysis), GRAPH (relationship traversal), or HYBRID (needs multiple). Routes to appropriate handler(s).
↓
Parallel retrieval (HYBRID path): Document retriever + SQL generator run simultaneously. Both return results independently. No sequential dependency.
↓
Result merging: Structured result: "47 refunds processed in November 2024." Document result: "Annual subscriptions are non-refundable after 30 days [Doc 1]." Both passed to synthesis step.
↓
Synthesis generation: LLM receives: structured data + document context + original query. Prompt: "Use the structured data for quantitative claims and the documents for policy claims. Cite both sources."
✓

Example hybrid answer

"In November 2024, Marevlo processed 47 approved refund requests [SQL: refund_requests table, November 2024 filter]. Under the current policy, annual subscriptions are non-refundable after the 30-day trial period [Doc 1], so these 47 refunds were likely monthly subscription cancellations or requests submitted within the trial window."

LangChain SQLChain, Self-Querying,
and CSV Table Agent

structured_rag.py

from langchain_community.utilities import SQLDatabase
from langchain_community.agent_toolkits import SQLDatabaseToolkit
from langchain.agents import AgentType, create_sql_agent
from langchain.retrievers.self_query.base import SelfQueryRetriever
from langchain.chains.query_constructor.base import AttributeInfo
from langchain_community.agent_toolkits import create_pandas_dataframe_agent
from langchain_anthropic import ChatAnthropic
from langchain_community.vectorstores import Qdrant
import pandas as pd

llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

# ── SQL Agent (safe: read-only toolkit) ──────────────────────
db = SQLDatabase.from_uri(
    "postgresql://user:pass@localhost/marevlo",
    include_tables=["users", "subscriptions", "refund_requests"],
    sample_rows_in_table_info=2  # show 2 example rows for schema context
)
toolkit = SQLDatabaseToolkit(db=db, llm=llm)
sql_agent = create_sql_agent(
    llm=llm,
    toolkit=toolkit,
    agent_type=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
    verbose=True,
    max_iterations=5  # limit self-correction retries
)
result = sql_agent.run(
    "How many users on annual plans submitted refunds in Q3 2024?")

# ── Self-Querying Retriever ───────────────────────────────────
metadata_fields = [
    AttributeInfo(name="level",
        description="Course difficulty: beginner, intermediate, or advanced",
        type="string"),
    AttributeInfo(name="topic",
        description="Primary topic covered by the course",
        type="string"),
    AttributeInfo(name="release_year",
        description="Year the course was published",
        type="integer"),
]
sqr = SelfQueryRetriever.from_llm(
    llm=llm,
    vectorstore=vectorstore,
    document_contents="ML and AI course content",
    metadata_field_info=metadata_fields,
    verbose=True
)
# LLM auto-extracts: query="Python tutorials", filter={level:intermediate, release_year>=2024}
docs = sqr.invoke("Intermediate Python tutorials from 2024")

# ── CSV Table Agent ───────────────────────────────────────────
df = pd.read_csv("course_metrics.csv")
# IMPORTANT: always sandbox this in production
table_agent = create_pandas_dataframe_agent(
    llm=llm, df=df,
    agent_type=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
    verbose=True,
    allow_dangerous_code=False  # disables exec() of arbitrary code
)
answer = table_agent.run(
    "Which course has the highest refund rate?")

# ── Query router (classify then dispatch) ────────────────────
def route_query(query: str, llm, sql_agent, doc_retriever, table_agent) -> str:
    route_prompt = (
        "Classify this question as exactly one of: DOCUMENT, SQL, TABLE, HYBRID.\n"
        "DOCUMENT: policy/documentation questions.\n"
        "SQL: aggregation/filter over the database.\n"
        "TABLE: analysis over uploaded CSV files.\n"
        "HYBRID: needs both documents and SQL.\n"
        f"Question: {query}\nClass:"
    )
    route = llm.invoke(route_prompt).content.strip().upper()
    if route == "SQL": return sql_agent.run(query)
    elif route == "TABLE": return table_agent.run(query)
    elif route == "DOCUMENT": return rag_chain.invoke(query)
    else:  # HYBRID: run both in parallel, synthesize
        sql_result = sql_agent.run(query)
        doc_result = doc_retriever.invoke(query)
        return llm.invoke(
            f"Synthesize: SQL data: {sql_result}\nDocuments: {doc_result}\nQ: {query}"
        ).content
09 · Assessment

Module 11 Quiz

1. A user asks: "How many users on the Teams plan enrolled in a course in the last 30 days?" Your vector RAG system returns documentation pages about the Teams plan features. What is wrong and what is the right approach?

Correct. Vector RAG retrieves text passages. "How many users enrolled" requires executing a COUNT SQL query against a live database. Even if you stored enrollment data as documents, it would be stale and you could not perform exact aggregations. The fix is structural: route aggregate queries to a SQL agent.

2. Schema linking passes only 3 of 50 tables to the SQL generation prompt. Why is this better than passing the full schema?

Correct. This is the most important NL2SQL engineering insight. Full-schema injection is the most common NL2SQL failure mode. With 50 tables, foreign key relationships and column name conflicts make the LLM produce wrong JOIN conditions or reference the wrong table. Schema linking acts as a retrieval step for the schema itself, ensuring the LLM works with a clean, minimal context.

3. A self-querying retriever receives: "Show me intermediate Python courses from 2024." What two things does it extract and what does it do with each?

Correct. Self-querying decomposes natural language into two components: semantic meaning (handled by vector search) and structured constraints (handled by metadata filters). This is exactly what makes it powerful: you get the flexibility of semantic search AND the precision of structured filtering in one retriever, without requiring users to write filter syntax.

4. Table QA generates pandas code and executes it. What is the single most critical production safety requirement?

Correct. LLM-generated code execution is the highest-severity security risk in structured RAG. The LLM can generate code that reads files, makes network requests, or uses system libraries — even without malicious intent, just as a "helpful" attempt to answer the question. Sandboxing is non-negotiable. Logging is useful but insufficient on its own.

5. A user asks: "What is the refund policy for Teams users, and how many Teams users requested refunds last month?" Which query route is correct and why?

Correct. The HYBRID classification is the right choice whenever a question contains both a semantic/policy component and a quantitative/aggregate component. The router fires both retrievers in parallel, then the synthesis prompt tells the LLM: "use document context for policy claims [Doc N], use SQL data for quantitative claims [SQL]." This produces a grounded answer across both knowledge types.
