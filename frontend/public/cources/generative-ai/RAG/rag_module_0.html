01 · The Problem

LLMs Are Frozen in Time

Every large language model — GPT-4, Claude, Gemini — is trained on a massive snapshot of the internet, books, and code. That snapshot has a cutoff date. After that date, the model knows nothing new. And it was never trained on your data: your company's documents, your codebase, your customer records.

🧊 The frozen knowledge problem

GPT-4's training data cuts off in early 2024. Ask it about a product launch from last month, a new law, or a recent research paper — it either hallucinates or admits ignorance. Either way: useless for real work.

🏢 The private data problem

Your company's internal wiki, Slack threads, PDFs, customer contracts — none of that was in the training data. The model genuinely has never seen it. You can't just "ask" it about your own business.

🎭 The hallucination problem

When LLMs don't know something, they often confidently make things up. Not because they're broken — because their job is to predict the most plausible continuation of text, even when that continuation is fiction.

📏 The context limit problem

Even if you tried to dump all your documents into a prompt, you'd quickly hit the context window limit (typically 128K–1M tokens). For enterprise knowledge bases with millions of documents, this approach simply doesn't scale.

⚠️

The real cost of these problems

In a 2024 study of enterprise AI deployments, hallucinations and stale knowledge were cited as the #1 reason AI projects failed in production. Not model quality — data access. RAG was built specifically to solve this.

04 · The Full Picture

How RAG Actually Works

RAG has two distinct phases that run at different times. Understanding this separation is the key to understanding why RAG is so powerful — and where it can go wrong.

Phase 1 — Offline: Build the Knowledge Base (run once)

Step 1
Load Documents PDFs, Word docs, web pages, databases, APIs
→
Step 2
Chunk Split into meaningful, overlapping passages
→
Step 3
Embed Convert each chunk to a dense vector (embedding)
→
Step 4
Index Store vectors in a searchable vector database

Phase 2 — Online: Answer Queries (runs every request)

Step 1
Receive Query User asks a natural language question
→
Step 2
Embed Query Same model converts query to vector
→
Step 3
Retrieve Find top-k most similar chunks by vector distance
→
Step 4
Augment Inject retrieved chunks into the LLM prompt
→
Step 5
Generate LLM produces a grounded, source-backed answer
💡

Why the two-phase design matters

Phase 1 (indexing) is expensive and runs infrequently — when your data changes. Phase 2 (querying) is cheap and fast — it runs on every user request. This design lets you scale to millions of queries without re-processing all your documents each time.

05 · Decision Framework

When to Use RAG vs Alternatives

RAG is not always the right answer. Here is a clear decision framework for choosing between prompt engineering, RAG, and fine-tuning — a question that confuses even experienced ML engineers.

Approach Best For Knowledge Freshness Cost Complexity
Prompt Engineering General tasks, simple instructions, few-shot examples Frozen Very Low Low
RAG Dynamic knowledge, large document sets, private data, factual Q&A Real-time Medium Medium
Fine-tuning Style/format adaptation, domain vocabulary, consistent behaviour Frozen at training High High
RAG + Fine-tuning Production systems needing both style and factual accuracy Real-time Very High Very High
✅

Rule of thumb from the book (LLM Applications with LangChain, 2024)

Start with RAG before even considering fine-tuning. RAG solves 80% of the "the model doesn't know our data" problem with 20% of the cost. Fine-tune only when you need the model to behave differently, not just know more.

06 · First Code

Your First RAG System in 30 Lines

Let's build the simplest possible RAG system from scratch using Python — no LangChain yet, just raw numpy and OpenAI. This helps you understand every step before we add abstractions.

minimal_rag.py — RAG from scratch

Python 
import numpy as np
from openai import OpenAI

client = OpenAI()  # uses OPENAI_API_KEY env var

# ── Phase 1: Build the knowledge base ────────────────────────────

# Your documents (in real life: load from PDFs, DBs, etc.)
documents = [
    "Marevlo annual subscriptions cancelled after 30 days are non-refundable.",
    "Marevlo Pro plan costs $49/month or $399/year.",
    "Support tickets are answered within 24 hours on business days.",
    "API access is included in all plans above Starter tier.",
]

def embed(texts: list[str]) -> np.ndarray:
    """Get embeddings from OpenAI's text-embedding-3-small."""
    resp = client.embeddings.create(
        model="text-embedding-3-small",
        input=texts
    )
    return np.array([e.embedding for e in resp.data])

# Embed all documents and store (in production: save to vector DB)
doc_embeddings = embed(documents)  # shape: (4, 1536)

# ── Phase 2: Answer a query ───────────────────────────────────────

def retrieve(query: str, k: int = 2) -> list[str]:
    """Find the top-k most relevant documents for a query."""
    query_emb = embed([query])[0]          # shape: (1536,)

    # Cosine similarity = dot product of normalized vectors
    norms = np.linalg.norm(doc_embeddings, axis=1, keepdims=True)
    normed = doc_embeddings / norms
    scores = normed @ query_emb / np.linalg.norm(query_emb)

    top_k = np.argsort(scores)[::-1][:k]       # highest similarity first
    return [documents[i] for i in top_k]

def rag_answer(query: str) -> str:
    """Full RAG pipeline: retrieve context, then generate."""
    context_docs = retrieve(query, k=2)
    context = "\n".join(f"- {d}" for d in context_docs)

    prompt = f"""Answer the question using ONLY the context below.
If the answer isn't in the context, say "I don't know."

Context:
{context}

Question: {query}
Answer:"""

    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        temperature=0  # 0 = deterministic, good for factual answers
    )
    return resp.choices[0].message.content

# ── Test it ───────────────────────────────────────────────────────
query = "What happens if I cancel my annual plan after 30 days?"
answer = rag_answer(query)
print(f"Q: {query}\nA: {answer}")
# Q: What happens if I cancel my annual plan after 30 days?
# A: Annual subscriptions cancelled after 30 days are non-refundable.
🔍

What makes this RAG and not just "search"?

The retrieval step finds relevant text. The generation step synthesizes an answer. Both are needed — search alone gives you documents, not answers. LLMs alone give you answers without evidence. RAG combines both.
