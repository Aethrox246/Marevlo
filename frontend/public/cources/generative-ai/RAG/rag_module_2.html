01 · The Core Idea

Words Are Not Just Text Anymore

Before RAG can retrieve anything, it needs to understand meaning — not just match keywords. Embeddings are the mathematical translation of meaning into numbers. Once text is a vector, you can do geometry on language: measure distance between ideas, find neighbours, cluster topics.

🔤 Before embeddings

Keyword search: "bank" always matches "bank" — whether river bank, blood bank, or financial bank. No understanding of meaning, context, or synonyms.

🧠 After embeddings

"bank" in the context of "loan" gets a vector close to "financial institution" — not "river." Context changes the vector. Similar meaning = similar vector.

💡

The key insight: geometry encodes meaning

In a well-trained embedding space: "king" − "man" + "woman" ≈ "queen". "Paris" − "France" + "Italy" ≈ "Rome". Meaning is direction and distance. This is why semantic search works — it finds vectors pointing in the same direction, not just sharing the same letters.

03 · The Mechanics

How an Embedding Model Works

An embedding model is a neural network trained to map text to vectors such that semantically similar text maps to geometrically close vectors. It does this by learning from massive amounts of text — predicting context, masked tokens, or contrastive pairs.

Step-by-step: from text to vector

1
Tokenization"The cat sat" → ["The", "cat", "sat"] → [464, 3797, 3332] (token IDs from vocabulary of ~50K words)
2
Transformer encodingEach token becomes a 768-dim vector. Self-attention lets tokens interact — "bank" near "river" gets a different vector than "bank" near "loan".
3
PoolingMultiple token vectors are collapsed to one sentence vector — via [CLS] token, mean pooling, or max pooling. Result: one vector for the entire input.
4
L2 NormalizationVector is normalized to unit length (magnitude = 1.0). Now cosine similarity = dot product — cheaper to compute. Standard for all production embedding models.

embeddings_from_scratch.py — understand the full pipeline

Python
# Understanding embeddings from first principles
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('all-MiniLM-L6-v2')  # 384-dim, fast, free

sentences = [
    "The patient has chest pain and shortness of breath",
    "Symptoms include cardiac discomfort and breathing difficulty",  # similar ↑
    "The Python programming language was created in 1991",            # different ↓
    "Machine learning requires large amounts of training data",
]

# Encode: text → vectors (shape: 4 × 384)
embeddings = model.encode(sentences, normalize_embeddings=True)
print(f"Shape: {embeddings.shape}")  # (4, 384)

# Cosine similarity (= dot product for normalized vectors)
def cosine_sim(a, b):
    return float(np.dot(a, b))  # already normalized → no division needed

# Medical sentences should be close; medical vs code should be far
print(f"Medical ↔ Medical: {cosine_sim(embeddings[0], embeddings[1]):.3f}")
# Medical ↔ Medical: 0.847  ← HIGH (same concept, different words)

print(f"Medical ↔ Python:  {cosine_sim(embeddings[0], embeddings[2]):.3f}")
# Medical ↔ Python:  0.102  ← LOW (completely different domains)

print(f"Python  ↔ ML:      {cosine_sim(embeddings[2], embeddings[3]):.3f}")
# Python  ↔ ML:      0.491  ← MEDIUM (tech domain, different topics)

# Nearest neighbor search (what retrieval does)
query = model.encode(["heart attack symptoms"], normalize_embeddings=True)[0]
scores = embeddings @ query  # dot product with all docs at once
ranked = np.argsort(scores)[::-1]
print("\nTop match for 'heart attack symptoms':")
print(f"  → {sentences[ranked[0]]} (score: {scores[ranked[0]]:.3f})")
# → "The patient has chest pain and shortness of breath" (score: 0.782)
04 · Measuring Distance

Cosine, Dot Product, Euclidean

Once you have vectors, you need a way to measure "how similar" they are. Three metrics dominate. Choosing the wrong one for your use case silently degrades retrieval quality.

Metric Formula Range Best For RAG?
Cosine similarityA·B / (|A||B|)−1 to +1Semantic similarity; angle between vectors regardless of magnitude✓ Standard
Dot productA·B = ΣAᵢBᵢ−∞ to +∞Normalized vectors (= cosine); also encodes magnitude (confidence)✓ After normalize
Euclidean (L2)√Σ(Aᵢ−Bᵢ)²0 to +∞Clustering, image embeddings, cases where magnitude matters⚠ Rarely
📐

Why cosine is the default for text RAG

A short 5-word chunk and a 500-word document have different magnitudes but can express identical ideas. Cosine ignores magnitude and measures angle — so both can have high similarity to a matching query. Euclidean would penalize the short chunk just for being shorter.

05 · Choosing a Model

Which Embedding Model Should You Use?

There are hundreds of embedding models. Most RAG tutorials use OpenAI's API — convenient but expensive and opaque. Here is a practical comparison of the models that actually matter in production.

all-MiniLM-L6-v2
Dims: 384
Speed: Very fast (~14K tokens/s CPU)
Size: 80MB
Cost: Free (local)
Best for: prototyping, low-latency apps, when GPU is unavailable
⭐ Production pick
BAAI/bge-large-en-v1.5
Dims: 1024
Speed: Fast (GPU), good on CPU
Size: 1.3GB
Cost: Free (local)
Best for: high-quality production RAG; top MTEB leaderboard open model
text-embedding-3-small
Dims: 1536 (adjustable)
Speed: API latency (~100ms)
Size: API-hosted
Cost: $0.02/1M tokens
Best for: quick start; Matryoshka dims let you shrink at query time
E5-mistral-7b
Dims: 4096
Speed: Slow (large model)
Size: ~14GB
Cost: Free (GPU needed)
Best for: maximum accuracy when latency is acceptable; SOTA on MTEB
Cohere embed-v3
Dims: 1024
Speed: API latency
Size: API-hosted
Cost: $0.10/1M tokens
Best for: multilingual (100+ langs); int8 compression built in
nomic-embed-text
Dims: 768
Speed: Fast
Size: ~550MB
Cost: Free (local via Ollama)
Best for: fully local RAG stacks; open weights, auditable
⚠️

The embedding model mismatch trap

You MUST use the same embedding model for indexing and querying. If you index with BGE and query with OpenAI, the vector spaces are completely different — like translating a French document into German, then asking questions in Spanish. Your retrieval will return garbage. Pick one model and stick to it.

06 · Advanced Concepts

Matryoshka Embeddings and Dimension Reduction

Modern embedding models support Matryoshka Representation Learning (MRL) — where the first N dimensions of a large embedding are themselves a valid lower-dimensional embedding. This lets you trade quality for speed dynamically at query time.

🪆 Matryoshka (MRL) embeddings

OpenAI's text-embedding-3-small and large both support this. A 1536-dim vector truncated to 256 dims still works — just with slightly lower accuracy. Useful: index at full dims, retrieve fast candidates at 256, rerank at full dims.

📦 Quantized embeddings

int8 quantization: convert float32 vectors (4 bytes/dim) to int8 (1 byte/dim). 4× memory savings, marginal quality loss. Cohere Embed v3 and BGE models support this. Critical for storing billions of vectors.

matryoshka_demo.py — dimension reduction in practice

Python
from openai import OpenAI
import numpy as np

client = OpenAI()

def embed_with_dims(text: str, dims: int) -> np.ndarray:
    """Get a Matryoshka embedding at specified dimension."""
    resp = client.embeddings.create(
        model="text-embedding-3-small",
        input=text,
        dimensions=dims  # Matryoshka: truncate at this dimension
    )
    vec = np.array(resp.data[0].embedding)
    return vec / np.linalg.norm(vec)  # normalize

query = "machine learning for medical diagnosis"
doc   = "AI systems are increasingly used in radiology and pathology"

# Compare quality at different dimensions
for dims in [64, 256, 512, 1536]:
    q = embed_with_dims(query, dims)
    d = embed_with_dims(doc, dims)
    sim = np.dot(q, d)
    print(f"Dims={dims:4d}: similarity={sim:.4f}  memory={dims*4/1024:.1f}KB/vector")

# Dims=  64: similarity=0.6821  memory=0.2KB/vector
# Dims= 256: similarity=0.7203  memory=1.0KB/vector
# Dims= 512: similarity=0.7389  memory=2.0KB/vector
# Dims=1536: similarity=0.7412  memory=6.0KB/vector
# Note: 64-dim loses ~9% quality but uses 30× less memory!

# Production trick: two-stage retrieval
# Stage 1: retrieve 100 candidates at 64 dims (fast, cheap)
# Stage 2: rerank those 100 using full 1536 dims (accurate)
# Cost: ~10× faster than full-dim search on the whole corpus
