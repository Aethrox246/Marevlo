01 · What Chunking Actually Is

The Problem: Embeddings Can't
Handle Entire Documents

Embedding models have a hard token limit — typically 512 or 8192 tokens. A 50-page contract has ~40,000 tokens. You cannot embed it whole. Chunking splits documents into retrievable units small enough to embed and specific enough to retrieve precisely.

What is a token? The Math You Need

Tokens are the units language models actually process. They are not characters, not words — they sit somewhere in between. The OpenAI cl100k tokenizer (used by GPT-4 and text-embedding-3) uses byte-pair encoding (BPE):

Common English words

"hello" → 1 token
"tokenization" → 4 tokens
"the", "is", "a" → 1 token each

~0.75 words per token on average

Rare / technical words

"unstructured" → 3 tokens
"vectorstore" → 3 tokens
"elasticsearch" → 4 tokens

Technical text uses more tokens/word

Practical estimate

1 page of text ≈ 300–500 tokens
1,000 tokens ≈ 750 words
GPT-4 context = 128K tokens ≈ 100K words

Always measure, never guess

The Two Failure Modes: Too Large vs Too Small

❌ Too large (2000+ tokens)

Imagine your chunk is an entire section about refund policies, product warranties, and shipping times. A user asks "what is the refund window?" The embedding of this chunk is influenced by all three topics — it's semantically blurry. The retriever fetches it, but the LLM gets 2000 tokens of unrelated noise along with the answer. Context pollution.

One embedding → multiple semantic topics → imprecise retrieval

❌ Too small (50 tokens)

Your chunk is: "Non-refundable." That's it. It's technically accurate — annual subscriptions are non-refundable. But a user asking "what is your refund policy?" retrieves this chunk and the LLM has no context about which product, under what conditions, or what "non-refundable" means here. The answer is technically correct and completely useless.

High precision → zero context → useless generation
🎯

The Goldilocks Zone: 200–800 tokens for most text

This range gives each chunk one primary topic (good for embedding precision) while retaining enough context for the LLM to generate a complete answer. The right size depends on your document type and query patterns — we'll build a decision framework in Section 6.

02 · Strategy 1 — Fixed-Size Chunking

The Simplest Approach:
Splitting by Token Count

Split the text into chunks of exactly N tokens, with M tokens of overlap between consecutive chunks. Zero linguistic intelligence. The split happens wherever the token counter hits the limit — mid-sentence, mid-paragraph, anywhere.

How It Works — Step by Step

Step 1
Tokenize the entire document
Convert the text to a token stream using tiktoken (OpenAI) or the model's own tokenizer. This gives you a flat list of integers. All whitespace, newlines, punctuation become tokens.
Step 2
Slide a window of size chunk_size
Take tokens [0 : chunk_size] as chunk 1. Then tokens [(chunk_size - overlap) : (2*chunk_size - overlap)] as chunk 2. Continue until document is exhausted.
Step 3
Decode each window back to text
Convert each token slice back to readable text. The overlap region appears in both adjacent chunks — this is intentional insurance against splitting important information at a boundary.

Live Example — Same Text, Three Configurations

Source document excerpt (34 tokens total):

"Annual subscriptions are non-refundable after the 30-day trial period ends. Monthly subscriptions may be cancelled at any time and take effect at the end of the billing cycle. Enterprise customers should contact billing@marevlo.com for custom refund arrangements."
Configuration A — chunk_size=20, overlap=0
"Annual subscriptions are non-refundable after the 30-day trial period ends. Monthly" ~20 tok
"subscriptions may be cancelled at any time and take effect at the end of the billing" ~20 tok
"cycle. Enterprise customers should contact billing@marevlo.com for custom refund arrangements." ~14 tok
⚠️

Notice chunk 1 ends mid-idea — "Monthly" is cut off from its predicate. A query about monthly subscriptions would retrieve chunk 2, which starts with "subscriptions" but has no referent. Context is broken.

Configuration B — chunk_size=20, overlap=5
"Annual subscriptions are non-refundable after the 30-day trial period ends. Monthly" 20 tok
"trial period ends. Monthly OVERLAP subscriptions may be cancelled at any time and take effect at the end" 20 tok
"take effect at the end OVERLAP of the billing cycle. Enterprise customers should contact billing@marevlo.com for" 20 tok
✓

Overlap means "trial period ends. Monthly" appears in both chunk 1 and chunk 2. Now a query about monthly subscriptions retrieves chunk 2 which has enough context to form a coherent answer.

Configuration C — chunk_size=40, overlap=8 (production-like)
"Annual subscriptions are non-refundable after the 30-day trial period ends. Monthly subscriptions may be cancelled at any time and take effect at the end of the billing cycle." ~36 tok
"take effect at the end of the billing cycle. OVERLAP Enterprise customers should contact billing@marevlo.com for custom refund arrangements." ~22 tok
✓

Each chunk covers a complete thought. The overlap preserves the connection between the billing cycle sentence and the enterprise note. This is close to what you'd use in production for policy documents.

fixed_size_chunking.py

import tiktoken
from langchain.text_splitter import TokenTextSplitter

# ── Raw tiktoken approach (understand the mechanics) ───────────
def fixed_chunk_raw(text: str, chunk_size: int = 500,
                     overlap: int = 100) -> list[str]:
    enc = tiktoken.get_encoding("cl100k_base")   # GPT-4 / text-embedding-3
    tokens = enc.encode(text)
    chunks = []
    step = chunk_size - overlap
    for start in range(0, len(tokens), step):
        end = start + chunk_size
        chunk_tokens = tokens[start:end]
        chunk_text = enc.decode(chunk_tokens)
        chunks.append(chunk_text)
        if end >= len(tokens):  # reached end of document
            break
    return chunks

# Example
text = open("refund_policy.txt").read()
chunks = fixed_chunk_raw(text, chunk_size=500, overlap=80)
print(f"Document → {len(chunks)} chunks")
print(f"Token counts: {[len(tiktoken.get_encoding('cl100k_base').encode(c)) for c in chunks]}")

# ── LangChain TokenTextSplitter (production use) ───────────────
splitter = TokenTextSplitter(
    encoding_name="cl100k_base",
    chunk_size=500,
    chunk_overlap=80,
)
docs = splitter.create_documents([text])

# ── Sanity check: verify chunk sizes ──────────────────────────
enc = tiktoken.get_encoding("cl100k_base")
for i, doc in enumerate(docs):
    n_tokens = len(enc.encode(doc.page_content))
    print(f"Chunk {i:03d}: {n_tokens:4d} tokens | {doc.page_content[:60]}...")

03 · Strategy 2 — Recursive Character Splitting

The Production Default:
Respecting Text Structure

RecursiveCharacterTextSplitter is LangChain's default and the right starting point for most RAG systems. It tries a hierarchy of separators — paragraphs first, then sentences, then words — falling back to smaller units only if the chunk would be too large. This preserves natural language boundaries whenever possible.

The Separator Hierarchy — How the Algorithm Decides

DEFAULT SEPARATOR PRIORITY (tries in order, stops when chunk fits):
Try 1st
"\n\n" — Paragraph breaks
If splitting on double-newlines keeps chunks under chunk_size, use them. Paragraphs are the most natural unit of thought in prose.
Try 2nd
"\n" — Single newlines
If a paragraph is still too big (common in dense technical writing), split on line breaks. Lists, code with line-per-statement, and long paragraphs get handled here.
Try 3rd
". " — Sentence boundaries
A very long single line? Split at sentence boundaries. ". " catches most English sentences. The splitter also respects common abbreviations to avoid splitting "Dr. Smith" incorrectly.
Try 4th
", " " " "" — Last resorts
For very long unbroken strings (no sentences, no newlines), fall back to commas, then spaces, then individual characters. You should never reach the character level with real text.

Worked Example on the Same Policy Document

RAW DOCUMENT (3 paragraphs, ~90 tokens total)

Annual subscriptions are non-refundable after the 30-day trial period expires. Customers who subscribed before January 2024 are subject to legacy terms.

Monthly subscriptions may be cancelled at any time. Cancellations take effect at the end of the current billing cycle. No partial refunds are issued for unused days.

Enterprise customers with custom SLAs should contact billing@marevlo.com. Response time is one business day. All enterprise refund arrangements are handled case by case.
Result with chunk_size=200, overlap=30 — splits on "\n\n" (paragraph), all fit
CHUNK 1 "Annual subscriptions are non-refundable after the 30-day trial period expires. Customers who subscribed before January 2024 are subject to legacy terms." 30 tok
CHUNK 2 "Monthly subscriptions may be cancelled at any time. Cancellations take effect at the end of the current billing cycle. No partial refunds are issued for unused days." 35 tok
CHUNK 3 "Enterprise customers with custom SLAs should contact billing@marevlo.com. Response time is one business day. All enterprise refund arrangements are handled case by case." 33 tok
✓

Each chunk covers exactly one complete topic — annual policy, monthly policy, enterprise policy. A query about "enterprise refunds" maps cleanly to chunk 3. This is dramatically better than fixed-size splitting of the same text.

recursive_splitting.py

from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.schema import Document
import tiktoken

# ── Standard setup ─────────────────────────────────────────────
enc = tiktoken.get_encoding("cl100k_base")

splitter = RecursiveCharacterTextSplitter(
    chunk_size=600,
    chunk_overlap=100,
    length_function=lambda t: len(enc.encode(t)),  # measure in tokens, not chars!
    separators=["\n\n", "\n", ". ", ", ", " ", ""],
    is_separator_regex=False,
)

# CRITICAL: use length_function=lambda that counts TOKENS not characters.
# Default is len() which counts characters — 1 char != 1 token.
# A 600-char split is ~150 tokens. A 600-token split is ~450 words. Very different!

docs = [
    Document(page_content=text, metadata={"source": "policy.pdf", "page": 1})
    for text in [raw_text]  # your documents here
]

chunks = splitter.split_documents(docs)

# Metadata is automatically propagated to all chunks from the same document
print(f"Split {len(docs)} documents into {len(chunks)} chunks")
for i, c in enumerate(chunks[:3]):
    n_tok = len(enc.encode(c.page_content))
    print(f"[{i}] {n_tok:3d} tok | {c.page_content[:80]}...")

# ── Custom separators for code documentation ──────────────────
code_doc_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=60,
    length_function=lambda t: len(enc.encode(t)),
    separators=[
        "\ndef ",          # split at function definitions first
        "\nclass ",        # then class definitions
        "\n\n",           # then blank lines (between blocks)
        "\n", ". ", " ", ""
    ],
)
⚠️

The #1 mistake: not using a token-based length function

RecursiveCharacterTextSplitter defaults to counting characters. This is wrong for almost every use case. chunk_size=1000 with character counting gives you ~250 tokens — 4x too small. Always pass length_function=lambda t: len(enc.encode(t)) to measure in actual tokens.

04 · Strategy 3 — Structure-Aware Splitting

When Documents Have
Built-In Structure

Markdown, HTML, Word documents, and wikis already have structure encoded in their headers and tags. MarkdownHeaderTextSplitter and HTMLHeaderTextSplitter use that structure as natural chunk boundaries — and critically, they add the header hierarchy to chunk metadata, enabling structured filtering at query time.

How Headers Become Metadata

# Subscription Plans
Our pricing is designed for teams of all sizes.

## Annual Plans
Annual subscriptions are billed upfront. They are non-refundable after 30 days.
### Refund Policy
To request a refund within the 30-day window, submit a ticket via the billing portal.

## Monthly Plans
Monthly plans can be cancelled at any time with no penalty.
Output chunks with MarkdownHeaderTextSplitter — notice the metadata
CHUNK 1 text: "Our pricing is designed for teams of all sizes."
metadata: {"h1": "Subscription Plans"}
CHUNK 2 text: "Annual subscriptions are billed upfront. They are non-refundable after 30 days."
metadata: {"h1": "Subscription Plans", "h2": "Annual Plans"}
CHUNK 3 text: "To request a refund within the 30-day window, submit a ticket via the billing portal."
metadata: {"h1": "Subscription Plans", "h2": "Annual Plans", "h3": "Refund Policy"}
CHUNK 4 text: "Monthly plans can be cancelled at any time with no penalty."
metadata: {"h1": "Subscription Plans", "h2": "Monthly Plans"}
💡

Now a query filtered by h2="Annual Plans" only searches chunks from that section. This is what powers SelfQueryingRetriever (Module 11) — metadata transforms retrieval from "find similar text" to "find within a specific section."

structure_aware_splitting.py

from langchain.text_splitter import (
    MarkdownHeaderTextSplitter,
    RecursiveCharacterTextSplitter,
)

# ── Step 1: Split on Markdown headers ─────────────────────────
md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#",   "h1"),   # stored as metadata key "h1"
        ("##",  "h2"),   # stored as metadata key "h2"
        ("###", "h3"),   # stored as metadata key "h3"
    ],
    strip_headers=False,   # keep header text inside the chunk
    return_each_line=False, # merge lines within same header into one chunk
)

md_sections = md_splitter.split_text(markdown_text)
# Returns Documents with page_content (text) + metadata (header hierarchy)

print(f"Header-based sections: {len(md_sections)}")
for s in md_sections[:3]:
    print(f"  {s.metadata} → {s.page_content[:60]}...")

# ── Step 2: Sub-split sections that are still too large ────────
# Header splitter ignores chunk_size — sections can be huge
# Run a second-pass recursive splitter to size them properly
secondary_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=60,
    length_function=lambda t: len(enc.encode(t)),
)

final_chunks = secondary_splitter.split_documents(md_sections)
# Header metadata is preserved in all sub-chunks!
# A chunk from h2="Annual Plans" keeps that metadata even if split further

# ── Query-time filtering (preview of Module 11) ───────────────
# With Chroma:
results = vectorstore.similarity_search(
    query="refund process",
    filter={"h2": "Annual Plans"},  # only search Annual Plans section
    k=5,
)
05 · Strategy 4 — Semantic Chunking

Using Embeddings to Find
Where Topics Actually Change

Fixed and recursive splitting split at arbitrary positions. Semantic chunking splits where the meaning actually shifts — using embedding similarity between consecutive sentences to detect topic boundaries. It costs more (embedding API calls during ingestion) but produces fundamentally better chunks.

The Algorithm — How It Detects Topic Shifts

Step 1
Sentence tokenization
Split the document into individual sentences using a sentence boundary detector (spaCy or NLTK). This gives you S₁, S₂, S₃, ... Sₙ.
Step 2
Embed sentence windows
Create rolling windows: window(i) = concat(S_{i-k}, ..., S_i, ..., S_{i+k}). Embed each window. The window provides local context so individual short sentences aren't embedded in isolation.
Step 3
Compute adjacent similarity scores
For each consecutive pair (window_i, window_{i+1}), compute cosine similarity. High similarity = same topic continues. Low similarity = potential topic boundary.
Step 4
Apply breakpoint threshold
Collect all similarity scores. Find the Nth percentile (e.g., 95th percentile). Any position where similarity drops below this threshold is a chunk boundary. High percentile = fewer, larger chunks. Low percentile = many small chunks.
Step 5
Merge sentences within groups
Join all sentences between two breakpoints into a single chunk. The result: chunks where each unit is semantically homogeneous — one topic, one embedding, one retrieval target.

Visualized: Similarity Drops Reveal Topic Boundaries

SIMILARITY SCORES BETWEEN CONSECUTIVE SENTENCE PAIRS — lower = topic shift:

semantic_chunking.py

from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
# Small is fine for ingestion — you want speed and cost efficiency

# ── Percentile threshold ───────────────────────────────────────
# The most reliable method. Finds the 95th percentile of all dissimilarity
# scores and splits wherever dissimilarity exceeds that.
semantic = SemanticChunker(
    embeddings=embeddings,
    breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=95,  # higher = fewer splits = larger chunks
)

# ── Standard deviation method ─────────────────────────────────
# Splits when dissimilarity exceeds mean + 1.25 * std_dev
# More principled statistically but can produce very variable chunk sizes
semantic_std = SemanticChunker(
    embeddings=embeddings,
    breakpoint_threshold_type="standard_deviation",
    breakpoint_threshold_amount=1.25,
)

# ── Interquartile range method ────────────────────────────────
# Uses IQR (Q3 - Q1) * multiplier to detect outlier dissimilarity scores
semantic_iqr = SemanticChunker(
    embeddings=embeddings,
    breakpoint_threshold_type="interquartile",
    breakpoint_threshold_amount=1.5,
)

docs = semantic.create_documents([long_text])
print(f"Semantic chunks: {len(docs)}")
for d in docs[:4]:
    print(f"  ~{len(d.page_content.split()):4d} words | {d.page_content[:70]}...")

# ── Cost estimate ────────────────────────────────────────────
# text-embedding-3-small: $0.02 / 1M tokens
# 100-page document ≈ 40,000 tokens → $0.0008 per document
# 10,000 documents → $8 ingestion cost
# Ingest once, query millions of times → very cost efficient
06 · Strategy 5 — Parent-Child Chunking

The Production Winner:
Index Small, Return Large

Parent-child chunking solves a fundamental tension: you want small chunks for precise retrieval, but large chunks for rich LLM context. The solution — index the small child chunks in the vector database, but store and return the larger parent chunks. You get both.

Architecture: Two Stores, One Query

Parent chunks — stored in document store (not vector DB)
📄 Parent Chunk 1 ~1000 tok stored in InMemoryStore / Redis
"Annual subscriptions are billed upfront and auto-renew unless cancelled 7 days before renewal. They are non-refundable after the 30-day trial window. Customers who subscribed before January 2024 are subject to legacy pricing terms which include a grace period of 14 additional days. To cancel, visit Account → Billing → Cancel Subscription. You will retain access until the end of the current period."
↓ split into child chunks ↓
Child chunks — indexed in vector DB for retrieval
🔍 "Annual subscriptions billed upfront, non-refundable after 30-day trial" ~50 tok
🔍 "Pre-2024 customers: legacy pricing with 14-day grace period" ~40 tok
🔍 "Cancel via Account → Billing → Cancel Subscription" ~30 tok
🔍 "Retain access until end of current billing period after cancellation" ~35 tok
↓ Query hits child → returns parent ↓
Query: "when does access end after I cancel?" → child 4 matches → parent 1 returned
✓ LLM receives the full 1000-token parent context — including the cancellation procedure, grace period, and billing cycle details — not just the 35-token child that matched. Complete, grounded answer.

parent_document_retriever.py

from langchain.retrievers import ParentDocumentRetriever
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.storage import InMemoryStore
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
tf = lambda t: len(enc.encode(t))  # token length function

# Child splitter — small, for precise embedding + retrieval
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=30,
    length_function=tf,
)

# Parent splitter — large, for rich generation context
parent_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=100,
    length_function=tf,
)

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

# Vector store: holds child chunk EMBEDDINGS + their parent IDs
vectorstore = Chroma(
    collection_name="children",
    embedding_function=embeddings,
)

# Document store: holds full parent chunk TEXT (not embedded)
# In production: use Redis or a SQL table instead of InMemoryStore
docstore = InMemoryStore()

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
    search_kwargs={"k": 5},   # retrieve top-5 children, return their parents
)

# Ingestion: add documents once
retriever.add_documents(docs, ids=None)  # auto-generates IDs
# Internally:
#   1. Splits each doc into parent chunks, stores in docstore with IDs
#   2. Splits each parent into children, embeds, stores in vectorstore
#   3. Each child's metadata["doc_id"] points to its parent in docstore

# Retrieval: returns parent chunks, not children
results = retriever.invoke("when does access end after cancellation")
for r in results:
    n = tf(r.page_content)
    print(f"Parent chunk ({n} tok): {r.page_content[:100]}...")
07 · Choosing Your Strategy

A Decision Framework That
Actually Helps

The wrong chunking strategy can make a well-built RAG system consistently fail. Use these questions to guide your choice — then verify with the evaluation metrics in Module 14.

Interactive Decision Framework

1. Does your document have explicit structural markers? (Markdown headers, HTML tags, Word headings, numbered sections)
→ Use MarkdownHeaderTextSplitter or HTMLHeaderTextSplitter

The structure already encodes your domain knowledge about topic boundaries. Use it. Add a secondary RecursiveCharacterTextSplitter for oversized sections. Follow up with question 2 to decide if you also need parent-child.

→ Continue to question 2
2. Do users ask narrow, specific questions that need precise retrieval but broad context to answer? (e.g., "what is the rate for X" in a 100-page contract)
→ Use ParentDocumentRetriever (parent-child chunking)

This is exactly the scenario parent-child was designed for. Child chunks (200 tok) give precise retrieval. Parent chunks (800-1200 tok) give the LLM the surrounding context it needs to fully answer.

→ Continue to question 3
3. Is ingestion cost / speed critical? (Large corpus, tight budget, need to re-index frequently)
→ Use RecursiveCharacterTextSplitter with token-based length function

No extra API calls during ingestion. chunk_size=400-600 tokens, overlap=60-80 tokens. This is the right default for most production systems.

→ Use SemanticChunker (percentile method, 95th)

Worth the extra embedding cost during ingestion if you have a high-value corpus and quality matters most. Chunks align with actual semantic topics — cleaner embeddings, better retrieval.

08 · Assessment

Module Quiz

These questions test understanding, not recall. Read each scenario carefully.

1. You're building a RAG system over a 500-page medical reference manual. Users ask narrow questions like "what is the dosage range for metformin in type 2 diabetes?" which require a specific value but the answer only makes sense with surrounding clinical context. Which chunking strategy fits best?

✓ Correct. This is exactly the tension parent-child solves. "What is the dosage?" needs precise retrieval (small child chunk with the specific number). "What does this mean clinically?" needs the large parent for context — contraindications, interactions, monitoring parameters that surround the dosage value.

2. A teammate wrote this code: RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50). After testing, chunks are consistently ~125 tokens. What's the bug?

✓ Correct. This is the most common chunking bug. The default length_function is len() which counts characters. 1 character ≈ 0.25 tokens. So chunk_size=500 chars ≈ 125 tokens — 4x smaller than intended. Always pass a token-counting length function.

3. In the ParentDocumentRetriever, child chunks go into the vector store and parent chunks go into the document store. If you reverse this — putting parents in the vector store — what breaks?

✓ Correct. The whole point of parent-child is that small child embeddings are semantically focused — they embed one specific concept. Embedding large parent chunks makes retrieval imprecise for exactly the same reason that 2000-token fixed chunks do.

4. Semantic chunking uses a "95th percentile" threshold. If you lower this to 50th percentile, what happens to your chunks?

✓ Correct. A lower percentile threshold means "split whenever similarity is below the median dissimilarity." Half of all sentence boundaries qualify, producing many tiny chunks. The 95th percentile is standard because it only splits at the 5% most dramatic topic shifts.

5. Your Confluence wiki has 200 articles, each organized with H1 → H2 → H3 headers. After MarkdownHeaderTextSplitter, some H2 sections are still 3000 tokens. What's the correct next step?

✓ Correct. Two-pass splitting is the standard pattern for structured documents: first pass uses headers to get semantic boundaries and build metadata, second pass uses recursive splitter to enforce size limits. The header metadata (h1, h2, h3) is preserved on all sub-chunks.
