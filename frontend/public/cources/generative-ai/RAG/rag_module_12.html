Agentic RAG:
Agents, Tools, and LangGraph

A pipeline executes a fixed sequence. An agent decides what to do next based on what it has seen so far. Agentic RAG gives an LLM a set of retrieval tools — vector search, SQL, web search, calculators — and lets it plan multi-step retrieval strategies, self-correct on failure, and route dynamically to the right data source.

01 · From Pipeline to Agent

What Changes When RAG
Gains the Ability to Think

A RAG pipeline is deterministic: query goes in, retrieval runs once, generation produces output. An agent is adaptive: it sees the query, decides which tool to call, inspects the result, decides whether to call another tool or generate, and can loop until it is confident. The shift from pipeline to agent unlocks multi-hop retrieval, dynamic routing, and self-correction — at the cost of unpredictability and added latency.

Pipeline vs Agent: the fundamental difference

RAG Pipeline (fixed)

User query
↓ Embed query
↓ Vector search (always)
↓ Rerank top-k
↓ Generate answer
Output

Fixed sequence. No decisions. Cannot handle: "I need SQL for part 1 and web search for part 2."

RAG Agent (adaptive)

User query
↓ Think: what tool do I need?
↓ Call: vector_search("refund policy")
↓ Think: do I have enough? No.
↓ Call: sql_query("COUNT refunds Q3")
↓ Think: now I have both. Generate.
Output (multi-source grounded)

Decides tool sequence at runtime. Handles hybrid questions, multi-hop retrieval, self-correction on empty results.

What agents enable

Multi-hop retrieval: retrieve context A, use it to form query for context B
Dynamic routing: pick SQL vs vector based on the question
Self-correction: empty retrieval result triggers query rewrite
Tool composition: calculator + retriever + web search in one answer

What agents cost

Latency: each tool call + reasoning step adds 200ms-2s
Unpredictability: non-deterministic execution paths
Loop risk: agent can call tools indefinitely without exit condition
Cost: more LLM calls per query (reasoning + tool calls + generation)
02 · Agent Architectures

ReAct, Tool-Calling, and
Plan-and-Execute

Three agent architectures dominate production RAG. ReAct interleaves reasoning and action in a single loop. Tool-calling uses function schemas to select tools. Plan-and-execute separates high-level planning from execution, enabling parallelism and better error recovery.

ReAct (Reason + Act)

Yao et al. 2022

The LLM generates Thought: (reasoning), then Action: (tool call), then reads Observation: (tool result), then decides next Thought. Loop until Final Answer: is emitted.

Simple, widely supported. Single LLM call per step. Cannot parallelize tool calls.

Thought: I need the refund policy first.
Action: vector_search("refund policy")
Observation: "Annual plans non-refundable after 30 days"
Thought: Now I need the count. Action: sql_query(...)

Tool-Calling (Function Calling)

OpenAI/Anthropic APIs

The LLM is given a list of tool schemas (name, description, parameters as JSON Schema). It returns a structured tool_call object when it needs a tool. The framework executes the tool and returns the result.

Structured, type-safe, supports parallel tool calls in one LLM response. Native API feature.

LLM response: {tool_calls: [{name:"vector_search",
args:{query:"refund policy"}}]}
Framework executes and returns result
LLM sees result, may call another tool

Plan-and-Execute

LangGraph multi-node

Phase 1: Planner LLM creates a full task list. Phase 2: Executor processes each task, optionally in parallel. Phase 3: Replanner adjusts remaining tasks based on results.

Best for complex multi-step queries. Parallelizable. Higher latency on first step (planning).

Plan: [retrieve_policy, count_refunds, compare_to_avg]
Execute task 1 + task 2 in parallel
Replan if task 2 fails: retry with different SQL
Final synthesis from all completed tasks
03 · Tool Design for RAG Agents

Every Tool Your RAG Agent
Will Need in Production

Tool design is the most impactful engineering decision in agentic RAG. A good tool description tells the LLM precisely when to use it, what it expects, and what it returns. Vague descriptions cause wrong tool selection. Overly specific descriptions cause the agent to miss valid use cases.

🔍 vector_search

Search the Marevlo knowledge base for documents relevant to a question. Use for: policy questions, documentation lookups, explanations of features, how-to questions.

Input: query: str (natural language search query)

Returns: List of relevant text passages with source metadata

📊 sql_query

Execute a read-only SQL query on the Marevlo analytics database. Use for: counting users, aggregating metrics, filtering by date/plan, comparing cohorts. NOT for: document content.

Input: sql: str (valid PostgreSQL SELECT statement, no mutations)

Returns: List of result rows as dicts

🌐 web_search

Search the web for current information not in the Marevlo knowledge base. Use for: industry benchmarks, competitor information, recent events, anything dated after 2024.

Input: query: str (search query)

Returns: List of web result snippets with URLs

🧮 calculate

Evaluate a mathematical expression. Use for: percentage calculations, rate computations, unit conversions. Always use for numeric operations, never compute in your head.

Input: expression: str (e.g. "87/340*100")

Returns: Numeric result as float

📄 get_document

Retrieve a specific document by its ID or filename from the knowledge base. Use when: vector_search returned a relevant document and you need its full text, not just the chunk.

Input: doc_id: str (document identifier from vector_search metadata)

Returns: Full document text as string

💡

The golden rule of tool descriptions

The tool description IS the routing logic. The LLM selects tools based on description similarity to the current reasoning step. Include: (1) what the tool does, (2) when to use it, (3) when NOT to use it, (4) what format the input should be in. "Search documents" is a bad description. "Search the Marevlo knowledge base for policy and documentation questions. NOT for numeric data or user counts." is a good description.

04 · LangGraph: State Machines for RAG

Explicit Control Flow With
Typed State and Conditional Edges

LangChain's LangGraph models agentic workflows as state machines: nodes are Python functions that transform state, edges define transitions, and conditional edges route based on state values. This gives you the flexibility of an agent with the predictability of a pipeline — every possible execution path is visible in the graph definition.

LangGraph core concepts

State

A TypedDict that every node reads from and writes to. All agent state — messages, retrieved documents, tool results, iteration count — lives here. Nodes return partial state updates; LangGraph merges them automatically.

Nodes

Python functions (sync or async) that take state, perform work (call LLM, execute tool, transform data), and return a partial state update dict. Each node is a named step in the workflow.

Edges

Define what runs after a node. Simple edges always go to the same next node. Conditional edges call a function on state and route to different nodes based on the return value (e.g., "tool_call" vs "final_answer").

END

A special node that terminates the graph. A conditional edge must route to END when the agent has produced its final answer; without this exit condition the graph loops forever.

💡

Why LangGraph over LangChain AgentExecutor

AgentExecutor is a black box: you cannot see or modify what happens between tool calls. LangGraph exposes every step as a named node. You can add human-in-the-loop checkpoints, save/restore agent state between sessions, branch on specific conditions, and inspect the full execution trace. For production RAG agents this control is essential.

06 · Multi-Agent Patterns

Orchestrator + Specialist Agents:
Divide and Conquer

A single agent with too many tools becomes unreliable: the LLM must choose between 10+ tools and can select the wrong one. Multi-agent patterns divide responsibility: an orchestrator plans and delegates, and specialist agents handle specific domains (documents, SQL, web search) with a focused set of 2-3 tools each.

Orchestrator + specialist architecture

ORCHESTRATOR AGENT

Receives user query. Decomposes into subtasks. Routes each subtask to the right specialist. Synthesizes final answer from specialist results.

DOCUMENT SPECIALIST

Tools: vector_search, get_document

Handles all policy/documentation questions. Returns cited passages with source metadata.

DATA SPECIALIST

Tools: sql_query, calculate

Handles all quantitative questions. Returns structured data with SQL provenance.

WEB SPECIALIST

Tools: web_search, scrape_url

Handles questions requiring current information. Returns summarized web content with URLs.

💡

When to use multi-agent vs single agent

Use multi-agent when: you have more than 6 tools (LLMs struggle with large tool sets), different tools require different system prompts or LLM sizes, or you want to run specialist agents in parallel. Use single agent when: the task is simple (2-4 tools), you want minimal latency, or the query types are homogeneous.

07 · Guardrails and Loop Prevention

Preventing Infinite Loops,
Runaway Costs, and Bad Tool Calls

Agentic systems can loop indefinitely if not bounded. An agent that keeps searching because it never finds a satisfactory answer will exhaust your API budget in minutes. Production RAG agents need explicit loop guards, tool call validation, and graceful degradation when tools fail.

Failure ModeWhat HappensGuard Mechanism
Infinite tool loopAgent keeps calling tools because it never decides to stop. SQL returns empty → agent rewrites query → still empty → loops.max_iterations: int in graph state. Conditional edge: if iteration > N, route to fallback_answer node regardless of tool result.
Repeated identical tool callsAgent calls vector_search("refund policy") 5 times with the same query. Retrieval is deterministic; results do not change.Track called_tools: List[str] in state. Before tool call, check if identical call was already made. If yes, skip and move forward.
Malformed SQL injectionAgent generates SQL with DROP TABLE or DELETE without WHERE. Executed on production DB.SQL validator: parse generated SQL, reject if it contains mutation keywords (DELETE, DROP, UPDATE, INSERT, TRUNCATE). Return error to agent.
Tool timeoutWeb search or vector search hangs. Agent waits indefinitely.Wrap every tool call with asyncio.wait_for(tool.ainvoke(args), timeout=10). On TimeoutError, return error string to agent state.
Token budget exhaustionLong agent loop accumulates thousands of tokens in message history, exceeding context window.Trim message history: keep only last N tool results and the original query in state. Summarize older tool results before trimming.
⚠️

The max_iterations guard is non-negotiable

Every production LangGraph agent must have a maximum iteration limit enforced at the graph level via a conditional edge that checks iteration count before running the agent node again. Without this, a subtle prompt change or unexpected tool response can send your agent into an infinite billing loop. Set it to 8-12 iterations for most RAG use cases.

08 · Production Code

Full LangGraph RAG Agent
With Tools, Guards, and State

agentic_rag.py

from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from langchain_anthropic import ChatAnthropic
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage, AIMessage
import operator

# ── State definition ─────────────────────────────────────────
class AgentState(TypedDict):
    messages: Annotated[list, operator.add]  # append-only message history
    iteration: int
    max_iterations: int

# ── Tool definitions ─────────────────────────────────────────
@tool
def vector_search(query: str) -> str:
    """Search the knowledge base for policy/documentation questions.
    Use for: policy questions, feature explanations, how-to guides.
    NOT for: numeric data, user counts, or time-series metrics."""
    results = retriever.invoke(query)
    return "

".join(d.page_content for d in results[:3])

@tool
def sql_query(sql: str) -> str:
    """Execute a read-only SQL query on the analytics database.
    Use for: counting users, aggregating metrics, filtering by date.
    MUST be a SELECT statement. No mutations allowed."""
    if not sql.strip().upper().startswith("SELECT"):
        return "ERROR: Only SELECT statements are allowed."
    result = db.run(sql)
    return str(result)

tools = [vector_search, sql_query]
llm = ChatAnthropic(model="claude-sonnet-4-20250514").bind_tools(tools)

# ── Nodes ────────────────────────────────────────────────────
def agent_node(state: AgentState) -> dict:
    response = llm.invoke(state["messages"])
    return {"messages": [response], "iteration": state["iteration"] + 1}

# ── Conditional edge: continue or stop ───────────────────────
def should_continue(state: AgentState) -> Literal["tools", "end"]:
    last = state["messages"][-1]
    if state["iteration"] >= state["max_iterations"]:
        return "end"  # hard stop: max iterations reached
    if hasattr(last, "tool_calls") and last.tool_calls:
        return "tools"  # LLM wants to call tools
    return "end"  # LLM produced final answer

# ── Graph assembly ────────────────────────────────────────────
graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", ToolNode(tools))
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", should_continue,
    {"tools": "tools", "end": END})
graph.add_edge("tools", "agent")  # tools always return to agent
app = graph.compile()

# ── Run ──────────────────────────────────────────────────────
result = app.invoke({
    "messages": [HumanMessage(content="Refund policy for Teams users?")],
    "iteration": 0,
    "max_iterations": 8
})
print(result["messages"][-1].content)
09 · Assessment

Module 12 Quiz

1. A user asks: "What is the refund policy, and what percentage of Teams users claimed it in Q3?" A pipeline-based RAG system returns a document about the refund policy but cannot answer the percentage. What is the root cause and the fix?

Correct. This is the canonical agentic RAG use case: a single pipeline run cannot satisfy both halves of the question. An agent equipped with vector_search and sql_query tools can: step 1 retrieve the policy, step 2 run the SQL count, step 3 compute the percentage using the calculate tool, step 4 synthesize all results into a single grounded answer.

2. Your LangGraph agent runs 40 tool calls on a single query before running out of context window. What was the missing mechanism and how do you implement it?

Correct. Max iteration guards are non-negotiable in production LangGraph agents. Without them, a subtle prompt ambiguity or unexpected tool response can loop the agent indefinitely. The guard must live in the conditional edge function (not just the agent prompt) because prompt-based stops are unreliable — the LLM can ignore them. The iteration counter in state is the authoritative stop signal.

3. You are writing a tool description for vector_search. Which description is better and why?

Correct. Tool descriptions are the routing logic. The LLM selects tools by matching the current reasoning step to tool descriptions. "NOT for: user counts, revenue figures" explicitly teaches the boundary between vector_search and sql_query. Without this, the agent will try vector_search for "how many users enrolled" and get irrelevant policy passages instead of running SQL.

4. In the Plan-and-Execute architecture, when does the Replanner run and what does it do?

Correct. The Replanner is the adaptive intelligence in Plan-and-Execute. The Planner creates an initial task list based on the query alone. The Replanner sees actual results and can adapt: if a tool returned empty results, the replanner might retry with a different query; if a tool returned more information than expected, it might remove previously planned tasks that are now redundant.

5. Why does a multi-agent system (orchestrator + specialists) handle large tool sets better than a single agent with all tools?

Correct. LLM tool selection accuracy degrades with the number of tools. Research shows selection accuracy drops significantly beyond 6-8 tools. Multi-agent architecture solves this by partitioning: the orchestrator selects a specialist (3 choices), the specialist selects a tool (2-3 choices within its domain). Each selection step is from a small, distinguishable set, yielding much higher combined accuracy than a 15-tool single-agent setup.
