Production RAG:
Observe, Cache, and Scale

A RAG system that works in a notebook is not a production system. Production adds ten new dimensions: observability to diagnose failures, caching to control costs, streaming to meet latency budgets, horizontal scaling to handle load, and cost modeling to keep the economics viable. This module covers each systematically.

02 · Observability with LangSmith

Every Query Traced:
Spans, Latency, and Eval Runs

LangSmith captures every step in your RAG pipeline as a hierarchical trace: the root span is the full query, child spans are retrieval, reranking, and generation, and each span records input, output, latency, and token counts. This makes debugging a failed query a matter of clicking into the trace rather than adding print statements.

What a LangSmith trace contains

    ● BM25Retriever [3ms | top: "non-refundable after 30 days"]
    ● DenseRetriever (HNSW) [21ms | top similarity: 0.912]

Latency breakdown

Identify which stage is slow. Retrieval 127ms (9%) vs generation 1085ms (76%). Optimization target is clear: generation dominates, so stream it.

Token accounting

Every LLM call logs input + output tokens. Multiply by price/token to get per-query cost. Sum across queries for daily cost. Alert on cost spikes.

Inline evaluation

Run RAGAS metrics on every production query (sample 10% for cost). Track faithfulness and relevancy trends. Alert when mean faithfulness drops below threshold.

03 · Semantic Caching

Exact Cache Plus Semantic Cache:
Targeting 30-50% Hit Rate

Caching is the highest-ROI optimization in production RAG. A cache hit costs ~0.1ms and $0. A fresh query costs 300-1500ms and $0.001-$0.01. Even a 30% cache hit rate cuts costs and median latency by nearly a third. Two caching layers work in tandem: exact matching for repeated queries and semantic matching for paraphrased equivalents.

Layer 1: Exact cache (Redis)

Hash the normalized query string (lowercase, stripped whitespace). Store (hash, full response) in Redis with TTL. Hit rate: 15-25% of production queries are exact repeats. Cost: ~$0.02/GB/month Redis storage.

key = hashlib.md5(query.strip().lower()
            .encode()).hexdigest()
cached = redis.get(f"rag:exact:{key}")
if cached: return json.loads(cached)
# Miss: run pipeline, then store:
redis.setex(f"rag:exact:{key}",
          ttl=86400, value=json.dumps(result))

Layer 2: Semantic cache (vector similarity)

Embed the query. Search a cache vector store for similar past queries (cosine > 0.95 threshold). Hit rate: additional 10-20% catch of paraphrased repeats. "Can I get a refund?" matches "Is my plan refundable?"

q_vec = embed(query)
hits = cache_store.similarity_search_with_score(
    q_vec, k=1, score_threshold=0.95)
if hits:
  cached_q, score = hits[0]
  return cached_q.metadata["response"]
# Miss: run pipeline, add to cache store:
cache_store.add_texts([query],
    metadatas=[{"response": json.dumps(result)}])

Cache invalidation strategy

TTL-based: Set TTL based on content volatility: pricing pages = 1 hour TTL, legal policies = 24 hours TTL, stable documentation = 7 days TTL.
Event-based: On document update/delete in your CMS/knowledge base, purge cache entries whose source_doc_id matches the updated document.
Version-based: Include your retriever model version in the cache key (e.g., "rag:v2:exact:{hash}"). Changing embedding models automatically invalidates all cached responses.
04 · Streaming

Token-by-Token to the Client:
SSE and WebSocket Patterns

Users perceive latency from the first token, not the last. Without streaming, a 3-second response feels like 3 seconds of waiting. With streaming, the first token arrives in ~400ms (retrieval + LLM prefill time) and the user reads at generation speed. Streaming cuts perceived latency by 5-10x for typical answer lengths.

Server-Sent Events (SSE)

Best for: REST APIs, simple integrations. One-way server-to-client. Built into browsers. HTTP/1.1 compatible. EventSource API on the client.

GET /chat?question=... → HTTP 200
Content-Type: text/event-stream
data: {"token": "Annual"}
data: {"token": " subscriptions"}
data: {"token": " are"}
data: [DONE]

WebSocket

Best for: multi-turn conversations, bidirectional. Lower overhead per message. Requires WebSocket-capable server (FastAPI, Starlette). Persistent connection per session.

ws.send({"question": "..."})
ws.onmessage: {"token": "Annual"}
ws.onmessage: {"token": " subscriptions"}
ws.onmessage: {"type": "done", "citations": [...]}
ws stays open for next turn
💡

What to stream and what not to stream

Stream: LLM generation tokens. Do NOT stream: retrieval results or reranker scores (users do not see these). The latency-reduction comes from starting to show text while generation continues. Always buffer the full response server-side too (for logging, caching, and RAGAS evaluation) even while streaming tokens to the client.

05 · Latency Budget

Where Time Goes and
How to Cut Each Stage

RAG latency is the sum of four stages: embedding the query, retrieval, reranking, and generation. Most developers assume generation dominates. It does for short answers, but for a production hybrid + reranking pipeline, retrieval can represent 30-40% of total latency. Optimize based on measurement, not assumption.

Latency breakdown: full hybrid + reranking pipeline

StageTypicalCut it by
Query embedding8-15msCache query embeddings for repeated queries. Use smaller embedding model (bge-small vs bge-large saves 60%).
BM25 retrieval1-3msAlready fast. Ensure tokenization is pre-computed at index time.
Dense ANN search15-30msUse HNSW ef_search=64 (lower = faster, higher = more accurate). Deploy Qdrant on GPU for 3x speedup.
RRF fusion1-2msPure Python list ops. No optimization needed.
Cross-encoder reranking150-300msBatch all candidates in single forward pass. Use MiniLM-L-6 (22M params) instead of BGE-large (560M) if quality permits. Run on GPU.
LLM generation400-2000msStream (perceived latency ÷ 5-10x). Use flash attention. Reduce context window (compression). Cache repeated queries.

💡

The async imperative

Every I/O call in your RAG pipeline (vector search, LLM API, SQL query, Redis cache) must be awaited asynchronously. A single synchronous blocking call in an async FastAPI handler blocks the entire event loop, causing all other concurrent requests to wait. Profile with pytest-asyncio and asyncio debug mode to find sync-in-async violations.

07 · Cost Model

Per-Query Economics:
Token Counting, Caching ROI, Tradeoffs

Production RAG cost has three components: embedding cost (query + indexing), reranker cost (API or compute), and LLM cost (input tokens = context + query, output tokens = answer). Understanding each lets you make informed quality-vs-cost tradeoffs.

Per-query cost breakdown (Claude Sonnet 4 pricing, approximate)

Query embedding (bge-large-en-v1.5)

1%

Self-hosted GPU: ~$0.0000003 per query. Negligible.

2%

Self-hosted: infrastructure cost ~$0.000001 per query at 1K QPS. Negligible.

Cross-encoder reranking (BGE)

15%

Self-hosted GPU: ~$0.00002 per query (100 docs). Cohere API: $0.001 per 100 docs.

LLM input tokens (3 chunks × 400 tokens + 50 token query)

55%

1,250 tokens × $3/M = $0.00375

LLM output tokens (200 token answer)

44%

200 tokens × $15/M = $0.003

Total per query (no cache)

100%

~$0.0068 without reranker | ~$0.0088 with Cohere rerank

Caching ROI at 35% hit rate

Without cache: 1000 queries × $0.0068 = $6.80/day
With 35% cache hit: 650 full queries ($4.42) + 350 cache hits ($0.01) = $4.43/day
Savings: $2.37/day (35%). At 100K queries/day: $237/day = $86K/year.

When to skip the cross-encoder reranker

Cohere Rerank adds $0.001 per query (12% cost increase). Worth it when: retrieval precision is low (< 0.7 NDCG). Skip when: corpus is small and well-structured, precision already high, or cost sensitivity is high.

08 · Production Code

LangSmith Tracing, Redis Cache,
and Async Streaming Chain

production_rag.py

import os, hashlib, json, asyncio
from langsmith import traceable
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
import redis.asyncio as aioredis
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

# ── LangSmith setup ───────────────────────────────────────────
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "YOUR_LANGSMITH_KEY"
os.environ["LANGCHAIN_PROJECT"] = "marevlo-rag-prod"

# ── Redis async client ────────────────────────────────────────
redis_client = aioredis.from_url("redis://localhost:6379")

# ── Cache helpers ─────────────────────────────────────────────
async def cache_get(query: str) -> str | None:
    key = f"rag:v1:{hashlib.md5(query.strip().lower().encode()).hexdigest()}"
    cached = await redis_client.get(key)
    return json.loads(cached) if cached else None

async def cache_set(query: str, result: dict, ttl: int = 3600) -> None:
    key = f"rag:v1:{hashlib.md5(query.strip().lower().encode()).hexdigest()}"
    await redis_client.setex(key, ttl, json.dumps(result))

# ── Traced RAG function ───────────────────────────────────────
@traceable(name="rag_pipeline")  # auto-traces to LangSmith
async def rag_query(question: str) -> dict:
    # Check exact cache first
    cached = await cache_get(question)
    if cached: return {**cached, "cache_hit": True}

    # Parallel: embed + BM25 simultaneously
    embed_task = asyncio.create_task(embedder.aembed_query(question))
    bm25_task = asyncio.create_task(bm25.ainvoke(question))
    q_vec, bm25_docs = await asyncio.gather(embed_task, bm25_task)

    dense_docs = await vectorstore.asimilarity_search_by_vector(q_vec, k=20)
    all_docs = rrf_merge(bm25_docs, dense_docs)  # RRF fusion
    reranked = await reranker.arerank(question, all_docs[:20])
    context = format_context(reranked[:5])  # top-5 after reranking

    llm = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)
    answer = await (RAG_PROMPT | llm | StrOutputParser()).ainvoke(
        {"context": context, "question": question})

    result = {"answer": answer, "cache_hit": False}
    await cache_set(question, result)
    return result

# ── FastAPI streaming endpoint ────────────────────────────────
app = FastAPI()

@app.get("/chat")
async def chat_stream(question: str):
    async def event_stream():
        cached = await cache_get(question)
        if cached:
            yield f"data: {json.dumps({'text': cached['answer'], 'cache_hit': True})}\n\n"
            return
        docs = await hybrid_retriever.ainvoke(question)
        context = format_context(docs)
        full_response = ""
        async for chunk in llm.astream(
            RAG_PROMPT.format_messages(context=context, question=question)):
            full_response += chunk.content
            yield f"data: {json.dumps({'token': chunk.content})}\n\n"
        await cache_set(question, {"answer": full_response})
        yield "data: [DONE]\n\n"
    return StreamingResponse(event_stream(), media_type="text/event-stream")
09 · Assessment

Module 13 Quiz

1. LangSmith shows your RAG query takes 1.8s total: embedding 12ms, retrieval 140ms, reranking 280ms, generation 1,368ms. Where should you focus optimization?

Correct. Measure before optimizing. At 76% of total time, generation is the primary target. Streaming is the highest-impact intervention: it converts a 1.8s blocked wait into a response that starts appearing in ~400ms. After streaming, if further latency reduction is needed, context compression reduces prefill time (fewer input tokens = faster to start generating).

2. Your production RAG system has a 35% cache hit rate. How does semantic caching capture hits that exact hashing would miss?

Correct. Exact caching only hits on character-for-character matches (after normalization). In practice, users paraphrase the same question in many ways. Semantic caching finds near-duplicate queries by embedding similarity. The threshold (0.95 cosine) must be tuned: too low (0.85) catches unrelated questions and serves wrong cached answers; too high (0.99) barely improves over exact matching.

3. A user on your platform reports answers appear slowly. LangSmith shows generation starts at t=1.4s but the full answer arrives at t=3.2s. What is the single highest-impact fix?

Correct. The generation pipeline already starts producing tokens at t=1.4s. Without streaming, the client receives nothing until t=3.2s. With streaming, tokens start arriving at t=1.4s. The 1.8s generation time has not changed, but perceived latency drops by 56% (1.4s vs 3.2s). This is the fastest, highest-impact production improvement for any RAG system that currently buffers responses.

4. You are calculating per-query cost. Your query results in 1,200 input tokens and 300 output tokens. Claude Sonnet 4 costs $3/M input and $15/M output. What is the LLM cost per query?

Correct. Input and output tokens are priced differently: output tokens cost 5x more than input tokens for Claude Sonnet 4. This makes long answers significantly more expensive than long contexts. Practical implication: adding 200 extra output tokens (a longer answer) costs $0.003, while adding 200 extra input tokens (another context chunk) costs $0.0006. Constrain output length more aggressively than input length to control costs.

5. You have a synchronous call to an external embedding API inside an async FastAPI endpoint. What is the production impact and how do you fix it?

Correct. This is the most common production async mistake. A single sync call in an async handler degrades concurrency for ALL users, not just the one making the request. At 100 concurrent users, 100 queries are all blocked waiting for one sync operation to complete before the next can start. asyncio.to_thread() is the correct escape hatch for sync libraries: it moves the blocking call to a thread pool, freeing the event loop to process other requests.
