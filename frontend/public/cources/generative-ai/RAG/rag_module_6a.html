01 · The Inverted Index

Why Sparse Retrieval Scales to
Billions of Documents

Before touching BM25, understand why it is fast. Naive search compares your query against every document: O(N) per query. Sparse retrieval uses an inverted index — a data structure mapping each unique term to the list of documents containing it. Query time becomes O(query terms), completely independent of corpus size. Google answers queries over 50 billion pages in milliseconds using this structure.

Our 4-document corpus — click any term to explore the index

D1"annual subscriptions are non-refundable after thirty days"
D2"monthly subscriptions can be cancelled any time"
D3"refund requests must include your annual subscription id"
D4"enterprise support handles annual contract refund disputes"

Click a term to see its posting list

Each term maps to a posting list: documents containing it with positions. For query "annual refund", the system intersects posting lists for both terms in microseconds, regardless of how large the corpus is.

💡

How the index makes BM25 scale

Without an index: "annual refund" against 1M documents reads all 1M. With the index: look up "annual" (D1,D3,D4) and "refund" (D3,D4). Only 3-4 documents need BM25 computation. Index lookup is O(1) per term. This is why Elasticsearch handles 100M documents with sub-second query latency.

02 · TF-IDF From Scratch

Term Frequency ×
Inverse Document Frequency

TF-IDF answers two questions: how often does this term appear in this document (TF), and how rare is this term across the whole corpus (IDF)? Common words like "the" appear in every document so their IDF is near zero. A rare, domain-specific term appearing many times in one document gets both high TF and high IDF: it is a diagnostic signal for that document.

Raw TF

TF(t,d) = count(t in d)

Simply count occurrences. Problem: biased toward long documents. A 1000-word doc always has higher raw counts than a 100-word doc on the same topic.

TF("annual", D1) = 1

Normalized TF

TF(t,d) = count(t) / |d|

Divide by total words. Now 3 occurrences in a 10-word doc scores higher than 3 in a 100-word doc. Fixes length bias. Most commonly used in practice.

TF("annual", D1) = 1/7 = 0.143

Log TF

TF(t,d) = 1 + log(count)

Log-dampens high frequencies. A term appearing 100 times should not score 100x more than one appearing once. Diminishing returns. BM25 formalizes this saturation idea.

TF=10 → 1+log(10) = 3.30

IDF(t) = log( N / df(t) )
N = total documents  ·  df(t) = number of documents containing term t
BM25 smoothed IDF: log( (N − df(t) + 0.5) / (df(t) + 0.5) + 1 )    prevents log(0) and smooths extreme values

⚠️

TF-IDF's two problems BM25 fixes

Problem 1: Unbounded TF. A document mentioning "refund" 50 times scores 50x higher than one mentioning it once. After the first mention you know it is about refunds; the extra 49 add almost nothing. TF-IDF does not model diminishing returns.

Problem 2: No length normalization. A 10,000-word document can score higher than a focused 100-word document purely by virtue of being longer, even if the short one is more on-topic.

03 · BM25 Formula — Every Parameter Explained

The Formula That Fixed
TF-IDF's Problems

BM25 (Best Match 25) was developed at City University London in the 1990s by Robertson and Jones. "25" refers to it being the 25th iteration in a series of probabilistic ranking models. It adds two precise mechanisms to TF-IDF: a saturation ceiling on term frequency controlled by k1, and document length normalization controlled by b.

BM25(D,Q) = Σt in Q  IDF(t)  ·  TF(t,D) · (k1+1) / (TF(t,D) + k1 · (1 − b + b · |D| / avgdl))
IDF(t) = log[(N − df(t) + 0.5) / (df(t) + 0.5) + 1] — term rarity score
TF(t,D) = raw count of term t in document D (integer)
k1 = saturation parameter, default 1.2–2.0. Higher = more weight to high TF.
b = length normalization strength, default 0.75. 0 = disabled, 1 = full normalization.
|D| = word count of document D    avgdl = average doc length across corpus

k1: Saturation Parameter — What It Does

As TF grows toward infinity, the TF component TF × (k1+1) / (TF + k1) approaches a ceiling of (k1 + 1). With k1=1.2 the ceiling is 2.2. A document where "refund" appears 1000 times gets a TF component of 2.18 — barely more than a document where it appears once (1.00). This prevents spam repetition from winning.

k1=0: binary (present/absent only). k1=infinity: reduces to raw TF, no saturation.

b: Length Normalization — What It Does

The denominator includes k1 × (1 − b + b × |D|/avgdl). When a document is 2x longer than average and b=0.75: this factor = 0.25 + 0.75 × 2 = 1.75. The effective TF is divided by 1.75 — longer documents must have proportionally more occurrences to score the same as shorter ones.

b=0: length has zero effect. b=0.75: standard tradeoff. b=1.0: fully normalized by length.

06 · BM25 Variants

When Standard BM25
Needs Adjustment

BM25 (Okapi) has a subtle flaw for very long documents: the length normalization factor in the denominator can grow so large that a matching term contributes near-zero score, even if the document is highly relevant. BM25+ and BM25L were designed to fix this specific edge case.

VariantProblem FixedKey ChangeWhen to Choose It
BM25 OkapiTF-IDF unbounded TF and length biasTF saturation via k1, length norm via b. The standard.Default choice. Works in Elasticsearch, Opensearch, rank_bm25, Whoosh, Lucene
BM25+Very long documents penalized so hard that TF component approaches zero for any termAdds floor parameter delta (default 1.0) ensuring every matching term contributes at least deltaCorpora with extreme length variance: mix of 50-word FAQ answers and 50,000-word contracts
BM25LDenominator grows too fast for documents at 5x-10x average lengthReplaces length ratio with a smoothed, capped version that grows sub-linearly past a thresholdAll-long corpora: every document is 5,000+ tokens (legal manuals, technical specs)
BM25-AdptSingle global k1 is wrong for all terms: common terms need low k1, rare terms need high k1Learns a per-term k1 from labeled corpus statisticsWhen you have labeled relevance judgments for tuning. Rarely used in production RAG.
07 · When BM25 Wins and When It Fails

Knowing These Limits Tells You
When to Add Dense Retrieval

✓ BM25 wins here

Exact technical identifiers

"GET /api/v2/users 404" or "CVE-2024-1234". These must match exactly. Dense models embed "404" near "error" and return wrong results. BM25 requires the exact token to be present.

Drug names, product codes, formulas

"metformin 500mg", "H2SO4", "iPhone 15 Pro Max". Semantic similarity would blur these into related-but-wrong entities. Exact match is what is required.

Zero training data (day-one deployment)

Dense models need fine-tuning or in-domain training to perform well. BM25 requires nothing except the documents themselves. Instant deployment.

Low-resource languages

No embedding model exists for your language? BM25 works on any Unicode text. Character n-grams extend it to morphologically rich languages.

CPU-only, cost-constrained environments

BM25 on CPU: microsecond latency on millions of documents. Dense retrieval requires GPU or expensive ANN infrastructure (Pinecone, Weaviate, Qdrant).

✗ BM25 fails here

Synonyms and abbreviations

Query "MI" does not match "myocardial infarction". No shared tokens = score of zero. The most relevant document in your corpus may be completely invisible to BM25.

Semantic intent and paraphrase

Query "how to fix authentication not working" vs document "troubleshoot login failures". Same meaning, different tokens. BM25 returns near-zero score for a perfectly relevant result.

Cross-lingual retrieval

Hindi query against English documents: zero results. No Unicode overlap between different language scripts without explicit translation preprocessing.

Abstract or conceptual queries

"What is our company culture?" The answer is distributed across many documents using varied vocabulary. BM25 cannot aggregate meaning across different phrasings of the same idea.

Single ambiguous token queries

Query: "policy". Appears in hundreds of documents. All get similar low-IDF scores. Intent and context are completely invisible to a lexical model.

08 · Production Code

BM25 From Installation
to LangChain Integration

bm25_production.py

from rank_bm25 import BM25Okapi, BM25Plus
from langchain_community.retrievers import BM25Retriever
from langchain.schema import Document
import re

# ── Tokenization is as important as the algorithm ─────────────
# BM25 is exact-match. "Refunds" and "refund" are DIFFERENT tokens.
# Your tokenizer determines what matches. Design it carefully.
def tokenize(text: str) -> list:
    text = text.lower()
    text = re.sub(r'[^\w\s]', ' ', text)   # remove punctuation
    tokens = text.split()
    stopwords = {'the', 'is', 'a', 'an', 'and',
                 'or', 'of', 'in', 'to', 'for', 'be'}
    tokens = [t for t in tokens if t not in stopwords]
    # Optional: add stemming so "refunds" matches "refund"
    # from nltk.stem import PorterStemmer
    # tokens = [PorterStemmer().stem(t) for t in tokens]
    return tokens

corpus = [
    "Annual subscriptions are non-refundable after the 30-day trial.",
    "Monthly subscriptions may be cancelled at any time.",
    "Refund requests must include your annual subscription ID.",
    "Enterprise support handles annual contract refund disputes.",
]
tokenized = [tokenize(doc) for doc in corpus]

# ── BM25Okapi with explicit parameters ────────────────────────
bm25 = BM25Okapi(tokenized, k1=1.2, b=0.75)
scores = bm25.get_scores(tokenize("annual refund"))
ranked = sorted(enumerate(scores), key=lambda x: -x[1])
for rank, (idx, score) in enumerate(ranked, 1):
    print(f"#{rank} [{score:.4f}] {corpus[idx][:65]}")

# ── BM25Plus: better for variable-length corpora ──────────────
bm25plus = BM25Plus(tokenized, k1=1.2, b=0.75, delta=1.0)

# ── LangChain integration: drop-in retriever for RAG chain ────
docs = [Document(page_content=c, metadata={"id": i, "dept": "legal"})
        for i, c in enumerate(corpus)]

bm25_retriever = BM25Retriever.from_documents(
    docs,
    k=3,                        # top-3 results
    preprocess_func=tokenize,    # inject custom tokenizer
)
results = bm25_retriever.invoke("annual refund policy")

# ── Metadata-aware: filter corpus before BM25 ─────────────────
# BM25 itself is not metadata-aware. Filter first, then index.
def filtered_search(query: str, all_docs: list, fn) -> list:
    subset = [d for d in all_docs if fn(d)]
    if not subset: return []
    r = BM25Retriever.from_documents(subset, k=5,
            preprocess_func=tokenize)
    return r.invoke(query)

legal = filtered_search("refund clause", docs,
            lambda d: d.metadata["dept"] == "legal")
09 · Assessment

Module 6A Quiz

Questions that require applying the math, not recalling definitions.

1. Document D has TF("refund")=1. Document E has TF("refund")=20. With k1=1.2, what is the approximate ratio of their BM25 TF components?

Correct. D: TFcomp = 1x2.2/(1+1.2) = 1.00. E: TFcomp = 20x2.2/(20+1.2) = 2.08. Ratio 1:2.08, not 1:20. The extra 19 occurrences contributed only 1.08 score units. This is why BM25 resists keyword stuffing: repeating a term many times gives rapidly diminishing returns.

2. You set b=0 in BM25. A 10,000-word legal brief mentions "indemnification" once. A 60-word clause also mentions it once. Which scores higher for query "indemnification"?

Correct. When b=0: the denominator simplifies to TF(t,D) + k1 x 1. The length term (1-b+b x |D|/avgdl) becomes just 1, regardless of |D|. Both documents have TF=1 so their TF components are identical. b=0 is almost always wrong for production use because it lets a 100,000-token document with one mention of a term compete evenly with a 50-token focused document.

3. Query: "Python programming". In a corpus of 1,000,000 docs: "Python" has df=1,000, "programming" has df=400,000. Compute the approximate IDF ratio between them.

Correct. IDF("Python") = log(1,000,000/1,000) = log(1000) = 6.91. IDF("programming") = log(1,000,000/400,000) = log(2.5) = 0.92. Python is 7.5x more discriminating. A document matching "Python" specifically is far more likely to be a Python tutorial than a document matching "programming" is. IDF quantifies exactly how much information each term carries.

4. You switch from BM25Okapi to BM25Plus for a legal corpus where documents range from 500 to 80,000 tokens. What specific problem are you fixing?

Correct. The "lower-bounding problem": when |D|/avgdl = 16, the denominator factor = 1.2 x (0.25 + 0.75 x 16) = 14.7. TFcomp for TF=1 = 2.2/15.7 = 0.14. A highly relevant legal clause buried in an 80,000-word contract barely contributes. BM25+ floor delta ensures it always contributes at least 1.0, keeping long-document matches visible.

5. A medical RAG system has query "heart attack" but all relevant documents use "acute myocardial infarction". Tuning k1 and b extensively does not fix retrieval. Why not?

Correct. k1 and b weight how term frequency and document length affect scoring. They have zero effect when TF=0. No BM25 variant can bridge vocabulary gaps. This is why Module 6B (Dense Retrieval) exists: transformers learn that "heart attack" and "myocardial infarction" are semantically equivalent and return a high similarity score even with zero token overlap.
