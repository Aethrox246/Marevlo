01 · Why Hybrid Search Consistently Wins

Two Retrievers, Complementary Signals,
One Better Ranking

From the BEIR benchmark results in Module 6C, hybrid search outperformed both BM25 and dense retrieval alone on 7 of 8 datasets. This is not coincidence. BM25 and dense bi-encoders fail on entirely different query types. Their union catches what either alone misses — and their intersection provides high-confidence results that both agree on.

The complementarity argument with numbers

Query: "annual refund" — BM25 ranking

#1D3: "refund requests must include annual subscription id"0.870
#2D4: "enterprise support handles annual refund disputes"0.870
#3D1: "annual subscriptions non-refundable after thirty days"0.435
#4D2: "monthly subscriptions cancelled any time"0.000

BM25 ranks D3=D4 top (both contain "annual" AND "refund"). D1 is #3 because "non-refundable" != "refund" without stemming. D2 = 0.

Query: "how do I get a refund" — Dense ranking

#1D1: "annual subscriptions are non-refundable after thirty days"0.91
#2D3: "refund requests must include your annual subscription id"0.88
#3D4: "enterprise support handles annual contract refund disputes"0.85
#4D2: "monthly subscriptions may be cancelled any time"0.54

Dense ranks D1 as #1 because "non-refundable" is semantically near "refund". It retrieves relevant docs even without exact token overlap.

💡

Hybrid search captures what both miss individually

BM25 missed D1 (third place) on the keyword query because "non-refundable" != "refund". Dense retrieved D1 first. On exact-match queries (product codes, error strings), BM25 is precise and dense is noisy. Hybrid search fuses both ranked lists: documents appearing high in BOTH lists rank highest, and documents appearing in only one list still get credit.

02 · Hybrid Search Architecture

How the Pipeline Fits Together:
From Query to Fused Ranking

Hybrid search runs two retrieval paths in parallel and merges them with a fusion algorithm. The merge can happen at different stages: score-level fusion (requires compatible scores), rank-level fusion (RRF, works with any scores), or learned fusion (trained on labeled data). Most production systems use rank-level fusion because it requires no score normalization.

Why parallel, not sequential

Both retrievers run on the same query simultaneously. The BM25 index lookup takes ~1ms; the dense ANN search takes ~20ms. Running them in parallel adds almost no latency over the dense retrieval alone. Sequential would double latency. In production, async tasks or threading handles this.

03 · Reciprocal Rank Fusion — The Formula

RRF Derived: Why Rank Position
Beats Raw Scores

Reciprocal Rank Fusion (Cormack, Clarke, Buettcher 2009) fuses ranked lists by position rather than raw score. This solves a critical problem: BM25 scores (0.0 to ~2.0) and cosine similarity scores (0.0 to 1.0) are not comparable. You cannot simply add them. But you CAN compare rank positions, and RRF does exactly that.

RRF(d) = Σr ∈ R   1 / (k + rankr(d))
rankr(d) = position of document d in ranked list r (1-indexed: rank 1 = top result)
k = smoothing constant, default 60 (from the original paper, explains below)
R = set of ranked lists (e.g. {BM25_ranking, dense_ranking})

Final fused ranking: sort all documents by their RRF score descending. Higher = more relevant.

Why k=60? The intuition behind the smoothing constant

Without k (k=0), the score for rank 1 would be 1/1 = 1.0 and rank 2 would be 1/2 = 0.5. This gives excessive weight to tiny rank differences at the top. A document ranked #1 by both retrievers would score 2.0; ranked #1 and #2 would score 1.5. Too volatile.

With k=60, rank 1 → 1/61 = 0.0164, rank 2 → 1/62 = 0.0161. The difference is tiny (2%). Even a document ranked #10 gets 1/70 = 0.0143 — 87% of the top result's score. This makes RRF robust to small ranking disagreements.

05 · Score Fusion Alternatives

Beyond RRF: When to Use
Score-Based Fusion Methods

RRF is the default choice because it requires no score normalization and is robust to score scale mismatches. But there are situations where score-level fusion methods outperform rank-level RRF — particularly when the scores from both retrievers are well-calibrated and meaningful.

Score normalization: required before CombSUM

BM25 scores range 0 to ~5. Cosine scores range -1 to 1. You cannot add these directly. Two approaches:

Min-Max normalization

norm(s) = (s − min) / (max − min)

Maps all scores to [0, 1]. Problem: sensitive to outliers. A single very high BM25 score compresses all other scores toward zero.

Z-score normalization

norm(s) = (s − mean) / std

Robust to outliers. Can produce negative normalized scores for below-average documents.

CombSUM

CombSUM(d) = Σr norm_scorer(d)

Add normalized scores. Works well when both retrievers produce well-calibrated relevance estimates. Requires normalization step. More sensitive to score quality than RRF.

CombMNZ (recommended over CombSUM)

CombMNZ(d) = CombSUM(d) × n_nonzero(d)

Multiply by the count of retrievers that returned d with a non-zero score. Rewards documents that appear in multiple retriever results. Consistently outperforms CombSUM in TREC evaluations.

Weighted RRF (most practical)

wRRF(d) = Σr wr × 1/(k + rankr(d))

Add weights to each retriever. w_BM25=0.3, w_dense=0.7 for semantic-heavy corpora. w_BM25=0.7, w_dense=0.3 for exact-match-heavy corpora. Tune based on query type distribution.

07 · Asymmetric Weighting

When to Boost BM25 vs Dense:
Query Type Distribution

The default w_BM25=0.5, w_dense=0.5 is a reasonable starting point but suboptimal for most real corpora. Analyze your query logs to understand the distribution of query types, then tune weights accordingly.

Use CaseQuery ExamplesRecommended WeightsRationale
Developer documentation / APIs"GET /users 401", "authentication error", "rate limit exceeded"w_BM25=0.7, w_dense=0.3Error codes and endpoint paths must match exactly. Dense generalizes these away.
Medical / scientific literature"MI", "myocardial infarction", "statin therapy", "reduce cholesterol"w_BM25=0.3, w_dense=0.7High abbreviation use, paraphrase, and synonym density. Dense handles all of these.
General enterprise knowledge base"vacation policy", "how to submit expenses", "org chart"w_BM25=0.4, w_dense=0.6Mix of keyword and semantic queries. Slight dense preference for natural language questions.
E-commerce product catalog"Sony WH-1000XM5", "noise cancelling headphones under 200", "best earbuds"w_BM25=0.6, w_dense=0.4Specific model numbers and brand names need exact match. Generic queries benefit from dense.
Legal contracts / compliance"force majeure clause", "indemnification", "GDPR article 17"w_BM25=0.7, w_dense=0.3Legal terms and article citations must match exactly. Semantic generalization can retrieve wrong clauses.
Customer support chat logs"my package hasn't arrived", "I want to return this", "subscription renewal"w_BM25=0.2, w_dense=0.8Highly paraphrased, conversational, intent-based. Dense retrieval handles this domain best.
08 · Production Code

LangChain EnsembleRetriever
and Qdrant Native Hybrid Search

hybrid_search.py

from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever
from langchain_community.vectorstores import Qdrant
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain.schema import Document
import re

# ── Our corpus ────────────────────────────────────────────────
corpus = [
    "Annual subscriptions are non-refundable after the 30-day trial.",
    "Monthly subscriptions may be cancelled at any time.",
    "Refund requests must include your annual subscription ID.",
    "Enterprise support handles annual contract refund disputes.",
]
docs = [Document(page_content=c, metadata={"id": i}) for i, c in enumerate(corpus)]

# ── Build BM25 retriever ───────────────────────────────────────
def tokenize(text):
    return re.sub(r'[^\w\s]', ' ', text.lower()).split()

bm25_retriever = BM25Retriever.from_documents(
    docs, preprocess_func=tokenize, k=4
)

# ── Build dense retriever ──────────────────────────────────────
embeddings = HuggingFaceEmbeddings(
    model_name="BAAI/bge-large-en-v1.5",
    encode_kwargs={"normalize_embeddings": True},
    query_instruction="Represent this sentence for searching relevant passages: "
)
vectorstore = Qdrant.from_documents(
    docs, embeddings, location=":memory:",
    collection_name="policy_docs"
)
dense_retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

# ── EnsembleRetriever with RRF fusion ─────────────────────────
# weights must sum to 1.0. These are w_r in the weighted RRF formula.
hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, dense_retriever],
    weights=[0.4, 0.6],    # 40% BM25, 60% dense (semantic-heavy corpus)
    c=60                 # RRF k parameter
)
results = hybrid_retriever.invoke("how do I get a refund on my annual plan?")
for i, doc in enumerate(results, 1):
    print(f"#{i}: {doc.page_content[:70]}")

# ── Qdrant native hybrid search (sparse + dense in one call) ──
# Qdrant v1.7+ supports hybrid search natively via prefetch + fusion
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Prefetch, FusionQuery, Fusion,
    SparseVector, NamedSparseVector, NamedVector
)

# Assumes collection has both "dense" and "sparse" vector configs
results = client.query_points(
    collection_name="hybrid_docs",
    prefetch=[
        Prefetch(query=NamedVector(name="dense", vector=query_dense_vec), limit=50),
        Prefetch(query=NamedSparseVector(name="sparse",
            vector=SparseVector(indices=bm25_indices, values=bm25_weights)), limit=50),
    ],
    query=FusionQuery(fusion=Fusion.RRF),  # native RRF in Qdrant
    limit=10
)
09 · Assessment

Module 7 Quiz

1. Document D appears at rank 1 in BM25 and rank 3 in dense retrieval. Document E appears at rank 2 in BM25 and rank 2 in dense. Compute which scores higher in RRF with k=60.

Correct. RRF(D) = 1/(60+1) + 1/(60+3) = 0.01639 + 0.01587 = 0.03226. RRF(E) = 1/(60+2) + 1/(60+2) = 0.01613 + 0.01613 = 0.03226. They tie exactly. This demonstrates RRF's core property: consistent performance across all retrievers is as valuable as topping one list.

2. Why does RRF use k=60 as the default rather than k=0 or k=1?

Correct. k is a smoothing constant that controls the impact of rank position differences. A large k (relative to typical corpus sizes) means adjacent ranks contribute nearly equal scores. This is desirable because both BM25 and dense retrieval have noise in their exact rankings — you want to reward documents that consistently appear in the top results without over-penalizing small rank differences.

3. You want to fuse BM25 scores (range 0 to 2.5) and cosine scores (range 0 to 1) using CombSUM. What must you do first and why?

Correct. CombSUM adds raw scores directly. BM25 max of 2.5 would dominate cosine max of 1.0, making the dense retriever contribute only 29% of the combined signal at best. Min-Max normalization maps both to [0,1], ensuring each retriever has equal influence. This is exactly why RRF is often preferred in practice — it uses rank positions which are already on the same scale.

4. You run EnsembleRetriever with weights=[0.7, 0.3] (BM25, dense) on a customer support corpus of natural language questions. Retrieval quality is poor. What adjustment would you make?

Correct. Weights should reflect query type distribution. Customer support is dominated by conversational, paraphrased queries where dense retrieval excels. High BM25 weight penalizes documents that express the same content differently. Analyze a sample of queries, check where BM25 fails (look for zero-score relevant documents) and adjust weights toward the retriever that performs better on your actual query distribution.

5. Document F appears in the BM25 top-50 at rank 8 but does NOT appear in the dense top-50 at all. What is F's RRF score?

Correct. Documents not appearing in a retriever's result set contribute 0 from that retriever. RRF sums contributions from all lists a document appears in. F gets 1/(60+8) = 0.01471 from BM25 only. This is deliberately lower than documents appearing in both lists (~0.03), reflecting that only one retriever found it relevant. This is a feature: hybrid search rewards inter-retriever agreement.
