01 · Scaling Architecture — From 1M to 10B Vectors

The math behind every scaling decision

Every scaling decision reduces to arithmetic. This section gives you the exact formulas for every index type and the systematic process for making the right call at every order of magnitude.

Capacity planning table — every scale with RAM formulas and hardware
🔢

Complete RAM formulas for every index type

FLAT: N×d×4 bytes (FP32) or N×d×2 (FLOAT16)

HNSW: N×d×4 + N×M×2×8 bytes. Layer 0 uses M₀=2M. Example: N=10M, d=768, M=16 → 30.7GB + 2.56GB = 33.3GB

IVF_FLAT: nlist×d×4 (centroids) + N×d×4 (vectors). Centroids are tiny vs vectors.

IVF_SQ8: nlist×d×4 + N×d×1 (INT8 quantized). 4× less than IVF_FLAT for vectors.

IVF_PQ (m subquantizers): nlist×d×4 + N×m×1. For m=32: N×32 bytes. At N=100M: 3.2GB.

DiskANN: N×m_pq bytes in RAM (PQ only). Full N×d×4 bytes on SSD. RAM = 3-32GB for any scale.

Horizontal scaling patterns

QueryNode scaling (read)

Search is embarrassingly parallel. Adding QueryNodes scales QPS linearly. Each QueryNode holds a fraction of the total index. QueryCoord routes each query to the QueryNode(s) holding the relevant segments.

Multi-replica: load_collection(replica_number=N) puts N copies in RAM. Each query hits only 1 replica. N× QPS capacity at N× RAM cost. Use when QPS > single QueryNode capacity.

DataNode scaling (write)

DataNode throughput: ~50,000 vectors/sec per node. Each DataNode subscribes to separate Pulsar channel partitions. Adding DataNodes increases write throughput linearly.

The bottleneck shifts to MinIO at high write rates. Size MinIO IOPS accordingly: each segment flush = ~100-500MB burst write. SSD-backed MinIO recommended for >10K vectors/sec.

IndexNode scaling (build)

IndexNode build rate: ~1M vectors/min (HNSW CPU), ~10M vectors/min (HNSW GPU). If ingestion rate exceeds build rate, the index build queue grows and recall degrades.

Sizing rule: number of IndexNodes ≥ ingestion_rate / build_rate. At 500K vectors/hour with CPU build: 1 IndexNode sufficient. At 10M vectors/hour: 10+ IndexNodes or GPU acceleration.

scaling_calculator.py — right-size for any scale

def plan_cluster(N, d, target_qps, target_latency_ms, recall_target=0.95):
    """
    Generate a complete Milvus deployment plan.
    Returns: index config, hardware sizing, expected performance.
    """
    # Step 1: Choose index based on RAM requirements
    hnsw_gb = (N*d*4 + N*16*2*8) / 1e9
    pq_gb   = (N*32) / 1e9
    
    if hnsw_gb < 200:
        idx = "HNSW"; idx_ram = hnsw_gb; idx_params = {"M":16,"ef":64}
    elif N > 1e8:
        idx = "DiskANN"; idx_ram = pq_gb; idx_params = {"R":64,"L":100}
    else:
        idx = "IVF_SQ8"; nlist = int(4*N**0.5)
        idx_ram = (nlist*d*4 + N*d*1) / 1e9
        idx_params = {"nlist": nlist, "nprobe": int(nlist/8)}
    
    # Step 2: QueryNodes (each node handles idx_ram / node_ram fraction)
    node_ram_gb = 64  # standard node
    qnodes = max(1, int(idx_ram / (node_ram_gb * 0.75) + 1))
    
    # Step 3: QPS capacity (single QueryNode: ~2000 QPS at 5ms for HNSW)
    qps_per_node = 2000 if idx == "HNSW" else 800
    qnodes_for_qps = int(target_qps / qps_per_node + 1)
    qnodes = max(qnodes, qnodes_for_qps)
    
    print(f"=== Deployment Plan: N={N/1e6:.0f}M d={d} ===")
    print(f"Index: {idx} {idx_params}")
    print(f"Index RAM: {idx_ram:.1f} GB")
    print(f"QueryNodes: {qnodes} × {node_ram_gb}GB")
    print(f"DataNodes: 2 (HA), IndexNodes: 2")
    print(f"etcd: 3-node cluster")
    print(f"Expected QPS: {qnodes*qps_per_node}")
    
# Examples:
# plan_cluster(1e6,  768, 1000, 5)   → HNSW, 1 QueryNode, 3.3GB RAM
# plan_cluster(50e6, 768, 5000, 5)   → HNSW, 3 QueryNodes, 167GB total
# plan_cluster(1e9,  768, 2000, 10)  → DiskANN, 1 QueryNode, 32GB RAM + 3TB SSD
02 · Streaming Ingestion and Real-Time Search

Kafka → Milvus: production ingestion pipeline

Batch inserts are easy. Production ingestion is a continuous stream with failures, backpressure, and consistency requirements. This is the complete pattern.

⚡

Write amplification — the batching anti-pattern

Calling insert([v1]) 1000 times/sec creates 1000 segments. Each seals at 1 row — immediate index build job for a 1-row segment. Result: 86,400 tiny segment builds per day. Fix: batch to at least 1,000 vectors per insert call. Use BulkInsert for initial loads (>1M vectors).

⏱️

The consistency gap and write-through search

30-120 second gap from insert to searchable. For real-time: write to both Milvus (async, batched) AND Redis sorted set (TTL=24h). Search merges Milvus results + Redis recent items. After 24h all items are indexed and Redis entries expire naturally.

kafka_milvus_pipeline.py — production ingestion with DLQ

from kafka import KafkaConsumer, KafkaProducer
from pymilvus import MilvusClient
import json, time

BATCH_SIZE = 1000    # Minimum batch for efficient Milvus writes
FLUSH_INTERVAL = 5   # Flush every 5 seconds even if batch not full

class MilvusIngestionPipeline:
    def __init__(self, kafka_topic, milvus_collection):
        self.consumer = KafkaConsumer(
            kafka_topic,
            bootstrap_servers=['kafka:9092'],
            value_deserializer=lambda x: json.loads(x),
            max_poll_records=BATCH_SIZE
        )
        self.dlq = KafkaProducer(bootstrap_servers=['kafka:9092'])
        self.milvus = MilvusClient("http://milvus:19530")
        self.collection = milvus_collection
        self.buffer = []
        self.last_flush = time.time()
    
    def embed_batch(self, texts):
        # Your embedding model here — batched for efficiency
        return embedding_model.encode(texts)  # Returns numpy array
    
    def flush_to_milvus(self):
        if not self.buffer: return
        
        texts = [r['text'] for r in self.buffer]
        ids   = [r['id']   for r in self.buffer]
        
        try:
            embeddings = self.embed_batch(texts)
            data = [{"id": ids[i], "embedding": embeddings[i].tolist(),
                      "text": texts[i]} for i in range(len(texts))]
            self.milvus.insert(self.collection, data)
            self.buffer.clear()
            self.last_flush = time.time()
            
        except Exception as e:
            # Send to DLQ for retry — don't block main pipeline
            for record in self.buffer:
                self.dlq.send('milvus-dlq', 
                    value=json.dumps({**record, 'error': str(e),
                                      'retry_count': record.get('retry_count',0)+1}).encode())
            self.buffer.clear()
    
    def run(self):
        for msg in self.consumer:
            self.buffer.append(msg.value)
            age = time.time() - self.last_flush
            if len(self.buffer) >= BATCH_SIZE or age > FLUSH_INTERVAL:
                self.flush_to_milvus()

# CDC: Postgres → Debezium → Kafka → Milvus

# Handle deletes: collection.delete(expr='id==' + str(deleted_id))

Zero-downtime migration — the alias swap pattern

migration.py — full zero-downtime migration implementation

from pymilvus import MilvusClient, utility
import time

def migrate_collection(client, old_name, new_schema, new_index_params,
                         alias, batch_size=10000, verify_queries=100):
    """
    Zero-downtime collection migration using alias swap.
    - old_name: current physical collection behind alias
    - new_schema: updated schema (new fields, new vector type, etc.)
    - alias: the alias pointing to old_name (app uses this)
    """
    new_name = f"{old_name}_v{int(time.time())}"
    
    # 1. Create new collection with new schema
    print(f"Creating {new_name}...")
    client.create_collection(new_name, schema=new_schema)
    for idx_param in new_index_params:
        client.create_index(new_name, **idx_param)
    client.load_collection(new_name)
    
    # 2. Bulk copy with transformation
    print("Copying vectors...")
    offset, total = 0, 0
    while True:
        rows = client.query(old_name, "", offset=offset, limit=batch_size,
                            output_fields=["*"])
        if not rows: break
        # Apply any transformations here (field rename, type convert, etc.)
        client.insert(new_name, rows)
        offset += len(rows); total += len(rows)
        print(f"  {total:,} vectors copied", end="
")
    
    # 3. Wait for indexing to complete
    utility.wait_for_index_building_progress(new_name)
    
    # 4. Verify recall parity on test queries
    print("Verifying recall...")
    test_queries = generate_test_queries(verify_queries)
    old_recall = measure_recall(client, old_name, test_queries)
    new_recall = measure_recall(client, new_name, test_queries)
    print(f"  Old recall: {old_recall:.3f}, New recall: {new_recall:.3f}")
    assert new_recall >= old_recall * 0.99, "New recall is more than 1% worse!"
    
    # 5. Atomic alias swap — no downtime
    print(f"Swapping alias '{alias}' from {old_name} → {new_name}")
    client.alter_alias(alias, new_name)  # O(1), atomic
    
    # 6. Keep old collection for 48h rollback window
    print(f"✅ Migration complete. Old collection {old_name} kept for 48h rollback.")
    return new_name

Question 1 of 8

You're scaling from 10M to 100M vectors (d=768). HNSW M=16. Calculate exact RAM and determine if you can stay on a single 256GB node.

The correct answer requires showing multiple options. FP32 HNSW: 332.6GB > 256GB — doesn't fit. FLOAT16 halves vector storage: 153.6 + 25.6 = 179.2GB — fits on 256GB with headroom. IVF_PQ is the most compressed but 3-8% recall drop. The systematic approach: calculate RAM, compare to budget, if exceeds then consider FLOAT16 → IVF_SQ8 → IVF_PQ in that order of recall impact.
Question 2 of 8

You need to migrate from HNSW M=16 to HNSW M=32 on a production collection with 20M vectors. The collection is serving live traffic. What is the correct procedure?

The alias swap is the only correct zero-downtime approach. Milvus does NOT support in-place index parameter changes — create_index() on an existing field drops and rebuilds the index, causing a searchability gap during rebuild. Dual-write adds complexity and 2× storage cost temporarily. The alias pattern: your application always queries the alias name 'products', never the physical collection name. alter_alias() is O(1) and atomic.
Question 3 of 8

A Kafka→Milvus ingestion pipeline is inserting 1000 vectors/sec. After 1 hour, you notice 3600 growing segments (one per second of inserts). What is the problem and the fix?

Write amplification from small batches. Each insert() call creates or extends one growing segment. 1000 calls/sec × 3600sec = 3600 segments with ~3600 rows each. Problems: (1) 3600 index build jobs queued, (2) 3600 segments in QueryNode RAM, (3) extremely high segment count → compaction pressure. Fix: batch inserts. Instead of insert([v1]) 1000 times/sec, insert([v1,...,v1000]) once/sec. Better: use BulkWriter to accumulate 100K+ vectors and do a single BulkInsert. Target: segments should seal at 500K-1M rows.
Question 4 of 8

Your milvus_querynode_search_latency_p99 suddenly goes from 3ms to 280ms. milvus_indexcoord_index_task_num is 0 (no build backlog). What are the top 3 failure hypotheses and how do you check each?

Latency spike with no build backlog requires checking the I/O and memory path. With zero index build jobs, the latency spike is NOT from searching unindexed segments. Most likely causes: (1) Compaction I/O: compaction reads many segment files from MinIO simultaneously, creating I/O contention with search. (2) MinIO slowness: if S3 is throttled or degraded, segment loads during rebalancing are slow. (3) QueryNode memory pressure: if RSS is near limit, GC pauses cause p99 spikes. Check each with: Prometheus dashboard + correlated timestamps.
Question 5 of 8

Describe the Kafka→Milvus production pipeline including error handling. What happens when the embedding model returns an error for one batch?

The dead letter queue pattern is the production standard. Pipeline: Kafka consumer reads events → embedding model batch → Milvus BulkWriter. When embedding fails: catch exception, publish to DLQ Kafka topic with original message + error metadata. DLQ consumer: retry with backoff. This prevents: (1) pipeline stall when model is temporarily overloaded, (2) data loss, (3) blocking healthy messages behind a failing one. Monitoring: DLQ depth is a critical alert — growing DLQ means the embedding service is degraded.
Question 6 of 8

When should you use collection.compact() manually, and what happens inside Milvus during compaction?

Manual compaction has specific use cases. After bulk deletes: deleted vectors occupy space (tombstones) until compaction. A collection with 20% deletes wastes 20% of index RAM. Compaction permanently removes them. After migration: you may have many tiny segments from the migration process. Compaction merges them. Milvus auto-compaction triggers at: (1) segment count > threshold, (2) binlog file count > threshold. For large delete operations, auto-compaction may be too slow — trigger manually.
Question 7 of 8

Explain the RPO and RTO targets for Milvus and how to achieve RPO=1h, RTO=15min using milvus-backup.

RPO/RTO require separate strategies for metadata (etcd) and data (MinIO). etcd: 3-node Raft cluster gives RPO=0 for metadata. MinIO/S3: object storage is durable by default (11 nines). milvus-backup backs up collection data to S3. Incremental backup: only new segments since last backup. Restore time depends on data size and S3 throughput. For N=100M vectors ≈ 300GB: restore takes 5-15min with 500MB/s S3. RTO=15min is achievable for most production sizes.
Question 8 of 8

A production Milvus cluster has: 100M vectors, 3 QueryNodes (64GB each), HNSW M=16 at d=768. A fourth QueryNode is added. What happens automatically and what requires manual action?

QueryCoord is the automatic rebalancing brain. When a new QueryNode comes online and registers with etcd, QueryCoord detects it and begins migrating segments to balance memory usage. This is one of Milvus's strongest features — horizontal scaling is truly elastic. The migration is done by: (1) load segment on new node, (2) verify loaded, (3) unload from old node. During migration, the old node still serves the segment — zero downtime. For replica_number changes: explicit API call required.
