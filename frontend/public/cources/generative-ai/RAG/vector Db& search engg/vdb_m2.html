01 · Schema Design — Decisions That Survive Production

Schema that doesn't break at 10M vectors

Your schema is the hardest thing to change in production. A wrong primary key type, a missing scalar index, or the wrong partition strategy means a full rebuild. Get these decisions right before you write a line of ingestion code.

Four production schema patterns — field types, indexes, and partition strategy

Field type decisions

Primary key: INT64 (auto-id=True) for high-throughput writes. VARCHAR for human-readable IDs (UUIDs, doc slugs) but 2× slower for equality lookups.

Vector type: FLOAT_VECTOR (FP32, 4 bytes/dim) default. FLOAT16_VECTOR (2 bytes/dim) for 2× RAM savings with ~0.1% recall drop. BINARY_VECTOR (1 bit/dim) for near-duplicate detection and hashing.

Scalar types: Use INT8/INT16 when values fit (saves storage). BOOL for binary flags. VARCHAR over TEXT for indexed string fields. JSON for dynamic attributes.

Scalar index types — when to use each

IndexField TypeQuery Pattern
STL_SORTINT, FLOATRange queries: price < 100, date > X
TRIEVARCHARPrefix match, equality: category == "X"
BITMAPBOOL, low-cardinality VARCHARBoolean filters: in_stock == True
INVERTEDVARCHAR, ARRAYText search, array contains
NoneOutput-only fieldscontent, url — never filtered
⚠️

The selectivity cliff — pre-filter vs post-filter

Rule: if filter_selectivity < nprobe/nlist → post-filter is safe. If filter_selectivity < 1% → pre-filter required.

Worked example: 10M vectors, nlist=12648, nprobe=1265 (10%), filter matches 5% of data. Ratio: 0.05 vs 0.10. Post-filter is safe — ANN already narrows to 10% of data. But at 0.1% selectivity (100K matching vectors): post-filter would return too few results after filtering. Use pre-filter with BITMAP index.

Consistency levels — the right choice for each use case

Strong
Always latest
Linearizable. Every search sees all previous writes. 2-3× latency penalty. Use: financial data, audit logs.
Bounded
T-second lag
Read data ≤ T seconds old. Default T=5s. Good balance. Use: most production apps, content platforms.
Session
Own writes
Guaranteed to see your own inserts. Default. Use: CRUD apps, user-facing search.
Eventually
Fastest
May miss recent data. Best throughput. Use: analytics, recommendation, batch processing.

schema_design.py — production schema patterns

from pymilvus import (
    MilvusClient, DataType, CollectionSchema, FieldSchema,
    Function, FunctionType
)

def create_rag_collection(client, name="rag_docs"):
    """Production RAG schema: dense + sparse hybrid search."""
    schema = MilvusClient.create_schema(
        auto_id=False,
        enable_dynamic_field=True  # JSON for flexible metadata
    )
    # Primary key
    schema.add_field("chunk_id", DataType.VARCHAR, max_length=64, is_primary=True)
    # Dense vector for semantic search
    schema.add_field("dense_emb", DataType.FLOAT_VECTOR, dim=1536)
    # Sparse vector for BM25 keyword search
    schema.add_field("sparse_emb", DataType.SPARSE_FLOAT_VECTOR)
    # Scalar fields for filtering
    schema.add_field("doc_id",   DataType.VARCHAR, max_length=64)
    schema.add_field("created_at", DataType.INT64)  # unix timestamp
    schema.add_field("chunk_text", DataType.VARCHAR, max_length=4000)
    
    # BM25 function: automatically generates sparse_emb from chunk_text
    bm25_fn = Function(
        name="bm25", function_type=FunctionType.BM25,
        input_field_names=["chunk_text"],
        output_field_names=["sparse_emb"]
    )
    schema.add_function(bm25_fn)
    
    client.create_collection(name, schema=schema)
    
    # Index: HNSW for dense, SPARSE_INVERTED_INDEX for sparse
    client.create_index(name, field_name="dense_emb", index_type="HNSW",
                        metric_type="COSINE", M=16, efConstruction=200)
    client.create_index(name, field_name="sparse_emb",
                        index_type="SPARSE_INVERTED_INDEX",
                        metric_type="BM25")
    # Scalar indexes for filtering
    client.create_index(name, field_name="doc_id",    index_type="TRIE")
    client.create_index(name, field_name="created_at", index_type="STL_SORT")
    
    client.load_collection(name)
    return name
02 · Index Tuning — From Parameters to SLAs

Turning parameter knobs into recall and latency guarantees

Every HNSW and IVF parameter has a precise effect on recall, latency, and memory. This section gives you the formulas and a systematic tuning process.

HNSW complete parameter arithmetic

Memory = N×d×4 + N×M×2×8 bytes
Build time ∝ N × efConstruction × M × log(N)
recall(ef) ≈ 1 - exp(-ef × log(N) / √N)
Search cost = O(ef × M × log(N))

Example: N=10M, d=768, M=16, ef=64
Memory: 10M×768×4 + 10M×16×2×8 = 30.7GB + 2.56GB = 33.3GB
Recall: ≈ 1-exp(-64×16.1/3162) ≈ 97%
Latency: ~23 hops × ~0.1ms = <3ms p50

IVF complete parameter arithmetic

nlist = 4×√N (Faiss rule)
recall(nprobe) ≈ 1-(1-nprobe/nlist)^K
Latency = nprobe × (N/nlist) × d × 4 FLOPs

Example: N=10M, K=10, nlist=12648
90% recall: nprobe=1196 (10% of nlist)
95% recall: nprobe=2529 (20% of nlist)
99% recall: nprobe=7584 (60% of nlist)
Latency at nprobe=1264: 10M/12648×768×4 = ~2.4ms
📊

How to run a proper recall benchmark

Ground truth: brute-force search on 1000 random queries. Store the exact top-K for each. ANN recall: measure |ANN top-K ∩ exact top-K| / K averaged over all queries. Do NOT measure recall on the same data you indexed. The benchmark should use held-out queries. Report p50/p95/p99 latency at your peak QPS, not average latency at 1 QPS.

benchmark.py — recall and latency measurement

import numpy as np
import time
from pymilvus import MilvusClient

def benchmark_index(client, collection, queries, ground_truth, top_k=10,
                     ef_values=[16,32,64,128,256]):
    """
    Sweep ef values to plot recall vs latency tradeoff.
    ground_truth: dict mapping query_id → set of true top-K ids
    """
    results = []
    
    for ef in ef_values:
        latencies = []
        recall_scores = []
        
        for i, q in enumerate(queries):
            t0 = time.perf_counter()
            hits = client.search(
                collection, [q.tolist()], limit=top_k,
                search_params={"ef": ef},
                output_fields=["id"]
            )
            latencies.append((time.perf_counter()-t0)*1000)
            
            # Compute recall@K
            returned_ids = set(h["id"] for h in hits[0])
            true_ids = ground_truth[i]
            recall_scores.append(len(returned_ids & true_ids) / top_k)
        
        lat = np.array(latencies)
        results.append({
            "ef": ef,
            "recall": round(np.mean(recall_scores), 4),
            "p50":  round(np.percentile(lat, 50),  2),
            "p95":  round(np.percentile(lat, 95),  2),
            "p99":  round(np.percentile(lat, 99),  2),
            "qps":  round(1000 / np.mean(lat), 0)
        })
        print(f"ef={ef:4d}: recall={results[-1]['recall']:.4f}, "
              f"p99={results[-1]['p99']:.1f}ms, QPS={results[-1]['qps']:.0f}")
    
    return results

# Example output:
# ef=  16: recall=0.9124, p99= 1.2ms, QPS=4200
# ef=  32: recall=0.9563, p99= 1.8ms, QPS=3100
# ef=  64: recall=0.9781, p99= 3.1ms, QPS=1800
# ef= 128: recall=0.9892, p99= 5.8ms, QPS= 950
# ef= 256: recall=0.9944, p99=11.2ms, QPS= 480
# → Choose ef=64 for 97.8% recall at p99=3.1ms
03 · Hybrid Search — Dense + Sparse, Done Right

When neither alone is enough

Dense retrieval wins on semantic similarity. Sparse retrieval wins on exact keyword match. Production systems need both. Here is how to implement it correctly, including why RRF works and when to use weighted sum instead.

Hybrid search pipeline — dual retrieval with RRF fusion

Why hybrid always wins

Dense failures: Query "GPT-4o pricing" → dense returns semantically similar documents about AI model costs. But misses the exact document with "GPT-4o" in the title if that document has atypical embedding.

Sparse failures: Query "show me cozy sweaters" → BM25 only matches "cozy" and "sweaters" literally. Misses documents mentioning "warm knitwear" or "chunky knit".

Combined: BEIR benchmark shows hybrid consistently +3-8% nDCG@10 over either alone across all datasets tested.

RRF formula and why k=60

score(d) = Σᵣ 1/(k + rankᵣ(d))
For k=60: rank 1 → 1/61≈0.0164
rank 10 → 1/70≈0.0143
rank 100 → 1/160=0.00625
Score difference shrinks rapidly → robust to outliers

k=60 comes from Cormack et al. 2009 SIGIR paper — empirically optimal across TREC benchmarks. Higher k → more conservative fusion (penalizes low ranks less). RRF is robust because you only need rank order, not comparable scores.

hybrid_search.py — complete implementation

from pymilvus import (
    MilvusClient, AnnSearchRequest, RRFRanker, WeightedRanker
)
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-m3")  # dense + sparse in one

def hybrid_search(client, collection, query, top_k=10,
                   dense_top_k=100, sparse_top_k=100,
                   ranker="rrf", rrf_k=60):
    """
    Hybrid search: dense ANN + sparse BM25 with RRF or weighted fusion.
    dense_top_k/sparse_top_k: retrieve more candidates for better fusion.
    """
    # Generate both embedding types
    output = model.encode([query], return_dense=True, return_sparse=True)
    dense_vec  = output["dense_vecs"][0].tolist()
    sparse_vec = output["lexical_weights"][0]  # dict: token→weight
    
    # Dense ANN request
    dense_req = AnnSearchRequest(
        data=[dense_vec], anns_field="dense_emb", limit=dense_top_k,
        param={"metric_type": "COSINE", "params": {"ef": 128}}
    )
    # Sparse BM25 request
    sparse_req = AnnSearchRequest(
        data=[sparse_vec], anns_field="sparse_emb", limit=sparse_top_k,
        param={"metric_type": "BM25"}
    )
    
    # Choose fusion strategy
    if ranker == "rrf":
        fusion = RRFRanker(k=rrf_k)
    elif ranker == "weighted":
        fusion = WeightedRanker(0.6, 0.4)  # dense 60%, sparse 40%
    
    results = client.hybrid_search(
        collection,
        reqs=[dense_req, sparse_req],
        ranker=fusion,
        limit=top_k,
        output_fields=["chunk_id", "chunk_text", "doc_id"]
    )
    return results[0]

# Consistently +3-8% on BEIR benchmark datasets
# Largest gains on entity-heavy queries (product IDs, names, codes)

Question 1 of 8

A filter expression 'category=\'electronics\' AND price<100' is applied to a search. You have 10M vectors with nlist=12648 (4√10M). 5% of vectors match the filter. Should you pre-filter or post-filter, and why?

The selectivity cliff determines the strategy. Formula: if filter_selectivity < nprobe/nlist, post-filter is safe — the vector index already narrows to nprobe cells. At 5% selectivity and nprobe/nlist=10%: 0.05 < 0.10, so post-filter works. But at 0.1% selectivity: pre-filter is required (post-filter would return too few results after filtering). Milvus 2.4+ uses iterative filtering which automatically picks the right strategy.
Question 2 of 8

Explain the BM25 formula and what the parameters k1=1.2 and b=0.75 control.

BM25 is the gold standard sparse retrieval formula. IDF(t)=log((N-df(t)+0.5)/(df(t)+0.5)+1) weights rare terms higher. The TF component tf×(k1+1)/(tf+k1×...) saturates at high frequency — a term appearing 10× is not 10× more relevant than appearing 3×. k1=1.2: saturation is gentle (good for short queries). k1=2.0 would saturate later. b=0.75: partially normalizes for document length — prevents long documents dominating just because they mention a term more times.
Question 3 of 8

You are implementing hybrid search. Dense search returns scores in [-1, 1] (cosine similarity). BM25 returns scores in [0, 20]. You want to combine them. Why does simple weighted sum fail and how does RRF fix it?

RRF proof of robustness: The key insight is that ranks are comparable across any scoring function, while raw scores are not. If you normalize BM25 to [0,1], the normalization is data-dependent — a score of 0.8 means 'high' on one dataset but might be 'average' on another. RRF with k=60 (the Cormack et al. 2009 default) provides: smooth rank fusion, insensitivity to outliers, and no need to tune relative weights. When to use weighted instead: you have ground-truth data to tune α from, and both retrievers have similar score distributions.
Question 4 of 8

What is the HNSW selectivity formula and when does DiskANN replace HNSW in production?

The transition is purely RAM-driven. HNSW formula: RAM = N×(d×4 + M×2×8). Break-even: when this exceeds your available RAM budget. DiskANN RAM: N×m_pq bytes (typically 32 bytes for d=768 with m=32 PQ subquantizers). At N=100M: HNSW needs ~333GB, DiskANN needs ~3.2GB in RAM (+ 300GB NVMe SSD at $300). The latency cost: HNSW ≈ 0.5-2ms, DiskANN ≈ 1-4ms (SSD I/O adds ~0.5-2ms per hop). For most applications this is acceptable.
Question 5 of 8

An e-commerce site has 50M product vectors at d=512. Peak QPS is 5000. Recall must be ≥95%. RAM per node is 64GB. Design the complete index configuration including scalar indexes.

Multiple valid solutions exist — the key is showing the arithmetic. With 64GB per node: HNSW needs 114.8GB — doesn't fit without RAM upgrade. If you can use 128GB nodes: HNSW M=16 is better (95-99% recall vs IVF_PQ's 88-95%). IVF_PQ: 0.8GB RAM, recall ≈ 1-(1-2000/28284)^10 = 1-(0.929)^10 = 1-0.48 = 52% — wait, that's too low! Fix: nprobe must be higher. For 95% recall with IVF_PQ: need nprobe≈5000 (recall≈1-(0.823)^10=86%) — IVF_PQ at 50M needs careful tuning. Best answer: upgrade to 128GB nodes and use HNSW M=16.
Question 6 of 8

What is the consistency gap in Milvus and how do you handle it in a real-time recommendation system?

The write-through pattern is the production solution. Calling flush() after every insert: (1) forces small segment sealing (thousands of tiny segments), (2) causes index build backlog, (3) massively increases MinIO I/O. For real-time: write to Milvus asynchronously in batches (1000+), AND write to Redis with TTL=24h. Search merges: ZADD rec:user_123 timestamp item_id for new items. At query time: redis_recent=ZRANGE rec:user_123 -inf +inf → merge with Milvus results. After 24h, all items are in Milvus and Redis entries expire.
Question 7 of 8

Compare the three result fusion strategies for hybrid search — weighted sum, RRF, and cross-encoder reranking — and give a concrete decision rule for each.

The decision depends on data availability and latency budget. Weighted sum requires: (1) evaluation ground truth to find optimal α, (2) score normalization (min-max or sigmoid), (3) same score distribution at test and production. If you lack these → RRF. Cross-encoder doubles model serving cost and adds 5-30ms, but can add 3-8% recall@10 on top of RRF. Use it when: latency budget > 50ms, query volume < 500 QPS (otherwise too expensive), you have a pre-trained cross-encoder for your domain.
Question 8 of 8

A tenant isolation bug: tenant A's search results include documents from tenant B. Your schema uses partition_key=tenant_id. What are the possible causes and fixes?

Partition key is a routing mechanism, not a security boundary. The partition key determines which physical partition a vector is stored in — it reduces search scope but does NOT automatically filter results to that tenant. You must ALSO add the filter expression tenant_id=='...' to every search. This is a common production bug. Solution: add a middleware layer that wraps all search calls and injects the authenticated tenant's filter. Never rely on application developers to remember the filter.
