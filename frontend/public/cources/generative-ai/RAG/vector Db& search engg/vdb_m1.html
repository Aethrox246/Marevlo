01 · The Distributed Architecture — All 11 Components

What every component actually does

Milvus has 11 distinct components. Most documentation names them. This module explains what each one actually does, what fails if it goes down, and why it was designed that way.

DEPLOYMENT

Milvus Lite

In-process library. No external dependencies. Perfect for dev/test. Upgrade trigger: >1M vectors or need for persistence across restarts.

DEPLOYMENT

Standalone

Single Docker container. Embeds Pulsar + etcd + MinIO internally. Minimum: 8 vCPU, 32GB RAM. Upgrade trigger: >10M vectors or >100 QPS sustained.

DEPLOYMENT

Distributed

Kubernetes. Separate pods for each component. Supports horizontal scaling of DataNodes, IndexNodes, QueryNodes independently. Required above 10M vectors.

vs OTHERS

Why not pgvector?

pgvector: Postgres-native, simple, HNSW+IVF, excellent for 1M-10M. Milvus: cloud-native, distributed, built for 100M-100B. Choose pgvector when you're already on Postgres and scale is modest.

Complete Milvus architecture — all 11 components with data flows

The 3 Coordinators — The Control Plane

RootCoord

The brain — DDL and global clock

DDL operations: All schema changes go through RootCoord. create_collection(), create_index(), drop_collection() — these are serialized through RootCoord to prevent race conditions.

TSO (Timestamp Oracle): RootCoord is the only component that generates global timestamps. Every write operation gets a monotonically increasing TSO timestamp. This is what makes Milvus's consistency levels possible — readers know which timestamp to read at.

DataCoord

The write orchestrator

Segment assignment: When a DataNode needs to write data, it asks DataCoord for a segment. DataCoord tracks all growing segments: which DataNode owns them, how many rows are written, when they need to be sealed.

Seal trigger: When a growing segment reaches max_rows (default: 1,000,000), DataCoord tells the DataNode to seal it. The sealed segment is then queued for indexing. DataCoord also triggers compaction — merging small segments and removing deleted vector tombstones.

QueryCoord

The search orchestrator

Segment management: QueryCoord decides which segments are loaded on which QueryNodes. When IndexCoord marks a segment as indexed, QueryCoord assigns it to a QueryNode for loading.

Load balancing: QueryCoord monitors QueryNode memory usage. If one QueryNode is overloaded (too many segments), it migrates segments to another. When you call load_collection(replica_number=2), QueryCoord loads two copies across different QueryNodes.

The 5 Worker Components

DataNode — writing vectors

DataNode subscribes to a Pulsar topic for its assigned collection. Every insert goes through Pulsar first, not directly to the DataNode. This gives Milvus durability — even if the DataNode crashes mid-write, the messages remain in Pulsar and can be replayed.

It writes vectors to a growing segment in memory. When sealed, it creates three types of binlog files in MinIO: insert log (raw vectors), delta log (delete tombstones), stats log (min/max/count per field for filter pushdown).

IndexNode — building indexes

IndexNode is the most compute-intensive component. It downloads raw vector binlogs from MinIO, runs the HNSW/IVF/DiskANN build algorithm, and uploads the finished index file back to MinIO.

IndexNode can be GPU-accelerated for HNSW/IVF builds — roughly 10× faster than CPU. For large collections (100M+ vectors), you may need multiple IndexNodes running in parallel to keep up with the DataNode seal rate.

QueryNode — serving searches

QueryNode loads index segments from MinIO into RAM. Once loaded, it holds the full index in memory. A search request arrives from Proxy → QueryCoord → QueryNode. The QueryNode executes the ANN search against its loaded segments.

One QueryNode handles both growing segments (brute-force scan, no index) and historical segments (HNSW/IVF search). Results from all segments are merged and re-ranked by distance score before returning to the client.

Pulsar, etcd, MinIO

Pulsar: The write-ahead log for all insert operations. Why Pulsar over Kafka? Pulsar supports multi-tenant topics natively (one topic per collection without overhead), tiered storage for old segments, and exactly-once delivery. Can be swapped for Kafka in Milvus 2.3+.

etcd: Stores schemas, segment state, index status, component registration. 3-node Raft consensus for HA. MinIO: Object storage for binlogs and index files. Can be replaced by S3, GCS, or Azure Blob in production.

02 · The Data Lifecycle — From insert() to Searchable

Complete write and search path

Every insert follows a deterministic path through 7 components before becoming searchable. Understanding this path is what lets you debug the "why can't I find my data" problem at 3am.

Complete data lifecycle — write path, segment states, and search path

The write path — annotated step by step

1
client.insert([v1, v2, v3]) → Proxy

PyMilvus SDK serializes vectors to gRPC. Proxy validates field types against the collection schema. Assigns a TSO timestamp to the batch.

2
Proxy → DataCoord (DML routing)

Proxy identifies the collection's Pulsar topic from its local cache (refreshed from RootCoord). Sends the insert to the appropriate Pulsar topic — not directly to DataNode.

3
Pulsar → DataNode (durable buffer)

DataNode subscribes to the collection's Pulsar topic. Reads the insert message. This gives Milvus WAL-level durability — even if DataNode crashes here, the message is still in Pulsar.

4
DataNode writes to growing segment

Vectors are written to an in-memory growing segment buffer (default max: 1M rows or 128MB). Also writes to insert binlog on local disk for crash recovery.

5
Segment reaches max_rows → Sealed

DataCoord detects the growing segment is full. Issues a seal command. DataNode flushes all buffers to MinIO as binlog files (insert_log, delta_log, stats_log). Typical flush size: 100-500MB.

6
IndexCoord detects sealed segment → assigns build

IndexCoord watches for newly sealed segments (via Pulsar). Picks the least-loaded IndexNode and assigns the index build job. IndexNode downloads binlogs from MinIO.

7
IndexNode builds HNSW/IVF → uploads → QueryNode loads

IndexNode runs the index build algorithm. For N=1M vectors HNSW M=16: takes ~60s on CPU, ~6s on GPU. Uploads finished index to MinIO. IndexCoord marks as INDEXED. QueryCoord assigns to QueryNode. QueryNode downloads and loads into RAM. Total time insert→searchable: 30-120 seconds.

Segment lifecycle code

segment_lifecycle_monitor.py

from pymilvus import connections, utility, Collection
import time

connections.connect("default", host="localhost", port="19530")
col = Collection("my_collection")

def watch_segments(collection_name, interval=5):
    """Watch segment state transitions in real time."""
    print(f"Watching segments for {collection_name}...")
    prev_states = {}
    
    while True:
        # Get segment info from utility
        segments = utility.get_query_segment_info(collection_name)
        growing = [s for s in segments if s.state == 1]  # Growing
        sealed  = [s for s in segments if s.state == 2]  # Sealed (indexing)
        loaded  = [s for s in segments if s.state == 3]  # Loaded (searchable)
        
        total_rows = sum(s.num_rows for s in segments)
        growing_rows = sum(s.num_rows for s in growing)
        
        print(f"[{time.strftime('%H:%M:%S')}] "
              f"Growing: {len(growing)} segs ({growing_rows:,} rows) | "
              f"Indexing: {len(sealed)} | "
              f"Loaded: {len(loaded)} | "
              f"Total: {total_rows:,}")
        
        # Detect transitions
        for s in segments:
            if s.segment_id in prev_states:
                old = prev_states[s.segment_id]
                if old != s.state:
                    states = {1:'GROWING',2:'SEALED',3:'LOADED'}
                    print(f"  ⚡ Segment {s.segment_id}: {states.get(old,'?')} → {states.get(s.state,'?')}")
            prev_states[s.segment_id] = s.state
        
        time.sleep(interval)

def wait_for_index(collection_name, timeout=300):
    """Wait until all segments are indexed and loaded."""
    col = Collection(collection_name)
    start = time.time()
    
    while time.time() - start < timeout:
        progress = utility.index_building_progress(collection_name)
        indexed = progress['indexed_rows']
        total   = progress['total_rows']
        pct = (indexed/total*100) if total > 0 else 0
        print(f"Index progress: {indexed:,}/{total:,} ({pct:.1f}%)")
        if indexed == total and total > 0:
            print("✅ All segments indexed and loaded")
            return True
        time.sleep(10)
    raise TimeoutError(f"Index not complete after {timeout}s")
03 · Failure Modes and Production Diagnostics

The 8 failures every engineer hits

These are not hypothetical. Every production Milvus deployment encounters these exact failure modes. The difference between a 5-minute fix and a 3-hour outage is knowing the failure chain.

🔴

[CRITICAL] Search returns 0 results right after insert

Symptom: client.search() returns empty results on data that was just inserted.

Root cause: Data is in the growing segment in memory. With consistency='Eventually', the search may not see the latest writes.

Fix: Use consistency_level='Strong' for the search call, or call collection.flush() first. In production, use consistency='Session' to guarantee you see your own writes.

🔴

[CRITICAL] Recall dropped after large bulk insert

Symptom: After inserting 10M vectors overnight, morning searches show 85% recall instead of 97%.

Root cause: IndexNode couldn't build indexes fast enough. Searches are hitting unindexed segments (brute-force on binlogs). Check: utility.index_building_progress() shows indexed_rows << total_rows.

Fix: Scale IndexNodes horizontally. Call utility.wait_for_index_building_progress() before serving traffic after bulk imports. Add alert: milvus_indexcoord_index_task_num > 50.

🔴

[CRITICAL] QueryNode OOM crash loop

Symptom: QueryNode pod restarts every 5-10 minutes. OOMKilled in Kubernetes events.

Root cause: Too many segments loaded in QueryNode RAM. Total index size exceeds available memory.

Fix: Calculate required RAM: N×d×4 + N×M×2×8. Either increase QueryNode memory, switch to FLOAT16 vectors, or use IVF_PQ to compress. Quick fix: reduce replica_number, unload unused collections.

🔴

[CRITICAL] etcd runs out of disk space

Symptom: All DDL/DML operations start failing with 'etcd: mvcc: database space exceeded'.

Root cause: etcd's WAL (write-ahead log) grows without bound if auto-compaction is not configured. Default etcd does not compact automatically.

Fix: Immediately: etcdctl defrag. Permanently: set ETCD_AUTO_COMPACTION_MODE=periodic, ETCD_AUTO_COMPACTION_RETENTION=1h in etcd config. Add alert: etcd_mvcc_db_total_size_in_bytes > 4GB.

🟡

[WARNING] Index build backlog growing

Symptom: milvus_indexcoord_index_task_num keeps increasing. Search latency is normal but recall is degrading.

Root cause: DataNodes are sealing segments faster than IndexNodes can build indexes. Unindexed segments are searched with brute force.

Fix: Scale IndexNodes horizontally (Kubernetes: kubectl scale deployment milvus-indexnode --replicas=4). Alternatively reduce ingestion rate temporarily.

🟡

[WARNING] Pulsar disk full — all ingestion stops

Symptom: DataNode logs: 'failed to publish message: topic storage quota exceeded'.

Root cause: Pulsar message retention is set too long, or a consumer (DataNode) fell behind and messages are accumulating.

Fix: Increase Pulsar disk allocation. Set retention policy: backlogQuotaLimitBytes per topic. Ensure DataNode is consuming normally. Emergency fix: increase disk and restart Pulsar.

🟡

[WARNING] Search latency spikes every 10 minutes

Symptom: p99 latency is normally 5ms but spikes to 200ms every 10-15 minutes for 30-60 seconds.

Root cause: Compaction I/O is competing with search I/O on the same QueryNode or MinIO. Compaction reads many segment files from MinIO simultaneously.

Fix: Schedule compaction during off-peak hours. Separate compaction nodes from QueryNodes. Increase MinIO IOPS. Set compaction.trigger.singleCompactionBottomPriority=true.

🟡

[WARNING] Deleted vectors still appearing in search results

Symptom: After calling collection.delete(expr='id==123'), the vector still appears in search results.

Root cause: Milvus deletion is tombstone-based. The delete creates a delta log entry. Until compaction, deleted vectors are filtered by a bloom filter — but the bloom filter has false negative rate, and stale results can appear with Eventually consistency.

Fix: Call collection.compact() after heavy deletes. Use consistency_level='Strong' for searches that must not show deleted data. The bloom filter catch rate is >99.9% but not 100%.

0/8 answered
Question 1 of 8

After calling client.insert(1000 vectors), a search 2 seconds later returns 0 results. What is happening and how do you fix it?

Growing segment visibility. Data written to a growing segment is immediately visible in Milvus with the right consistency level. With consistency='Session' (default), you see your own writes. The issue is usually: (1) using consistency='Eventually' which may miss recent writes, or (2) the insert hasn't been acknowledged yet. Fix: collection.flush() forces growing→sealed transition and waits for confirmation. For real-time apps, use consistency_level='Strong'.
Question 2 of 8

The IndexCoord is showing 200 pending index build tasks and growing. Searches are returning degraded recall. What is the root cause and what are your options?

IndexNode backlog is a classic production failure mode. When DataNodes seal segments faster than IndexNodes can build indexes, the queue grows. Searches on unindexed segments use brute-force (O(N·d)) instead of HNSW (O(log N)), causing recall and latency spikes. Solution: IndexNodes are stateless workers — add more pods in Kubernetes and the backlog drains. Long term: right-size IndexNodes vs DataNodes based on your ingestion rate.
Question 3 of 8

What is Milvus's Timestamp Oracle (TSO) and why does it matter for search consistency?

TSO is the consistency backbone. Every write gets a logical timestamp from RootCoord's TSO. Readers use this timestamp to implement the 4 consistency levels: Strong (read at max TSO), BoundedStaleness (read at TSO - delta), Session (read at your own write's TSO), Eventually (read at any TSO). Without TSO, Milvus couldn't offer any consistency guarantees. This is why RootCoord is the coordinator that dies last — losing TSO means losing consistency.
Question 4 of 8

A QueryNode running on a 64GB RAM machine is OOM-crashing. The collection has 50M vectors at d=768 with HNSW M=16. How much RAM does loading this collection require and what are your options?

RAM = raw vectors + graph, both loaded into QueryNode memory. The formula: N×d×4 + N×M×2×8. For 50M, d=768, M=16: 153.6 + 12.8 = 166.4GB. Real-world addition: 10-20% overhead for metadata and buffers → ~185GB actual. Options ranked by cost: mmap (lowest latency impact but experimental), FLOAT16 (halves vector storage, 0.1% recall drop), IVF_PQ (3GB but ~5% recall drop), larger node, horizontal sharding.
Question 5 of 8

Explain exactly what happens when a Milvus user calls collection.delete(expr='id in [123, 456]'). Why don't the vectors disappear immediately from search results?

Milvus uses tombstone-based deletion. Delete operations write to a delta binlog (delete log), not the main data. QueryNodes hold a bloom filter or bitset of deleted IDs and apply it as a post-filter during search. This means: (1) deleted vectors temporarily waste space, (2) search is slightly slower (bloom filter check), (3) actual space is reclaimed only after compaction. For heavy delete workloads: schedule regular compaction with collection.compact().
Question 6 of 8

What is the role of etcd in Milvus and what happens to the cluster if etcd loses quorum (2 of 3 nodes fail)?

etcd is the single source of truth for all metadata. Without etcd: you can't create/drop collections, can't assign new segments, can't track which segments are indexed, can't balance QueryNodes. In-flight queries on already-loaded segments may complete, but the cluster is effectively read-only for existing loaded data. This is why etcd HA (3-node minimum with Raft consensus) is mandatory in production. Monitor with: etcd_server_has_leader == 0 → CRITICAL alert.
Question 7 of 8

A DataNode keeps restarting. The logs show: 'binlog flush to MinIO failed: context deadline exceeded'. What is the failure chain and how do you diagnose?

DataNode → MinIO is the critical flush path. DataNode buffers growing segment data in memory (configurable, default 128MB per segment). When sealed, it flushes to MinIO as binlog files (insert log + delete log + stats log). If MinIO is unavailable, the DataNode cannot seal segments, cannot free memory, and eventually OOMs. The DataNode log will show exponential backoff on flush retries. Fix sequence: restore MinIO connectivity → DataNode auto-recovers → segments flush → IndexCoord picks up and builds indexes.
Question 8 of 8

You want to monitor Milvus in production. List the most critical metrics and their alert thresholds.

Production monitoring requires 6+ metrics across the full data path. Missing one means silent degradation: a build backlog (metric 2) causes recall drops without any latency alert. Flush pressure (metric 4) predicts OOM crashes before they happen. etcd health (metric 5) predicts total cluster failure. Each metric covers a different failure mode. Complete set: proxy latency, query latency, index build queue, growing segment size, etcd leader, Pulsar disk, QueryNode memory, DataNode flush latency.
