01 · From Exact to Approximate — The Mathematical Necessity

Why exact search breaks at scale

Before understanding approximate search, you need to understand exactly why exact search is mathematically impossible at production scale — not just slow, but literally infeasible on any hardware you can buy.

The curse of dimensionality — distance concentration and complexity wall

What is a vector?

A vector is a point in high-dimensional space. OpenAI's text-embedding-3-small produces 1536-dimensional vectors. Sentence-transformers produce 384–768-dimensional vectors. Each dimension captures a latent semantic feature.

Two vectors are "similar" if their geometric distance is small. The most common metrics: L2 (Euclidean) for spatial data, cosine similarity for text embeddings (normalized L2), inner product for recommendation systems.

Exact nearest neighbour — the O(N·d) wall

Brute force: compare query vector against every vector in the database. For N vectors of dimension d:

cost = N × d multiplications per query
N=1M, d=512, 100 QPS → 51.2B ops/sec
N=100M, d=768, 1000 QPS → 76.8T ops/sec

A 100-core server at 10 GFLOPS/core handles 1 trillion ops/sec. 76.8T requires 77 such servers — for a single query type.

The curse of dimensionality — mathematical proof

Consider N unit-variance random vectors in d dimensions. The squared L2 distance between two random vectors x, y is:

||x-y||² = Σᵢ(xᵢ-yᵢ)² for i=1..d
E[||x-y||²] = Σᵢ E[(xᵢ-yᵢ)²] = Σᵢ Var[xᵢ-yᵢ] = Σᵢ 2 = 2d
Var[||x-y||²] = 4d (by independence)
Std[||x-y||²] / E[||x-y||²] = 2√d / 2d = 1/√d → 0 as d→∞

This means: in high dimensions, all pairwise distances concentrate around the same value 2d. The ratio max_dist/min_dist → 1. Your nearest neighbour is barely closer than your farthest neighbour.

Consequence for KD-trees: KD-trees prune subtrees by checking if the minimum possible distance to a subtree exceeds the current best distance. When all distances are nearly equal, no subtree can be pruned. Every leaf is visited: O(log N) becomes O(N) above d≈20.

🌀

LSH fails at high recall

Locality-Sensitive Hashing: P[h(x)=h(y)] = 1-θ/π. For cosine=0.9 (θ=26°): P≈0.86 per hash. To get 95% recall with L=10 tables, K=8 functions: need 10 hash tables × full scan each. Memory grows 10× and recall still degrades below 90% for high-dimensional data.

📐

The ANN contract

Approximate Nearest Neighbour formally guarantees: ||q-x̂|| ≤ (1+ε)||q-x*|| where x* is the true nearest. ε=0 is exact. ε=0.1 allows 10% farther results. In practice we measure recall@K = |ANN top-K ∩ exact top-K| / K.

△

The recall-latency-memory triangle

You can optimise for exactly 2 of 3: high recall (accurate results), low latency (fast queries), low memory (cheap infra). HNSW: high recall + low latency (high memory). IVF_PQ: low memory + low latency (lower recall). FLAT: high recall + low memory (high latency).

Real numbers from ANN-Benchmarks (glove-100, 1.2M vectors)

FLAT: recall=1.00, latency=450ms/query, QPS=2. Unusable at production scale.

IVF_PQ (m=16, nprobe=128): recall=0.92, latency=0.8ms, QPS=1200. 10% recall drop, 562× faster.

HNSW (M=16, ef=64): recall=0.96, latency=0.4ms, QPS=2500. Best recall/latency ratio.

DiskANN (R=64, L=100): recall=0.97, latency=1.2ms (SSD I/O), QPS=800. Best for N>100M.

IVF — Inverted File Index

How it works

IVF partitions the vector space into nlist Voronoi cells using k-means clustering. Each vector is assigned to its nearest centroid's "inverted list".

Build: Run Lloyd's algorithm for k-means on N vectors to get nlist centroids. Assign each vector to nearest centroid. Cost: O(N·d·nlist·iterations).

Query: Find the nprobe nearest centroids to q, then brute-force search only the vectors in those cells. Cost: O(nprobe · N/nlist · d).

IVF recall formula

recall ≈ 1 - (1 - nprobe/nlist)^K

Example: nlist=4000, K=10
nprobe=400: 1-(0.9)^10 = 65% ✗
nprobe=1200: 1-(0.7)^10 = 97% ✓
nprobe=2000: 1-(0.5)^10 = 99.9% ✓

Rule: nlist = 4√N (Faiss recommendation). At N=1M: nlist=4000. At N=100M: nlist=40000.

HNSW — Hierarchical Navigable Small World

Parameter: M

Connections per node per layer. Layer 0 uses M₀=2M.

Memory = N×M×2×8 bytes
N=10M, M=16: 2.56 GB
N=10M, M=32: 5.12 GB

Rule: M=16 default, M=32 for recall≥99%

Parameter: efConstruction

Build-time beam width. Higher = better graph quality but slower build.

Build cost ∝ efConstruction
ef=200: good quality (default)
ef=400: +20% build time, +1-2% recall
Minimum: efConstruction ≥ M×2

Never go below M×2 — graph degrades

Parameter: ef (search)

Query-time beam width. Controls recall vs speed tradeoff. Can change per query without rebuilding.

ef must be ≥ top_k
ef=64: ~95% recall, fast
ef=128: ~99% recall, 2× slower
ef=256: ~99.5%, diminishing returns

Rule: ef=2×top_k for 95%+, ef=4×top_k for 99%+

DiskANN — Billion-Scale on Commodity Hardware

The RAM wall problem and DiskANN's solution

At N=1B vectors d=768: HNSW requires 307GB (vectors) + 25.6GB (M=16 graph) = 333GB RAM. That's 4-5 A100 servers just for one index. DiskANN stores the Vamana graph on SSD and only PQ-compressed vectors in RAM.

HNSW @ 1B vectors d=768
RAM: 333 GB
Cost: ~$5K/month (5× A100)
Latency: <1ms
DiskANN @ 1B vectors d=768
RAM: ~25 GB (PQ only)
SSD: 3 TB NVMe ($400)
Latency: 1-3ms (SSD I/O)

IVF_PQ — Maximum Compression

🗜️

Product Quantization memory formula

IVF_PQ compresses each d-dimensional vector into m bytes (m sub-quantizers × 1 byte each). For d=768 and m=32: compression = 768×4 / 32 = 96× smaller. N=100M vectors: 100M×768×4=307GB → 100M×32=3.2GB. The recall drop is typically 3-8% vs IVF_FLAT at the same nprobe. Use when RAM is the primary constraint.

def calculate_ram(N, d, index_type, M=16, m_pq=32):
    """
    Calculate RAM requirements for different Milvus index types.
    N: number of vectors
    d: vector dimension  
    M: HNSW graph degree (default 16)
    m_pq: IVF_PQ subquantizers (default 32)
    Returns: RAM in GB
    """
    bytes_per_float = 4
    
    if index_type == 'FLAT':
        # Raw vectors only
        return (N * d * bytes_per_float) / 1e9
    
    elif index_type == 'HNSW':
        # Vectors + graph (layer 0 uses M0=2M connections)
        vec_bytes = N * d * bytes_per_float
        graph_bytes = N * M * 2 * 8  # 8 bytes per int64 node ID
        return (vec_bytes + graph_bytes) / 1e9
    
    elif index_type == 'IVF_FLAT':
        nlist = int(4 * N**0.5)
        centroid_bytes = nlist * d * bytes_per_float
        vec_bytes = N * d * bytes_per_float
        return (centroid_bytes + vec_bytes) / 1e9
    
    elif index_type == 'IVF_SQ8':
        nlist = int(4 * N**0.5)
        centroid_bytes = nlist * d * bytes_per_float
        vec_bytes = N * d * 1  # INT8: 1 byte per dimension
        return (centroid_bytes + vec_bytes) / 1e9
    
    elif index_type == 'IVF_PQ':
        nlist = int(4 * N**0.5)
        centroid_bytes = nlist * d * bytes_per_float
        code_bytes = N * m_pq  # m bytes per vector (1 byte per subquantizer)
        return (centroid_bytes + code_bytes) / 1e9
    
    elif index_type == 'DiskANN':
        # Only PQ-compressed vectors in RAM, full graph on SSD
        pq_bytes = N * m_pq
        return pq_bytes / 1e9

Real company decisions — with actual numbers

Spotify — 500M track recommendations

Problem: 500M audio embeddings at d=128, need <10ms for "similar tracks", 50K QPS peak.

Why not HNSW: 500M×128×4 = 256GB vectors alone. Graph adds 64GB. 320GB × 3 replicas = 960GB RAM. At $5/GB/month = $4,800/month just for one index.

Decision: DiskANN on NVMe SSD cluster. PQ-compressed vectors in RAM: ~8GB. SSD: 256GB × 3 replicas = ~$400 hardware. Latency: 2-5ms. Result: 95× cheaper infra.

Notion — document semantic search

Problem: 200M document chunks at d=768, need <50ms, 500 QPS, high recall (users expect exact matches).

Why not IVF_PQ: 5-8% recall drop is unacceptable for document search where users expect to find their own documents.

Decision: HNSW M=16 in pgvector (Postgres). 200M×768×4=614GB vectors + graph=25.6GB ≈ 640GB. Sharded across 10 nodes × 64GB each. ef=128 gives 99%+ recall. Result: users find their documents.

Question 1 of 8

You have N=5M vectors at d=768. Your p99 search latency must be under 20ms and recall@10 must exceed 97%. RAM budget is 64GB. Which index and why?

HNSW is correct. At N=5M d=768 FLOAT32: vectors=5M×768×4=15.3GB, HNSW graph (M=32)=5M×32×2×8=2.56GB, total≈18GB — well under 64GB. O(log N)≈22 hops × ~1ms per hop = <5ms p50. ef=128 gives 98%+ recall on most datasets. DiskANN is for N>100M or RAM <20GB. IVF_PQ would work but recall drops to 88-94%.
Question 2 of 8

The recall formula for IVF with nprobe cells searched out of nlist total cells is: recall ≈ 1-(1-nprobe/nlist)^K. For nlist=4000 and K=10, what nprobe gives ~95% recall?

The formula: recall ≈ 1-(1-nprobe/nlist)^K. For 95% recall: 0.95=1-(1-p)^10 → (1-p)^10=0.05 → 1-p=0.05^0.1=0.741 → p=0.259 → nprobe=0.259×4000=1036. Closest standard value: nprobe=1200 gives 97.2%. The rule nlist=4√N means for N=1M: nlist=4000, confirming the formula. DiskANN and HNSW don't use this formula — it's IVF-specific.
Question 3 of 8

A team reports their HNSW index uses 200GB RAM for 50M vectors at d=768 with M=16. Is this correct? What should it actually be?

Correct formula: RAM = raw vectors + graph. Vectors: 50M×768×4 bytes = 153.6GB. Graph (M=16, layer 0 uses M0=32): approximately 50M×16×2×8 = 12.8GB. Total ≈ 166.4GB. The extra 34GB is likely from loading 2 replicas (QueryNode failover). HNSW in Milvus stores FLOAT32 vectors by default unless you use FLOAT16_VECTOR. To reduce: use FLOAT16 (halves vector storage) or IVF_PQ for 10× compression.
Question 4 of 8

Distance concentration means all pairwise distances in high dimensions converge. What is the precise mathematical statement and its consequence for KD-trees?

The precise statement: E[||x-y||²]→2d and Var[||x-y||²]=O(d). So the standard deviation is O(√d) while the mean is O(d), giving coefficient of variation = O(1/√d) → 0. In practice at d=512: all pairwise distances are within ~3% of each other. KD-tree pruning works by eliminating subtrees where the minimum possible distance exceeds the current best. When all distances are similar, no subtree can be eliminated, so you must visit every node → O(N).
Question 5 of 8

The ANN contract specifies ||q-x̂|| ≤ (1+ε)||q-x*||. For ε=0.1 and true nearest distance 10.0, what distances qualify as valid ANN results?

The (1+ε) factor is multiplicative, not additive. (1+0.1)×10.0=11.0. This means the ANN result can be up to 10% farther than the true nearest neighbour. In practice recall@K measures this empirically: recall@10=0.97 means 97% of the ANN top-10 overlap with the exact top-10. The ε-ANN guarantee is stronger than recall — it guarantees every result is within (1+ε)× the optimal distance.
Question 6 of 8

Spotify needs to serve 'similar songs' for 500M tracks at d=128 (audio embeddings) with 8ms p99 latency. RAM budget per node: 32GB. What is the correct architecture?

Both B and C are viable; DiskANN is the production choice. Spotify actually uses an internal graph-based system similar to DiskANN. IVF_PQ: 500M×16bytes=8GB PQ codes per node, but recall drops to 88-93% with m=16. DiskANN: 500M×128×4=256GB on SSD (cheap), ~8GB PQ in RAM, 95-98% recall, 1-3ms SSD overhead. At d=128 the SSD overhead is small per hop. For 8ms p99, DiskANN on NVMe SSD easily meets budget. HNSW is eliminated by RAM — 256GB + graph would need 8+ nodes.
Question 7 of 8

You are benchmarking two indexes: Index A achieves recall@10=0.97 at 2000 QPS, Index B achieves recall@10=0.95 at 3500 QPS. Your SLA requires recall@10≥0.96 and latency≤5ms at 1000 QPS. Which do you choose and why?

Index A is the correct choice. Requirements: recall≥0.96 AND latency≤5ms at 1000 QPS. Index B fails on recall (0.95<0.96). Index A meets recall at 2000 QPS headroom. At 1000 QPS (half its max throughput), latency will be well under the limit for most index types. Moreover, HNSW/IVF allow tuning ef/nprobe at query time — you can reduce ef slightly to get lower latency while keeping recall above 0.96. Never sacrifice a hard SLA requirement (recall≥0.96) for throughput when you have headroom.
Question 8 of 8

LSH uses random projections with collision probability P[h(x)=h(y)]=1-θ/π where θ is the angle between vectors. For cosine similarity = 0.9 (θ≈26°), what is P[collision] and why does LSH need multiple hash tables?

P=1-θ/π=1-26°/180°≈0.86. So for cos_sim=0.9, similar vectors collide 86% of the time per hash function. But with K hash functions in one table: P[all K match]=(0.86)^K — drops quickly. To maintain high recall, use L tables, each with K hash functions. A candidate is retrieved if it collides in ANY of the L tables: recall≈1-(1-p^K)^L. Typical: K=8, L=10 gives recall≈1-(1-0.86^8)^10≈94%. The tradeoff: more tables = higher recall but more memory and slower query (scan each table).
