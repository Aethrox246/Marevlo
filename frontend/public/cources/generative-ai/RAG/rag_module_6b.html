01 · The Vocabulary Mismatch Problem

Why BM25 Fails and
What Dense Retrieval Fixes

In Module 6A, we saw that BM25 scores based on shared tokens. If query and document share no tokens, the score is zero regardless of semantic meaning. "Heart attack" and "myocardial infarction" describe the same condition but share zero tokens. "Buy" and "purchase" are synonyms but BM25 treats them as completely different. Dense retrieval solves this by mapping text into a continuous vector space where semantically similar text lands near each other — regardless of the specific words used.

The Same Problem, Three Query Types BM25 Cannot Handle

Synonyms

Query: "buy a plan"   Document: "purchase a subscription"

Shared tokens: 0   BM25 score: 0.000

Dense cosine: 0.87 (very similar)

Abbreviations

Query: "MI treatment protocol"   Document: "myocardial infarction guidelines"

Shared tokens: 0   BM25 score: 0.000

Dense cosine: 0.91 (highly similar)

Paraphrase

Query: "how to undo a transaction"   Document: "steps to reverse a payment"

Shared tokens: 1 ("to")   BM25 score: ~0.001

Dense cosine: 0.84 (semantically close)

02 · The Bi-Encoder Architecture

Two BERT Towers,
One Vector Space

A bi-encoder encodes queries and documents independently using the same (or separate) transformer encoders. Both produce dense vectors of the same dimensionality. At retrieval time, similarity is computed with a single dot product or cosine similarity — making it fast enough to search millions of documents.

Bi-Encoder Inference Architecture

OFFLINE (once per document)

"Annual subscriptions are non-refundable..."
↓
BERT Encoder (12-24 transformer layers)
↓ [CLS] token or mean pooling
ddoc = [0.23, -0.41, 0.87, ...]   (768 or 1024 dims)
↓ stored in vector DB
Qdrant / Pinecone / Chroma

ONLINE (every query, real-time)

"how do I cancel my annual plan?"
↓
Same BERT Encoder (shared weights)
↓
dquery = [0.19, -0.38, 0.91, ...]   (same 768 dims)
↓ cosine(d_query, all d_docs) via ANN
Top-k most similar documents returned
💡

Why this is fast

Documents are encoded once at ingestion time and stored. At query time, only the query needs encoding (one forward pass, ~5ms). Similarity is then computed via Approximate Nearest Neighbor search (HNSW, IVF), which finds the closest vectors without comparing against every document. This is why Pinecone can search 1 billion vectors in under 100ms.

03 · Cosine Similarity — The Math

How Vectors Score Relevance:
A Worked Calculation

Dense retrieval scores documents by cosine similarity between query and document embeddings. Cosine measures the angle between two vectors, not their magnitude. Two texts can express the same idea in different lengths and still have cosine similarity close to 1.0 if their embeddings point in the same direction.

cosine(q, d) = (q · d) / (||q|| · ||d||) = Σ qidi / (√Σqi² · √Σdi²)
q = query embedding vector  ·  d = document embedding vector  ·  ||v|| = L2 norm (Euclidean length) of vector v
Range: −1 (opposite) to +1 (identical direction). For normalized embeddings the dot product q·d equals cosine similarity directly.

Worked Example: 4-dimensional embeddings (real models use 768-1024 dims)

We have simplified 4-dimensional embeddings for illustration. In production, text-embedding-3-small uses 1536 dimensions, BGE-large uses 1024. The math is identical, just with more terms.

Query: "annual refund" q = [0.80, 0.20, 0.50, 0.10] ||q|| = sqrt(0.64+0.04+0.25+0.01) = 0.964
D1: "annual subscriptions non-refundable after 30 days" d1 = [0.75, 0.15, 0.55, 0.05] ||d1|| = 0.942
D2: "monthly cancellation no penalty" d2 = [0.10, 0.80, 0.15, 0.60] ||d2|| = 1.018
// dot products
q · d1 = (0.80×0.75) + (0.20×0.15) + (0.50×0.55) + (0.10×0.05)
     = 0.600 + 0.030 + 0.275 + 0.005 = 0.910
q · d2 = (0.80×0.10) + (0.20×0.80) + (0.50×0.15) + (0.10×0.60)
     = 0.080 + 0.160 + 0.075 + 0.060 = 0.375

// cosine similarity
cosine(q, d1) = 0.910 / (0.964 × 0.942) = 0.910 / 0.908 = 1.002 ≈ 1.00 (very similar)
cosine(q, d2) = 0.375 / (0.964 × 1.018) = 0.375 / 0.981 = 0.382 (not similar)
✓

D1 (annual subscriptions, non-refundable) scores 1.00 — it is semantically aligned with "annual refund". D2 (monthly cancellation) scores 0.38 — different semantic territory. Notice neither the query nor D1 mention "refund" explicitly; the vector captures the semantic relationship between "non-refundable" and "refund". This is what BM25 cannot do.

04 · DPR: Dense Passage Retrieval

The Foundational Paper:
How Bi-Encoders Are Trained

DPR (Dense Passage Retrieval, Karpukhin et al., Facebook AI 2020) was the paper that proved dense retrieval could outperform BM25 on open-domain question answering. It established the training paradigm that most modern embedding models still follow.

DPR Training Setup: Contrastive Learning with In-Batch Negatives

DPR trains two BERT encoders (one for questions, one for passages) using a batch of (question, positive passage, negative passages) triples:

Positive pair: Question "What is Marevlo's refund policy?" paired with passage "Annual subscriptions are non-refundable after 30 days per Marevlo's ToS section 4.2."
In-batch negatives: All other passages in the batch become negatives. If batch_size=64, each question has 63 negative passages. These are efficient: no extra sampling, just reuse what is already in GPU memory.
Hard negatives (ANCE improvement): Passages that are topically similar but not the actual answer. BM25 is used to find passages that match lexically but are wrong answers — forcing the model to learn deeper semantic distinctions.
L = −log( exp(q · p+) / ( exp(q · p+) + Σi exp(q · pi−) ) )
This is the InfoNCE / NT-Xent contrastive loss. It maximizes the dot product between query and positive passage while minimizing it with all negative passages.
p+ = positive passage  ·  pi− = negative passages  ·  temperature is typically set to 1.0 in DPR
💡

What DPR learns

After training on 58,880 questions from Natural Questions and TriviaQA, DPR's encoders learn a vector space where semantically related questions and passages have high dot product scores. "MI treatment" and "myocardial infarction guidelines" will be near each other because the model has seen many such semantic equivalences during training. The vectors encode meaning, not vocabulary.

05 · Bi-Encoder vs Cross-Encoder

The Precision vs Speed
Fundamental Tradeoff

Bi-encoders encode query and document independently and score with a dot product. Cross-encoders concatenate query and document and process them together through the full transformer. Cross-encoders are dramatically more accurate but cannot scale to large corpora — which is why the two are used in different stages of the same pipeline.

Bi-Encoder (Retrieval Stage)

Query → BERT → q_vec (768d)
encoded independently
Doc → BERT → d_vec (768d) → stored offline
similarity = dot(q_vec, d_vec)
✓ Sub-100ms on millions of docs via ANN index
✓ Documents encoded once offline, reused forever
✓ Scales to any corpus size
✗ Cannot model query-document interactions (each is encoded in isolation)
✗ Less accurate than cross-encoder on hard relevance judgments

Complexity: O(1) per doc at query time (ANN lookup)

Cross-Encoder (Reranking Stage)

[CLS] Query [SEP] Document [SEP]
concatenated, processed together
BERT full forward pass on the pair
relevance_score = linear([CLS])
✓ Highest accuracy — sees query and doc together, models full interaction
✓ Captures fine-grained relevance (negation, conditionals, context)
✗ Cannot pre-compute: every (query, doc) pair requires a fresh forward pass
✗ 50-200ms per pair → only feasible for top-50 candidates, not millions
✗ Cannot be used for first-stage retrieval

Complexity: O(N) per query, can only score N~50 candidates

💡

Standard 2-stage pipeline

Stage 1 (Retrieval): Bi-encoder retrieves top-100 candidates from millions of documents in <100ms. Stage 2 (Reranking): Cross-encoder rescores the 100 candidates and returns top-5 in ~500ms. The cross-encoder sees the query and each candidate together and can make much more accurate relevance judgments. Module 8 covers reranking in depth.

06 · ColBERT: Late Interaction

Token-Level Matching:
Precision Without Reranker Latency

ColBERT (Contextualized Late Interaction over BERT, Khattab & Zaharia 2020) introduced a middle ground between bi-encoders and cross-encoders. Instead of encoding each passage into a single vector, ColBERT stores per-token embeddings for every document. At query time, each query token finds its best matching document token (MaxSim operation), giving much finer-grained matching than single-vector bi-encoders.

ColBERT MaxSim Scoring — Worked Example

Query: "annual refund" → tokenized to [annual, refund]. Document: "annual subscriptions non-refundable" → tokenized to [annual, subscriptions, non-refundable]. ColBERT stores one embedding per document token.

S(q,d) = Σi∈q maxj∈d (Eq(qi) · Ed(dj))
For each query token, find the document token with maximum similarity. Sum these per-query-token maximums. This allows "refund" to match "non-refundable" by finding the nearest document token in the embedding space.
// Token embeddings (simplified 2D for illustration)
E("annual") = [0.90, 0.20]   E("refund") = [0.10, 0.85]

E("annual") = [0.88, 0.22]   E("subscriptions") = [0.40, 0.30]   E("non-refundable") = [0.15, 0.80]
                                                                 ^^ close to "refund"

// MaxSim for query token "annual"
sim(annual_q, annual_d) = 0.90×0.88 + 0.20×0.22 = 0.836 ← max
sim(annual_q, subscriptions) = 0.90×0.40 + 0.20×0.30 = 0.420
MaxSim("annual") = 0.836

// MaxSim for query token "refund"
sim(refund_q, annual_d) = 0.10×0.88 + 0.85×0.22 = 0.275
sim(refund_q, non-refundable) = 0.10×0.15 + 0.85×0.80 = 0.695 ← max
MaxSim("refund") = 0.695

S(query, doc) = 0.836 + 0.695 = 1.531
💡

Why ColBERT finds "non-refundable" for query "refund"

In the embedding space learned by ColBERT, "refund" and "non-refundable" are semantically close neighbors (both relate to the refund concept). MaxSim finds this connection that a single-vector bi-encoder would miss unless its pooled representation happened to capture the relationship. ColBERT is more accurate than standard bi-encoders at the cost of higher storage (one vector per token vs one per document).

⚠️

ColBERT storage cost

A 200-token document with 128-dimensional token embeddings requires 200 × 128 × 4 bytes = 102KB per document. One million documents = 97GB. Standard bi-encoders: 1 vector × 768 dims per document = 3KB per document, 2.9GB for 1M docs. ColBERT v2 adds compression to reduce this ~10x, but storage remains significantly higher than single-vector approaches.

07 · Modern Embedding Models

E5, BGE, Nomic, NV-Embed:
What Makes Each Different

After DPR established the bi-encoder paradigm, a series of models improved retrieval quality through better training data, instruction-following capabilities, and architecture changes. Here are the models you will actually use in production and why they differ.

Meta DPR (2020)

The original. Separate question and passage encoders trained on NQ and TriviaQA. Still a valid baseline. Not instruction-following — queries are embedded as-is without any prefix.

768dOpen sourceNQ NDCG@10: 41.5

Microsoft E5 family (2022-2024)

E5 (Embeddings from bidirectional Encoder representations) trained on a massive curated mixture of text pairs from multiple domains. Key innovation: instruction prefixes. For retrieval queries you prepend "query: " and for documents "passage: ". E5-large-v2 and E5-mistral-7b are strong all-round choices. Multilingual E5 covers 100+ languages.

1024dOpen sourceMTEB avg: 56.5Instruction-following

BAAI BGE family (2023-2024)

BGE (BAAI General Embedding) models are among the top performers on MTEB. BGE-large-en-v1.5 requires the instruction prefix "Represent this sentence for searching relevant passages: " for retrieval queries. BGE-M3 is multilingual and handles documents up to 8192 tokens. BGE-reranker models provide a matching cross-encoder for the reranking stage.

1024dOpen sourceMTEB avg: 64.28K token support

Nomic nomic-embed-text-v1.5 (2024)

First truly open embedding model (training code + data released). Outperforms OpenAI text-embedding-ada-002. Supports 8192 context length. Task-specific prefixes: "search_query: " for queries, "search_document: " for documents, "clustering: " for clustering tasks. Fully local deployment, no API calls needed.

768dFully open (data+code)8K context

OpenAI text-embedding-3-small/large (2024)

Strong baseline, minimal setup. text-embedding-3-small is 1536d, 8192 token context. Supports Matryoshka Representation Learning (MRL): you can truncate to 256d or 512d and still get good performance, saving vector DB storage costs. Does NOT need instruction prefixes. API-only — not locally deployable.

1536d / 3072dAPI onlyMRL support
💡

How to choose: MTEB Leaderboard

The MTEB (Massive Text Embedding Benchmark) at huggingface.co/spaces/mteb/leaderboard evaluates models on 56 datasets across 8 tasks. Look at the "Retrieval" subtask scores for your domain. For production RAG: BGE-large-en-v1.5 or nomic-embed-text for self-hosted, text-embedding-3-small for managed API. Always evaluate on a sample of your own queries before committing.

08 · Production Code

Dense Retrieval From Model
to LangChain Vector Store

dense_retrieval.py

from sentence_transformers import SentenceTransformer
from langchain_community.vectorstores import Qdrant
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain.schema import Document
import numpy as np

# ── BGE-large: instruction prefix required for queries ────────
model = SentenceTransformer("BAAI/bge-large-en-v1.5")

# For BGE models: queries need the instruction prefix
# Documents do NOT need the prefix
QUERY_PREFIX = "Represent this sentence for searching relevant passages: "

corpus = [
    "Annual subscriptions are non-refundable after the 30-day trial.",
    "Monthly subscriptions may be cancelled at any time.",
    "Refund requests must include your annual subscription ID.",
    "Enterprise support handles annual contract refund disputes.",
]

# ── Embed documents (offline, store results) ──────────────────
doc_embeddings = model.encode(
    corpus,
    normalize_embeddings=True,   # L2-normalize so dot product = cosine
    batch_size=32,
    show_progress_bar=True,
)
# doc_embeddings.shape: (4, 1024) for BGE-large

# ── Embed and retrieve a query ─────────────────────────────────
query = "how do I get a refund on my annual plan?"
q_emb = model.encode(
    [QUERY_PREFIX + query],
    normalize_embeddings=True,
)[0]

# Exact cosine similarity (small corpus): dot product since normalized
scores = doc_embeddings @ q_emb
ranked = np.argsort(scores)[::-1]
print(f"Query: {query}")
for i in ranked:
    print(f"  [{scores[i]:.4f}] {corpus[i][:65]}")

# ── LangChain + Qdrant production setup ───────────────────────
embeddings = HuggingFaceEmbeddings(
    model_name="BAAI/bge-large-en-v1.5",
    encode_kwargs={"normalize_embeddings": True},
    query_instruction=QUERY_PREFIX,
)
docs = [Document(page_content=c, metadata={"source": "policy.pdf"})
        for c in corpus]

# Create Qdrant collection and index documents
vectorstore = Qdrant.from_documents(
    docs, embeddings,
    location=":memory:",   # use URL for production: "http://localhost:6333"
    collection_name="policy_docs",
)

# Retrieve top-5 similar documents
retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 5}
)
results = retriever.invoke("refund for annual subscription")

# ── Cosine similarity with threshold (filter low-quality) ─────
retriever_with_threshold = vectorstore.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.7, "k": 10}
    # Only returns docs with cosine similarity >= 0.7
)
09 · Assessment

Module 6B Quiz

Questions about architecture tradeoffs and when to use each approach.

1. Query: "MI symptoms". The most relevant document uses "myocardial infarction" throughout with zero token overlap with "MI". A BGE-large bi-encoder returns this document as #1. Why can it do this when BM25 cannot?

Correct. Dense models learn semantic relationships from data. "MI" and "myocardial infarction" appear in contexts suggesting equivalence in medical literature. The contrastive training objective pushes their embeddings close together. This generalization is what makes dense retrieval fundamentally different from lexical methods.

2. You have two cosine scores. Query vector q = [0.6, 0.8] (already L2-normalized). Doc A = [0.7, 0.7] (normalized). Doc B = [0.9, 0.1] (normalized). Which document is more relevant and why?

Correct. The calculation: cosine(q,A) = (0.6x0.7)+(0.8x0.7) = 0.42+0.56 = 0.98 (near-identical direction). cosine(q,B) = (0.6x0.9)+(0.8x0.1) = 0.54+0.08 = 0.62 (different direction). Doc A has high alignment on both dimensions; Doc B dominates only on the first dimension but diverges on the second. Cosine measures angle, not magnitude.

3. You need to retrieve from 10 million documents at query time with p50 latency under 100ms. Should you use a bi-encoder or cross-encoder for the retrieval stage?

Correct. Cross-encoders cannot pre-compute anything because the score depends on both query and document together. At retrieval time they must process every document fresh. Even a fast cross-encoder at 10ms per pair would need 27.8 hours per query on 10M documents. Bi-encoders pre-compute all document vectors offline; at query time you only embed the query once and search the ANN index.

4. ColBERT stores per-token embeddings instead of a single pooled vector. This increases storage cost. What accuracy advantage does this provide over standard bi-encoders?

Correct. Standard bi-encoder: "refund" and "non-refundable" are both averaged into the document's single 768-dimensional vector along with all other tokens. Whether they align with the query depends on how well pooling preserved their relationship. ColBERT: "refund" query token directly computes max similarity against all document tokens. "non-refundable" will be a close neighbor in token embedding space and will score high.

5. You are using BGE-large-en-v1.5. A colleague removes the query instruction prefix, arguing "the model should work without it." Retrieval quality drops significantly. Why does removing the prefix hurt?

Correct. Instruction-following embedding models were fine-tuned with task-specific prefixes. The prefix shapes what aspect of the text the encoder emphasizes. "search relevant passages" tells the encoder: optimize for retrieval relevance. The document embeddings in your index were computed without any prefix, and the query encoder was trained to align with those when given the retrieval instruction. Removing it creates a mismatch.
