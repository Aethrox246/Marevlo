HPO.
The GP optimizes the optimizer.

Every model in this track has hyperparameters — learning rate, dropout, number of layers, batch size. We've picked them by intuition, rules of thumb, and tables from earlier modules. Bayesian Hyperparameter Optimization (HPO) replaces intuition with a principled search: a GP surrogate models the relationship between hyperparameters and validation performance, then an acquisition function uses the GP's uncertainty to decide what to try next. In 20-50 evaluations, it finds configurations that grid search would need thousands of trials to reach.

The hyperparameter problem.

CineMatchTransformer has at least 8 hyperparameters: learning rate, warmup steps, weight decay, dropout, number of layers, dmodel, number of heads, dff. If you try 5 values per hyperparameter, grid search needs 5⁸ = 390,625 evaluations. Each evaluation trains the model for ~30 minutes. Total: 22 years of GPU time.

Random search is better — Bergstra & Bengio (2012) showed that random samples find good configurations faster than grid search because they don't waste trials on irrelevant dimensions. But random search is still blind — it doesn't learn from past evaluations. Trial 50 is no smarter than trial 1.

Bayesian optimization (BO) fixes this: it uses past evaluations to build a model of the hyperparameter-to-performance landscape, then uses that model to choose the most informative next configuration to try.

The BO principle

Don't evaluate hyperparameters randomly. Use a GP to model what you've seen so far, then choose the next trial to maximize expected improvement — balancing exploitation (try configurations the GP thinks are good) with exploration (try configurations the GP is uncertain about).

Search strategiesQuestion 01 / 07
Why does random search outperform grid search for hyperparameter tuning?

BRandom search always finds the global optimum.
CIn most problems, only 2-3 hyperparameters matter significantly. Grid search wastes trials on a regular lattice — many points differ only in irrelevant dimensions. Random search projects more unique values onto each important dimension, covering the important subspace more efficiently with the same budget.
DRandom search is faster to implement in Python.

The Bayesian optimization loop.

BO is a loop with four steps, repeated until the budget is exhausted:

Step 1: Initialize. Evaluate 5-10 random configurations to seed the GP. You need initial data before the GP can model anything.

Step 2: Fit the GP surrogate. Train a GP on all (hyperparameter, validation-loss) pairs observed so far. The GP provides a posterior mean (predicted performance for any untried configuration) and posterior variance (uncertainty about that prediction).

Step 3: Maximize the acquisition function. Choose the next configuration by optimizing an acquisition function over the GP's posterior. The acquisition function balances exploitation (low predicted loss) and exploration (high uncertainty).

Step 4: Evaluate. Train the model with the chosen hyperparameters. Record the validation loss. Add to the GP's dataset. Go to Step 2.

# Simplified Bayesian Optimization loop
import numpy as np
from scipy.optimize import minimize
from scipy.stats import norm

def expected_improvement(x, gp, best_y):
    """EI acquisition function."""
    mu, var = gp.predict(x)
    sigma = np.sqrt(var + 1e-8)
    z = (best_y - mu) / sigma
    return sigma * (z * norm.cdf(z) + norm.pdf(z))

def bayesian_optimization(objective, bounds, n_init=5, n_iter=30):
    # Step 1: Initialize with random samples
    X = np.random.uniform(bounds[:, 0], bounds[:, 1], (n_init, bounds.shape[0]))
    y = np.array([objective(x) for x in X])

    for i in range(n_iter):
        # Step 2: Fit GP
        gp = fit_gp(X, y)

        # Step 3: Maximize acquisition function
        best_y = y.min()
        next_x = maximize_ei(gp, best_y, bounds)

        # Step 4: Evaluate
        next_y = objective(next_x)
        X = np.vstack([X, next_x])
        y = np.append(y, next_y)

    return X[y.argmin()], y.min()

Acquisition functions — EI and UCB.

The acquisition function decides where to look next. Two dominant choices:

Expected Improvement (EI).

Given the best validation loss f* observed so far, EI measures the expected amount by which a new evaluation at x might improve over f*:

EI(x) = E[max(f* − f(x), 0)] = σ(x) · [z · Φ(z) + φ(z)] (3.1)

Where z = (f* − μ(x)) / σ(x), Φ is the standard normal CDF, and φ is its PDF. EI is high when the GP predicts low loss (μ(x) < f*) OR when uncertainty is high (σ(x) is large). It naturally balances exploitation and exploration.

Math Core — deriving the EI closed form.

EI starts from the definition: the expected value of max(f* − f(x), 0) under the GP posterior f(x) ~ N(μ, σ²):

EI(x) = ∫−∞f* (f* − f) · φ((f − μ)/σ) / σ  df (3.3)

Substituting u = (f − μ)/σ and integrating by parts:

EI(x) = (f* − μ) · Φ(z) + σ · φ(z)    where z = (f* − μ)/σ (3.4)

The two terms have clear meanings: (f* − μ)·Φ(z) is the exploitation term — large when the GP predicts the point is good (μ < f*). σ·φ(z) is the exploration term — large when uncertainty is high. Neither dominates; EI balances them without any tuning parameter.

Worked example — computing EI for two candidate configurations.

EI computation with f* = 0.16 (best validation loss so far)
Config A: μ_A = 0.15, σ_A = 0.01. z_A = (0.16 − 0.15) / 0.01 = 1.0GP is fairly confident A is slightly better than f*
EI(A) = (0.16 − 0.15) · Φ(1.0) + 0.01 · φ(1.0) = 0.01 · 0.8413 + 0.01 · 0.2420= 0.00841 + 0.00242 = 0.01083
Config B: μ_B = 0.18, σ_B = 0.12. z_B = (0.16 − 0.18) / 0.12 = −0.167GP thinks B is slightly worse than f*, but very uncertain
EI(B) = (0.16 − 0.18) · Φ(−0.167) + 0.12 · φ(−0.167) = −0.02 · 0.4338 + 0.12 · 0.3939= −0.00868 + 0.04727 = 0.03859
EI(B) = 0.039 > EI(A) = 0.011 — BO picks B, the uncertain option!The exploration term (σ·φ) dominates. BO bets on B's upside potential.

Upper Confidence Bound (UCB).

UCB(x) = μ(x) − κ · σ(x) (3.2)

For minimization, we subtract κ · σ — optimistic in the face of uncertainty. Pick x that has the lowest optimistic estimate. The parameter κ controls the exploration-exploitation balance: κ = 0 is pure exploitation (just pick the lowest predicted loss), κ = 3 is aggressive exploration (heavily explore uncertain regions).

CineMatch Integration

50 trials vs 390,625.

BO with 50 trials (each training CineMatchTransformer for ~30 min) takes ~25 hours of GPU time. Grid search over the same 8 hyperparameters needs 390,625 trials = 22 GPU-years. BO typically finds a configuration within 2-5% of the global optimum. The result on CineMatch: Hits@10 improves from ~35% (hand-tuned from Module 4.2) to ~38% (BO-tuned) — a meaningful production improvement from automated search alone.

Failure case — BO gets stuck in a local basin.

Common BO failure mode

The GP over-exploits a good-looking region and misses better ones.

After 10 trials, the GP finds that lr ≈ 3e-4 with 4 layers works well (val loss 0.17). Subsequent trials cluster tightly around this region — the GP is confident here (low σ), so EI for nearby points is dominated by the exploitation term. Meanwhile, the GP has never tried lr ≈ 1e-5 with 8 layers — it has high σ there, but the exploration term isn't enough to overcome the exploitation pull. Symptoms: the Optuna "optimization history" plot shows rapid early improvement then a long plateau. Fixes: (1) increase n_startup_trials from 5 to 15 (more initial random exploration), (2) use Hyperband instead of pure BO (forces diversity), (3) periodically inject random trials (Optuna's CmaEsSampler with restart).

Build It — minimal GP-BO from scratch (no libraries).

import numpy as np
from scipy.stats import norm

class SimpleGPBO:
    """GP-based Bayesian Optimization from scratch. No Optuna, no GPyTorch."""
    def __init__(self, bounds, l=0.5, sigma=1.0, noise=1e-4):
        self.bounds = np.array(bounds)  # (D, 2) min/max per dim
        self.l, self.sigma, self.noise = l, sigma, noise
        self.X, self.y = [], []

    def _rbf(self, X1, X2):
        sq = np.sum((X1[:, None] - X2[None, :])**2, axis=-1)
        return self.sigma**2 * np.exp(-sq / (2 * self.l**2))

    def _predict(self, X_test):
        X = np.array(self.X)
        K = self._rbf(X, X) + self.noise * np.eye(len(X))
        Ks = self._rbf(X, X_test)
        Kss = self._rbf(X_test, X_test)
        L = np.linalg.cholesky(K + 1e-6 * np.eye(len(K)))
        alpha = np.linalg.solve(L.T, np.linalg.solve(L, self.y))
        mu = Ks.T @ alpha
        v = np.linalg.solve(L, Ks)
        var = np.diag(Kss) - np.sum(v**2, axis=0)
        return mu, np.maximum(var, 1e-8)

    def _ei(self, X_test):
        mu, var = self._predict(X_test)
        sigma = np.sqrt(var)
        best = np.min(self.y)
        z = (best - mu) / sigma
        return (best - mu) * norm.cdf(z) + sigma * norm.pdf(z)

    def suggest(self, n_candidates=5000):
        """Suggest next point by maximizing EI over random candidates."""
        cands = np.random.uniform(self.bounds[:, 0], self.bounds[:, 1],
                                  (n_candidates, self.bounds.shape[0]))
        ei = self._ei(cands)
        return cands[np.argmax(ei)]

    def tell(self, x, y):
        self.X.append(x); self.y.append(y)

Practical HPOQuestion 04 / 07
Why does Optuna use TPE (Tree-structured Parzen Estimator) instead of a standard GP for Bayesian optimization?
AGP-based BO requires inverting an N×N kernel matrix, which scales poorly as the number of completed trials grows. More critically, GPs struggle with mixed continuous/categorical hyperparameters. TPE models P(hyperparameters | good results) and P(hyperparameters | bad results) separately, which handles categorical variables naturally and scales to higher-dimensional search spaces.
BTPE is always more accurate than GPs.
COptuna can't use GPs because of licensing.
DTPE doesn't require any data to work.

Multi-fidelity methods — don't train to convergence every time.

The biggest cost in HPO is training time per evaluation. A CineMatch trial training for 20 epochs takes 30 minutes. But you can often tell a bad configuration after 3 epochs — its validation loss is already worse than the best completed trial. Multi-fidelity methods exploit this: start many trials at low fidelity (few epochs), and only promote promising ones to full training.

Successive Halving / Hyperband. Start 64 random configurations, each training for 1 epoch. Keep the best 32 and train 2 more epochs. Keep the best 16, train 4 more. Continue halving until one remains. Total compute: ~16 full trainings instead of 64.

ASHA (Asynchronous SHA). The asynchronous variant — doesn't wait for all trials at a rung to finish before promoting. Better GPU utilization, especially on multi-GPU clusters.

Multi-fidelityQuestion 05 / 07
With 50 trials and pruning, Optuna runs some trials for only 3 epochs. Doesn't this miss configurations that start slow but finish strong?
AYes — pruning always misses the best configuration.
BNo — all configurations converge at the same rate.
COccasionally yes — some good configs start slow. But empirically, early validation loss is a strong predictor of final performance (rank correlation ~0.7-0.9 between epoch-3 and epoch-20 loss). Pruning bad trials after 3 epochs frees compute to evaluate more candidates, which more than compensates for the rare missed late-bloomer. The net effect: ~3× more configurations explored for the same total compute.
DPruning is never used in practice because of this issue.
