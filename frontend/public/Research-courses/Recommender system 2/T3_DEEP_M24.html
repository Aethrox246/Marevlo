D1 / FORMALIZATION
Retrieval-augmented recommendation (RAR)
↳ corresponds to M24 S1: Role 2 & Role 4
Real-life analogy

Imagine a personal shopper who is brilliant at understanding what you want (the LLM) but hasn't seen the store's inventory (the catalog). Before making suggestions, they first search the inventory database for relevant options (retrieval), then reason about which ones best match your needs (ranking with LLM). RAR is this two-step process: retrieve candidates with fast classical methods, then reason about them with the LLM.

RAR architecture
$$\text{RAR}(u, q) = \text{LLM}\left(\text{prompt}(u, q, \underbrace{\text{Retrieve}(q, K)}_{\text{top-K candidates from classical model}})\right)$$
$u$User context: history, preferences, current session
$q$Query or context: "I need a birthday gift for my mother-in-law"
$\text{Retrieve}(q, K)$Classical retrieval: BPR-MF + FAISS → K candidates (K typically 20–50 for LLM input). Fast (~10ms). Handles scale
$\text{prompt}$Structured prompt containing: user profile, query, K candidate items with metadata (title, price, category, reviews). The LLM sees concrete items from the catalog — no hallucination risk for item existence
$\text{LLM}$Reasons about the candidates: ranks by relevance, filters by constraints, generates explanations. Slow (~500ms–2s) but high quality for complex queries
Why RAR, not pure LLM?

Without retrieval, the LLM must "recall" items from its training data — which may be outdated, incomplete, or nonexistent for Kartify's catalog. RAR grounds the LLM in the ACTUAL catalog. The retrieval step handles scale (480K items → 50 candidates). The LLM handles reasoning (50 candidates → ranked 10 with explanations). Each component does what it's best at.

D2 / WORKED
Cost analysis — classical vs LLM-augmented serving
↳ corresponds to M24 S2: Honest Limits
Kartify daily serving cost: 3 architectures compared
Production math
TRAFFIC
$$\text{DAU} = 10\text{M} \quad \text{Recs per user} = 20 \quad \text{Total} = 200\text{M inferences/day}$$
OPTION A: CLASSICAL (BPR-MF + DeepFM)
$$\text{Retrieval: 4 GPU instances} \times \$8/\text{hr} \times 24 = \$768/\text{day}$$ $$\text{Ranking: 8 GPU instances} \times \$8/\text{hr} \times 24 = \$1{,}536/\text{day}$$ $$\text{Feature store + infra: } \$200/\text{day}$$ $$\text{Total: } \$2{,}504/\text{day} \approx \$0.0000125/\text{rec}$$
OPTION B: LLM FOR ALL RANKING
$$\text{200M recs} \times 500 \text{ input tokens} \times \$0.0015/1\text{K tokens} = \$150{,}000/\text{day}$$

60× more expensive than classical. Not viable for Kartify's scale at current LLM pricing.

OPTION C: HYBRID (classical + LLM features + LLM for high-value)
$$\text{Classical serving (same as A): } \$2{,}504/\text{day}$$ $$\text{Batch LLM embeddings (480K items, nightly): } 480\text{K} \times 200\text{ tokens} \times \$0.0005 = \$48/\text{day}$$ $$\text{Conversational chatbot (50K convos): } 50\text{K} \times 2000\text{ tokens} \times \$0.0015 = \$150/\text{day}$$ $$\text{Explanation generation (1M high-value impressions): } 1\text{M} \times 300\text{ tokens} \times \$0.0015 = \$450/\text{day}$$ $$\text{Total: } \$3{,}152/\text{day} \approx 1.26\times \text{ Option A cost}$$

26% more expensive, but adds: richer item features (improved nDCG), conversational discovery (higher AOV), explanations (higher trust). This is the viable architecture.

D3 / INTERVIEW
Interview problems — LLM + Recsys
↳ tests M24
Problem: LLM as ranker — when it fails
Interview
PROBLEM

You run an A/B test: group A uses DeepFM for ranking, group B uses an LLM (GPT-4 class) for ranking the same 1000 retrieval candidates. Group B has slightly higher offline nDCG but significantly LOWER online conversion rate. Why?

SOLUTION

Three likely causes:

1. Latency degradation. LLM ranking takes ~1s vs DeepFM's ~80ms. Users see a loading spinner. Bounce rate increases. Every 100ms of added latency costs ~1% conversion (Amazon's famous finding). The 920ms latency increase may cost 5–10% conversion — more than the nDCG improvement recovers.

2. No behavioral learning. The LLM ranks based on text understanding of items. It doesn't know that "item X converts 3× better when shown after item Y" — a pattern DeepFM learns from click/purchase logs. The LLM produces a "reasonable" ranking that a knowledgeable human might agree with, but misses the non-obvious behavioral patterns that actually drive conversion.

3. Position bias mismatch. DeepFM is trained on impression data with position bias — it implicitly learns that items shown in position 1 get more clicks regardless of quality, and compensates. The LLM has no concept of display position — its "best item" might not be the item that converts best in position 1 of this specific UI layout.
